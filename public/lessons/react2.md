### Ситуация
Ты пишешь счётчик лайков: `let likes = 0`, по клику `likes++`. Добавляешь `console.log` — в консоли 1, 2, 3, всё растёт. А на экране упрямо висит 0. Переменная меняется, но React об этом не знает и экран не перерисовывает. Чтобы компонент «запоминал» данные и обновлялся, нужен первый и главный хук.

### На пальцах
Состояние — память компонента. Обычная переменная в компоненте — запись мелом на доске, которую стирают при каждой перерисовке. `useState` — блокнот, который React хранит за компонент: запись не пропадает, а когда ты меняешь её через специальную функцию, React понимает, что пора перерисовать экран.

### Как это работает
>> `const [count, setCount] = useState(0)` → клик → `setCount(count + 1)` → перерисовка

```tsx
const [value, setValue] = useState(начальное);
```

- `value` — текущее значение.
- `setValue(новое)` — заменить значение и попросить React перерисовать компонент.
- Нельзя менять значение напрямую (`value = 5`) — React об этом не узнает.
- После вызова `setValue` значение меняется не сразу, а при следующей отрисовке. В той же функции `value` ещё старое.
- Если новое значение зависит от старого, передавай функцию: `setCount(c => c + 1)`.
- Хуки вызываются только на верхнем уровне компонента — не внутри `if`, циклов и обычных функций.

В TypeScript тип выводится из начального значения. Если начальное `null` или пустой массив — подскажи: `useState<User | null>(null)`.

?: Почему хуки нельзя вызывать внутри `if`? || React не знает имён твоих состояний — он различает их по порядку вызова: первое `useState`, второе, третье. Если вызов спрятан в `if`, при следующей отрисовке порядок сдвинется, и состояния перепутаются.

### Пример
```tsx
import { useState } from "react";

export function Counter() {
  const [count, setCount] = useState(0);

  function addThreeWrong() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }

  function addThree() {
    setCount(c => c + 1);
    setCount(c => c + 1);
    setCount(c => c + 1);
  }

  return <p>{count}</p>;
}
```

?! Счётчик стоит на 0. Каким он станет после `addThreeWrong()`, а каким — после `addThree()`? || После `addThreeWrong` — 1: все три вызова видят одно и то же старое `count = 0` и трижды просят «поставь 1». После `addThree` — 3: каждая функция получает свежее значение от предыдущей.

### Частые ошибки
- **`let count = 0; count++`** — экран не обновится.
- **Ожидание нового значения сразу после `setCount`** в той же функции — там ещё старое.
- **`useState` внутри `if`** — React перепутает состояния между отрисовками.

?? Объясни своими словами, чем состояние отличается от обычной переменной в компоненте. || Обычная переменная создаётся заново при каждой отрисовке и не вызывает перерисовку. Состояние React хранит между отрисовками, и его изменение обновляет экран.

### Как это работает
>> `onClick={handle}` → событие → обработчик меняет состояние → экран обновляется

- События пишутся camelCase: `onClick`, `onChange`, `onSubmit`, `onKeyDown`, `onMouseEnter`.
- Передаётся функция, а не её вызов: `onClick={save}`, а не `onClick={save()}`.
- Нужно передать аргумент — оборачивай в стрелочную: `onClick={() => remove(item.id)}`.
- Обработчик получает объект события: `(e) => ...`. `e.preventDefault()`, `e.target`, `e.key` работают как в обычном JS.
- Типы событий в TypeScript: `React.MouseEvent<HTMLButtonElement>`, `React.ChangeEvent<HTMLInputElement>`, `React.FormEvent<HTMLFormElement>`. Если писать обработчик прямо в JSX, тип выводится сам.

Обработчики принято называть `handleЧто-то`, а props с обработчиками — `onЧто-то`: `<Button onClick={handleSave} />`.

### На пальцах
Неуправляемое поле — человек, который сам пишет в бланке, а ты узнаёшь об этом, только когда он отдаст бланк. Управляемое — ты диктуешь, а он записывает: в каждый момент ты точно знаешь, что написано. В React значение поля хранится в состоянии, и поле показывает ровно то, что в состоянии.

### Как это работает
>> `value={text}` → ввод → `onChange` → `setText` → поле показывает состояние

1. Значение поля лежит в `useState`.
2. `value={state}` — поле показывает состояние.
3. `onChange={e => setState(e.target.value)}` — каждое нажатие клавиши обновляет состояние.

Цикл: нажал клавишу → `onChange` → `setState` → перерисовка → поле показывает новое значение.

Что это даёт:

- значение всегда под рукой — для проверки, счётчика, неактивной кнопки;
- можно преобразовывать ввод: убирать пробелы, приводить к верхнему регистру;
- форму можно сбросить, обнулив состояние.

Для чекбокса — `checked` и `e.target.checked`. Для формы из многих полей удобно хранить один объект и обновлять поле по `name`.

?: Почему поле с `value`, но без `onChange` перестаёт принимать ввод? || Поле показывает значение из состояния. Ты нажимаешь клавишу, но некому обновить состояние — и на следующей отрисовке React снова ставит старое значение. Поле «замерзает».

### Пример
```tsx
import { useState } from "react";

export function LeadForm() {
  const [form, setForm] = useState({ name: "", agree: false });

  function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
    const { name, value, type, checked } = e.target;
    setForm(f => ({ ...f, [name]: type === "checkbox" ? checked : value }));
  }

  const canSend = form.name.trim().length >= 2 && form.agree;

  return (
    <form>
      <input name="name" value={form.name} onChange={handleChange} />
      <input type="checkbox" name="agree" checked={form.agree} onChange={handleChange} />
      <button disabled={!canSend}>Отправить</button>
    </form>
  );
}
```

### Частые ошибки
- **`value` без `onChange`** — поле замерзает.
- **Начальное значение `undefined`, потом строка** — предупреждение о переходе от неуправляемого поля к управляемому. Начинай с `""`.
- **`value` вместо `checked`** у чекбокса.

?? Как правильно читать состояние чекбокса в обработчике? || Через `e.target.checked`.

### Как это работает
>> Два компонента нужны одни данные → состояние в общем родителе → вниз через props

1. Найди ближайшего общего родителя компонентов, которым нужны данные.
2. Перенеси `useState` в него.
3. Передай вниз значение через props.
4. Передай вниз функцию изменения (`onChange`, `onSelect`), чтобы дети могли попросить родителя обновить данные.

Данные текут вниз, события — вверх. Это главный поток данных в React.

Не поднимай выше, чем нужно: если состояние нужно одному компоненту, пусть живёт в нём. Чем выше состояние, тем больше компонентов перерисовывается при его изменении.

React замечает изменения по «конверту», а не по содержимому. Если ты достал письмо, дописал строчку и положил обратно в тот же конверт — для React это тот же конверт, он ничего не заметит. Нужно положить письмо в новый конверт. Неизменяемое обновление — всегда новый массив или объект вместо правки старого.

### Как это работает
>> Старый массив → копия `[...arr, новый]` → `setState(копия)` → React видит изменение

React сравнивает старое и новое состояние через `===`. Изменённый на месте массив — тот же самый объект, поэтому React может решить, что ничего не поменялось.

| Действие | Неправильно (меняет) | Правильно (новый массив) |
|---|---|---|
| добавить | `arr.push(x)` | `[...arr, x]` |
| удалить | `arr.splice(i, 1)` | `arr.filter(x => x.id !== id)` |
| изменить | `arr[i].done = true` | `arr.map(x => x.id === id ? { ...x, done: true } : x)` |
| отсортировать | `arr.sort()` | `[...arr].sort()` или `arr.toSorted()` |

Для объектов: `{ ...obj, field: newValue }`. Для вложенных — копировать каждый уровень: `{ ...user, address: { ...user.address, city: "Казань" } }`.

?: Почему React сравнивает по ссылке, а не проверяет содержимое? || Глубокое сравнение больших объектов и массивов на каждой отрисовке было бы очень медленным. Сравнение ссылок мгновенное. Цена — договорённость: изменил данные — создай новый объект.

### Пример
```tsx
const [todos, setTodos] = useState([{ id: 1, text: "useState", done: false }]);

function toggleWrong(id: number) {
  const t = todos.find(t => t.id === id)!;
  t.done = !t.done;
  setTodos(todos);
}

function toggle(id: number) {
  setTodos(prev => prev.map(t => (t.id === id ? { ...t, done: !t.done } : t)));
}
```

?! Пользователь нажимает на чекбокс, и вызывается `toggleWrong(1)`. Отметится ли задача на экране? || Скорее всего, нет: массив тот же самый (`todos === todos`), и React решит, что изменений нет. Данные при этом уже испорчены. `toggle` создаёт новый массив и новый объект задачи — и экран обновится.

### Частые ошибки
- **`todos.push(x); setTodos(todos)`** — экран может не обновиться.
- **Копирование только верхнего уровня** и правка вложенного — изменения «протекают» в старое состояние.
- **Сортировка состояния на месте прямо в JSX:** `todos.sort(...)` меняет состояние при каждой отрисовке.

### Проверь себя
?? Как добавить элемент в массив-состояние правильно? || Создать новый массив: `setArr(prev => [...prev, x])`.
?? Как изменить одно поле объекта в состоянии? || Создать новый объект через spread: `setUser(u => ({ ...u, name: "Анна" }))`.
?? Объясни своими словами, почему в React нельзя менять состояние на месте. || React замечает изменения по ссылке. Изменённый на месте объект — тот же самый, и React может не перерисовать экран, а старые данные окажутся испорчены.
