### На пальцах
CRUD — четыре операции с любой картотекой: завести новую карточку, посмотреть, исправить, выбросить. Коды ответа — штампы на квитанции: «выдано» (200), «заведено» (201), «выброшено, расписываться не надо» (204), «заполнено неправильно» (400), «такой карточки нет» (404).

### Как это работает
| Операция | Маршрут | Успех | Ошибки |
|---|---|---|---|
| Список | `GET /api/tasks` | 200 + массив | — |
| Один | `GET /api/tasks/:id` | 200 + объект | 404 |
| Создать | `POST /api/tasks` | 201 + новый объект | 400 |
| Изменить | `PATCH /api/tasks/:id` | 200 + обновлённый объект | 400, 404 |
| Заменить | `PUT /api/tasks/:id` | 200 + объект | 400, 404 |
| Удалить | `DELETE /api/tasks/:id` | 204 без тела | 404 |

Детали, которые отличают аккуратный API:

- после создания и изменения возвращай итоговый объект — клиенту не нужен второй запрос;
- id генерирует сервер, а не клиент;
- поля, которые клиент не должен менять (`id`, `createdAt`, `ownerId`), игнорируй в теле PATCH;
- удаление несуществующего — 404 (или 204, если так договорились — главное, единообразно).

### Пример
```js
import { Router } from "express";
export const tasks = Router();

let items = [{ id: 1, title: "Макет", done: false }];
let nextId = 2;
const find = id => items.find(t => t.id === Number(id));

tasks.get("/", (req, res) => res.json(items));

tasks.get("/:id", (req, res) => {
  const t = find(req.params.id);
  if (!t) return res.status(404).json({ error: "Задача не найдена" });
  res.json(t);
});

tasks.post("/", (req, res) => {
  const title = String(req.body?.title ?? "").trim();
  if (!title) return res.status(400).json({ error: "Укажите название" });
  const t = { id: nextId++, title, done: false };
  items.push(t);
  res.status(201).json(t);
});

tasks.patch("/:id", (req, res) => {
  const t = find(req.params.id);
  if (!t) return res.status(404).json({ error: "Задача не найдена" });
  const { title, done } = req.body ?? {};
  if (title !== undefined) t.title = String(title).trim();
  if (done !== undefined) t.done = Boolean(done);
  res.json(t);
});

tasks.delete("/:id", (req, res) => {
  const before = items.length;
  items = items.filter(t => t.id !== Number(req.params.id));
  if (items.length === before) return res.status(404).json({ error: "Задача не найдена" });
  res.status(204).end();
});
```

### Частые ошибки
- 200 вместо 201 после создания, тело в ответе на 204.
- Позволять клиенту присылать свой `id` или `ownerId` в теле.
- Разные форматы ответов в разных маршрутах.

### На пальцах
Валидация — охранник на входе склада. Форма в браузере тоже проверяет данные, но это вахтёр на улице: его легко обойти, просто пройдя через служебный вход (отправив запрос напрямую через curl). Поэтому настоящая проверка всегда на сервере — на последней двери перед складом.

### Как это работает
Что проверять:

- наличие обязательных полей;
- типы (строка, число, булево);
- длину и диапазон (название 2–100 символов, бюджет больше 0);
- формат (email, телефон, дата);
- допустимые значения (статус из списка);
- лишние поля — отбросить.

Вручную это быстро становится громоздким. zod описывает правила схемой и сам собирает все ошибки:

- `schema.safeParse(data)` → `{ success: true, data }` или `{ success: false, error }`;
- `data` уже очищен и приведён к типам; лишние поля по умолчанию отброшены;
- `error.flatten().fieldErrors` — ошибки по полям, удобно отдать фронтенду;
- `z.infer<typeof schema>` даёт TypeScript-тип.

Удобно оформить проверку в middleware `validate(schema)`.

### Пример
```js
import { z } from "zod";

const taskSchema = z.object({
  title: z.string().trim().min(2, "Минимум 2 символа").max(100),
  priority: z.enum(["low", "normal", "high"]).default("normal"),
  dueDate: z.coerce.date().optional(),
  estimateHours: z.number().positive().max(200).optional(),
});

function validate(schema) {
  return (req, res, next) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({
        error: "Проверьте данные",
        fields: result.error.flatten().fieldErrors,
      });
    }
    req.body = result.data;          // уже очищенные данные
    next();
  };
}

tasks.post("/", validate(taskSchema), (req, res) => {
  const task = { id: nextId++, ...req.body, done: false };
  items.push(task);
  res.status(201).json(task);
});

// PATCH — те же правила, но все поля необязательные
tasks.patch("/:id", validate(taskSchema.partial()), (req, res) => { /* ... */ });
```

```json
// ответ на {"title": "А", "priority": "urgent"}
{
  "error": "Проверьте данные",
  "fields": {
    "title": ["Минимум 2 символа"],
    "priority": ["Invalid enum value. Expected 'low' | 'normal' | 'high'"]
  }
}
```

### Частые ошибки
- Валидация только на фронтенде.
- Сохранять `req.body` целиком в базу — туда попадут любые лишние поля, включая `isAdmin: true`.
- Возвращать первую ошибку, а не все сразу — пользователь чинит форму по одному полю.

### На пальцах
Если каждый отдел присылает отказы в своём формате — один письмом, другой открыткой, третий звонком — приёмной (фронтенду) приходится разбираться с каждым отдельно. Единый формат ошибок — один бланк отказа на весь офис: всегда понятно, где причина и что исправить.

### Как это работает
Договорись об одной структуре и используй её во всех ответах с ошибкой. Минимальный вариант:

```json
{ "error": "Понятное сообщение для человека" }
```

Расширенный, когда нужно:

```json
{
  "error": "Проверьте данные",
  "code": "VALIDATION_ERROR",
  "fields": { "email": ["Неверный формат"] }
}
```

- `error` — текст, который можно показать пользователю.
- `code` — машиночитаемый код, по нему фронтенд может решить, что делать (например, `EMAIL_TAKEN` → подсветить поле email).
- `fields` — ошибки по полям для форм.

Правила:

- Код статуса HTTP соответствует ошибке (400, 401, 404, 409…), а формат тела одинаковый.
- Никаких технических подробностей наружу: стек, SQL-запрос, пути к файлам — только в логи сервера.
- Даже 404 для несуществующего адреса и ошибки разбора JSON — в том же формате.

### Пример
```js
// src/errors.js
export class HttpError extends Error {
  constructor(status, message, code, fields) {
    super(message);
    this.status = status;
    this.code = code;
    this.fields = fields;
  }
}
export const notFound = (what = "Ресурс") => new HttpError(404, `${what} не найден`, "NOT_FOUND");
```

```js
// маршрут
tasks.get("/:id", (req, res, next) => {
  const t = find(req.params.id);
  if (!t) return next(notFound("Задача"));
  res.json(t);
});

// 404 для неизвестных адресов — в том же формате
app.use((req, res) => res.status(404).json({ error: "Нет такого адреса", code: "ROUTE_NOT_FOUND" }));
```

### Частые ошибки
- В одном маршруте `{ error }`, в другом `{ message }`, в третьем `{ errors: [...] }`.
- Отдавать наружу текст исключения базы данных.
- 200 со статусом ошибки внутри тела.

### На пальцах
Отдать клиенту все 50 000 заказов разом — как вывалить на стол весь архив, когда человек спросил последние документы. Пагинация — выдавать по страничке: «вот 20 последних, хочешь — дам следующие». Сортировка — договориться, в каком порядке складывать.

### Как это работает
Параметры в query:

- `?page=2&limit=20` — номер страницы и размер. Смещение: `offset = (page - 1) * limit`.
- `?sort=createdAt` или `?sort=-budget` (минус — по убыванию).
- Фильтры: `?status=open&clientId=5`.

Обязательно:

- проверяй и ограничивай: `limit` не больше 100, `page` не меньше 1;
- сортировку разрешай только по списку полей — иначе в SQL можно протащить что угодно;
- возвращай в ответе метаданные: общее количество и текущую страницу, чтобы фронтенд нарисовал навигацию.

Формат ответа:

```json
{ "items": [...], "page": 2, "limit": 20, "total": 134, "pages": 7 }
```

Есть и пагинация курсором (`?after=id`): быстрее на больших таблицах и не «прыгает», если добавились новые записи. Для начала хватит page/limit.

### Пример
```js
const SORTABLE = ["createdAt", "budget", "title"];

projects.get("/", (req, res) => {
  const page = Math.max(1, Number.parseInt(req.query.page) || 1);
  const limit = Math.min(100, Math.max(1, Number.parseInt(req.query.limit) || 20));
  const sortRaw = String(req.query.sort ?? "-createdAt");
  const desc = sortRaw.startsWith("-");
  const field = sortRaw.replace(/^-/, "");
  if (!SORTABLE.includes(field)) return res.status(400).json({ error: "Нельзя сортировать по этому полю" });

  let list = items;
  if (req.query.status) list = list.filter(p => p.status === req.query.status);

  list = [...list].sort((a, b) => (a[field] > b[field] ? 1 : -1) * (desc ? -1 : 1));
  const total = list.length;
  const pageItems = list.slice((page - 1) * limit, page * limit);

  res.json({ items: pageItems, page, limit, total, pages: Math.ceil(total / limit) });
});
```

В SQL то же самое — `ORDER BY ... LIMIT $1 OFFSET $2` и отдельный `SELECT COUNT(*)`.

### Частые ошибки
- Нет верхней границы `limit` — кто-то запросит `?limit=1000000`.
- Подставлять поле сортировки из запроса прямо в SQL — инъекция.
- Нет стабильной сортировки: без `ORDER BY` база возвращает строки в непредсказуемом порядке, и записи «перескакивают» между страницами.

### На пальцах
Обработчик ошибок — единое бюро жалоб в конце коридора. Где бы в здании ни случилась неприятность, её не разбирают на месте, а отправляют в бюро. Там знают, что ответить посетителю, что записать в журнал и какие подробности никому не показывать.

### Как это работает
- Обработчик ошибок в Express отличается от обычного middleware числом аргументов: их четыре — `(err, req, res, next)`.
- Подключается последним, после всех маршрутов и 404.
- Ошибка попадает в него, если:
  - в маршруте вызвали `next(err)`;
  - в синхронном маршруте выбросили исключение (`throw`);
  - в Express 5 — если async-маршрут отклонил промис (в Express 4 async-ошибки нужно ловить самому и передавать в `next`, или использовать обёртку).
- Внутри: свои ошибки (`HttpError`) превращаем в их статус и сообщение, всё остальное — в 500 с общим текстом, а подробности пишем в лог.

### Пример
```js
// для Express 4: обёртка для async-маршрутов
export const wrap = fn => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);

projects.get("/:id", wrap(async (req, res) => {
  const p = await db.findProject(req.params.id);
  if (!p) throw new HttpError(404, "Проект не найден", "NOT_FOUND");
  res.json(p);
}));

// в самом конце app.js
app.use((err, req, res, next) => {
  if (err instanceof HttpError) {
    return res.status(err.status).json({ error: err.message, code: err.code, fields: err.fields });
  }
  if (err.type === "entity.parse.failed") {
    return res.status(400).json({ error: "Некорректный JSON", code: "BAD_JSON" });
  }
  console.error(`[${req.method} ${req.path}]`, err);          // подробности только в лог
  res.status(500).json({ error: "Внутренняя ошибка сервера", code: "INTERNAL" });
});
```

### Частые ошибки
- Три аргумента вместо четырёх — Express примет функцию за обычный middleware, и ошибки до неё не дойдут.
- Обработчик подключён до маршрутов.
- Async-ошибка в Express 4 без обёртки — запрос висит, а в консоли «UnhandledPromiseRejection».

### На пальцах
API без документации — прибор без инструкции: может, и работает, но как им пользоваться, знает только тот, кто его собрал. Документация — инструкция для фронтенд-разработчиков, коллег и тебя самого через три месяца: какие адреса есть, что отправлять и что придёт в ответ.

### Как это работает
Два уровня:

**README** — подходит для учебных и небольших проектов. Для каждого маршрута: метод и путь, нужна ли авторизация, параметры, пример тела запроса, пример ответа, возможные ошибки.

**OpenAPI (Swagger)** — стандартное машиночитаемое описание API в YAML или JSON. Из него:

- генерируется интерактивная страница документации (Swagger UI, Scalar, Redoc), где запросы можно отправлять прямо из браузера;
- генерируются клиенты и TypeScript-типы для фронтенда;
- можно проверять, что API соответствует описанию.

Описание можно писать руками или генерировать из zod-схем (библиотеки вроде `zod-to-openapi`), чтобы документация не расходилась с кодом.

Минимум, который нужен в любом случае: базовый адрес, способ авторизации, формат ошибок и список маршрутов.

### Пример
```markdown
## POST /api/tasks
Создать задачу. Требуется заголовок `Authorization: Bearer <token>`.

Тело запроса:

    { "title": "Сверстать шапку", "priority": "high", "dueDate": "2026-11-01" }

Ответ 201:

    { "id": 17, "title": "Сверстать шапку", "priority": "high", "done": false }

# openapi.yaml (фрагмент)

info: { title: Studio API, version: 1.0.0 }

        "201": { description: Создано }
        "400": { description: Неверные данные }
```

### Частые ошибки
- Документация написана один раз и больше не обновляется.
- Нет примеров ответов — только список адресов.
- Не описан формат ошибок и авторизация.
