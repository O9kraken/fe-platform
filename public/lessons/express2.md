Рабочий CRUD собрать легко. Аккуратный CRUD, с которым удобно работать, отличается десятком мелочей — разберём их.

### На пальцах
CRUD — четыре операции с любой картотекой: завести новую карточку, посмотреть, исправить, выбросить. Коды ответа — штампы на квитанции: «выдано» (200), «заведено» (201), «выброшено, расписываться не надо» (204), «заполнено неправильно» (400), «такой карточки нет» (404).

### Как это работает
| Операция | Маршрут | Успех | Ошибки |
|---|---|---|---|
| Список | `GET /api/tasks` | 200 + массив | — |
| Один | `GET /api/tasks/:id` | 200 + объект | 404 |
| Создать | `POST /api/tasks` | 201 + новый объект | 400 |
| Изменить | `PATCH /api/tasks/:id` | 200 + обновлённый объект | 400, 404 |
| Заменить | `PUT /api/tasks/:id` | 200 + объект | 400, 404 |
| Удалить | `DELETE /api/tasks/:id` | 204 без тела | 404 |

Детали аккуратного API:

- после создания и изменения возвращай итоговый объект — клиенту не нужен второй запрос;
- id генерирует сервер, а не клиент;
- поля, которые клиент не должен менять (`id`, `createdAt`, `ownerId`), игнорируй в теле PATCH;
- удаление несуществующего — 404 (или 204, если так договорились — главное, единообразно).

?: Почему id должен генерировать сервер, а не клиент? || Два клиента могут прислать один и тот же id, и записи перезапишут друг друга. Кроме того, клиент может нарочно подставить id чужой записи. Сервер гарантирует уникальность и контроль.

### Пример
```js
tasks.patch("/:id", (req, res) => {
  const t = find(req.params.id);
  if (!t) return res.status(404).json({ error: "Задача не найдена" });
  Object.assign(t, req.body);
  res.json(t);
});
```

?! Клиент отправляет `PATCH /api/tasks/1` с телом `{"done": true, "id": 999, "ownerId": 7}`. Что случится с задачей? || Её id станет 999, а владелец — 7: `Object.assign` копирует все присланные поля. Так можно украсть чужую задачу или сломать ссылки на неё. Нужно явно брать только разрешённые поля — `title` и `done`.

### Частые ошибки
- **200 вместо 201** после создания, тело в ответе на 204.
- **Клиент присылает свой `id` или `ownerId`** — и сервер их принимает.
- **Разные форматы ответов** в разных маршрутах.

### Проверь себя
?? Какой код и что в теле вернуть после успешного создания? || 201 и созданный объект целиком, включая выданный сервером id.
?? Какой код обычно возвращают после успешного удаления? || 204 No Content без тела.
?? Объясни своими словами, почему PATCH нельзя просто копировать всё тело в объект. || Клиент может прислать служебные поля — id, владельца, права — и подменить их. Сервер должен менять только явно разрешённые поля.

А пользователь однажды увидел на экране «duplicate key value violates unique constraint users_email_key». Единый формат ошибок экономит время всем и не выдаёт лишнего.

### На пальцах
Если каждый отдел присылает отказы в своём формате — один письмом, другой открыткой, третий звонком — приёмной (фронтенду) приходится разбираться с каждым. Единый формат ошибок — один бланк отказа на весь офис: всегда понятно, где причина и что исправить.

### Как это работает
Минимальный вариант:

```json
{ "error": "Понятное сообщение для человека" }
```

Расширенный, когда нужно:

```json
{
  "error": "Проверьте данные",
  "code": "VALIDATION_ERROR",
  "fields": { "email": ["Неверный формат"] }
}
```

- `error` — текст, который можно показать пользователю.
- `code` — машиночитаемый код, по нему фронтенд решает, что делать (например, `EMAIL_TAKEN` → подсветить поле email).
- `fields` — ошибки по полям для форм.

Правила:

- Код статуса HTTP соответствует ошибке, а формат тела одинаковый.
- Никаких технических подробностей наружу: стек, SQL-запрос, пути к файлам — только в логи сервера.
- Даже 404 для неизвестного адреса и ошибки разбора JSON — в том же формате.

?: Зачем поле `code`, если уже есть текст ошибки и HTTP-статус? || Текст для людей — его могут перевести или переформулировать, и код на нём ломается. Статус слишком общий: 409 может быть и «email занят», и «логин занят». Стабильный `code` позволяет фронтенду точно понять, что случилось.

### Пример
```js
app.post("/api/users", async (req, res) => {
  try {
    const user = await db.createUser(req.body.email);
    res.status(201).json(user);
  } catch (e) {
    res.status(500).json({ error: e.message });
  }
});
```

?! Пользователь регистрируется с уже занятым email. Что он увидит и что здесь не так? || Код 500 и текст исключения базы, например «duplicate key value violates unique constraint users_email_key». Это неправильный статус (должен быть 409), утечка устройства базы и непонятный для человека текст. Нужно `{ error: "Email уже занят", code: "EMAIL_TAKEN" }`.

### Частые ошибки
- **Разные поля в разных маршрутах:** `{ error }`, `{ message }`, `{ errors: [...] }`.
- **Текст исключения базы данных наружу.**
- **200 со статусом ошибки внутри тела.**

### Проверь себя
?? Какие три поля обычно содержит расширенный формат ошибки? || `error` — сообщение для человека, `code` — машиночитаемый код, `fields` — ошибки по полям формы.
?? Что нельзя отдавать клиенту в ответе с ошибкой? || Стек вызовов, тексты SQL-запросов и исключений базы, пути к файлам и другие технические подробности.
?? Объясни своими словами, зачем единый формат ошибок во всём API. || Фронтенд обрабатывает все ошибки одной функцией, пользователю показываются понятные сообщения, а внутреннее устройство сервера не утекает наружу.

### Как это работает
Параметры в query:

- `?page=2&limit=20` — номер страницы и размер. Смещение: `offset = (page - 1) * limit`.
- `?sort=createdAt` или `?sort=-budget` (минус — по убыванию).
- Фильтры: `?status=open&clientId=5`.

Обязательно:

- проверяй и ограничивай: `limit` не больше 100, `page` не меньше 1;
- сортировку разрешай только по списку полей;
- возвращай метаданные: общее количество и текущую страницу.

```json
{ "items": [...], "page": 2, "limit": 20, "total": 134, "pages": 7 }
```

Есть и пагинация курсором (`?after=id`): быстрее на больших таблицах и не «прыгает», если добавились новые записи. Для начала хватит page/limit.

?: Почему поле сортировки нужно сверять со списком разрешённых? || В SQL имя колонки нельзя передать параметром — его подставляют в текст запроса. Если брать его прямо из адреса, злоумышленник подставит туда кусок SQL. Белый список гарантирует, что в запрос попадёт только известное поле.

### Пример
```js
const page = Math.max(1, Number.parseInt(req.query.page) || 1);
const limit = Math.min(100, Math.max(1, Number.parseInt(req.query.limit) || 20));
const offset = (page - 1) * limit;
```

?! Какие `page`, `limit` и `offset` получатся для запросов `?page=3&limit=10`, `?page=0&limit=500` и `?page=abc`? || Первый: 3, 10, 20. Второй: 1, 100, 0 — значения прижаты к границам. Третий: 1, 20, 0 — `parseInt("abc")` даёт `NaN`, и срабатывает значение по умолчанию.

### Частые ошибки
- **Нет верхней границы `limit`** — кто-то запросит `?limit=1000000`.
- **Поле сортировки из запроса прямо в SQL** — инъекция.
- **Нет стабильной сортировки:** без `ORDER BY` база возвращает строки в непредсказуемом порядке, и записи «перескакивают» между страницами.

### Проверь себя
?? Как посчитать смещение для страницы `page` при размере `limit`? || `offset = (page - 1) * limit`.
?? Какие метаданные стоит вернуть вместе со страницей списка? || Текущую страницу, размер страницы, общее количество записей и число страниц.
?? Объясни своими словами, зачем ограничивать `limit` сверху. || Чтобы никто не мог одним запросом выкачать всю таблицу и перегрузить сервер и базу.

### Ситуация

В третьем пользователь видит стек вызовов с путями к файлам. Ошибки случаются всегда. Вопрос в том, есть ли у тебя одно место, где они аккуратно обрабатываются.

### На пальцах
Обработчик ошибок — единое бюро жалоб в конце коридора. Где бы в здании ни случилась неприятность, её не разбирают на месте, а отправляют в бюро. Там знают, что ответить посетителю, что записать в журнал и какие подробности никому не показывать.

### Как это работает
- Обработчик ошибок отличается от обычного middleware числом аргументов: их четыре — `(err, req, res, next)`.
- Подключается последним, после всех маршрутов и 404.
- Ошибка попадает в него, если:
  - в маршруте вызвали `next(err)`;
  - в синхронном маршруте выбросили исключение (`throw`);
  - в Express 5 — если async-маршрут отклонил промис (в Express 4 async-ошибки нужно ловить самому или через обёртку).
- Внутри: свои ошибки (`HttpError`) превращаем в их статус и сообщение, всё остальное — в 500 с общим текстом, а подробности пишем в лог.

?: Как Express отличает обработчик ошибок от обычного middleware? || По количеству параметров функции: у обработчика ошибок их ровно четыре — `(err, req, res, next)`. Если написать три, Express будет считать функцию обычным middleware, и ошибки до неё не дойдут.

### Пример
```js
export const wrap = fn => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);

projects.get("/:id", wrap(async (req, res) => {
  const p = await db.findProject(req.params.id);
  if (!p) throw new HttpError(404, "Проект не найден", "NOT_FOUND");
  res.json(p);
}));

app.use((err, req, res, next) => {
  if (err instanceof HttpError) {
    return res.status(err.status).json({ error: err.message, code: err.code });
  }
  console.error(`[${req.method} ${req.path}]`, err);
  res.status(500).json({ error: "Внутренняя ошибка сервера", code: "INTERNAL" });
});
```

?! База упала с ошибкой «connection refused to 10.0.0.5:5432». Что получит клиент и где окажется адрес базы? || Клиент получит 500 «Внутренняя ошибка сервера» с кодом `INTERNAL`. Подробности вместе с адресом базы попадут только в лог сервера через `console.error` и наружу не утекут.

### Частые ошибки
- **Три аргумента вместо четырёх** — ошибки до обработчика не доходят.
- **Обработчик подключён до маршрутов.**
- **Async-ошибка в Express 4 без обёртки** — запрос висит, в консоли «UnhandledPromiseRejection».

### Проверь себя
?? Где в `app.js` подключают обработчик ошибок? || В самом конце: после всех маршрутов и обработчика 404.
?? Зачем в Express 4 обёртка `wrap` для async-маршрутов? || Express 4 не ловит отклонённые промисы. Обёртка перехватывает ошибку через `.catch(next)` и передаёт её в обработчик ошибок.
?? Объясни своими словами, зачем единый обработчик ошибок. || Чтобы любая ошибка в любом маршруте превращалась в аккуратный ответ в одном формате, подробности записывались в лог, а технические детали не попадали к пользователю.

### Мини-задание

- генерируются клиенты и TypeScript-типы для фронтенда;
- можно проверять, что API соответствует описанию.

Описание можно писать руками или генерировать из zod-схем (`zod-to-openapi`), чтобы документация не расходилась с кодом.

Минимум: базовый адрес, способ авторизации, формат ошибок и список маршрутов.

?: Чем генерация документации из zod-схем лучше написания руками? || Схема — то, что реально проверяет данные. Если документация строится из неё, при изменении правил она обновляется сама и не может разойтись с кодом. Рукописная документация устаревает при первой же правке.

### Пример
```markdown
## POST /api/tasks
Создать задачу.

Ответ 201:

    { "id": 17, "title": "Сверстать шапку", "done": false }
```

?! Чего не хватает в этом описании маршрута, чтобы фронтендер смог им воспользоваться без вопросов? || Нужна ли авторизация и как передать токен, пример тела запроса с обязательными полями и возможные ошибки — например, 400 с полем `fields` и 401 без токена.

### Частые ошибки
- **Документация написана один раз** и больше не обновляется.
- **Нет примеров ответов** — только список адресов.
- **Не описан формат ошибок и авторизация.**

### Проверь себя
?? Что нужно описать для каждого маршрута API? || Метод и путь, нужна ли авторизация, параметры, пример тела запроса, пример ответа и возможные ошибки.
?? Что такое OpenAPI? || Стандартный машиночитаемый формат описания API в YAML или JSON, из которого генерируются интерактивная документация, клиенты и типы.
?? Объясни своими словами, кому и зачем нужна документация API. || Фронтенд-разработчикам и коллегам — чтобы пользоваться API без чтения кода, и тебе самому — чтобы через время вспомнить, как всё устроено.

### Мини-задание
Опиши в README своего API все маршруты по шаблону: метод, путь, авторизация, пример запроса, пример ответа, ошибки. Отдельно опиши формат ошибок и как получить токен.
