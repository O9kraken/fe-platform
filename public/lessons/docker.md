### На пальцах
Образ — замороженный полуфабрикат с инструкцией: в коробке уже есть всё — продукты, специи, рецепт. Контейнер — блюдо, разогретое из этого полуфабриката. Из одной коробки можно сделать сколько угодно одинаковых порций, и на любой кухне (у тебя, у коллеги, на сервере) вкус будет одинаковый. Конец вечной фразе «у меня на компьютере работает».

### Как это работает
| | Образ (image) | Контейнер (container) |
|---|---|---|
| Что это | шаблон только для чтения: ОС, Node.js, код, зависимости | запущенный экземпляр образа |
| Как получить | `docker build` из Dockerfile или `docker pull` из реестра | `docker run образ` |
| Сколько | один образ | сколько угодно контейнеров из него |
| Изменения | неизменяем | изменения внутри пропадают при удалении контейнера |

Контейнер похож на лёгкую виртуальную машину, но использует ядро основной системы, поэтому стартует за секунды и занимает мало ресурсов.

Основные команды:

| Команда | Что делает |
|---|---|
| `docker pull postgres:16` | скачать образ из Docker Hub |
| `docker run -d -p 5432:5432 --name db postgres:16` | запустить контейнер в фоне |
| `docker ps` / `docker ps -a` | запущенные / все контейнеры |
| `docker logs -f db` | логи контейнера |
| `docker exec -it db psql -U postgres` | выполнить команду внутри |
| `docker stop db` / `docker rm db` | остановить / удалить |
| `docker images` / `docker rmi образ` | список / удалить образ |

### Пример
```bash
# Postgres для разработки — одной командой, без установки
docker run -d --name studio-db \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=studio \
  -p 5432:5432 \
  postgres:16

docker ps
docker logs studio-db
docker exec -it studio-db psql -U postgres -d studio -c "select now();"

# ещё один контейнер из того же образа — для тестов, на другом порту
docker run -d --name studio-test-db -e POSTGRES_PASSWORD=test -p 5433:5432 postgres:16
```

### Частые ошибки
- Хранить важные данные внутри контейнера без тома — `docker rm` удалит их навсегда.
- Тег `latest` — через месяц скачается другая версия.
- Путать остановку и удаление: `stop` сохраняет контейнер, `rm` удаляет.

Установи Docker Desktop, запусти PostgreSQL и Redis в контейнерах, подключись к базе через `docker exec ... psql` и посмотри логи обоих. Останови и снова запусти контейнер базы — данные на месте? А после `rm`?

### На пальцах
Dockerfile — рецепт полуфабриката по шагам: «возьми основу — Node.js 22 (FROM), перейди к рабочему столу (WORKDIR), положи список ингредиентов (COPY package.json), закупи их (RUN npm ci), положи остальные продукты (COPY .), при подаче делай вот это (CMD)».

### Как это работает
| Инструкция | Что делает |
|---|---|
| `FROM node:22-alpine` | базовый образ: ОС + Node.js нужной версии |
| `WORKDIR /app` | рабочая папка внутри образа |
| `COPY package*.json ./` | скопировать файлы с компьютера в образ |
| `RUN npm ci --omit=dev` | выполнить команду при сборке |
| `ENV NODE_ENV=production` | переменная окружения по умолчанию |
| `EXPOSE 3000` | документация: какой порт слушает приложение |
| `USER node` | запускать не от root |
| `CMD ["node", "src/index.js"]` | команда при запуске контейнера |

- `RUN` выполняется при **сборке** образа, `CMD` — при **запуске** контейнера.
- `CMD` пишут массивом — так приложение получает сигналы остановки напрямую.
- Образы `alpine` и `slim` — маленькие, полные `node:22` — большие, но с инструментами.

Сборка и запуск:

- `docker build -t studio-api .` — собрать образ с именем;
- `docker run -p 3000:3000 --env-file .env studio-api` — запустить.

### Пример
```dockerfile
# Dockerfile
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev

COPY . .

ENV NODE_ENV=production
EXPOSE 3000
USER node

CMD ["node", "src/index.js"]
```

```bash
docker build -t studio-api:1.0 .
docker run --rm -p 3000:3000 --env-file .env studio-api:1.0
curl localhost:3000/api/health
```

### Частые ошибки
- `COPY . .` до `npm ci` — каждая правка кода заново скачивает все зависимости.
- Сервер слушает `127.0.0.1` — снаружи контейнера он недоступен. Нужен `0.0.0.0` (или просто не указывать хост).
- Секреты через `ENV` в Dockerfile — они навсегда остаются в образе.

### Мини-задание
Напиши Dockerfile для своего API, собери образ и запусти контейнер с `--env-file`. Проверь `/api/health` через curl. Потренируйся в задаче «Ревизор Dockerfile».

### На пальцах
Образ собирается слоями, как многослойный торт: каждая инструкция — слой. Docker запоминает готовые слои. Если основа и крем не менялись, а поменялась только посыпка — переделывают только посыпку. Поэтому редко меняющееся (зависимости) кладут внизу, а часто меняющееся (код) — сверху.

### Как это работает
- Каждая инструкция `RUN`, `COPY`, `ADD` создаёт слой.
- При повторной сборке Docker использует кеш слоя, если инструкция и входные файлы не изменились.
- Как только один слой изменился — все слои **выше** пересобираются.

Отсюда правило порядка:

1. базовый образ;
2. системные пакеты;
3. `COPY package*.json` + `RUN npm ci` — меняются редко;
4. `COPY . .` — код, меняется постоянно.

Тогда правка одной строки кода пересобирает только последний слой — секунды вместо минут.

`.dockerignore` — список того, что не копировать в образ при `COPY . .`:

- `node_modules` — их поставит `npm ci` внутри, а локальные могут быть под другую ОС;
- `.git`, `.env`, логи, тесты, `dist` — меньше образ и никаких секретов внутри.

Многоэтапная сборка (multi-stage): в первом этапе собрать проект (TypeScript, фронтенд) со всеми инструментами, во второй — скопировать только результат. Итоговый образ маленький и без лишнего.

### Пример
```text
# .dockerignore
node_modules
.git
.env
.env.*
*.log
coverage
dist
```

```dockerfile
# многоэтапная сборка для API на TypeScript
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build                 # tsc → dist/

FROM node:22-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/index.js"]
```

```bash
docker build -t studio-api .     # первый раз — долго
# правим одну строку в src/
docker build -t studio-api .     # быстро: слои с зависимостями из кеша (CACHED)
docker history studio-api        # слои и их размер
```

### Частые ошибки
- Нет `.dockerignore` — в образ уезжают `node_modules`, `.git` и `.env`.
- Порядок «сначала код, потом зависимости».
- Инструменты сборки и devDependencies в итоговом образе.

### Мини-задание
Добавь `.dockerignore`, поменяй порядок инструкций в своём Dockerfile, собери образ дважды с правкой кода между сборками и посмотри, какие шаги взяты из кеша. Сравни размер образа на `node:22` и `node:22-alpine`.

### На пальцах
Контейнер — квартира в многоэтажке со своей внутренней нумерацией комнат. Проброс портов — табличка на входе в дом: «кто пришёл на дверь 8080 — проходите в квартиру 3000». Переменные окружения — записка с настройками, которую жилец получает при заселении: адрес базы, ключи, режим работы.

### Как это работает
Порты:

- приложение внутри контейнера слушает свой порт, например 3000;
- снаружи его не видно, пока не пробросишь: `-p 8080:3000` — «порт 8080 компьютера → порт 3000 контейнера» (сначала снаружи, потом внутри);
- внутри контейнера сервер должен слушать `0.0.0.0`, а не `localhost`.

Переменные окружения:

- `-e NAME=value` — одна переменная;
- `--env-file .env` — из файла;
- в Docker Compose — секции `environment` и `env_file`;
- секреты передают при запуске, а не зашивают в образ.

Важная деталь про адреса: `localhost` внутри контейнера — это сам контейнер, а не твой компьютер. Чтобы контейнер с API достучался до базы:

- если база тоже в Docker Compose — по имени сервиса: `postgres://postgres:secret@db:5432/studio`;
- если база на компьютере — `host.docker.internal` (Docker Desktop).

### Пример
```bash
# API внутри слушает 3000, снаружи откроем на 8080
docker run --rm -p 8080:3000 \
  -e NODE_ENV=production \
  -e PORT=3000 \
  --env-file .env \
  studio-api

curl localhost:8080/api/health
```

```js
// src/index.js — слушать все интерфейсы, иначе снаружи контейнера недоступно
const port = Number(process.env.PORT) || 3000;
app.listen(port, "0.0.0.0", () => console.log(`API на порту ${port}`));
```

### Частые ошибки
- Путать порядок в `-p`: `-p 3000:8080` откроет 3000 снаружи на 8080 внутри.
- `DATABASE_URL=...@localhost:5432` внутри контейнера — подключение к самому себе, «connection refused».
- Два контейнера на одном внешнем порту — второй не запустится.

### Мини-задание
Запусти два контейнера своего API на внешних портах 8081 и 8082 с разными значениями переменной `GREETING` и проверь, что каждый отвечает своим приветствием.

### На пальцах
Docker Compose — сценарий для целого спектакля: не один актёр, а вся труппа — API, база, Redis — с описанием, кто кого знает, кто выходит на сцену первым и какие у каждого реквизиты. Одна команда `docker compose up` — и весь проект поднят, как у всех в команде.

### Как это работает
- Файл `compose.yaml` (или `docker-compose.yml`) в корне проекта.
- `services:` — список контейнеров. У каждого: `image` или `build`, `ports`, `environment`, `volumes`, `depends_on`.
- Сервисы автоматически в одной сети и видят друг друга **по имени сервиса**: API обращается к базе по адресу `db:5432`.
- `depends_on` с `condition: service_healthy` — ждать, пока база реально готова, а не просто запущена.
- `volumes` — тома для данных базы, чтобы они переживали пересоздание контейнеров.

Команды:

| Команда | Что делает |
|---|---|
| `docker compose up -d` | поднять всё в фоне |
| `docker compose up --build` | пересобрать образы и поднять |
| `docker compose logs -f api` | логи одного сервиса |
| `docker compose exec db psql -U postgres` | команда в сервисе |
| `docker compose down` | остановить и удалить контейнеры (тома остаются) |
| `docker compose down -v` | то же, вместе с томами (данные удалятся) |

### Пример
```yaml
# compose.yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: studio
    volumes:
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 3s
      retries: 10

  redis:
    image: redis:7-alpine

  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://postgres:secret@db:5432/studio
      REDIS_URL: redis://redis:6379
      JWT_SECRET: local-dev-secret-0123456789abcdef0123
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started

volumes:
  pgdata:
```

```bash
docker compose up -d --build
docker compose exec api node scripts/migrate.js
curl localhost:3000/api/health
docker compose logs -f api
```

### Частые ошибки
- `localhost` вместо имени сервиса в адресе базы.
- `depends_on` без healthcheck — API стартует раньше, чем база готова принимать подключения, и падает.
- `docker compose down -v` «чтобы почистить» — и пропали все локальные данные.

### Мини-задание
Опиши в `compose.yaml` свой API, PostgreSQL и Redis, подними всё одной командой, примени миграции и проверь API. Добавь в README раздел «Запуск через Docker Compose».

### На пальцах
Контейнер — номер в гостинице: когда ты выезжаешь, номер убирают начисто. Том (volume) — твоя камера хранения в той же гостинице: выехал, заехал в другой номер — вещи на месте. Для базы данных это вопрос жизни и смерти: без тома все данные исчезнут при первом же пересоздании контейнера.

### Как это работает
Файловая система контейнера временная: `docker rm` — и всё, что было записано внутри, пропало.

Два способа сохранить данные:

| Способ | Запись | Где лежат данные | Для чего |
|---|---|---|---|
| **Именованный том** | `pgdata:/var/lib/postgresql/data` | в области Docker, им управляет Docker | данные баз, Redis |
| **Bind mount** (папка с компьютера) | `./src:/app/src` | в указанной папке твоего компьютера | разработка: правишь код на компьютере — изменения сразу в контейнере |

Команды:

- `docker volume ls` — список томов;
- `docker volume inspect pgdata` — где лежит;
- `docker volume rm pgdata` — удалить (данные пропадут).

Резервная копия базы из контейнера: `docker compose exec db pg_dump -U postgres studio > backup.sql`.

На продакшене базу часто не держат в контейнере вообще, а используют управляемый сервис (Neon, Supabase, RDS): там резервные копии и восстановление уже настроены.

### Пример
```yaml
services:
  db:
    image: postgres:16-alpine
    volumes:
      - pgdata:/var/lib/postgresql/data       # именованный том — данные переживут пересоздание
      - ./db/init:/docker-entrypoint-initdb.d # SQL-скрипты для первого запуска

  api:
    build: .
    volumes:
      - ./src:/app/src                         # для разработки: правки кода видны сразу
    command: node --watch src/index.js

volumes:
  pgdata:
```

```bash
docker compose down        # контейнеры удалены, том pgdata остался
docker compose up -d       # данные на месте

docker compose exec db pg_dump -U postgres studio > backup-2026-10-24.sql
cat backup-2026-10-24.sql | docker compose exec -T db psql -U postgres studio   # восстановление
```

### Частые ошибки
- База в контейнере без тома.
- Bind mount `node_modules` с компьютера — зависимости под другую ОС ломают запуск.
- Не делать резервных копий, потому что «данные же в томе» — том можно удалить одной командой.

### Мини-задание
Подними базу с именованным томом, создай таблицу и запись, сделай `docker compose down` и снова `up` — убедись, что данные сохранились. Сделай `pg_dump`, удали том, подними базу заново и восстанови данные из дампа.
