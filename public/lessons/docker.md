### Ситуация
Новый разработчик в команде весь первый день ставит PostgreSQL нужной версии, Redis, Node.js 22 и ловит ошибки «у меня другая версия». Проект запускается у всех, кроме него. А на сервере вообще всё иначе, чем на ноутбуке. Фраза «у меня на компьютере работает» — классика, и Docker придуман, чтобы её больше никто не произносил.

### На пальцах
Образ — замороженный полуфабрикат с инструкцией: в коробке уже есть всё — продукты, специи, рецепт. Контейнер — блюдо, разогретое из этого полуфабриката. Из одной коробки можно сделать сколько угодно одинаковых порций, и на любой кухне (у тебя, у коллеги, на сервере) вкус будет одинаковый.

### Как это работает
>> `Dockerfile` → `docker build` → образ → `docker run` → контейнер

| | Образ (image) | Контейнер (container) |
|---|---|---|
| Что это | шаблон только для чтения: ОС, Node.js, код, зависимости | запущенный экземпляр образа |
| Как получить | `docker build` из Dockerfile или `docker pull` из реестра | `docker run образ` |
| Сколько | один образ | сколько угодно контейнеров из него |
| Изменения | неизменяем | изменения внутри пропадают при удалении контейнера |

Контейнер похож на лёгкую виртуальную машину, но использует ядро основной системы, поэтому стартует за секунды и занимает мало ресурсов.

| Команда | Что делает |
|---|---|
| `docker pull postgres:16` | скачать образ из Docker Hub |
| `docker run -d -p 5432:5432 --name db postgres:16` | запустить контейнер в фоне |
| `docker ps` / `docker ps -a` | запущенные / все контейнеры |
| `docker logs -f db` | логи контейнера |
| `docker exec -it db psql -U postgres` | выполнить команду внутри |
| `docker stop db` / `docker rm db` | остановить / удалить |
| `docker images` / `docker rmi образ` | список / удалить образ |

?: Почему контейнер стартует за секунды, а виртуальная машина — минуты? || Виртуальная машина загружает целую операционную систему со своим ядром. Контейнер использует ядро основной системы и запускает только процесс приложения в изолированном окружении — грузить почти нечего.

### Пример
```bash
docker run -d --name studio-db -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres:16
# создаём таблицу и данные внутри...
docker stop studio-db
docker start studio-db
docker rm -f studio-db
docker run -d --name studio-db -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres:16
```

?! Будут ли данные на месте после `stop` и `start`? А после `rm -f` и нового `run`? || После `stop`/`start` — да: контейнер остановлен, но его файлы сохранились. После `rm -f` и нового `run` — нет: это новый контейнер с чистой базой. Чтобы данные переживали удаление, нужен том (о нём — в последнем пункте).

### Частые ошибки
- **Важные данные внутри контейнера без тома** — `docker rm` удалит их навсегда.
- **Тег `latest`** — через месяц скачается другая версия.
- **Путаница остановки и удаления:** `stop` сохраняет контейнер, `rm` удаляет.

### Проверь себя
?? Чем образ отличается от контейнера? || Образ — неизменяемый шаблон с приложением и окружением. Контейнер — запущенный экземпляр образа; из одного образа можно запустить много контейнеров.
?? Какая команда показывает логи контейнера? || `docker logs имя` (с `-f` — следить в реальном времени).
?? Объясни своими словами, какую проблему решает Docker. || Он упаковывает приложение вместе со всем окружением в образ, который одинаково запускается на любом компьютере и сервере, и избавляет от «у меня работает, а у тебя нет».

### На пальцах
Dockerfile — рецепт полуфабриката по шагам: «возьми основу — Node.js 22 (FROM), перейди к рабочему столу (WORKDIR), положи список ингредиентов (COPY package.json), закупи их (RUN npm ci), положи остальные продукты (COPY .), при подаче делай вот это (CMD)».

### Как это работает
>> `FROM node:22` → `WORKDIR /app` → `COPY` → `RUN npm ci` → `CMD ["node", …]`

| Инструкция | Что делает |
|---|---|
| `FROM node:22-alpine` | базовый образ: ОС + Node.js нужной версии |
| `WORKDIR /app` | рабочая папка внутри образа |
| `COPY package*.json ./` | скопировать файлы с компьютера в образ |
| `RUN npm ci --omit=dev` | выполнить команду при сборке |
| `ENV NODE_ENV=production` | переменная окружения по умолчанию |
| `EXPOSE 3000` | документация: какой порт слушает приложение |
| `USER node` | запускать не от root |
| `CMD ["node", "src/index.js"]` | команда при запуске контейнера |

- `RUN` выполняется при **сборке** образа, `CMD` — при **запуске** контейнера.
- `CMD` пишут массивом — так приложение получает сигналы остановки напрямую.
- Образы `alpine` и `slim` — маленькие, полные `node:22` — большие, но с инструментами.

Сборка и запуск: `docker build -t studio-api .` и `docker run -p 3000:3000 --env-file .env studio-api`.

?: Зачем запускать приложение в контейнере от пользователя `node`, а не от root? || Если в приложении найдут уязвимость и злоумышленник выполнит свой код, у него будут права только этого пользователя. От root он смог бы менять всё внутри контейнера и легче выбраться наружу.

### Пример
```dockerfile
FROM node:22-alpine
WORKDIR /app
ENV JWT_SECRET=super-secret-key-123
COPY . .
RUN npm ci --omit=dev
CMD ["node", "src/index.js"]
```

?! Найди в этом Dockerfile две проблемы. || Секрет зашит в образ через `ENV` — он навсегда останется в слоях, и любой, у кого есть образ, его прочитает. И `COPY . .` стоит до `npm ci` — любая правка кода заново скачивает все зависимости (почему — в следующем пункте).

### Частые ошибки
- **`COPY . .` до `npm ci`** — каждая правка кода заново скачивает все зависимости.
- **Сервер слушает `127.0.0.1`** — снаружи контейнера недоступен. Нужен `0.0.0.0`.
- **Секреты через `ENV` в Dockerfile** — они навсегда остаются в образе.

### Проверь себя
?? Чем `RUN` отличается от `CMD` в Dockerfile? || `RUN` выполняется один раз при сборке образа, `CMD` — каждый раз при запуске контейнера.
?? Как собрать образ с именем `studio-api`? || `docker build -t studio-api .` в папке с Dockerfile.
?? Объясни своими словами, как передать секреты в контейнер правильно. || Не зашивать в образ, а передавать при запуске через `-e`, `--env-file` или настройки хостинга, чтобы в самом образе их не было.

### На пальцах
Образ собирается слоями, как многослойный торт: каждая инструкция — слой. Docker запоминает готовые слои. Если основа и крем не менялись, а поменялась только посыпка — переделывают только посыпку. Поэтому редко меняющееся (зависимости) кладут внизу, а часто меняющееся (код) — сверху.

### Как это работает
>> Каждая инструкция — слой → не изменился — из кеша → `package.json` раньше кода

- Каждая инструкция `RUN`, `COPY`, `ADD` создаёт слой.
- При повторной сборке Docker использует кеш слоя, если инструкция и входные файлы не изменились.
- Как только один слой изменился — все слои **выше** пересобираются.

Правило порядка:

1. базовый образ;
2. системные пакеты;
3. `COPY package*.json` + `RUN npm ci` — меняются редко;
4. `COPY . .` — код, меняется постоянно.

`.dockerignore` — список того, что не копировать в образ при `COPY . .`:

- `node_modules` — их поставит `npm ci` внутри, а локальные могут быть под другую ОС;
- `.git`, `.env`, логи, тесты, `dist` — меньше образ и никаких секретов внутри.

Многоэтапная сборка (multi-stage): в первом этапе собрать проект (TypeScript, фронтенд) со всеми инструментами, во второй — скопировать только результат.

?: Почему изменение одного слоя пересобирает все слои выше него? || Каждый слой — это изменения поверх предыдущих. Если нижний слой стал другим, Docker не может быть уверен, что команды выше дадут тот же результат, и выполняет их заново.

### Пример
```dockerfile
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/index.js"]
```

?! Ты поменял одну строку в `src/` и запустил сборку снова. Какие шаги возьмутся из кеша, а какие выполнятся заново? Попадёт ли TypeScript в итоговый образ? || Из кеша: оба `FROM`, `WORKDIR`, копирование `package*.json` и оба `npm ci`. Заново: `COPY . .`, `npm run build` и копирование `dist` во второй этап. TypeScript и devDependencies останутся в первом этапе — итоговый образ получит только `dist` и боевые зависимости.

### Частые ошибки
- **Нет `.dockerignore`** — в образ уезжают `node_modules`, `.git` и `.env`.
- **Порядок «сначала код, потом зависимости».**
- **Инструменты сборки и devDependencies в итоговом образе.**

### Проверь себя
?? В каком порядке располагать инструкции в Dockerfile для быстрого кеша? || От редко меняющихся к часто меняющимся: базовый образ, системные пакеты, файлы зависимостей и их установка, затем код.
?? Что обычно кладут в `.dockerignore`? || `node_modules`, `.git`, `.env` и другие файлы с секретами, логи, отчёты тестов, папку сборки `dist`.
?? Объясни своими словами, зачем многоэтапная сборка. || В первом этапе собирают проект со всеми инструментами, а в итоговый образ копируют только результат. Образ получается маленьким, быстрым в загрузке и без лишнего.

### Ситуация
Контейнер с API запущен, логи говорят «Сервер на порту 3000», а `curl localhost:3000` отвечает «connection refused». Ещё и сам API внутри контейнера не может подключиться к базе по `localhost:5432`, хотя база работает. Сеть в Docker устроена не так, как кажется, и две эти ошибки встречаются у всех.

### На пальцах
Контейнер — квартира в многоэтажке со своей внутренней нумерацией комнат. Проброс портов — табличка на входе в дом: «кто пришёл на дверь 8080 — проходите в квартиру 3000». Переменные окружения — записка с настройками, которую жилец получает при заселении: адрес базы, ключи, режим работы.

### Как это работает
>> `-p 3000:3000` — порт наружу → `-e DATABASE_URL=…` — переменные

Порты:

- приложение внутри контейнера слушает свой порт, например 3000;
- снаружи его не видно, пока не пробросишь: `-p 8080:3000` — «порт 8080 компьютера → порт 3000 контейнера» (сначала снаружи, потом внутри);
- внутри контейнера сервер должен слушать `0.0.0.0`, а не `localhost`.

Переменные окружения:

- `-e NAME=value` — одна переменная;
- `--env-file .env` — из файла;
- в Docker Compose — секции `environment` и `env_file`;
- секреты передают при запуске, а не зашивают в образ.

Адреса: `localhost` внутри контейнера — это сам контейнер, а не твой компьютер. Чтобы API достучался до базы:

- если база тоже в Docker Compose — по имени сервиса: `postgres://postgres:secret@db:5432/studio`;
- если база на компьютере — `host.docker.internal` (Docker Desktop).

?: Почему сервер в контейнере должен слушать `0.0.0.0`, а не `127.0.0.1`? || `127.0.0.1` — петля только внутри самого контейнера. Проброшенный порт приходит в контейнер через его сетевой интерфейс, а не через петлю, и сервер, слушающий только `127.0.0.1`, такие подключения не видит. `0.0.0.0` значит «все интерфейсы».

### Пример
```bash

  -e DATABASE_URL=postgres://postgres:secret@localhost:5432/studio \
  studio-api
curl localhost:3000/api/health
```

?! Почему `curl` не получит ответа и почему API не подключится к базе, которая запущена на компьютере? || Порт перепутан: `-p 3000:8080` ведёт снаружи 3000 на порт 8080 внутри, а API слушает 3000 — нужно `-p 3000:3000`. И `localhost` в `DATABASE_URL` — это сам контейнер, где базы нет; нужен `host.docker.internal` или имя сервиса в Compose.

### Частые ошибки
- **Перепутан порядок в `-p`:** `-p 3000:8080` откроет 3000 снаружи на 8080 внутри.
- **`DATABASE_URL=...@localhost:5432` внутри контейнера** — «connection refused».
- **Два контейнера на одном внешнем порту** — второй не запустится.

### Проверь себя
?? Что означает `-p 8080:3000`? || Порт 8080 компьютера пробрасывается на порт 3000 внутри контейнера.
?? Как контейнер с API обращается к базе в той же сети Docker Compose? || По имени сервиса базы, например `db:5432`.
?? Объясни своими словами, что значит `localhost` внутри контейнера. || Сам этот контейнер, а не компьютер, на котором он запущен. Поэтому сервисы снаружи или в соседних контейнерах по `localhost` недоступны.

README с инструкцией на страницу всё равно приводит к ошибкам. С Docker Compose весь проект описан в одном файле и поднимается одной командой — у тебя, у коллег и в CI одинаково.

### На пальцах
Docker Compose — сценарий для целого спектакля: не один актёр, а вся труппа — API, база, Redis — с описанием, кто кого знает, кто выходит на сцену первым и какие у каждого реквизиты. Одна команда `docker compose up` — и весь проект поднят, как у всех в команде.

### Как это работает
>> `compose.yaml` → `api` + `db` → `docker compose up` → сервисы видят друг друга по именам

- Файл `compose.yaml` (или `docker-compose.yml`) в корне проекта.
- `services:` — список контейнеров. У каждого: `image` или `build`, `ports`, `environment`, `volumes`, `depends_on`.
- Сервисы автоматически в одной сети и видят друг друга **по имени сервиса**: API обращается к базе по адресу `db:5432`.
- `depends_on` с `condition: service_healthy` — ждать, пока база реально готова, а не просто запущена.
- `volumes` — тома для данных базы, чтобы они переживали пересоздание контейнеров.

| Команда | Что делает |
|---|---|
| `docker compose up -d` | поднять всё в фоне |
| `docker compose up --build` | пересобрать образы и поднять |
| `docker compose logs -f api` | логи одного сервиса |
| `docker compose exec db psql -U postgres` | команда в сервисе |
| `docker compose down` | остановить и удалить контейнеры (тома остаются) |
| `docker compose down -v` | то же, вместе с томами (данные удалятся) |

?: Почему `depends_on` без healthcheck не гарантирует, что база готова? || Обычный `depends_on` ждёт только запуска контейнера базы, а Postgres ещё несколько секунд инициализируется и не принимает подключения. API стартует, пытается подключиться и падает. Healthcheck проверяет реальную готовность.

### Пример
```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: studio
    volumes:
      - pgdata:/var/lib/postgresql/data

  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://postgres:secret@db:5432/studio
    depends_on:
      - db

volumes:
  pgdata:
```

?! После `docker compose up` API иногда падает с «connection refused» при первом запуске, а при повторном — работает. Почему и как исправить? || API стартует, пока Postgres ещё инициализируется. Нужен healthcheck у `db` (например, `pg_isready -U postgres`) и `depends_on: db: condition: service_healthy` у API.

### Частые ошибки
- **`localhost` вместо имени сервиса** в адресе базы.
- **`depends_on` без healthcheck** — API стартует раньше, чем база готова.
- **`docker compose down -v` «чтобы почистить»** — и пропали все локальные данные.

### Проверь себя
?? Как сервисы в Docker Compose находят друг друга? || По имени сервиса: Compose создаёт общую сеть, где имя сервиса работает как адрес.
?? Чем `docker compose down` отличается от `docker compose down -v`? || Первая команда удаляет контейнеры, но оставляет тома с данными. Вторая удаляет и тома — данные базы пропадут.
?? Объясни своими словами, зачем проекту Docker Compose. || Чтобы весь набор сервисов — API, базу, Redis — с их настройками и связями описать в одном файле и поднимать одной командой одинаково у всех.

### Ситуация
Ты неделю наполнял локальную базу тестовыми клиентами и проектами. Потом сделал `docker compose down`, поменял версию образа, поднял заново — база пустая. Всё потерялось, потому что данные жили внутри контейнера, а контейнер — расходный материал. Тома — способ хранить данные отдельно от контейнера.

### На пальцах
Контейнер — номер в гостинице: когда ты выезжаешь, номер убирают начисто. Том (volume) — твоя камера хранения в той же гостинице: выехал, заехал в другой номер — вещи на месте. Для базы данных это вопрос жизни и смерти.

### Как это работает
>> Контейнер удалён → данные пропали → том `pgdata:` → данные живут отдельно

Файловая система контейнера временная: `docker rm` — и всё, что было записано внутри, пропало.

| Способ | Запись | Где лежат данные | Для чего |
|---|---|---|---|
| **Именованный том** | `pgdata:/var/lib/postgresql/data` | в области Docker | данные баз, Redis |
| **Bind mount** (папка с компьютера) | `./src:/app/src` | в указанной папке компьютера | разработка: правишь код — изменения сразу в контейнере |

Команды:

- `docker volume ls` — список томов;
- `docker volume inspect pgdata` — где лежит;
- `docker volume rm pgdata` — удалить (данные пропадут).

Резервная копия базы из контейнера: `docker compose exec db pg_dump -U postgres studio > backup.sql`.

На продакшене базу часто не держат в контейнере вообще, а используют управляемый сервис (Neon, Supabase, RDS): там резервные копии уже настроены.

?: Почему нельзя пробрасывать папку `node_modules` с компьютера в контейнер? || Часть пакетов содержит скомпилированный код под конкретную операционную систему. Модули, собранные на Windows или macOS, не запустятся в Linux-контейнере, и приложение упадёт с непонятными ошибками.

### Пример
```yaml
services:
  db:
    image: postgres:16-alpine
    volumes:
      - pgdata:/var/lib/postgresql/data
  api:
    build: .
    volumes:
      - ./src:/app/src
    command: node --watch src/index.js

volumes:
  pgdata:
```

?! Что произойдёт с данными базы после `docker compose down` и `up`? А с правкой в `src/index.js` на компьютере, пока всё запущено? || Данные сохранятся: они в именованном томе `pgdata`, а не в контейнере. Правка кода сразу появится внутри контейнера через bind mount, и `node --watch` перезапустит сервер без пересборки образа.

### Частые ошибки
- **База в контейнере без тома.**
- **Bind mount `node_modules` с компьютера** — зависимости под другую ОС ломают запуск.
- **Нет резервных копий**, потому что «данные же в томе» — том удаляется одной командой.

### Проверь себя
?? Чем именованный том отличается от bind mount? || Именованным томом управляет Docker и хранит его в своей области — это для данных. Bind mount связывает с контейнером конкретную папку компьютера — удобно для кода при разработке.
?? Как сделать резервную копию базы PostgreSQL из контейнера? || `docker compose exec db pg_dump -U postgres имя_базы > backup.sql`.
?? Объясни своими словами, зачем базе данных в Docker нужен том. || Файловая система контейнера временная, и при его удалении данные пропадают. Том хранит данные отдельно, поэтому они переживают пересоздание и обновление контейнера.

### Мини-задание
Подними базу с именованным томом, создай таблицу и запись, сделай `docker compose down` и снова `up` — убедись, что данные сохранились. Сделай `pg_dump`, удали том, подними базу заново и восстанови данные из дампа.
