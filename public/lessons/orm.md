### На пальцах
Писать SQL руками — готовить по старинке, самому отмеряя каждый ингредиент. ORM — кухонный комбайн: нажал кнопку «найти проекты клиента» — получил результат, а комбайн сам составил правильный SQL. Быстро и удобно для типовых блюд, но для сложного соуса шеф всё равно берёт венчик в руки.

### Как это работает
| Подход | Что это | Примеры |
|---|---|---|
| Сырой SQL | пишешь запросы текстом | `pg` |
| Query builder | строишь SQL цепочкой методов, близко к SQL | Knex, Kysely, Drizzle |
| ORM | работаешь с моделями и объектами, SQL генерируется | Prisma, TypeORM, Sequelize |

Плюсы ORM и построителей:

- типизация: TypeScript знает поля таблиц, опечатка в названии колонки — ошибка ещё в редакторе;
- безопасность: значения всегда передаются параметрами;
- миграции и описание схемы в одном месте;
- меньше однотипного кода для CRUD.

Минусы:

- сложные запросы (отчёты, оконные функции) выражаются неудобно или неэффективно;
- легко не заметить, сколько запросов на самом деле уходит в базу (проблема N+1);
- ещё один инструмент со своими правилами;
- без знания SQL трудно понять, почему что-то медленно.

?: Почему SQL нужно знать, даже если в проекте ORM? || ORM генерирует SQL за тебя, и когда запрос тормозит или возвращает не то, разбираться приходится на уровне SQL: читать сгенерированный запрос и `EXPLAIN`. Без знания SQL ORM — чёрный ящик, который ты не можешь починить.

### На пальцах
`include` — «принеси клиента и заодно все его проекты». `select` — «принеси только имя клиента и названия проектов, остальное не нужно». Первое удобно, второе экономно: меньше данных идёт из базы и в ответе API.

### Как это работает
- **include** — подгрузить связанные модели целиком: `include: { projects: true }`.
- **select** — выбрать конкретные поля, в том числе у связанных моделей. `select` и `include` на одном уровне вместе не используют.
- Внутри связи тоже можно фильтровать, сортировать и ограничивать: `include: { projects: { where: { status: "active" }, take: 5 } }`.
- `_count` — посчитать связанные записи без их загрузки.
- Создание вместе со связанными записями — вложенный `create`.
- Фильтр по связям: `where: { projects: { some: { status: "active" } } }` — клиенты, у которых есть хоть один активный проект.

?: Зачем `_count`, если можно загрузить связи и взять длину массива? || Загрузка всех связанных записей тянет из базы и по сети все их поля ради одного числа. `_count` превращается в `COUNT` прямо в базе и возвращает только число — в разы быстрее и легче.

### Пример
```ts
const list = await prisma.client.findMany({
  select: {
    id: true,
    name: true,
    _count: { select: { projects: true } },
    projects: { where: { status: "active" }, select: { title: true } },
  },
});
```

?! Какие поля будут у каждого клиента в ответе? Попадёт ли туда email? || `id`, `name`, `_count` с общим числом проектов и `projects` — только названия активных проектов. Email не попадёт: в `select` его нет. `_count` считает все проекты, а `projects` фильтрует только активные — числа могут не совпадать.

### Частые ошибки
- **`include` всего подряд** — огромные ответы и медленные запросы.
- **Пользователь с `passwordHash` в ответе API**, потому что не указали `select`.
- **Связанные данные в цикле** вместо `include` (проблема N+1 — следующий пункт).

?? Как найти клиентов, у которых есть хотя бы один активный проект? || `prisma.client.findMany({ where: { projects: { some: { status: "active" } } } })`.
?? Объясни своими словами, почему `select` важен для безопасности API. || Без него модель отдаётся целиком, включая служебные и секретные поля вроде хеша пароля. `select` гарантирует, что наружу уйдёт только то, что ты явно выбрал.

### На пальцах
Prisma — полноценный архитектурный пакет со своим чертёжным языком и генерацией. Drizzle — лёгкий набор инструментов: схема пишется обычным TypeScript, запросы очень похожи на сам SQL, а пакет маленький и быстро работает даже в serverless и edge-окружениях.

### Как это работает
- `npm install drizzle-orm pg` и `npm install -D drizzle-kit`.

- Есть и «реляционный» API, похожий на Prisma: `db.query.clients.findMany({ with: { projects: true } })`.
- Миграции: `npx drizzle-kit generate` создаёт SQL-файлы из изменений схемы, `npx drizzle-kit migrate` — применяет.
- Типы выводятся прямо из схемы, генерация клиента не нужна.

Когда что выбирать:

- **Prisma** — большой «всё в одном», отличная документация, Studio, много примеров.
- **Drizzle** — ближе к SQL, легче, без отдельного шага генерации, хорошо подходит тем, кто знает SQL.

?: Почему Drizzle не нужен отдельный шаг генерации клиента, как у Prisma? || Схема в Drizzle — обычный TypeScript-код, и типы выводятся из него напрямую компилятором. Prisma описывает схему на своём языке, поэтому из неё нужно сгенерировать TypeScript-код клиента.

### Пример
```ts

  id: serial("id").primaryKey(),
  clientId: integer("client_id").notNull().references(() => clients.id),
  title: text("title").notNull(),
  budget: integer("budget"),
});

const rich = await db
  .select({ title: projects.title, client: clients.name })
  .from(projects)
  .innerJoin(clients, eq(clients.id, projects.clientId))
  .where(gt(projects.budget, 50000));
```

?! Как называется колонка с id клиента в базе, а как — в TypeScript-коде? Какой SQL примерно выполнит запрос? || В базе — `client_id`, в коде — `clientId`. Запрос: `SELECT projects.title, clients.name FROM projects INNER JOIN clients ON clients.id = projects.client_id WHERE projects.budget > $1`.

- **Миграции не сгенерированы и не применены** после изменения схемы.

- **Prisma и Drizzle в одном проекте.**

### Ситуация
Страница со списком из 50 проектов грузится три секунды. Запрос в базу один и простой — откуда тормоза? Включаешь логирование и видишь: в базу ушёл 51 запрос. Один — за проектами, и ещё по одному за клиентом каждого проекта, в цикле. Это проблема N+1 — любимый вопрос на собеседованиях на бэкенд и одна из самых частых причин медленных API.

### На пальцах
Ты пришёл в магазин за продуктами по списку из 50 пунктов. Можно 50 раз сходить в магазин за одним продуктом (N+1), а можно один раз взять корзину и купить всё сразу. Проблема N+1 — когда программа незаметно для тебя ходит в базу «за каждым продуктом отдельно».

### Как это работает
Классический пример:

1. Один запрос: получить 50 проектов.
2. Потом в цикле для каждого проекта запрос: получить его клиента.

Итого 1 + 50 = 51 запрос вместо одного-двух. На маленьких данных незаметно, на реальных — страница грузится секунды, а база перегружена.

Почему возникает: ORM делает доступ к связанным данным очень простым, и цикл с запросом внутри выглядит безобидно. Также бывает в GraphQL и при «ленивой загрузке» связей.

Как найти: включить логирование запросов (`log: ["query"]` в Prisma) и посмотреть, сколько запросов уходит на одну страницу.

Как исправить:

- `JOIN` в SQL или `include` / `with` в ORM — один запрос;
- собрать все id и сделать один запрос `WHERE id IN (...)` / `id = ANY($1)`, потом сопоставить в коде;
- для GraphQL — DataLoader, который собирает запросы в пачку.

?: Почему 51 маленький запрос медленнее одного большого, если данных столько же? || Каждый запрос — это поход по сети к базе и обратно, разбор и планирование. Даже по 10 мс на запрос — это полсекунды только на ожидание сети, плюс нагрузка на базу. Один запрос с JOIN тратит эти накладные расходы один раз.

### Пример
```ts
const list = await prisma.project.findMany({ take: 20 });
for (const p of list) {
  const client = await prisma.client.findUnique({ where: { id: p.clientId } });
  console.log(p.title, client?.name);
}
```

?! Сколько запросов уйдёт в базу и как сократить их до одного? || 21: один за проектами и по одному за клиентом каждого из 20. Исправление: `prisma.project.findMany({ take: 20, include: { client: { select: { name: true } } } })` — один запрос со связью.

### Частые ошибки
- **`await` запроса к базе внутри `for` или `map`.**
- **Логи запросов не смотрят** при разработке.
- **N+1 лечат кешем** вместо правильного запроса.

### Проверь себя
?? Что такое проблема N+1? || Когда для списка из N элементов делается один запрос за списком и ещё N запросов — по одному на каждый элемент — вместо одного-двух запросов.
?? Как найти N+1 в проекте? || Включить логирование SQL-запросов и посмотреть, сколько запросов уходит при загрузке одной страницы.
?? Объясни своими словами два способа исправить N+1. || Загрузить связанные данные одним запросом через JOIN или `include`, либо собрать все нужные id и получить их одним запросом `WHERE id = ANY(...)`, а потом сопоставить в коде.

### Ситуация
Бухгалтер просит отчёт: выручка по месяцам и типам проектов. Через Prisma это превращается в выгрузку всех платежей в память и группировку в JavaScript — сервер ест гигабайт и думает десять секунд. На чистом SQL это пять строк и 30 миллисекунд. Хороший разработчик знает, когда ORM помогает, а когда пора открыть люк ручного управления.

### На пальцах
ORM — удобный автомобиль с автоматической коробкой для ежедневных поездок. Но если нужно проехать по сложной горной дороге (хитрый отчёт), иногда проще пересесть на «механику» — написать SQL руками. Хорошие ORM не запрещают это, а дают удобный люк для ручного управления.

### Как это работает
Когда стоит писать SQL самому:

- отчёты и аналитика: группировки, оконные функции (`ROW_NUMBER`, `SUM() OVER`), сложные CTE;
- массовые обновления: «поднять цены всех товаров категории на 10%» — один `UPDATE` вместо загрузки тысяч объектов;
- возможности конкретной базы: полнотекстовый поиск PostgreSQL, `jsonb`-операторы, `ON CONFLICT DO UPDATE` (upsert), рекурсивные запросы;
- когда запрос ORM медленный, и `EXPLAIN` показывает, что SQL можно написать лучше.

Как делать это безопасно:

- Prisma: `prisma.$queryRaw` с шаблонной строкой — значения в `${}` автоматически становятся параметрами. `$queryRawUnsafe` — без защиты, избегай.
- Drizzle: тег `sql` с теми же правилами.
- pg: обычные параметры `$1`.

Типы результата сырого запроса нужно указать самому.

?: Почему `${}` в `prisma.$queryRaw` безопасен, а в обычной строке — нет? || `$queryRaw` — это тегированный шаблон: Prisma получает куски текста и значения раздельно и передаёт значения параметрами. В обычной строке значения вклеиваются в текст до отправки, и база не отличит их от команды.

### Пример
```ts
const categoryId = req.query.cat;

await prisma.$executeRaw`UPDATE products SET price = price * 1.1 WHERE category_id = ${categoryId}`;

await prisma.$executeRawUnsafe(`UPDATE products SET price = price * 1.1 WHERE category_id = ${categoryId}`);
```

?! Что будет, если злоумышленник передаст `?cat=1 OR 1=1` в каждом из двух вариантов? || В первом `"1 OR 1=1"` уйдёт параметром, база не сможет сопоставить его с числовой колонкой — ошибка или ноль обновлений. Во втором строка вклеится в SQL, условие станет `category_id = 1 OR 1=1` — и цены поднимутся у всех товаров магазина.

### Частые ошибки
- **`$queryRawUnsafe` со строкой из пользовательского ввода.**
- **10 000 объектов в цикле** с сохранением по одному вместо одного `UPDATE`.
- **Всё в ORM «ради единообразия»**, даже то, что он делает плохо.

### Проверь себя
?? Как в Prisma безопасно выполнить сырой SQL-запрос со значением от пользователя? || Через `prisma.$queryRaw` (или `$executeRaw`) с тегированным шаблоном: значения в `${}` станут параметрами.
?? Приведи два случая, когда лучше написать SQL вручную. || Сложные отчёты с группировками и оконными функциями и массовые обновления одним `UPDATE`.
?? Объясни своими словами, почему массовое обновление лучше делать одним SQL-запросом. || Один `UPDATE` выполняется внутри базы за один проход. Загрузка тысяч объектов в приложение и сохранение по одному — это тысячи запросов, много памяти и времени.
