Ты хочешь сделать личный кабинет с заметками: регистрация, вход, у каждого свои данные. Фронтенд ты уже умеешь, а свой сервер с базой и авторизацией — пока нет. Учить бэкенд полгода ради одного проекта в портфолио? Есть готовая «кухня», к которой фронтенд подключается за вечер.

### На пальцах
Supabase — готовая кухня для твоего ресторана: база данных, вход для пользователей, хранилище файлов — всё уже подключено. Не нужно строить свой сервер, чтобы у приложения появились аккаунты и сохранённые данные. Ты просто подключаешь фронтенд к этой кухне.

### Как это работает
>> Проект в Supabase → вход по email → таблица → `supabase.from('notes').select()`

1. Зарегистрируйся на supabase.com, создай проект.
2. В Table Editor создай таблицу, например `notes` с колонками `id`, `user_id`, `title`, `done`, `created_at`.
3. В Settings → API возьми `Project URL` и `anon public key`. Этот ключ можно использовать во фронтенде: доступ к данным ограничивают правила RLS (следующий пункт).
4. `npm install @supabase/supabase-js`.
5. Создай клиент и работай с данными через методы вроде `from("notes").select()`.

Вход:

- `supabase.auth.signUp({ email, password })` — регистрация;
- `supabase.auth.signInWithPassword({ email, password })` — вход;
- `supabase.auth.getUser()` — кто сейчас вошёл;
- `supabase.auth.signOut()` — выход;
- `onAuthStateChange` — подписка на вход и выход.

Каждый запрос возвращает `{ data, error }` — всегда проверяй `error`.

?: Почему `anon` ключ можно держать во фронтенде, а `service_role` — нельзя? || `anon` ключ лишь пропускает к базе, а что именно разрешено, решают правила RLS — с ним видно только то, что политики позволяют. `service_role` обходит все правила и даёт полный доступ ко всем данным всех пользователей.

### Пример
```ts
export async function getMyNotes() {
  const { data } = await supabase
    .from("notes")
    .select("id, title, done, created_at")
    .order("created_at", { ascending: false });
  return data.map(n => n.title);
}
```

### Частые ошибки
- **`service_role` ключ во фронтенде** — полный доступ к базе для любого посетителя.
- **Нет проверки `error`** — `data = null` и падение дальше по коду.
- **Таблицы без RLS** — данные всех пользователей открыты всем.

### Ситуация
Твоё приложение заметок показывает пользователю только его записи — ты фильтруешь их в коде по `user_id`. Кажется, всё безопасно. Но любой может открыть консоль браузера, вызвать `supabase.from("notes").select()` без фильтра — и получить заметки всех пользователей. Защита в интерфейсе — не защита. Защищать нужно в самой базе.

### На пальцах
Row Level Security — консьерж в многоквартирном доме, который пускает каждого жильца только в его квартиру. Даже если кто-то знает номер чужой квартиры и вежливо просит, консьерж проверяет паспорт и не пускает. Правило живёт в самой базе, поэтому обойти его из браузера нельзя.

### Как это работает
>> Запрос к таблице → политика RLS → видны только свои строки

- RLS — правила доступа на уровне строк таблицы в PostgreSQL.
- Включается для каждой таблицы отдельно. После включения без правил никто ничего не видит.
- Политика (policy) описывает: для какой операции (SELECT, INSERT, UPDATE, DELETE) и при каком условии строка доступна.
- В Supabase функция `auth.uid()` возвращает id текущего пользователя из его сессии.

Типичная политика: «пользователь видит и меняет только строки, где `user_id = auth.uid()`».

Настраивается в Supabase: Authentication → Policies, или SQL-редактором.

?: Почему после включения RLS без политик никто ничего не видит? || Это принцип «по умолчанию запрещено». Безопаснее ошибиться в сторону «ничего не видно» и добавить нужные права, чем случайно открыть всё. Каждую разрешённую операцию нужно описать явно.

### Пример
```sql
alter table notes enable row level security;

create policy "читать свои" on notes
  for select using (user_id = auth.uid());

create policy "создавать свои" on notes
  for insert with check (user_id = auth.uid());

alter table notes alter column user_id set default auth.uid();
```

?! Анна вошла и пытается удалить свою заметку. Получится ли? А изменить заголовок? || Ни то, ни другое: политики есть только для чтения и создания. Для UPDATE и DELETE правил нет, а при включённом RLS без политики операция запрещена. Нужны ещё две политики с `using (user_id = auth.uid())`.

### Частые ошибки
- **Таблица без RLS** — Supabase помечает её как «unrestricted».
- **Политика `using (true)` «чтобы заработало»** — открывает всё всем.
- **Проверка прав только во фронтенде** (`if (note.user_id === me.id)`) — это интерфейс, а не защита.

### Проверь себя
?? Что возвращает функция `auth.uid()` в Supabase? || Id пользователя, который выполняет запрос, из его сессии.
?? Чем `using` отличается от `with check` в политике? || `using` проверяет, какие существующие строки можно читать, менять или удалять. `with check` проверяет новые или изменённые данные, которые пытаются записать.
?? Объясни своими словами, почему фильтр по `user_id` во фронтенде не защищает данные. || Код фронтенда выполняется у пользователя, и любой может отправить свой запрос без фильтра. Защищает только проверка на стороне базы или сервера.

### Ситуация
Форма брифа: имя, email, бюджет, сроки, описание. На `useState` это пять состояний, пять обработчиков, ручные проверки, тексты ошибок, блокировка кнопки — сто строк кода, а правила проверки на сервере всё равно пишешь заново. Две библиотеки превращают это в одну схему и пару строчек.

### На пальцах
Большая форма на чистом `useState` — бухгалтерия на счётах: работает, но каждое поле, ошибку и проверку ведёшь вручную. react-hook-form — бухгалтерская программа для формы: сама следит за полями, ошибками и отправкой. zod — свод правил: «имя от 2 символов, email похож на email, сумма больше нуля». Программа сверяет форму со сводом.

### Как это работает
>> Схема zod → `useForm({ resolver: zodResolver })` → ошибки у полей → отправка

- `npm install react-hook-form zod @hookform/resolvers`
- Описываешь схему zod — правила и тексты ошибок.
- Тип данных формы выводится из схемы: `z.infer<typeof schema>`, отдельно описывать не нужно.
- `useForm({ resolver: zodResolver(schema) })` связывает форму со схемой.
- `register("name")` подключает поле. Возвращает `name`, `onChange`, `onBlur`, `ref`.
- `handleSubmit(onValid)` — вызовет функцию, только если данные прошли проверку.
- `formState.errors` — ошибки по полям, `formState.isSubmitting` — идёт ли отправка.

react-hook-form не перерисовывает всю форму на каждый символ — большие формы работают быстро.

?: Почему тип формы лучше выводить из схемы через `z.infer`, а не описывать вручную? || Тогда правила и тип — одно и то же. Добавил поле в схему — тип обновился сам. При ручном описании их рано или поздно забудут синхронизировать, и TypeScript будет обещать поля, которых форма не проверяет.

### Пример
```tsx
const schema = z.object({
  name: z.string().trim().min(2, "Минимум 2 символа"),
  email: z.string().email("Проверьте email"),
  budget: z.number().min(10000, "Бюджет от 10 000 ₽"),
});
type FormData = z.infer<typeof schema>;

const { register, handleSubmit, formState: { errors } } =
  useForm<FormData>({ resolver: zodResolver(schema) });

// <input inputMode="numeric" {...register("budget")} />
```

?! Пользователь ввёл в поле бюджета «50000». Пройдёт ли проверка? || Нет: из `input` всегда приходит строка `"50000"`, а схема требует число. Нужно `z.coerce.number()` — тогда строка будет превращена в число перед проверкой.

### Частые ошибки
- **Забыт `resolver`** — схема не применяется.
- **Числовые поля без `z.coerce.number()`** — проверка «число» падает на строке.
- **Тип формы вручную отдельно от схемы** — они расходятся.

### Проверь себя
?? Что делает `handleSubmit(onSubmit)`? || Проверяет данные формы и вызывает `onSubmit`, только если проверка пройдена; иначе заполняет `errors`.
?? Как получить TypeScript-тип данных формы из схемы zod? || `type FormData = z.infer<typeof schema>`.
?? Объясни своими словами, зачем связывать react-hook-form со схемой zod. || Правила проверки и тексты ошибок описываются в одном месте, тип формы выводится автоматически, а ту же схему можно переиспользовать на сервере.

### Ситуация
Гость открывает ссылку `/notes`, которую ему прислали, — и видит пустой кабинет с ошибками в консоли. Вошедший пользователь обновляет страницу — и на секунду его выкидывает на экран входа, а потом возвращает. После входа его отправляет на главную, а не туда, куда он шёл. Три мелочи, по которым видно, доделан кабинет или нет.

### На пальцах
Защищённая страница — комната с охранником на двери. Без пропуска охранник вежливо отправляет на ресепшен (страницу входа) и запоминает, куда ты шёл, чтобы потом проводить туда. Но помни: охранник у двери — для удобства. Настоящие сейфы (данные) защищает сервер или RLS.

### Как это работает
>> Нет сессии → `<Navigate to="/login">` → после входа — обратно

1. Храни текущего пользователя в Context или сторе. Пока не выяснили, вошёл ли он, — состояние «проверяю» (`undefined`), иначе пользователь или `null`.
2. Компонент-обёртка `RequireAuth`:
   - пока проверяем — показать загрузку;
   - не вошёл — `<Navigate to="/login" state={{ from: location }} replace />`;
   - вошёл — показать содержимое.
3. После входа отправляй туда, откуда пришли: `navigate(location.state?.from?.pathname ?? "/account")`.
4. Можно сделать проверку роли: `RequireRole role="admin"`.

Защищённая страница прячет интерфейс, а данные защищает сервер, отвечая 401/403, или RLS.

?: Зачем три состояния пользователя — `undefined`, `null` и объект, — если достаточно «вошёл / не вошёл»? || Сразу после загрузки страницы приложение ещё не знает, есть ли сессия. Если считать это «не вошёл», пользователя на мгновение выкинет на экран входа. `undefined` значит «ещё проверяю» — и в это время показывают загрузку.

### Пример
```tsx
export function RequireAuth() {
  const { user } = useAuth();
  const location = useLocation();

  if (!user) return <Navigate to="/login" state={{ from: location }} />;
  return <Outlet />;
}
```

?! Найди две проблемы, которые заметит вошедший пользователь при обновлении страницы `/notes` и после входа. || `!user` срабатывает и для `undefined` (ещё проверяем), поэтому вошедшего на мгновение перекидывает на `/login`. А без `replace` в истории остаётся защищённая страница: кнопка «Назад» после входа вернёт туда и снова перекинет на вход.

### Частые ошибки
- **Нет состояния «проверяю»** — вошедшего пользователя на мгновение выкидывает на вход.
- **Без `replace`** — кнопка «Назад» создаёт петлю перенаправлений.
- **Вера, что спрятанная страница защищает данные.**

?? Что делает `replace` в `<Navigate replace />`? || Заменяет текущую запись в истории браузера вместо добавления новой, чтобы кнопка «Назад» не возвращала на страницу с перенаправлением.
?? Объясни своими словами, почему защищённый маршрут во фронтенде не защищает данные. || Он только решает, показывать ли интерфейс. Запрос к данным можно отправить и в обход интерфейса, поэтому права обязан проверять сервер или база.

### Ситуация
Заметки, задачи, заказы, посты, комментарии — открой любое бизнес-приложение, и окажется, что 80% его функций — четыре действия с записями. На собеседовании просят «сделать CRUD», и разница между джуном и мидлом видна не в том, работает ли он, а в деталях: что происходит при ошибке, при двойном клике, после удаления.

### На пальцах
CRUD — четыре действия, из которых состоит почти любое приложение: создать (Create), прочитать (Read), изменить (Update), удалить (Delete). Научился делать CRUD аккуратно — можешь сделать большинство бизнес-приложений.

### Как это работает
>> Create → Read → Update → Delete → интерфейс обновляется после каждого

| Действие | Supabase | REST API | В интерфейсе |
|---|---|---|---|
| Create | `insert({...})` | `POST /notes` | форма создания |
| Read | `select()` | `GET /notes`, `GET /notes/:id` | список и страница |
| Update | `update({...}).eq("id", id)` | `PATCH /notes/:id` | редактирование, галочка |
| Delete | `delete().eq("id", id)` | `DELETE /notes/:id` | кнопка с подтверждением |

Что сделать хорошо, а не «просто работает»:

- после создания и изменения — обновить список (через `invalidateQueries` или локально);
- блокировать кнопки на время запроса;
- подтверждение перед удалением или кнопка «Отменить» в уведомлении;
- понятные ошибки и пустые состояния;
- оптимистичное обновление для быстрых действий: галочка меняется сразу, а при ошибке откатывается.

?: Что такое оптимистичное обновление и зачем оно? || Интерфейс меняется сразу, ещё до ответа сервера, в расчёте на успех. Приложение ощущается мгновенным. Если сервер вернул ошибку, изменение откатывают и показывают сообщение.

### Пример
```ts
export async function toggleNote(id: number, done: boolean) {
  const { error } = await supabase.from("notes").update({ done });
  if (error) throw error;
}

export async function deleteNote(id: number) {
  const { error } = await supabase.from("notes").delete().eq("id", id);
  if (error) throw error;
}
```

?! Пользователь отметил одну заметку выполненной. Что произойдёт в базе? || Все заметки, к которым у него есть доступ, станут выполненными: в `update` забыт фильтр `.eq("id", id)`. RLS не даст тронуть чужие, но свои изменятся все.

### Частые ошибки
- **`update` или `delete` без `.eq("id", id)`** — изменятся все доступные строки.
- **Список не обновляется после создания** — пользователь думает, что ничего не сохранилось.
- **Удаление в один клик** без подтверждения и возможности отменить.

### Проверь себя
?? Расшифруй CRUD. || Create, Read, Update, Delete — создание, чтение, изменение, удаление.
?? Какие HTTP-методы соответствуют операциям CRUD в REST? || POST — создание, GET — чтение, PATCH или PUT — изменение, DELETE — удаление.
?? Объясни своими словами, чем аккуратный CRUD отличается от просто работающего. || В аккуратном список сразу обновляется, кнопки блокируются на время запроса, удаление подтверждается, ошибки понятны, а пустой список выглядит осмысленно.
