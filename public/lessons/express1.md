### Как это работает
1. `npm init -y`, в `package.json` добавить `"type": "module"`.

app.get("/", (req, res) => res.send("Привет"));

- `app.get(путь, обработчик)` — маршрут. Обработчик получает `req` (запрос) и `res` (ответ).
- `app.listen(порт, колбэк)` — начать слушать.
- `node --watch src/index.js` — перезапуск при сохранении.

├── .env

### На пальцах
Маршрут — правило на ресепшене: «Кто пришёл с вопросом GET про /projects — к менеджеру по проектам». Параметр `:id` — графа «номер», которая может быть любой: `/projects/42`, `/projects/7`. Query-параметры `?status=open` — дополнительные пожелания: «покажите только открытые».

### Как это работает
- Метод маршрута — метод HTTP: `app.get`, `app.post`, `app.put`, `app.patch`, `app.delete`.
- Параметры пути: `/projects/:id` → `req.params.id`. Всегда строка, для числа — `Number(...)`.
- Несколько параметров: `/projects/:projectId/tasks/:taskId`.
- Query-параметры: `/projects?status=open&page=2` → `req.query.status`, `req.query.page`. Тоже строки или массивы, если параметр повторяется.
- Маршруты проверяются по порядку сверху вниз. Конкретные (`/projects/stats`) ставь выше параметрических (`/projects/:id`).

Один путь — несколько методов — удобно через `app.route("/projects").get(...).post(...)`.

?: Почему параметры из адреса всегда строки? || Адрес — это просто текст в строке запроса. Express не знает, что ты имел в виду под `42`: число, код или имя. Преобразовывать тип — твоя задача, и заодно это место для проверки, что значение корректное.

### Ситуация
Сервер падает с загадочной ошибкой «Cannot set headers after they are sent to the client». Ты смотришь на маршрут — там один `res.json`. Нет, два: один для ошибки, другой для успеха, и без `return` выполнились оба. Объекты `req` и `res` — твои главные инструменты в Express, и у `res` есть одно жёсткое правило.

### На пальцах
`req` — входящее письмо: от кого, что просят, какие вложения. `res` — бланк ответа: ставишь печать с кодом (`status`), подписываешь служебные пометки (`set`), кладёшь содержимое (`json`) и отправляешь. Один ответ на одно письмо — второй раз отправить нельзя.

### Как это работает
| Поле `req` | Что внутри |
|---|---|
| `req.method`, `req.path` | метод и путь |
| `req.params` | параметры пути |
| `req.query` | query-параметры |
| `req.body` | тело (после `express.json()`) |
| `req.headers` / `req.get("Имя")` | заголовки |
| `req.ip` | адрес клиента |

| Метод `res` | Что делает |
|---|---|
| `res.status(201)` | поставить код, возвращает `res` для цепочки |
| `res.json(obj)` | отправить JSON с правильным `Content-Type` |
| `res.send(text)` | отправить текст или HTML |
| `res.set("X-Total-Count", "42")` | заголовок |
| `res.cookie(name, value, options)` | установить cookie |
| `res.redirect(302, "/login")` | редирект |
| `res.status(204).end()` | ответ без тела |

Правило: ответ отправляется ровно один раз. После ответа с ошибкой используй `return`.

?: Почему второй `res.json` вызывает ошибку, а не просто перезаписывает ответ? || Первый вызов уже отправил клиенту заголовки и тело по сети. Вернуть отправленное нельзя, поэтому Express сообщает об ошибке: попытка ответить второй раз почти всегда означает баг в логике.

### Пример
```js
app.post("/api/projects", (req, res) => {
  const { title } = req.body ?? {};
  if (!title) {
    res.status(400).json({ error: "Укажите название" });
  }
  const project = { id: Date.now(), title };
  projects.push(project);
  res.status(201).json(project);
});
```

?! Что произойдёт, если отправить пустое тело? || Клиент получит 400 «Укажите название», но код продолжит выполняться: в массив добавится проект без названия, а второй `res.json` вызовет в консоли «Cannot set headers after they are sent». Нужен `return` перед `res.status(400)`.

### Частые ошибки
- **Нет `return` после ответа с ошибкой.**
- **`res.send(42)`** — Express воспримет число как код статуса.
- **`req.body` без подключённого `express.json()`.**

### Проверь себя
?? Как отправить ответ с кодом 201 и JSON-телом? || `res.status(201).json(объект)`.
?? Как прочитать заголовок `User-Agent` из запроса? || `req.get("User-Agent")` или `req.headers["user-agent"]`.
?? Объясни своими словами, зачем писать `return` перед ответом с ошибкой. || Чтобы остановить выполнение обработчика: иначе код пойдёт дальше, сделает лишнюю работу и попытается отправить второй ответ.

### Ситуация
Нужно логировать каждый запрос, проверять токен на половине маршрутов, разбирать JSON и считать время ответа. Копировать эти строчки в каждый обработчик — путь к хаосу: где-то забудешь проверку прав, и данные утекут. В Express всё общее выносится в middleware — это главная идея фреймворка и частый вопрос на собеседованиях.

### На пальцах
Middleware — посты контроля на конвейере. Запрос едет по ленте: сначала пост «записать в журнал», потом «проверить пропуск», потом «распаковать посылку», и только в конце — нужный отдел. Каждый пост либо пропускает дальше (`next()`), либо сам отвечает и останавливает ленту. Порядок постов важен.

### Как это работает
Middleware — функция `(req, res, next) => { ... }`. Варианты действий:

- сделать что-то и вызвать `next()` — передать дальше;
- ответить (`res.status(401).json(...)`) и не вызывать `next()` — остановить цепочку;
- вызвать `next(error)` — перейти сразу к обработчику ошибок.

Подключение:

- `app.use(mw)` — для всех запросов;
- `app.use("/api", mw)` — для путей, начинающихся с `/api`;
- `app.get("/admin", requireAuth, requireAdmin, handler)` — для одного маршрута, по цепочке.

Выполняются в порядке подключения. Типичный порядок: логирование → безопасность и CORS → разбор тела → авторизация → маршруты → 404 → обработчик ошибок.

Middleware может добавлять данные в `req`: `req.user = user`.

?: Почему обработчик 404 подключают после всех маршрутов? || Middleware без пути срабатывает на любой запрос. Если поставить его первым, он ответит «нет такого адреса» на всё подряд. Внизу он получает только те запросы, которые не подошли ни под один маршрут выше.

### Пример
```js
function requireApiKey(req, res, next) {
  if (req.get("X-Api-Key") !== process.env.API_KEY) {
    return res.status(401).json({ error: "Нужен ключ доступа" });
  }
  next();
}

app.get("/api/private", (req, res) => res.json({ secret: 42 }));
app.use(requireApiKey);
app.get("/api/admin", (req, res) => res.json({ admin: true }));
```

?! Какой из двух маршрутов защищён ключом, а какой открыт всем? || `/api/private` открыт всем: он объявлен до `app.use(requireApiKey)`, и проверка до него не доходит. `/api/admin` защищён. Порядок подключения решает.

### Частые ошибки
- **Забыт `next()`** — запрос «зависает».
- **`next()` после отправки ответа** — следующие обработчики пытаются ответить ещё раз.
- **Проверка авторизации после маршрутов**, которые она должна защищать.

### Проверь себя
?? Какие три действия может сделать middleware? || Передать запрос дальше через `next()`, ответить сам и остановить цепочку или вызвать `next(error)`, чтобы перейти к обработчику ошибок.
?? Как подключить middleware только к одному маршруту? || Передать его аргументом перед обработчиком: `app.get("/путь", mw, handler)`.
?? Объясни своими словами, что такое middleware. || Функция-посредник, через которую проходит запрос по пути к обработчику. Она может что-то проверить или добавить к запросу, ответить сама или передать дальше.

### Ситуация
Фронтенд отправляет заявку, сервер падает на `const { name } = req.body` с ошибкой «Cannot destructure property of undefined». В другой раз кто-то присылает кривой JSON, и вместо понятной ошибки клиент получает HTML-страницу со стеком вызовов сервера. Работа с телом запроса — первая линия обороны API.

### На пальцах
Тело запроса приходит как запечатанная посылка — поток байтов. `express.json()` — работник на входе, который вскрывает посылку с пометкой «JSON», разбирает содержимое и кладёт аккуратно на стол: `req.body`. Без него посылка так и лежит запечатанной, и `req.body` пустой.

### Как это работает
- `app.use(express.json())` — подключить один раз, до маршрутов.
- Работает только для запросов с заголовком `Content-Type: application/json`.
- Если JSON кривой — Express передаст ошибку в обработчик ошибок.
- Лимит размера по умолчанию 100 КБ: `express.json({ limit: "1mb" })`. Большой лимит без нужды — риск, что сервер завалят огромными запросами.
- Для обычных HTML-форм — `express.urlencoded({ extended: true })`.
- Для файлов — отдельные библиотеки (`multer`).

Тело — данные от клиента, а значит, им нельзя доверять: проверяй наличие полей, типы и длину.

?: Зачем у `express.json()` ограничение размера тела? || Без лимита злоумышленник может прислать запрос на сотни мегабайт, сервер попытается целиком разобрать его в память и упадёт или станет тормозить для всех. 100 КБ хватает почти для любых JSON-данных форм.

### Пример
```js
app.use(express.json({ limit: "100kb" }));

app.post("/api/leads", (req, res) => {
  const { name } = req.body ?? {};
  if (typeof name !== "string" || name.trim().length < 2) {
    return res.status(400).json({ error: "Укажите имя" });
  }
  res.status(201).json({ ok: true, name: name.trim() });
});

app.use((err, req, res, next) => {
  if (err.type === "entity.parse.failed") return res.status(400).json({ error: "Некорректный JSON" });
  next(err);
});
```

### Частые ошибки
- **`express.json()` подключён после маршрутов.**
- **Деструктуризация `undefined` body** — используй `req.body ?? {}`.
- **HTML-ошибка клиенту на кривой JSON** вместо JSON-ответа.

### Проверь себя
?? Что делает `express.json()`? || Читает тело запросов с `Content-Type: application/json`, разбирает JSON и кладёт результат в `req.body`.
?? Почему `req.body` может оказаться пустым, хотя клиент отправил данные? || Не подключён `express.json()`, он подключён после маршрута, или запрос отправлен без заголовка `Content-Type: application/json`.
?? Объясни своими словами, почему телу запроса нельзя доверять. || Его формирует клиент, а клиент может быть кем угодно: прислать не те поля, не тех типов, огромного размера или специально подготовленные вредные данные.

### Ситуация
Файл `app.js` вырос до 600 строк: проекты, клиенты, задачи, авторизация, платежи — всё вперемешку. Чтобы найти маршрут удаления клиента, ты листаешь пять минут, а двое разработчиков постоянно правят один и тот же файл и получают конфликты. В Express проект делят на роутеры — по одному на сущность.

### На пальцах
Когда отделов становится много, ресепшен одного офиса не справляется. Router — отдельный ресепшен на каждом этаже: этаж «проекты», этаж «клиенты», этаж «авторизация». Главный вход только говорит: «по проектам — на третий этаж», а там уже разбираются сами.

### Как это работает
- `express.Router()` создаёт мини-приложение со своими маршрутами и middleware.
- Маршруты внутри роутера пишутся относительно точки подключения.
- `app.use("/api/projects", projectsRouter)` — подключить: все пути роутера получат префикс.
- У роутера могут быть свои middleware: `router.use(requireAuth)` защитит только его маршруты.
- Параметры из префикса доступны во вложенном роутере с опцией `Router({ mergeParams: true })`.

Так проект делится на файлы по сущностям: `routes/projects.js`, `routes/clients.js`, `routes/auth.js`.

?: Зачем вложенному роутеру опция `mergeParams: true`? || По умолчанию роутер видит только свои параметры. Параметр `:projectId` объявлен в адресе подключения у родителя, и без `mergeParams` в `req.params` вложенного роутера его просто не будет.

### Пример
```js
// src/routes/projects.js
export const projectsRouter = Router();
projectsRouter.get("/api/projects/:id", (req, res) => { /* ... */ });

// src/app.js
app.use("/api/projects", projectsRouter);
```

?! По какому адресу на самом деле окажется маршрут из роутера? || `/api/projects/api/projects/:id`: префикс из `app.use` добавился к пути, который уже содержит префикс. Внутри роутера нужно писать относительно точки подключения: `projectsRouter.get("/:id", ...)`.

### Частые ошибки
- **Префикс повторён внутри роутера** — адрес удваивается.
- **Забыт `mergeParams`** — во вложенном роутере нет `req.params.projectId`.
- **Роутер подключён до `express.json()`** — `req.body` в нём пустой.

### Проверь себя
?? Как подключить роутер с префиксом `/api/clients`? || `app.use("/api/clients", clientsRouter)`.
?? Как защитить авторизацией все маршруты одного роутера сразу? || Подключить middleware внутри роутера: `router.use(requireAuth)`.
?? Объясни своими словами, зачем делить API на роутеры. || Чтобы каждый файл отвечал за одну сущность: код легче найти и читать, у разных частей могут быть свои правила доступа, а разработчики меньше мешают друг другу.

### Мини-задание
Разнеси свой API на роутеры `projects`, `clients` и вложенный `tasks`. Добавь в роутер клиентов middleware, которое логирует только его запросы. Проверь, что все адреса работают как раньше. Потренируйся в задаче «Express: маршруты и middleware» в лаборатории.
