### Ситуация
Ты выкатил новую версию сайта, а заказчик звонит: «У меня всё старое!» Ты видишь новую, он — старую, и обновление страницы не помогает. В другой день тот же сайт летает при первом заходе, но на десятой странице подряд скачивает те же картинки снова и снова. Обе истории — про кеш: в первой он слишком агрессивный, во второй его нет вовсе.

### На пальцах
Кеш — запасы поближе к месту, где они нужны. Хлеб в хлебнице на кухне (кеш браузера), магазин у дома (CDN — сервер рядом с пользователем), склад при пекарне (кеш на сервере). Каждый раз идти на пекарню на другом конце города — медленно. Но у запасов есть срок годности, и за свежестью нужно следить.

### Как это работает
>> Браузер → CDN → кеш на сервере → база → чем ближе к пользователю, тем быстрее

| Где | Что кешируется | Чем управляется |
|---|---|---|
| **Браузер** | картинки, CSS, JS, иногда ответы API | заголовки `Cache-Control`, `ETag` |
| **CDN** (Cloudflare, Vercel, Netlify) | статические файлы и страницы на серверах по всему миру | заголовки и настройки CDN |
| **Сервер** | результаты тяжёлых запросов и вычислений | Redis, память процесса |
| **База** | сама кеширует часто читаемые данные в памяти | настройки базы |

Заголовок `Cache-Control`:

- `public, max-age=31536000, immutable` — файл с хешем в имени (`app-a1b2c3.js`) можно хранить год, он никогда не изменится;
- `no-cache` — можно хранить, но перед использованием спросить сервер, не изменилось ли (`ETag` → ответ `304 Not Modified` без тела);
- `no-store` — не хранить вообще (личные данные, банковские страницы);
- `private` — только в браузере пользователя, не в общих CDN.

Сборщики вроде Vite добавляют хеш в имена файлов: новая версия — новое имя, и кеш никогда не отдаст старый файл.

?: Почему `index.html` нельзя кешировать надолго, а JS-файлы с хешем — можно? || `index.html` всегда лежит по одному адресу и ссылается на актуальные имена JS-файлов. Если браузер держит старый `index.html`, он продолжает грузить старые скрипты. Файлы с хешем меняют имя при каждом изменении, поэтому старая копия никогда не подменит новую.

### Пример
```js
app.use("/assets", express.static("dist/assets", { maxAge: "1y", immutable: true }));
app.use(express.static("dist", { maxAge: "7d" }));

app.get("/api/me", requireUser, (req, res) => {
  res.set("Cache-Control", "public, max-age=300");
  res.json(req.user);
});
```

?! Найди две проблемы с кешем в этом коде. || `index.html` из `dist` кешируется на 7 дней — пользователи неделю будут видеть старую версию сайта; для него нужен `no-cache`. Личные данные `/api/me` помечены `public` — CDN может отдать профиль одного пользователя другому; нужно `no-store` или хотя бы `private`.

### Частые ошибки
- **Долгий кеш у `index.html`** — пользователи неделями видят старую версию сайта.
- **Кеш личных данных в общем CDN** — один пользователь видит страницу другого.
- **Файлы без хеша в имени с `max-age` на год.**

### Проверь себя
?? Чем `no-cache` отличается от `no-store`? || `no-cache` разрешает хранить копию, но перед использованием спрашивать сервер, не изменилась ли она. `no-store` запрещает хранить вообще.
?? Зачем сборщики добавляют хеш в имена файлов? || Чтобы при изменении файла менялось его имя. Тогда старые копии в кеше не подменят новую версию, и файлы можно кешировать надолго.
?? Объясни своими словами, что такое CDN. || Сеть серверов по всему миру, которые хранят копии файлов сайта и отдают их с ближайшего к пользователю сервера, поэтому сайт загружается быстрее.

### Ситуация
Главная страница маркетплейса показывает «популярные товары» — тяжёлый запрос к базе на 300 мс. Его выполняют для каждого из тысячи посетителей в минуту, хотя результат меняется раз в час. База стонет. Если запомнить ответ на пять минут в очень быстром хранилище, 999 из 1000 посетителей получат его за миллисекунду. Таким хранилищем почти всегда оказывается Redis.

### На пальцах
Redis — огромная доска с липкими записками в оперативной памяти. Каждая записка: имя (ключ) и содержимое (значение). Достать записку по имени — мгновенно, потому что всё в памяти, а не на диске. На записке можно написать «выбросить через 10 минут» (TTL) — и она сама исчезнет.

### Как это работает
>> `SET key value EX 60` → `GET key` → через 60 секунд ключ исчезнет сам

- Хранилище «ключ → значение» в памяти: ответ за доли миллисекунды.
- **TTL** (time to live) — срок жизни ключа в секундах. Истёк — ключ удаляется сам.
- Данные могут сохраняться на диск, но Redis обычно используют как быстрый слой, а главная копия данных живёт в PostgreSQL.

| Тип | Пример | Применение |
|---|---|---|
| String | `SET user:17:name "Анна"` | кеш JSON-ответов, счётчики (`INCR`) |
| Hash | `HSET user:17 name Анна city Москва` | объект с полями |
| List | `LPUSH queue:emails ...` | простые очереди, последние события |
| Set | `SADD online 17 42` | уникальные значения: кто онлайн |
| Sorted set | `ZADD leaderboard 1200 anna` | рейтинги, топы |

Ключи принято называть с двоеточиями по смыслу: `cache:projects:list`, `session:abc123`, `ratelimit:login:1.2.3.4`.

Подключение из Node.js — библиотека `redis` или `ioredis`.

?: Почему важные данные нельзя хранить только в Redis? || Redis держит всё в оперативной памяти и может потерять последние изменения при сбое или при нехватке памяти вытеснить ключи. Для кеша это не страшно — данные перечитаются из базы. Для единственной копии заказов или платежей — катастрофа.

### Пример
```bash
SET greeting "Привет" EX 60
INCR page:views
INCR page:views
SADD online:users 17 42 17
SCARD online:users
```

?! Что вернут обе команды `INCR` и последняя `SCARD`? Что будет с ключом `greeting` через две минуты? || `INCR` вернёт 1, затем 2 — счётчик создаётся с нуля автоматически. `SCARD` вернёт 2: множество хранит только уникальные значения, второй `17` не добавился. `greeting` через две минуты исчезнет — его TTL был 60 секунд.

### Частые ошибки
- **Единственная копия важных данных в Redis.**
- **Ключи без TTL** — память постепенно заканчивается.
- **Огромные значения в одном ключе** (мегабайты JSON).

### Проверь себя
?? Что такое TTL в Redis? || Срок жизни ключа в секундах: по истечении Redis сам удаляет ключ.
?? Почему Redis такой быстрый? || Он хранит данные в оперативной памяти и работает с простыми структурами по ключу, без сложных запросов и чтения с диска.
?? Объясни своими словами, для чего Redis используют в веб-проектах. || Как быстрый слой рядом с базой: кеш тяжёлых ответов, сессии, счётчики и ограничения запросов, очереди задач и рейтинги.

### Мини-задание
Подними Redis в Docker (`docker run -p 6379:6379 -d redis:7`) или возьми бесплатный в Upstash. Через `redis-cli` попробуй типы String, Hash и Set, поставь ключ с TTL и понаблюдай, как он исчезает.

### Ситуация
Ты закешировал каталог на час — сайт полетел. А потом менеджер снизил цену на распродажный товар, и весь час покупатели видят старую цену, пишут гневные отзывы и уходят. Положить в кеш — легко. Вовремя выбросить — одна из двух сложных вещей в программировании, если верить старой шутке.

### На пальцах
Cache-aside — «сначала загляни в холодильник». Нужно молоко: посмотрел в холодильнике (кеш) — есть, взял. Нет — сходил в магазин (база), купил, поставил в холодильник и взял. Инвалидация — выбросить молоко, когда знаешь, что оно испортилось (данные изменились), а не ждать, пока кто-то отравится.

### Как это работает
>> Запрос → есть в кеше? → да — вернуть → нет — база → положить в кеш → вернуть

Чтение по схеме cache-aside:

1. Ищем значение в кеше по ключу.
2. **Попадание** (hit) — отдаём сразу.
3. **Промах** (miss) — читаем из базы, кладём в кеш с TTL, отдаём.

Инвалидация — что делать, когда данные изменились:

- **удалить ключ** при изменении (самое простое и надёжное): следующий запрос перечитает из базы;
- **TTL** — подстраховка: даже если забыли удалить, данные устареют не навсегда;
- обновить ключ новым значением — сложнее, риск записать устаревшее при гонке запросов.

Что кешировать: дорогие и часто читаемые данные, которые меняются редко — каталог, справочники, публичные страницы, отчёты. Что не кешировать: то, что должно быть всегда точным (остатки при оформлении заказа, баланс).

?: Почему при изменении данных надёжнее удалить ключ, чем записать в него новое значение? || Два запроса на изменение могут прийти почти одновременно и записать значения в кеш не в том порядке, оставив устаревшие данные. После удаления следующий читающий запрос сам возьмёт актуальное из базы — гонке негде случиться.

### Пример
```js
async function cached(key, ttl, load) {
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);
  const value = await load();
  await redis.set(key, JSON.stringify(value), { EX: ttl });
  return value;
}

app.get("/api/me/orders", requireUser, async (req, res) => {
  const orders = await cached("cache:orders", 300, () =>
    q("SELECT * FROM orders WHERE user_id = $1", [req.user.id]).then(r => r.rows)
  );
  res.json(orders);
});
```

?! Анна открыла свои заказы, а через минуту то же сделал Борис. Что увидит Борис? || Заказы Анны. Ключ `cache:orders` общий для всех пользователей, и Борис получил закешированный ответ Анны. В ключ нужно включить id пользователя: `cache:orders:${req.user.id}`.

### Частые ошибки
- **Данные изменили, а кеш не сбросили** — пользователи видят старую цену до истечения TTL.
- **Персональные данные под общим ключом** — один пользователь видит данные другого.
- **Кешировать всё подряд без замеров** — сложность растёт, а ускорения нет.

### Проверь себя
?? Опиши три шага схемы cache-aside. || Поискать значение в кеше; если есть — отдать; если нет — прочитать из базы, положить в кеш с TTL и отдать.
?? Зачем ставить TTL, если ключ и так удаляется при изменении данных? || Как подстраховку: если где-то забыли сбросить кеш, данные устареют не навсегда, а только на время TTL.
?? Объясни своими словами, что такое инвалидация кеша. || Удаление или обновление закешированных данных, когда оригинал изменился, чтобы пользователи не получали устаревшую информацию.

### Ситуация
Под нагрузкой ты запустил три экземпляра сервера. Пользователь вошёл — первый сервер запомнил сессию у себя в памяти. Следующий запрос попал на второй сервер, который про сессию ничего не знает, — пользователя выкинуло на страницу входа. Ограничение попыток входа тоже сломалось: на каждом сервере свой счётчик. Нужно общее место для такой памяти.

### На пальцах
Когда сервер работает в одном экземпляре, он может держать сессии и счётчики в своей памяти — как продавец, который помнит постоянных покупателей в лицо. Но если открыть три кассы (три экземпляра сервера), каждая будет помнить своё. Redis — общая тетрадь для всех касс: кто вошёл, сколько раз ошибся паролем.

### Как это работает
>> Сессия или счётчик → `INCR` в Redis → общий для всех экземпляров сервера

**Сессии в Redis**:

- при входе генерируется случайный id сессии, в Redis кладётся `session:<id> → { userId, role }` с TTL (например, 30 дней);
- id отправляется в httpOnly-cookie;
- на каждый запрос — `GET session:<id>`: быстро, а выход или блокировка — просто `DEL`;
- в отличие от JWT, сессию можно отозвать мгновенно.

**Rate limit в Redis**:

- ключ `ratelimit:<что>:<кто>` с TTL, равным окну;
- `INCR` при каждой попытке, при первом — `EXPIRE` на длину окна;
- значение больше лимита — ответ 429;
- работает одинаково для всех экземпляров сервера.

Готовые решения: `connect-redis` для `express-session`, `rate-limit-redis` для `express-rate-limit`.

?: Почему id сессии нельзя делать из `Date.now()` или порядкового номера? || Такие значения легко угадать: зная своё, можно перебрать соседние и подставить чужую сессию в cookie — войти в чужой аккаунт без пароля. Криптографически случайные 32 байта перебрать невозможно.

### Пример
```js
export async function tooManyAttempts(ip, email) {
  const key = `ratelimit:login:${ip}:${email}`;
  const n = await redis.incr(key);
  return n > 10;
}
```

?! Пользователь ошибся паролем 11 раз в понедельник. Сможет ли он войти во вторник? || Нет — и никогда больше: у ключа нет срока жизни, счётчик не сбрасывается. При первой попытке нужно поставить `EXPIRE` на длину окна: `if (n === 1) await redis.expire(key, 15 * 60)`.

### Частые ошибки
- **Сессии в памяти процесса** при нескольких экземплярах — пользователя «выкидывает».
- **Нет TTL у ключей лимита** — счётчик никогда не сбрасывается.
- **Предсказуемые id сессий** — используй криптографически случайные байты.

### Проверь себя
?? Почему при нескольких экземплярах сервера сессии нельзя хранить в памяти процесса? || Каждый экземпляр видит только свою память. Запрос, попавший на другой экземпляр, не найдёт сессию, и пользователя разлогинит.
?? Как мгновенно разлогинить пользователя, если сессии лежат в Redis? || Удалить ключ его сессии командой `DEL`.
?? Объясни своими словами, как работает ограничение попыток на `INCR` и `EXPIRE`. || Каждая попытка увеличивает счётчик под ключом пользователя, а при первой ставится срок жизни ключа на длину окна. Если счётчик больше лимита — отказ; когда окно истекает, ключ удаляется и счёт начинается заново.

### Ситуация
Клиент нажимает «Оформить заказ» и смотрит на крутилку десять секунд: сервер в это время формирует PDF-счёт, отправляет письмо, СМС и уведомление в CRM. Почтовый сервис тормозит — и заказ «падает» с ошибкой, хотя он уже создан. Медленная и ненадёжная работа не должна держать пользователя у кассы. Для этого придуманы очереди.

### На пальцах
Когда клиент оформил заказ, официант не стоит у кассы, пока печатается чек, отправляется письмо и обновляется склад. Он кладёт записку «сделать» в лоток (очередь), а помощник на кухне (воркер) берёт записки по одной и выполняет. Клиент получает «Заказ принят» сразу, а не через 10 секунд.

### Как это работает
>> Медленная задача → в очередь → ответ пользователю сразу → воркер выполняет

- **Очередь** — список задач, ожидающих выполнения.
- **Продюсер** — код, который кладёт задачу: обработчик запроса «отправь письмо на такой-то адрес».
- **Воркер** — отдельный процесс, который забирает задачи и выполняет.
- Очередь обычно живёт в Redis (библиотека **BullMQ**) или специальных системах (RabbitMQ, SQS).

Что умеют очереди:

- **повторные попытки** с растущей паузой: почтовый сервис недоступен — повторить через 1, 5, 30 минут;
- **отложенные задачи**: напомнить об оплате через 3 дня;
- **ограничение скорости**: не больше 10 писем в секунду;
- **параллельность**: несколько воркеров разбирают очередь быстрее;
- **надёжность**: если воркер упал, задача не пропадает.

Задача должна быть идемпотентной: если её по ошибке выполнят дважды, ничего страшного не случится.

?: Почему задачи в очереди должны быть идемпотентными? || Очередь гарантирует «хотя бы один раз», а не «ровно один раз»: воркер мог выполнить задачу и упасть до того, как отметил её выполненной, — тогда она повторится. Если повтор ничего не ломает, сбой безопасен.

### Пример
```js
await emailQueue.add("order-created", { orderId: order.id, to: req.user.email }, {
  attempts: 5,
  backoff: { type: "exponential", delay: 60_000 },
  jobId: `order-created:${order.id}`,
});
res.status(201).json(order);
```

?! Почтовый сервис недоступен 10 минут. Что увидит клиент и когда придёт письмо? || Клиент сразу увидит «Заказ создан» — ответ не ждёт отправки письма. Воркер получит ошибку и повторит попытку через ~1, затем ~2, ~4, ~8 минут — когда сервис оживёт, письмо уйдёт. `jobId` не даст поставить одну и ту же задачу дважды.

### Частые ошибки
- **Долгие операции прямо в обработчике запроса** — пользователь ждёт, а при обрыве соединения работа теряется.
- **Задачи без повторных попыток** — временный сбой превращается в потерянные письма.
- **Неидемпотентные задачи** — повтор отправляет клиенту три одинаковых письма.

### Ситуация
Ты хочешь Redis для учебного проекта, но ставить свой сервер, следить за памятью и обновлениями — отдельная работа. А на Vercel-функциях обычный клиент Redis вообще ведёт себя плохо: каждое выполнение открывает новое соединение. Облачный Redis с бесплатным тарифом и HTTP-доступом решает обе проблемы.

### На пальцах
Upstash — Redis «в аренду» в облаке: не нужно ставить сервер, следить за памятью и обновлениями. Регистрируешься, получаешь адрес — и пользуешься. Бесплатного тарифа хватает для учебных проектов, кеша и лимитов небольшого сайта.

### Как это работает
>> Upstash → бесплатная база Redis → `REDIS_URL` → подключение из кода

1. Регистрация на upstash.com, «Create Database» → Redis.
2. Регион — ближе к своему серверу (например, рядом с Render во Frankfurt).
3. В панели будут:
   - адрес для обычного подключения `rediss://default:пароль@хост:6379` (две «s» — с TLS);
   - REST URL и токен — для serverless-окружений, где нельзя держать постоянное соединение (Vercel Functions, Cloudflare Workers).
4. Строку подключения — в переменную окружения `REDIS_URL` на хостинге.

Два способа работы:

- обычный клиент `redis` / `ioredis` по `REDIS_URL` — для постоянно работающего сервера (Render, VPS);
- `@upstash/redis` через HTTP — для serverless и edge, там же готовые `@upstash/ratelimit` для ограничения запросов.

Ограничения бесплатного тарифа: лимит команд в день и объём данных — следи в панели. Для очередей BullMQ проверь лимиты команд: воркеры делают много запросов.

?: Почему в serverless-функциях Redis лучше использовать через HTTP, а не обычным клиентом? || Serverless-функции живут секунды и запускаются заново на каждый запрос. Обычный клиент на каждом запуске открывает новое TCP-соединение — медленно и быстро упирается в лимит соединений. HTTP-запрос не требует постоянного соединения.

### Пример
```bash
REDIS_URL=redis://default:xxxxxxxx@eu1-cool-fox-12345.upstash.io:6379
```

```js
import { createClient } from "redis";
export const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();
```

?! Сервер на Render зависает на `redis.connect()`, а затем падает с ошибкой подключения. В чём, скорее всего, причина? || В протоколе: `redis://` вместо `rediss://`. Upstash требует TLS, а без второй «s» клиент пытается подключиться без шифрования.

### Частые ошибки
- **`redis://` вместо `rediss://`** — облако требует TLS.
- **Обычный TCP-клиент в serverless-функциях** — каждое выполнение открывает новое соединение.
- **Токен Upstash в репозитории.**

### Проверь себя
?? Что означает протокол `rediss://` с двумя «s»? || Подключение к Redis с шифрованием TLS.
?? Какой клиент Upstash выбрать для Vercel Functions? || `@upstash/redis`, который работает через HTTP.
?? Объясни своими словами, когда удобен облачный Redis вроде Upstash. || Для учебных и небольших проектов и serverless-приложений: не нужно поднимать и обслуживать свой сервер, есть бесплатный тариф и доступ через HTTP.
