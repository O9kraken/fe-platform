### На пальцах
Кеш — запасы поближе к месту, где они нужны. Хлеб в хлебнице на кухне (кеш браузера), магазин у дома (CDN — сервер рядом с пользователем), склад при пекарне (кеш на сервере). Каждый раз идти на пекарню на другом конце города — медленно. Но у запасов есть срок годности, и за свежестью нужно следить.

### Как это работает
| Где | Что кешируется | Чем управляется |
|---|---|---|
| **Браузер** | картинки, CSS, JS, иногда ответы API | заголовки `Cache-Control`, `ETag` |
| **CDN** (Cloudflare, Vercel, Netlify) | статические файлы и страницы на серверах по всему миру | заголовки и настройки CDN |
| **Сервер** | результаты тяжёлых запросов и вычислений | Redis, память процесса |
| **База** | сама кеширует часто читаемые данные в памяти | настройки базы |

Заголовок `Cache-Control`:

- `public, max-age=31536000, immutable` — файл с хешем в имени (`app-a1b2c3.js`) можно хранить год, он никогда не изменится;
- `no-cache` — можно хранить, но перед использованием спросить сервер, не изменилось ли (`ETag` → ответ `304 Not Modified` без тела);
- `no-store` — не хранить вообще (личные данные, банковские страницы);
- `private` — только в браузере пользователя, не в общих CDN.

Сборщики вроде Vite специально добавляют хеш в имена файлов: новая версия — новое имя, и кеш никогда не отдаст старый файл.

### Пример
```js
import express from "express";
const app = express();

// статика с хешами в именах — кешировать надолго
app.use("/assets", express.static("dist/assets", { maxAge: "1y", immutable: true }));

// index.html — всегда проверять свежесть
app.get("/", (req, res) => {
  res.set("Cache-Control", "no-cache");
  res.sendFile(new URL("./dist/index.html", import.meta.url).pathname);
});

// публичный список услуг — CDN и браузер могут держать 5 минут
app.get("/api/services", (req, res) => {
  res.set("Cache-Control", "public, max-age=300");
  res.json(services);
});

// личные данные — не кешировать нигде
app.get("/api/me", requireUser, (req, res) => {
  res.set("Cache-Control", "no-store");
  res.json(req.user);
});
```

### Частые ошибки
- Долгий кеш у `index.html` — пользователи неделями видят старую версию сайта.
- Кеш личных данных в общем CDN — один пользователь видит страницу другого.
- Файлы без хеша в имени с `max-age` на год.

Открой Network на своём сайте, обнови страницу дважды и посмотри колонку Size: что пришло «from memory cache» или «from disk cache». Проверь заголовки `Cache-Control` у HTML, JS и ответов API и настрой их по таблице.

### На пальцах
Redis — огромная доска с липкими записками в оперативной памяти. Каждая записка: имя (ключ) и содержимое (значение). Достать записку по имени — мгновенно, потому что всё в памяти, а не на диске. На записке можно написать «выбросить через 10 минут» (TTL) — и она сама исчезнет.

### Как это работает
- Хранилище «ключ → значение» в памяти: ответ за доли миллисекунды.
- **TTL** (time to live) — срок жизни ключа в секундах. Истёк — ключ удаляется сам.
- Данные могут сохраняться на диск, но Redis обычно используют как быстрый слой, а главная копия данных живёт в PostgreSQL.

Типы данных:

| Тип | Пример | Применение |
|---|---|---|
| String | `SET user:17:name "Анна"` | кеш JSON-ответов, счётчики (`INCR`) |
| Hash | `HSET user:17 name Анна city Москва` | объект с полями |
| List | `LPUSH queue:emails ...` | простые очереди, последние события |
| Set | `SADD online 17 42` | уникальные значения: кто онлайн |
| Sorted set | `ZADD leaderboard 1200 anna` | рейтинги, топы |

Ключи принято называть с двоеточиями по смыслу: `cache:projects:list`, `session:abc123`, `ratelimit:login:1.2.3.4`.

Подключение из Node.js — библиотека `redis` или `ioredis`.

### Пример
```bash
SET greeting "Привет" EX 60     # ключ на 60 секунд
GET greeting                    # "Привет"
TTL greeting                    # 57 — сколько осталось
INCR page:views                 # 1, 2, 3...
SADD online:users 17 42
SMEMBERS online:users           # 17, 42
```

```js
import { createClient } from "redis";

export const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

await redis.set("cache:services", JSON.stringify(services), { EX: 300 });   // на 5 минут
const cached = await redis.get("cache:services");
const list = cached ? JSON.parse(cached) : null;

const views = await redis.incr(`views:post:${postId}`);
```

### Частые ошибки
- Хранить в Redis единственную копию важных данных.
- Ключи без TTL — память постепенно заканчивается.
- Огромные значения в одном ключе (мегабайты JSON) — Redis быстрый, но не для этого.

### Мини-задание
Подними Redis в Docker (`docker run -p 6379:6379 -d redis:7`) или возьми бесплатный в Upstash. Через `redis-cli` попробуй типы String, Hash и Set, поставь ключ с TTL и понаблюдай, как он исчезает.

### На пальцах
Cache-aside — «сначала загляни в холодильник». Нужно молоко: посмотрел в холодильнике (кеш) — есть, взял. Нет — сходил в магазин (база), купил, поставил в холодильник и взял. Инвалидация — выбросить молоко, когда знаешь, что оно испортилось (данные изменились), а не ждать, пока кто-то отравится.

### Как это работает
Чтение по схеме cache-aside:

1. Ищем значение в кеше по ключу.
2. **Попадание** (hit) — отдаём сразу.
3. **Промах** (miss) — читаем из базы, кладём в кеш с TTL, отдаём.

Инвалидация — что делать, когда данные изменились:

- **удалить ключ** при изменении (самое простое и надёжное): следующий запрос перечитает из базы;
- **TTL** — подстраховка: даже если забыли удалить, данные устареют не навсегда;
- обновить ключ новым значением — сложнее, риск записать устаревшее при гонке запросов.

Знаменитая шутка: «В программировании две сложные вещи — инвалидация кеша и придумывание имён».

Что кешировать: дорогие и часто читаемые данные, которые меняются редко — каталог, справочники, публичные страницы, результаты отчётов. Что не кешировать: то, что должно быть всегда точным (остатки при оформлении заказа, баланс).

### Пример
```js
const TTL = 300;   // 5 минут

async function cached(key, ttl, load) {
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);                       // попадание
  const value = await load();                             // промах — в базу
  await redis.set(key, JSON.stringify(value), { EX: ttl });
  return value;
}

app.get("/api/catalog", async (req, res) => {
  const items = await cached("cache:catalog", TTL, () =>
    q("SELECT id, title, price FROM products WHERE active ORDER BY title").then(r => r.rows)
  );
  res.json(items);
});

app.patch("/api/products/:id", requireAdmin, async (req, res) => {
  const { rows } = await q("UPDATE products SET price = $1 WHERE id = $2 RETURNING *", [req.body.price, req.params.id]);
  await redis.del("cache:catalog");                       // инвалидация
  res.json(rows[0]);
});
```

### Частые ошибки
- Изменили данные, а кеш не сбросили — пользователи видят старую цену до истечения TTL.
- Кешировать персональные данные под общим ключом — один пользователь видит данные другого. Включай id пользователя в ключ.
- Кешировать всё подряд без замеров — сложность растёт, а ускорения нет.

### Мини-задание
Добавь cache-aside для списка услуг или каталога в своём API и сброс кеша при изменении. Залогируй попадания и промахи и посмотри, как они чередуются. Потренируйся в задаче «LRU-кеш со сроком жизни» и посмотри схему «Кеш» в уроке.

### На пальцах
Когда сервер работает в одном экземпляре, он может держать сессии и счётчики в своей памяти — как продавец, который помнит постоянных покупателей в лицо. Но если открыть три кассы (три экземпляра сервера), каждая будет помнить своё. Redis — общая тетрадь для всех касс: кто вошёл, сколько раз ошибся паролем.

### Как это работает
**Сессии в Redis**:

- при входе генерируется случайный id сессии, в Redis кладётся `session:<id> → { userId, role }` с TTL (например, 30 дней);
- id отправляется в httpOnly-cookie;
- на каждый запрос — `GET session:<id>`: быстро, а выход или блокировка — просто `DEL`;
- в отличие от JWT, сессию можно отозвать мгновенно.

**Rate limit в Redis**:

- ключ `ratelimit:<что>:<кто>` с TTL, равным окну;
- `INCR` при каждой попытке, при первом — `EXPIRE` на длину окна;
- значение больше лимита — ответ 429;
- работает одинаково для всех экземпляров сервера.

Готовые решения: `connect-redis` для `express-session`, `rate-limit-redis` для `express-rate-limit`.

### Пример
```js
import { randomBytes } from "node:crypto";

// сессии
export async function createSession(res, user) {
  const id = randomBytes(32).toString("hex");
  await redis.set(`session:${id}`, JSON.stringify({ uid: user.id, role: user.role }), { EX: 30 * 24 * 3600 });
  res.cookie("sid", id, { httpOnly: true, secure: true, sameSite: "lax", maxAge: 30 * 24 * 3600 * 1000 });
}

export async function requireUser(req, res, next) {
  const raw = req.cookies.sid && await redis.get(`session:${req.cookies.sid}`);
  if (!raw) return res.status(401).json({ error: "Войдите в аккаунт" });
  req.user = JSON.parse(raw);
  next();
}

export const destroySession = (sid) => redis.del(`session:${sid}`);

// rate limit: 10 неудачных входов за 15 минут
export async function tooManyAttempts(ip, email) {
  const key = `ratelimit:login:${ip}:${email}`;
  const n = await redis.incr(key);
  if (n === 1) await redis.expire(key, 15 * 60);
  return n > 10;
}
```

### Частые ошибки
- Хранить сессии в памяти процесса при нескольких экземплярах — пользователя «выкидывает» при попадании на другой сервер.
- Забыть TTL у ключей лимита — счётчик никогда не сбрасывается.
- Предсказуемые id сессий (`Date.now()`, порядковый номер) — используй криптографически случайные байты.

### Мини-задание
Переведи сессии своего API на Redis и сделай маршрут «выйти со всех устройств», который удаляет все сессии пользователя (подсказка: храни множество `user:<id>:sessions`). Добавь ограничение входов на Redis.

### На пальцах
Когда клиент оформил заказ, официант не стоит у кассы, пока печатается чек, отправляется письмо и обновляется склад. Он кладёт записку «сделать» в лоток (очередь), а помощник на кухне (воркер) берёт записки по одной и выполняет. Клиент получает «Заказ принят» сразу, а не через 10 секунд.

### Как это работает
- **Очередь** — список задач, ожидающих выполнения.
- **Продюсер** — код, который кладёт задачу: обработчик запроса «отправь письмо на такой-то адрес».
- **Воркер** — отдельный процесс, который забирает задачи и выполняет.
- Очередь обычно живёт в Redis (библиотека **BullMQ**) или специальных системах (RabbitMQ, SQS).

Что умеют очереди:

- **повторные попытки** с растущей паузой: почтовый сервис недоступен — повторить через 1, 5, 30 минут;
- **отложенные задачи**: напомнить об оплате через 3 дня;
- **ограничение скорости**: не больше 10 писем в секунду, чтобы не попасть в спам;
- **параллельность**: несколько воркеров разбирают очередь быстрее;
- **надёжность**: если воркер упал, задача не пропадает.

Что отправлять в очередь: письма и СМС, генерацию PDF и отчётов, обработку картинок и видео, вебхуки во внешние системы, массовые рассылки.

Задача должна быть идемпотентной: если её по ошибке выполнят дважды, ничего страшного не случится (письмо с одним и тем же id не отправится второй раз).

### Пример
```js
// queue.js
import { Queue, Worker } from "bullmq";
const connection = { url: process.env.REDIS_URL };

export const emailQueue = new Queue("emails", { connection });

// в обработчике запроса — быстро положить задачу и ответить
app.post("/api/orders", wrap(async (req, res) => {
  const order = await createOrder(req.body, req.user);
  await emailQueue.add("order-created", { orderId: order.id, to: req.user.email }, {
    attempts: 5,
    backoff: { type: "exponential", delay: 60_000 },
    jobId: `order-created:${order.id}`,     // защита от дублей
  });
  res.status(201).json(order);
}));
```

```js
// worker.js — отдельный процесс: node worker.js
import { Worker } from "bullmq";
new Worker("emails", async (job) => {
  if (job.name === "order-created") {
    await sendEmail(job.data.to, "Заказ принят", `Номер заказа: ${job.data.orderId}`);
  }
}, { connection: { url: process.env.REDIS_URL }, concurrency: 5 });
```

### Частые ошибки
- Долгие операции прямо в обработчике запроса — пользователь ждёт, а при обрыве соединения работа теряется.
- Задачи без повторных попыток — временный сбой внешнего сервиса превращается в потерянные письма.
- Неидемпотентные задачи — повтор отправляет клиенту три одинаковых письма.

### На пальцах
Upstash — Redis «в аренду» в облаке: не нужно ставить сервер, следить за памятью и обновлениями. Регистрируешься, получаешь адрес — и пользуешься. Бесплатного тарифа хватает для учебных проектов, кеша и лимитов небольшого сайта.

### Как это работает
1. Регистрация на upstash.com, «Create Database» → Redis.
2. Регион — ближе к своему серверу (например, рядом с Render во Frankfurt).
3. В панели будут:
   - адрес для обычного подключения `rediss://default:пароль@хост:6379` (две «s» — с TLS);
   - REST URL и токен — для serverless-окружений, где нельзя держать постоянное соединение (Vercel Functions, Cloudflare Workers).
4. Строку подключения — в переменную окружения `REDIS_URL` на хостинге.

Два способа работы:

- обычный клиент `redis` / `ioredis` по `REDIS_URL` — для постоянно работающего сервера (Render, VPS);
- `@upstash/redis` через HTTP — для serverless и edge, там же готовые `@upstash/ratelimit` для ограничения запросов.

Ограничения бесплатного тарифа: лимит команд в день и объём данных — следи в панели. Для очередей BullMQ проверь совместимость и лимиты команд: воркеры делают много запросов.

### Пример
```bash
# .env
REDIS_URL=rediss://default:xxxxxxxx@eu1-cool-fox-12345.upstash.io:6379
```

```js
// обычный сервер
import { createClient } from "redis";
export const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();
```

```ts
// Next.js / Vercel: ограничение запросов через HTTP-клиент
import { Redis } from "@upstash/redis";
import { Ratelimit } from "@upstash/ratelimit";

const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),                        // UPSTASH_REDIS_REST_URL и _TOKEN
  limiter: Ratelimit.slidingWindow(10, "1 m"),
});

export async function POST(req: Request) {
  const ip = req.headers.get("x-forwarded-for") ?? "anon";
  const { success } = await ratelimit.limit(`contact:${ip}`);
  if (!success) return Response.json({ error: "Слишком часто, попробуйте позже" }, { status: 429 });
  // ...отправить заявку
  return Response.json({ ok: true });
}
```

### Частые ошибки
- `redis://` вместо `rediss://` — облако требует TLS, подключение не устанавливается.
- Обычный TCP-клиент в serverless-функциях — каждое выполнение открывает новое соединение.
- Закоммитить токен Upstash в репозиторий.
