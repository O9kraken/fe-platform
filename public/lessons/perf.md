### На пальцах
Три главных ощущения посетителя: «как быстро я увидел главное», «как быстро сайт откликнулся на нажатие» и «не прыгает ли всё под пальцами». Core Web Vitals — три градусника, которые Google ставит сайту именно по этим ощущениям. И учитывает их в поиске.

### Как это работает
| Метрика | Что измеряет | Хорошо |
|---|---|---|
| **LCP** — Largest Contentful Paint | когда появился самый большой видимый элемент (обычно главная картинка или заголовок) | до 2,5 с |
| **INP** — Interaction to Next Paint | сколько проходит от клика или нажатия до видимой реакции | до 200 мс |
| **CLS** — Cumulative Layout Shift | насколько элементы сдвигаются во время загрузки | до 0,1 |

Что ухудшает каждую метрику и как лечить:

- **LCP**: тяжёлая главная картинка, медленный сервер, блокирующие CSS и шрифты. Лечение: сжать и уменьшить картинку, `fetchpriority="high"` для неё, не делать её ленивой.
- **INP**: долгий JavaScript в обработчиках, огромные перерисовки. Лечение: меньше работы в обработчике, разбить тяжёлые задачи, не перерисовывать весь список.
- **CLS**: картинки без размеров, баннеры и шрифты, которые появляются позже и сдвигают текст. Лечение: `width`/`height` или `aspect-ratio`, резервировать место под баннеры, `font-display: swap` с похожим запасным шрифтом.

Где смотреть: Lighthouse (лабораторные данные), PageSpeed Insights (реальные данные пользователей, если сайт посещаемый), вкладка Performance в DevTools.

### Пример
```html
<!-- LCP: главная картинка грузится сразу и с приоритетом -->
<img src="hero-1200.webp" width="1200" height="600" alt="..." fetchpriority="high">

<!-- CLS: место под картинку зарезервировано заранее -->
<img src="card.webp" width="400" height="300" alt="..." loading="lazy">
```

```css
/* CLS: место под рекламный баннер, который появится позже */
.ad-slot { min-height: 250px; }
```

### Частые ошибки
- Ленивая загрузка главной картинки первого экрана — LCP ухудшается.
- Картинки и iframe без размеров — CLS.
- Тяжёлые вычисления прямо в обработчике клика — INP.

### Мини-задание
Открой PageSpeed Insights (pagespeed.web.dev) и проверь свой опубликованный проект и один крупный сайт. Для своего сайта найди, какой элемент считается LCP, и ускорь его появление.

### На пальцах
Lighthouse — общий техосмотр с оценками. Вкладка Performance — запись с видеорегистратора: можно перемотать загрузку страницы кадр за кадром и увидеть, в какую секунду что происходило и кто «тормозил» — скрипт, отрисовка или сеть.

### Как это работает
Lighthouse: DevTools → Lighthouse → Mobile → Analyze. Даёт оценку и рекомендации. Для производительности главное — раздел «Diagnostics» и «Opportunities».

Performance:

1. DevTools → Performance.
2. Кнопка обновления с кругом — записать загрузку страницы. Кнопка записи — записать действия (клики, прокрутку).
3. Для честной картины включи замедление: CPU 4× slowdown и сеть Fast 4G — так страница ведёт себя на среднем телефоне.

Что смотреть в записи:

- **Кадры сверху** — скриншоты: видно, когда что появилось.
- **Main** — что делал главный поток. Жёлтое — JavaScript, фиолетовое — расчёт раскладки и стилей, зелёное — отрисовка.
- **Длинные задачи** помечены красным треугольником — всё, что дольше 50 мс, блокирует отклик на клики.
- Клик по задаче покажет, какая функция и в каком файле её вызвала.

В свежих версиях Chrome вкладка Performance сразу показывает LCP, CLS и INP в реальном времени.

### Пример
Типичная находка в Performance и исправление:

```js
// Было: при каждом вводе фильтруем 10 000 товаров и перерисовываем всё — длинная задача 300 мс
input.addEventListener("input", e => renderAll(filter(products, e.target.value)));

// Стало: ждём паузу в наборе 250 мс (debounce) и рисуем только первые 50 результатов
let timer;
input.addEventListener("input", e => {
  clearTimeout(timer);
  timer = setTimeout(() => render(filter(products, e.target.value).slice(0, 50)), 250);
});
```

### Частые ошибки
- Профилировать на мощном компьютере без замедления — «у меня всё летает».
- Смотреть только на общую оценку Lighthouse и не открывать рекомендации.
- Профилировать режим разработки — он медленнее сборки.

### Мини-задание
Запиши в Performance загрузку своего проекта с замедлением CPU 4×. Найди самую длинную задачу в Main и функцию, которая её вызвала. Попробуй её ускорить и запиши снова.

### На пальцах
Не нужно привозить на дачу весь гардероб, если ты едешь на выходные. Ленивая загрузка — привозить вещи, когда они понадобились. Разбиение кода — упаковать багаж по чемоданам: сначала самое нужное, остальное по мере надобности. Правильные размеры картинок — не брать зимнюю куртку, если на улице лето.

### Как это работает
Картинки — обычно самое тяжёлое на странице:

- формат WebP или AVIF вместо JPG и PNG — в 2–3 раза легче;
- размер под реальное место на экране, плюс `srcset` для разных экранов;
- `loading="lazy"` для всего, что ниже первого экрана;
- иконки — SVG.

Разбиение кода (code splitting):

- в React — `lazy(() => import("./pages/Admin"))` и `<Suspense>`: код страницы скачивается, только когда на неё перешли;
- тяжёлые библиотеки (графики, редакторы, карты) подключай динамическим `import()` там, где они нужны;
- проверяй размер бандла после `npm run build`.

Шрифты:

- только нужные начертания и наборы символов (latin + cyrillic);
- `font-display: swap`;
- `<link rel="preconnect">` к серверу шрифтов или хранение шрифтов у себя;
- `woff2` — самый лёгкий формат.

### Пример
```tsx
import { lazy, Suspense } from "react";

const AdminPage = lazy(() => import("./pages/AdminPage"));   // отдельный файл
const Chart = lazy(() => import("./components/Chart"));       // тяжёлая библиотека графиков

export function App() {
  return (
    <Suspense fallback={<p>Загрузка…</p>}>
      <AdminPage />
    </Suspense>
  );
}
```

```html
<img
  src="product-600.webp"
  srcset="product-300.webp 300w, product-600.webp 600w, product-1200.webp 1200w"
  sizes="(min-width: 1024px) 300px, 50vw"
  width="600" height="600"
  loading="lazy"
  alt="Кроссовки Run, вид сбоку">
```

### Частые ошибки
- Фото с телефона 4000×3000 на 6 МБ в карточке товара.
- Подключить всю библиотеку ради одной функции: `import _ from "lodash"` вместо `import debounce from "lodash/debounce"`.
- Ленивая загрузка всего подряд, включая первый экран.

### Мини-задание
Посмотри вес страниц своего проекта в Network (колонка Size, внизу — суммарно). Переведи картинки в WebP (например, через squoosh.app), сделай страницу админки или тяжёлый компонент ленивыми и сравни суммарный вес до и после.

### На пальцах
Доступность — то, насколько сайтом удобно пользоваться всем: человеку с плохим зрением, с больной рукой, с телефоном на ярком солнце. Контраст — можно ли прочитать серый текст на сером фоне. Фокус — видно ли, где ты находишься, когда ходишь клавиатурой. Порядок Tab — не прыгает ли фокус по странице хаотично.

### Как это работает
**Контраст** — отношение яркости текста и фона:

- обычный текст — не меньше 4.5:1;
- крупный текст (от 24px или от 19px жирный) и иконки — не меньше 3:1.

Проверить: DevTools → кликни по образцу цвета в Styles — Chrome покажет контраст и галочки AA/AAA. Или сервис webaim.org/resources/contrastchecker.

**Фокус**:

- у каждого интерактивного элемента должен быть видимый стиль `:focus-visible`;
- после открытия модального окна фокус переносится внутрь, после закрытия — возвращается на кнопку, которая его открыла;
- внутри модального окна Tab не должен уходить на страницу под ним.

**Порядок Tab**:

- идёт по порядку элементов в HTML, поэтому визуальный порядок должен совпадать с порядком в разметке;
- `order` во flex и `grid-area` меняют порядок только визуально — Tab пойдёт по-старому;
- `tabindex` больше 0 ломает естественный порядок — не используй.

Полезный приём — ссылка «Перейти к содержимому» первой на странице: человек с клавиатуры может пропустить меню.

### Пример
```html
<a class="skip-link" href="#main">Перейти к содержимому</a>
<header>...меню из 10 ссылок...</header>
<main id="main" tabindex="-1">...</main>
```

```css
.skip-link {
  position: absolute;
  left: -9999px;
}
.skip-link:focus {
  left: 16px;
  top: 16px;
  background: #fff;
  padding: 8px 12px;
}

:focus-visible {
  outline: 3px solid #1f4fd8;
  outline-offset: 2px;
}

/* контраст: серый #999 на белом — 2.8:1, не проходит; #666 — 5.7:1 */
.muted { color: #666; }
```

### Частые ошибки
- Светло-серый текст подсказок, который невозможно прочитать.
- Модальное окно, из которого фокус «утекает» на страницу.
- Перестановка блоков через CSS, из-за которой Tab прыгает снизу вверх.

### Мини-задание
Проверь контраст всех цветов текста своего сайта и исправь те, что ниже 4.5:1. Добавь ссылку «Перейти к содержимому» и проверь, что модальное окно (если есть) удерживает фокус и возвращает его после закрытия.

### На пальцах
ARIA — подписи для скринридера, которые можно наклеить на что угодно. Но первое правило ARIA: не клей подписи, если можно взять правильную вещь. Не нужно рисовать на коробке «это кнопка», если можно поставить настоящую кнопку. У неё уже есть и подпись, и фокус, и нажатие с клавиатуры.

### Как это работает
Нативные элементы уже всё умеют:

| Задача | Нативно | Вместо |
|---|---|---|
| кнопка | `<button>` | `<div role="button" tabindex="0" onkeydown=...>` |
| ссылка | `<a href>` | `<span onclick>` |
| флажок | `<input type="checkbox">` | `<div role="checkbox" aria-checked>` |
| раскрывашка | `<details><summary>` | самописный аккордеон |
| модальное окно | `<dialog>` | `div` с кучей атрибутов |

Когда ARIA действительно нужна:

- **`aria-label`** — у кнопки-иконки нет текста: `<button aria-label="Закрыть">✕</button>`.
- **`aria-expanded`** — состояние раскрытия у кнопки меню или аккордеона.
- **`aria-current="page"`** — активный пункт меню.
- **`aria-live="polite"`** или `role="status"` — область, изменения которой нужно зачитать (сообщение «Добавлено в корзину»).
- **`aria-describedby`** — связать поле с подсказкой или ошибкой.
- **`aria-hidden="true"`** — скрыть декоративное от скринридера (иконка рядом с текстом).

Неправильная ARIA хуже, чем никакой: `role="button"` на `div` обещает поведение кнопки, но клавиатура работать не будет.

### Пример
```html
<button class="burger" aria-label="Открыть меню" aria-expanded="false" aria-controls="menu">☰</button>
<nav id="menu" hidden>
  <a href="/" aria-current="page">Главная</a>
  <a href="/services">Услуги</a>
</nav>

<label for="email">Email</label>
<input id="email" type="email" aria-describedby="email-err" aria-invalid="true">
<p id="email-err">Введите адрес в формате name@mail.ru</p>

<p role="status" aria-live="polite">Товар добавлен в корзину</p>

<button><svg aria-hidden="true">...</svg> Скачать прайс</button>
```

### Частые ошибки
- `div` с `role="button"` вместо `button`.
- `aria-label` на элементе, у которого уже есть видимый текст, с другими словами — скринридер прочитает не то, что видят глаза.
- Забыть обновлять `aria-expanded` при открытии меню.

### Мини-задание
Найди в своём проекте все «кнопки» и «ссылки», сделанные не из `button` и `a`, и замени. Добавь `aria-label` иконкам-кнопкам и `aria-expanded` кнопке мобильного меню с обновлением из JavaScript.

### На пальцах
axe DevTools — металлоискатель для проблем доступности. Проводишь над страницей — он пищит и показывает: «здесь у картинки нет описания», «здесь кнопка без названия», «здесь текст не читается на фоне». Автоматически находит примерно треть проблем, остальное — ручная проверка.

### Как это работает
1. Установи расширение «axe DevTools» для Chrome или Firefox (бесплатной версии хватает).
2. DevTools → вкладка «axe DevTools» → «Scan all of my page».
3. Получишь список проблем по важности: Critical, Serious, Moderate, Minor.
4. Каждая проблема раскрывается: какой элемент, почему это плохо, как исправить, ссылка на подробности.
5. Кнопка «Highlight» подсвечивает элемент на странице.

Что axe находит хорошо: отсутствие `alt` и `label`, низкий контраст, кнопки и ссылки без названий, дубли `id`, неправильная ARIA, пропущенные уровни заголовков.

Что не найдёт: осмысленность `alt` («картинка» формально проходит), логичный порядок Tab, удобство работы со скринридером, понятность текстов. Поэтому после axe обязательно пройди сайт клавиатурой.

То же ядро axe встроено в Lighthouse (раздел Accessibility) и есть как библиотека для автотестов: `@axe-core/playwright`.

### Пример
```ts
// Проверка доступности в тестах Playwright
import { test, expect } from "@playwright/test";
import AxeBuilder from "@axe-core/playwright";

test("главная без серьёзных проблем доступности", async ({ page }) => {
  await page.goto("http://localhost:5173/");
  const results = await new AxeBuilder({ page }).analyze();
  const serious = results.violations.filter(v => ["critical", "serious"].includes(v.impact ?? ""));
  expect(serious).toEqual([]);
});
```

### Частые ошибки
- Считать, что раз axe ничего не нашёл, сайт полностью доступен.
- Исправлять ошибки «для галочки»: `alt="image"` убирает предупреждение, но не помогает людям.
- Проверять только главную страницу, а не формы, модальные окна и личный кабинет.

Установи axe DevTools и просканируй три страницы своего проекта, включая страницу с формой. Исправь все Critical и Serious, затем повтори сканирование до нуля серьёзных проблем.
