### Ситуация
Фронтенд отправляет заявку, а сервер отвечает «нет данных», хотя ты точно передал имя и телефон. Или сервер говорит «не авторизован», хотя пользователь вошёл. Чтобы найти, где именно потерялось, нужно уметь читать HTTP-сообщение целиком — как письмо, у которого есть конверт, отметки и содержимое. На бэкенде это базовый навык.

### На пальцах
HTTP-запрос — письмо на почте. На конверте: что сделать (метод), кому (адрес), отметки для почтальона — «срочно», «хрупкое», «я понимаю по-русски» (заголовки). Внутри — само письмо (тело), но не у всех писем оно есть. Ответ — письмо обратно: штамп с результатом (код), отметки и содержимое.

### Как это работает
Запрос:

```http
POST /api/projects?notify=true HTTP/1.1
Host: api.studio.ru
Content-Type: application/json
Authorization: Bearer eyJhbGci...
Accept: application/json

{"title": "Лендинг", "budget": 30000}
```

- **Метод** — `POST`.
- **URL** — путь `/api/projects` и query-параметры `?notify=true`.
- **Заголовки** — метаданные: тип тела, авторизация, что клиент готов принять, язык, cookie.
- **Тело** — данные. У GET тела нет.

Ответ:

```http
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: /api/projects/42

{"id": 42, "title": "Лендинг", "budget": 30000}
```

| Заголовок | Где | Зачем |
|---|---|---|
| `Content-Type` | запрос и ответ | формат тела |
| `Authorization` | запрос | токен доступа |
| `Cookie` / `Set-Cookie` | запрос / ответ | сессии |
| `Accept` | запрос | какой формат ответа нужен |
| `Location` | ответ | адрес созданного ресурса или редиректа |
| `Cache-Control` | ответ | можно ли кешировать |

?: Почему секретные данные нельзя передавать в query-параметрах, если запрос идёт по HTTPS? || HTTPS шифрует адрес в пути по сети, но URL с параметрами сохраняется в истории браузера, логах сервера и прокси, попадает в заголовок Referer при переходе на другие сайты. Секреты должны идти в заголовках или теле.

### Пример
```http

{"name": "Анна", "phone": "+79991234567"}
```

?! Сервер на Express с `express.json()` получил этот запрос. Что окажется в `req.body` и почему? || Пустой объект или `undefined`: в запросе нет заголовка `Content-Type: application/json`, и `express.json()` не стал разбирать тело.

### Частые ошибки
- **Секреты в query-параметрах** — попадают в логи и историю браузера.
- **Забыт `Content-Type`** у запроса с телом.
- **Путаница заголовков:** `Set-Cookie` присылает сервер, `Cookie` отправляет браузер.

### Проверь себя
?? Из каких частей состоит HTTP-запрос? || Метод, URL (путь и query-параметры), заголовки и необязательное тело.
?? Что сообщает заголовок `Location` в ответе 201? || Адрес только что созданного ресурса.
?? Объясни своими словами разницу между `Cookie` и `Set-Cookie`. || `Set-Cookie` сервер присылает в ответе, чтобы сохранить cookie в браузере. `Cookie` браузер отправляет в каждом следующем запросе к этому сайту.

### Ситуация
Пользователь нажимает «Оплатить», связь в метро обрывается, приложение автоматически повторяет запрос — и с карты списывают дважды. В другом проекте поисковый робот прошёл по ссылкам `GET /delete?id=…` в админке и удалил половину товаров. Обе катастрофы — от непонимания, какой метод для чего и что значит «идемпотентный».

### На пальцах
Методы — глаголы просьбы. GET — «покажи». POST — «добавь новое». PUT — «замени целиком». PATCH — «поправь кусочек». DELETE — «убери». Идемпотентность — «если повторить просьбу пять раз, результат такой же, как от одной». Попросить показать меню пять раз — безвредно. Попросить пять раз «добавь пиццу в заказ» — получишь пять пицц.

### Как это работает
| Метод | Смысл | Безопасный (не меняет данные) | Идемпотентный |
|---|---|---|---|
| GET | получить | да | да |
| POST | создать, выполнить действие | нет | нет |
| PUT | заменить целиком | нет | да |
| PATCH | изменить часть | нет | обычно нет |
| DELETE | удалить | нет | да |

Почему это важно:

- Браузеры, прокси и библиотеки могут повторить идемпотентный запрос при обрыве сети. Повторить POST «оплатить» без защиты — двойное списание.
- GET никогда не должен менять данные: поисковые роботы и предзагрузка ссылок ходят по GET.
- PUT ждёт полный объект: если не прислать поле, оно должно пропасть. PATCH меняет только присланные поля.

Защита от повторного POST — ключ идемпотентности: клиент генерирует уникальный id операции и шлёт его в заголовке `Idempotency-Key`, а сервер не выполняет одну операцию дважды.

?: Почему DELETE идемпотентный, хотя второй вызов вернёт 404? || Идемпотентность — про состояние данных, а не про ответ. После первого и после пятого DELETE ресурса нет — итог одинаковый. Код ответа может отличаться, но мир от повторов не меняется.

### Пример
```http
PUT /api/projects/42
{"title": "Лендинг 2.0"}
```

?! До запроса у проекта 42 были поля `title`, `budget` и `status`. Что с ними станет после этого PUT по правилам HTTP? || По смыслу PUT заменяет ресурс целиком, поэтому `budget` и `status`, которых нет в теле, должны пропасть. Чтобы поменять только название, нужен `PATCH` с тем же телом.

### Частые ошибки
- **Всё через POST** или всё через GET.
- **Удаление по ссылке `GET /delete?id=5`.**
- **PUT с одним полем**, который затирает остальные.

### Проверь себя
?? Какие методы идемпотентны? || GET, PUT и DELETE. POST не идемпотентен, PATCH обычно тоже.
?? Почему GET-запрос никогда не должен менять данные? || По GET-ссылкам ходят поисковые роботы, предзагрузка браузера и кеши. Если GET что-то меняет, данные изменятся без ведома пользователя.
?? Объясни своими словами, что такое идемпотентность. || Свойство операции: выполнить её один раз или несколько подряд — результат для данных одинаковый. Такие запросы безопасно повторять при сбоях сети.

### Ситуация
Фронтендер жалуется: «Ваш API при любой ошибке отвечает 200 с полем `error`, и мой TanStack Query думает, что всё успешно». Мониторинг показывает 100% успешных запросов, хотя половина регистраций падает. Правильный код ответа — не формальность, а язык, на котором API разговаривает с клиентами, браузерами и системами мониторинга.

### На пальцах
Код ответа — короткий вердикт сервера, который понимает любая программа без чтения текста. Первая цифра — категория: 2 — «получилось», 3 — «ищи в другом месте», 4 — «ты что-то сделал не так», 5 — «это мы сломались». Правильный код — половина хорошего API.

### Как это работает
| Код | Когда возвращать |
|---|---|
| 200 OK | успешный GET, PATCH, PUT с телом ответа |
| 201 Created | успешно создано (POST), в теле — новый объект |
| 204 No Content | успешно, тела нет (обычно DELETE) |
| 301 / 308 | ресурс переехал навсегда |
| 302 / 307 | временный редирект |
| 304 Not Modified | данные не изменились, бери из кеша |
| 400 Bad Request | неверные данные: не прошла валидация, кривой JSON |
| 401 Unauthorized | не вошёл или токен недействителен |
| 403 Forbidden | вошёл, но нет прав на это действие |
| 404 Not Found | ресурса нет (или чужой, который не стоит выдавать) |
| 409 Conflict | конфликт: email уже занят, версия устарела |
| 422 Unprocessable | формат верный, но нарушены правила |
| 429 Too Many Requests | превышен лимит запросов |
| 500 Internal Server Error | необработанная ошибка в коде сервера |
| 503 Service Unavailable | сервис временно недоступен |

Правила:

- Ошибку 4xx клиент может исправить сам. Ошибку 5xx — нет.
- Не возвращай 200 с `{ "error": "..." }`.
- В теле ошибки — понятное сообщение: `{ "error": "Email уже занят" }`.

?: Почему для чужого ресурса иногда возвращают 404, а не 403? || 403 подтверждает, что такой ресурс существует, — это уже утечка информации: можно перебором узнать, какие заказы или пользователи есть. 404 ничего не раскрывает: «для тебя такого нет».

### Пример
```js
app.post("/api/users", async (req, res) => {
  const { email } = req.body ?? {};
  if (!email) return res.status(400).json({ error: "Укажите email" });
  if (await db.userExists(email)) return res.status(409).json({ error: "Email уже занят" });
  const user = await db.createUser(email);
  res.status(201).json(user);
});
```

?! Какие коды получит клиент в трёх случаях: пустое тело, уже зарегистрированный email и новый email? А если база упала при создании? || 400 «Укажите email», 409 «Email уже занят», 201 с новым пользователем. Если база упала — исключение не перехвачено, и Express вернёт 500.

### Частые ошибки
- **Всегда 200 и ошибка в теле.**
- **500 на ошибку валидации** — клиент думает, что сломался сервер.
- **Путаница 401 и 403.**

### Проверь себя
?? Какой код вернуть при успешном создании ресурса? || 201 Created.
?? Чем 400 отличается от 500 с точки зрения того, кто должен исправлять? || 400 — ошибка клиента, он может исправить запрос. 500 — ошибка сервера, клиент ничего сделать не может.
?? Объясни своими словами, почему плохо отвечать 200 с полем `error`. || Клиенты, библиотеки и мониторинг смотрят на код и считают такой ответ успехом: ошибки не обрабатываются и не видны в статистике.

### На пальцах
REST — договорённость называть адреса в API как предметы, а не как действия. Не «/получитьВсеПроекты» и «/удалитьПроект», а просто «/projects» — и глагол (метод) говорит, что с этим предметом сделать. Как в библиотеке: полка «Проекты», на ней папки с номерами, внутри папки — вложенные «Задачи».

- Действие — метод HTTP, а не слово в адресе.

- Версию API часто добавляют в путь: `/api/v1/projects`.

### Ситуация
Фронтенд отправляет JSON, а сервер получает пустой `req.body`. Сервер отдаёт данные, а клиент получает строку вместо объекта. Цена товара `299.99 + 0.01` превращается в `300.00000000000006`. Все три бага — про то, как подписан и упакован формат данных. Сейчас разберёмся, как не наступать на них.

### На пальцах
`Content-Type` — подпись на посылке: «внутри документы», «внутри картинка», «внутри JSON». Без подписи получатель не знает, как распаковывать: читать как текст, сохранять как файл или разбирать как данные. JSON — самый частый формат «содержимого» в API.

### Как это работает
| Content-Type | Что внутри |
|---|---|
| `application/json` | JSON — основной формат API |
| `text/html; charset=utf-8` | HTML-страница |
| `application/x-www-form-urlencoded` | обычная HTML-форма |
| `multipart/form-data` | форма с файлами |
| `text/plain` | простой текст |
| `image/png`, `image/webp` | картинка |

- Клиент отправляет JSON → `Content-Type: application/json`, тело — `JSON.stringify(...)`. Сервер по заголовку понимает, что надо разобрать JSON.
- Сервер отвечает JSON → `res.json()` ставит заголовок сам. Клиент читает `response.json()`.
- `Accept: application/json` в запросе говорит: «я хочу JSON в ответ».

Хороший JSON API: ключи в одном стиле (camelCase или snake_case), даты в формате ISO `"2026-10-24T12:00:00Z"`, деньги — целым числом в копейках, пустое значение — `null`.

?: Почему деньги лучше хранить в копейках целым числом? || Дробные числа в компьютере хранятся приблизительно, и `0.1 + 0.2` даёт `0.30000000000000004`. В деньгах такие погрешности накапливаются и дают неверные суммы. Целые числа складываются точно.

### Пример
```js
const r = await fetch("/api/projects", {
  method: "POST",
  body: JSON.stringify({ title: "Лендинг", budget: 3000000 }),
});

app.use(express.json());
app.post("/api/projects", (req, res) => {
  console.log(req.body.title);
  res.status(201).json({ id: 42, ...req.body });
});
```

?! Что выведет сервер в `console.log` и что вернёт ответ? || Скорее всего ошибку «Cannot read properties of undefined» или `undefined`: без заголовка `Content-Type: application/json` браузер отправит тело как `text/plain`, и `express.json()` его не разберёт. Нужно добавить заголовок в `fetch`.

### Частые ошибки
- **JSON без заголовка** — `req.body` на сервере пустой.
- **JSON с `Content-Type: text/html`** — некоторые клиенты не разберут.
- **Деньги дробными числами** (`299.99`) — ошибки округления.

### Проверь себя
?? Какой `Content-Type` используют для формы с загрузкой файлов? || `multipart/form-data`.
?? В каком формате принято передавать даты в JSON? || В формате ISO 8601, например `"2026-10-24T12:00:00Z"`.
?? Объясни своими словами, зачем заголовок `Content-Type` в запросе. || Он сообщает серверу формат тела, чтобы тот правильно его разобрал: как JSON, как поля формы или как файл.

### Ситуация
Форма на сайте не работает. Где ошибка: во фронтенде, который неправильно отправляет данные, или в сервере, который неправильно отвечает? Пока проверяешь только через интерфейс, это гадание. Бэкендеры проверяют API напрямую: отправляют ровно тот запрос, который хотят, и видят ровно тот ответ, который вернул сервер.

### На пальцах
Проверять API только через свой фронтенд — как пробовать суп только через готовое блюдо, не пробуя бульон отдельно. curl, Bruno и Postman — ложки, которыми пробуют API напрямую: отправил любой запрос — увидел точный ответ, без браузера и кнопок.

### Как это работает
**curl** — в терминале, есть везде. Быстро проверить один запрос, вставить в документацию, в скрипты.

**Bruno / Postman** — программы с окнами:

- коллекции запросов, разложенные по папкам;
- переменные окружений: `{{baseUrl}}` = `http://localhost:3000` локально и боевой адрес на сервере;
- авторизация: токен сохраняется и подставляется во все запросы;
- тесты ответа: «статус 200, в ответе есть поле id».

Bruno хранит коллекции в обычных файлах прямо в репозитории — их коммитят вместе с кодом. Postman хранит в облаке, коллекцию можно экспортировать.

**Вкладка Network** в DevTools: правый клик по запросу → «Copy as cURL» — готовая команда, чтобы повторить запрос в терминале или импортировать в Bruno.

?: Чем «Copy as cURL» помогает искать ошибку? || Ты получаешь точную копию запроса фронтенда со всеми заголовками и телом. Повторив его в терминале и меняя по одному параметру, легко понять, что именно ломает ответ — без браузера и интерфейса.

### Пример
```bash
curl -i http://localhost:3000/api/health

curl -X POST http://localhost:3000/api/projects \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"title":"Лендинг","budget":30000}'
```

?! Что покажет флаг `-i` в первой команде и что будет со второй, если переменная `TOKEN` не задана? || `-i` выводит не только тело, но и статус и заголовки ответа. Во втором случае уйдёт заголовок `Authorization: Bearer ` с пустым токеном, и защищённый маршрут ответит 401.

### Частые ошибки
- **Проверка API только через интерфейс** — непонятно, где ошибка.
- **Токены и пароли в закоммиченной коллекции.** Секреты — в локальном файле окружения, который в `.gitignore`.
- **Запросы не сохраняются** — каждый раз пишутся заново.

### Проверь себя
?? Как в curl отправить POST-запрос с JSON-телом? || `curl -X POST адрес -H "Content-Type: application/json" -d '{"ключ":"значение"}'`.
?? Как быстро получить точную копию запроса, который сделал фронтенд? || В DevTools → Network кликнуть по запросу правой кнопкой и выбрать «Copy as cURL».
?? Объясни своими словами, зачем тестировать API отдельно от фронтенда. || Чтобы точно знать, правильно ли работает сервер, и быстро понимать, где ошибка — в клиенте или в API.

### Мини-задание
Установи Bruno (или Postman), создай коллекцию для своего API с переменной `baseUrl` и запросами на все CRUD-операции. Возьми один запрос из Network своего фронтенда через «Copy as cURL» и выполни его в терминале.
