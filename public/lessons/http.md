### На пальцах
HTTP-запрос — письмо на почте. На конверте: что сделать (метод), кому (адрес), отметки для почтальона — «срочно», «хрупкое», «я понимаю по-русски» (заголовки). Внутри — само письмо (тело), но не у всех писем оно есть. Ответ — письмо обратно: штамп с результатом (код), отметки и содержимое.

### Как это работает
Запрос:

```http
POST /api/projects?notify=true HTTP/1.1
Host: api.studio.ru
Content-Type: application/json
Authorization: Bearer eyJhbGci...
Accept: application/json

{"title": "Лендинг", "budget": 30000}
```

- **Метод** — `POST`.
- **URL** — путь `/api/projects` и query-параметры `?notify=true`.
- **Заголовки** — метаданные: тип тела, авторизация, что клиент готов принять, язык, cookie.
- **Тело** — данные. У GET тела нет.

Ответ:

```http
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: /api/projects/42

{"id": 42, "title": "Лендинг", "budget": 30000}
```

Важные заголовки:

| Заголовок | Где | Зачем |
|---|---|---|
| `Content-Type` | запрос и ответ | формат тела |
| `Authorization` | запрос | токен доступа |
| `Cookie` / `Set-Cookie` | запрос / ответ | сессии |
| `Accept` | запрос | какой формат ответа нужен |
| `Location` | ответ | адрес созданного ресурса или редиректа |
| `Cache-Control` | ответ | можно ли кешировать |

### Частые ошибки
- Передавать секретные данные в query-параметрах — они попадают в логи и историю браузера.
- Забыть `Content-Type` у запроса с телом.
- Путать заголовки запроса и ответа: `Set-Cookie` присылает сервер, `Cookie` отправляет браузер.

### На пальцах
Методы — глаголы просьбы. GET — «покажи». POST — «добавь новое». PUT — «замени целиком». PATCH — «поправь кусочек». DELETE — «убери». Идемпотентность — «если повторить просьбу пять раз, результат такой же, как от одной». Попросить показать меню пять раз — безвредно. Попросить пять раз «добавь пиццу в заказ» — получишь пять пицц.

### Как это работает
| Метод | Смысл | Безопасный (не меняет данные) | Идемпотентный |
|---|---|---|---|
| GET | получить | да | да |
| POST | создать, выполнить действие | нет | нет |
| PUT | заменить целиком | нет | да |
| PATCH | изменить часть | нет | обычно нет |
| DELETE | удалить | нет | да |

Почему это важно:

- Браузеры, прокси и библиотеки могут повторить идемпотентный запрос при обрыве сети. Повторить POST «оплатить» без защиты — двойное списание.
- GET никогда не должен менять данные: поисковые роботы и предзагрузка ссылок ходят по GET.
- PUT ждёт полный объект: если не прислать поле, оно должно пропасть. PATCH меняет только присланные поля.

Защита от повторного POST — ключ идемпотентности: клиент генерирует уникальный id операции и шлёт его в заголовке `Idempotency-Key`, а сервер не выполняет одну операцию дважды.

### Пример
```http
GET    /api/projects          → список
GET    /api/projects/42       → один проект
POST   /api/projects          → создать, тело: {"title":"Лендинг"}
PUT    /api/projects/42       → заменить: {"title":"Лендинг","budget":30000,"status":"new"}
PATCH  /api/projects/42       → изменить: {"status":"done"}
DELETE /api/projects/42       → удалить
```

```js
// Плохо: GET меняет данные
app.get("/api/projects/42/delete", ...);

// Хорошо
app.delete("/api/projects/:id", ...);
```

### Частые ошибки
- Делать всё через POST или всё через GET.
- Удаление по ссылке `GET /delete?id=5`.
- Использовать PUT, присылая только одно поле, и случайно затирать остальные.

### На пальцах
Код ответа — короткий вердикт сервера, который понимает любая программа без чтения текста. Первая цифра — категория: 2 — «получилось», 3 — «ищи в другом месте», 4 — «ты что-то сделал не так», 5 — «это мы сломались». Правильный код — половина хорошего API.

### Как это работает
| Код | Когда возвращать |
|---|---|
| 200 OK | успешный GET, PATCH, PUT с телом ответа |
| 201 Created | успешно создано (POST), в теле — новый объект |
| 204 No Content | успешно, тела нет (обычно DELETE) |
| 301 / 308 | ресурс переехал навсегда |
| 302 / 307 | временный редирект (например, после входа) |
| 304 Not Modified | данные не изменились, бери из кеша |
| 400 Bad Request | неверные данные: не прошла валидация, кривой JSON |
| 401 Unauthorized | не вошёл или токен недействителен |
| 403 Forbidden | вошёл, но нет прав на это действие |
| 404 Not Found | ресурса нет (или чужой ресурс, который не стоит выдавать) |
| 409 Conflict | конфликт: email уже занят, версия устарела |
| 422 Unprocessable | данные корректны по формату, но нарушают правила (часто вместо 400) |
| 429 Too Many Requests | превышен лимит запросов |
| 500 Internal Server Error | необработанная ошибка в коде сервера |
| 503 Service Unavailable | сервис временно недоступен, перегрузка, обслуживание |

Правила:

- Ошибку клиента (4xx) клиент может исправить сам. Ошибку 5xx — нет.
- Не возвращай 200 с `{ "error": "..." }` — клиенты и мониторинг сочтут это успехом.
- В теле ошибки — понятное сообщение: `{ "error": "Email уже занят" }`.

### Пример
```js
app.post("/api/users", async (req, res) => {
  const { email } = req.body ?? {};
  if (!email) return res.status(400).json({ error: "Укажите email" });
  if (await db.userExists(email)) return res.status(409).json({ error: "Email уже занят" });
  const user = await db.createUser(email);
  res.status(201).json(user);
});

app.delete("/api/projects/:id", requireAuth, async (req, res) => {
  const project = await db.getProject(req.params.id);
  if (!project) return res.status(404).json({ error: "Проект не найден" });
  if (project.ownerId !== req.user.id) return res.status(403).json({ error: "Нет прав" });
  await db.deleteProject(project.id);
  res.status(204).end();
});
```

### Частые ошибки
- Всегда 200 и ошибка в теле.
- 500 на ошибку валидации — клиент думает, что сломался сервер.
- Путать 401 и 403.

### На пальцах
REST — договорённость называть адреса в API как предметы, а не как действия. Не «/получитьВсеПроекты» и «/удалитьПроект», а просто «/projects» — и глагол (метод) говорит, что с этим предметом сделать. Как в библиотеке: полка «Проекты», на ней папки с номерами, а внутри папки — вложенные «Задачи».

### Как это работает
Правила именования:

- Ресурс — существительное во множественном числе: `/projects`, `/clients`, `/tasks`.
- Конкретный элемент — по id: `/projects/42`.
- Вложенность показывает принадлежность: `/projects/42/tasks` — задачи проекта 42. Больше двух уровней обычно не делают.
- Действие — метод HTTP, а не слово в адресе.
- Фильтры, сортировка, пагинация, поиск — в query-параметрах: `/tasks?status=open&sort=-createdAt&page=2&limit=20`.
- Адреса маленькими буквами, слова через дефис: `/time-entries`.
- Версию API часто добавляют в путь: `/api/v1/projects`.

Для действий, которые плохо ложатся на CRUD, допустимо отдельное существительное: `POST /projects/42/archive` или `POST /orders/7/payments`.

### Пример
```http
GET    /api/v1/projects?status=active&sort=-budget&page=1&limit=20
GET    /api/v1/projects/42
POST   /api/v1/projects
PATCH  /api/v1/projects/42
DELETE /api/v1/projects/42

GET    /api/v1/projects/42/tasks?done=false
POST   /api/v1/projects/42/tasks
PATCH  /api/v1/tasks/108              ← задача уже имеет свой id, длинная вложенность не нужна

POST   /api/v1/projects/42/archive    ← действие как отдельный ресурс
```

Плохо:

```http
GET  /api/getProjects
POST /api/deleteProject?id=42
GET  /api/project_list_by_client/5
```

### Частые ошибки
- Глаголы в адресах: `/createTask`, `/updateUser`.
- Разные стили в одном API: `/Projects`, `/client_list`, `/getTasks`.
- Фильтры в пути: `/projects/status/active/sort/budget`.

### На пальцах
`Content-Type` — подпись на посылке: «внутри документы», «внутри картинка», «внутри JSON». Без подписи получатель не знает, как распаковывать: читать как текст, сохранять как файл или разбирать как данные. JSON — самый частый формат «содержимого» в API.

### Как это работает
Частые типы:

| Content-Type | Что внутри |
|---|---|
| `application/json` | JSON — основной формат API |
| `text/html; charset=utf-8` | HTML-страница |
| `application/x-www-form-urlencoded` | обычная HTML-форма |
| `multipart/form-data` | форма с файлами |
| `text/plain` | простой текст |
| `image/png`, `image/webp` | картинка |

Как это работает в обе стороны:

- Клиент отправляет JSON → ставит `Content-Type: application/json`, тело — `JSON.stringify(...)`. Сервер по заголовку понимает, что надо разобрать JSON (`express.json()` делает это только при таком заголовке).
- Сервер отвечает JSON → ставит `Content-Type: application/json` (`res.json()` делает сам). Клиент читает `response.json()`.
- Заголовок `Accept: application/json` в запросе говорит: «я хочу JSON в ответ».

Хороший JSON API: ключи в одном стиле (camelCase или snake_case — договорись), даты в формате ISO `"2026-10-24T12:00:00Z"`, деньги — целым числом в копейках или строкой, пустое значение — `null`, а не пропущенное поле там, где это важно.

### Пример
```js
// клиент
const r = await fetch("/api/projects", {
  method: "POST",
  headers: { "Content-Type": "application/json", Accept: "application/json" },
  body: JSON.stringify({ title: "Лендинг", budget: 3000000, deadline: "2026-11-30" }),
});
console.log(r.headers.get("content-type"));   // application/json; charset=utf-8
const project = await r.json();
```

```js
// сервер (Express)
app.use(express.json());                       // разбирает тело только с Content-Type: application/json
app.post("/api/projects", (req, res) => {
  console.log(req.body.title);                 // "Лендинг"
  res.status(201).json({ id: 42, ...req.body, createdAt: new Date().toISOString() });
});
```

### Частые ошибки
- Отправить JSON без заголовка — `req.body` на сервере пустой.
- Отдавать JSON с `Content-Type: text/html` — некоторые клиенты не разберут.
- Хранить деньги дробными числами (`299.99`) и получать ошибки округления.

### На пальцах
Проверять API только через свой фронтенд — как пробовать суп только через готовое блюдо, не пробуя бульон отдельно. curl, Bruno и Postman — ложки, которыми пробуют API напрямую: отправил любой запрос — увидел точный ответ, без браузера и кнопок.

### Как это работает
**curl** — в терминале, есть везде. Быстро проверить один запрос, вставить в документацию, в скрипты.

**Bruno / Postman** — программы с окнами:

- коллекции запросов, разложенные по папкам;
- переменные окружений: `{{baseUrl}}` = `http://localhost:3000` локально и боевой адрес на сервере;
- авторизация: токен сохраняется и подставляется во все запросы;
- тесты ответа: «статус 200, в ответе есть поле id».

Bruno хранит коллекции в обычных файлах прямо в репозитории — их можно коммитить вместе с кодом, и коллеги получают готовый набор запросов. Postman хранит в облаке, коллекцию можно экспортировать.

**Вкладка Network** в DevTools — смотреть запросы, которые делает сам фронтенд. Правый клик по запросу → «Copy as cURL» — получить готовую команду и повторить запрос в терминале или импортировать в Bruno.

### Пример
```bash
# быстро проверить, что сервер живой
curl -i http://localhost:3000/api/health

# создать проект
curl -X POST http://localhost:3000/api/projects \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"title":"Лендинг","budget":30000}'
```

```text
# Bruno: файл api/projects/create.bru в репозитории
meta { name: Создать проект }
post { url: {{baseUrl}}/api/projects  body: json  auth: bearer }
auth:bearer { token: {{token}} }
body:json { { "title": "Лендинг", "budget": 30000 } }
tests {
  test("статус 201", () => expect(res.status).to.equal(201));
  test("есть id", () => expect(res.body.id).to.be.a("number"));
}
```

### Частые ошибки
- Проверять API только через интерфейс — сложно понять, где ошибка: во фронтенде или на сервере.
- Хранить токены и пароли в коллекции, закоммиченной в репозиторий. Секреты — в локальном файле окружения, который в `.gitignore`.
- Не сохранять запросы — каждый раз писать заново.
