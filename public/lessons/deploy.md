### На пальцах
Выбор хостинга — выбор жилья для проекта. Render, Railway, Fly.io — квартира с ремонтом и управляющей компанией: заехал с чемоданом (код) и живёшь, о трубах заботятся другие. VPS — собственный участок с домом: полная свобода, но крышу чинишь сам и сам следишь за замками.

### Как это работает
| | Render / Railway / Fly.io (PaaS) | VPS (Timeweb, Selectel, Hetzner, DigitalOcean) |
|---|---|---|
| Что делаешь ты | подключаешь репозиторий, задаёшь переменные | ставишь ОС, Node.js, Nginx, базу, настраиваешь HTTPS, обновления, безопасность |
| Деплой | автоматически по push | сам: скрипт, Docker, CI |
| HTTPS | автоматически | сам (Certbot, Caddy) |
| База | управляемая, в пару кликов | ставишь и обслуживаешь сам или берёшь отдельную облачную |
| Масштабирование | ползунок | сам |
| Цена | бесплатно для маленьких проектов, дальше дороже за ресурсы | дешевле за ресурсы, но время на обслуживание |
| Подходит | учебные проекты, MVP, небольшие команды | когда нужен полный контроль, особые требования или экономия на большом объёме |

Особенности бесплатных тарифов: Render засыпает после 15 минут без запросов, первое открытие после сна — 30–60 секунд. Это нормально для учебных проектов, но для работы клиента берут платный тариф.

Отдельно: фронтенд (статический сайт) удобно размещать на Vercel, Netlify, GitHub Pages; бэкенд — на Render, Railway, Fly.io; базу — Neon, Supabase.

### Пример
```yaml
# render.yaml — описание сервиса для Render (Blueprint)
services:
  - type: web
    name: studio-api
    runtime: node
    region: frankfurt
    plan: free
    buildCommand: npm ci --omit=dev
    startCommand: node src/index.js
    healthCheckPath: /healthz
    envVars:
      - key: NODE_ENV
        value: production
      - key: DATABASE_URL
        sync: false            # спросит при создании
      - key: JWT_SECRET
        generateValue: true    # Render сгенерирует сам
```

### Частые ошибки
- Арендовать VPS для первого учебного проекта и неделю настраивать сервер вместо кода.
- Не учитывать «сон» бесплатного тарифа на демонстрации заказчику.
- Хранить загружаемые пользователями файлы на диске PaaS-сервиса — он обнуляется при каждом деплое. Для файлов нужно хранилище (S3, Cloudflare R2, Supabase Storage).

### Мини-задание
Задеплой свой API на Render: подключи репозиторий, задай переменные, укажи health-check. Засеки, сколько занимает первое открытие после 20 минут простоя.

### На пальцах
Переменные окружения на продакшене — ключи от сейфов, которые хранятся у администратора здания, а не в чертежах. Код один для всех, а боевые ключи знает только сервер, на котором он работает. Если чертежи (репозиторий) случайно попадут к чужим, сейфы останутся закрыты.

### Как это работает
Где задаются:

- **Render, Railway, Fly.io** — в настройках сервиса (Environment). Можно объединять в группы для нескольких сервисов.
- **Vercel, Netlify** — Project Settings → Environment Variables, отдельно для Production, Preview, Development.
- **GitHub Actions** — Settings → Secrets.
- **VPS** — файл окружения systemd или Docker Compose, доступный только владельцу (`chmod 600`).

Правила:

- у продакшена свои секреты, не те же, что локально;
- никакого секрета в коде, Dockerfile, `render.yaml` открытым текстом (только ссылки на переменные);
- никаких секретов во фронтенд-переменных (`VITE_`, `NEXT_PUBLIC_`);
- после изменения переменной — перезапуск или повторный деплой;
- проверка всех обязательных переменных при старте приложения.

Доступ к панели хостинга = доступ ко всем секретам. Включи двухфакторную аутентификацию.

### Пример
```text
Render → studio-api → Environment
NODE_ENV        production
DATABASE_URL    postgresql://...neon.tech/neondb?sslmode=require
JWT_SECRET      (сгенерировано Render)
CORS_ORIGINS    https://studio.ru,https://www.studio.ru
SENTRY_DSN      https://...@sentry.io/...
```

```js
// при старте — понятная ошибка вместо падения через час
import { config } from "./config.js";   // модуль с проверкой через zod из урока про архитектуру
```

### Частые ошибки
- Забыть добавить новую переменную на продакшене — деплой падает или функция тихо не работает.
- Один `JWT_SECRET` локально и на сервере.
- Секрет в `render.yaml` или `docker-compose.yml`, закоммиченном в репозиторий.

### Мини-задание
Сравни список переменных в `.env.example` и в настройках своего хостинга. Добавь недостающие, сгенерируй для продакшена новый `JWT_SECRET` и включи двухфакторную аутентификацию в аккаунтах GitHub и хостинга.

### На пальцах
GitHub Actions — контролёр ОТК на конвейере: каждый pull request проходит через проверку — собирается ли, проходят ли тесты, нет ли нарушений стиля. Бракованная партия получает красную метку, и её нельзя смешать с хорошей продукцией в `main`.

### Как это работает
- Сценарии — YAML-файлы в `.github/workflows/`.
- Запуск на каждый pull request и push в `main`.
- Типичные шаги: скачать код → поставить Node.js с кешем npm → `npm ci` → линтер → проверка типов → тесты → сборка.
- Для тестов с базой — `services: postgres`.
- В настройках репозитория: Settings → Branches → правило для `main`: «Require status checks to pass» — нельзя слить pull request с красными проверками.

CI (непрерывная интеграция) — проверка каждого изменения. CD (непрерывная доставка) — автоматический деплой после успешной проверки: Render и Vercel умеют деплоить сами при push в `main`, или деплой запускается отдельным шагом сценария.

Матрица версий (`strategy.matrix`) позволяет прогнать тесты на нескольких версиях Node.js.

### Пример
```yaml
# .github/workflows/ci.yml
name: CI
on:
  pull_request:
  push:
    branches: [main]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npx tsc --noEmit
      - run: npx vitest run
      - run: npm run build
```

### Частые ошибки
- CI есть, но защита ветки не включена — красный pull request всё равно сливают.
- Тесты в CI ходят во внешние сервисы и падают случайно.
- Долгий CI (20+ минут) без кеша зависимостей — разработчики перестают ждать результата.

### Мини-задание
Добавь в свой проект сценарий CI с линтером, тестами и сборкой, включи защиту ветки `main` и сделай pull request. Посмотри, сколько времени занимает прогон, и включи кеш npm, если его нет.

### На пальцах
Домен — вывеска с названием вместо адреса «промзона, строение 47». DNS — справочное бюро, которое по названию говорит адрес. HTTPS — бронированный фургон, в котором данные едут от посетителя к тебе. Хостинги выдают такой фургон бесплатно и сами его обслуживают.

### Как это работает
1. Купи домен у регистратора (Reg.ru, Timeweb, Namecheap, Cloudflare).
2. В настройках хостинга добавь домен — он покажет, какие DNS-записи нужны.
3. У регистратора в управлении DNS добавь записи.
4. Подожди, пока DNS обновится (от минут до 24 часов).
5. Хостинг сам выпустит сертификат Let's Encrypt — сайт заработает по HTTPS.

Основные типы записей:

| Тип | Для чего | Пример |
|---|---|---|
| `A` | домен → IPv4-адрес | `@  →  76.76.21.21` |
| `AAAA` | домен → IPv6-адрес | |
| `CNAME` | поддомен → другое имя | `www  →  cname.vercel-dns.com`, `api  →  studio-api.onrender.com` |
| `MX` | куда доставлять почту | `@  →  mx.yandex.net` |
| `TXT` | подтверждения и почтовые записи (SPF, DKIM) | `@  →  "v=spf1 include:_spf.yandex.net ~all"` |

`@` — сам домен без поддомена. CNAME нельзя ставить на корень домена у большинства регистраторов — для корня используют A-запись или ALIAS/ANAME, если регистратор их поддерживает.

Удобная схема: `studio.ru` и `www.studio.ru` — фронтенд, `api.studio.ru` — бэкенд. Тогда cookie можно настроить на общий домен, и меньше сложностей с CORS.

### Пример
```text
Записи DNS для studio.ru:

@      A      76.76.21.21                  ← фронтенд на Vercel
www    CNAME  cname.vercel-dns.com
api    CNAME  studio-api.onrender.com      ← API на Render
@      MX     10 mx.yandex.net             ← почта
```

```bash
# проверить, что записи применились
dig +short studio.ru
dig +short api.studio.ru CNAME
nslookup studio.ru
```

### Частые ошибки
- Ждать мгновенного обновления DNS и переделывать настройки каждые 5 минут.
- Удалить MX-записи при настройке сайта — перестаёт работать почта на домене.
- Не настроить редирект с `www` на основной домен (или наоборот) — два адреса одного сайта.

### Мини-задание
Если у тебя есть домен (например, сайт студии), подключи поддомен `api.` к своему API на Render, а основной домен — к фронтенду. Если домена нет, распиши таблицу DNS-записей для такой схемы и проверь через `dig` записи любого известного сайта.

### На пальцах
Сайт в продакшене — машина в дороге. Логи — бортовой журнал. Health-check — датчик «двигатель работает», по которому хостинг понимает, что машина на ходу, и перезапускает её, если нет. Sentry — видеорегистратор, который при аварии сам присылает запись: где, когда, при каких обстоятельствах.

### Как это работает
**Логи**:

- на Render и Railway видны в панели в реальном времени;
- пиши структурированные логи (JSON через pino), чтобы по ним искать;
- для хранения и поиска за недели — сервисы логов (Better Stack, Grafana Loki).

**Health-check** — простой маршрут `/healthz`:

- хостинг регулярно запрашивает его и ждёт 200;
- при деплое новая версия получает трафик только после успешного health-check — сломанная версия не заменит работающую;
- можно проверять и базу (`SELECT 1`), но аккуратно: если база недолго недоступна, хостинг начнёт перезапускать здоровое приложение.

**Sentry** (или аналоги) — отслеживание ошибок:

- ловит необработанные исключения на сервере и во фронтенде;
- присылает уведомление со стеком, адресом, пользователем, браузером;
- группирует одинаковые ошибки и показывает, сколько людей затронуто.

**Внешний мониторинг доступности** (UptimeRobot, Better Stack) — раз в минуту проверяет сайт снаружи и пишет в Telegram, если он упал.

### Пример
```js
app.get("/healthz", (req, res) => res.json({ status: "ok" }));

app.get("/readyz", async (req, res) => {
  try {
    await pool.query("SELECT 1");
    res.json({ status: "ready" });
  } catch {
    res.status(503).json({ status: "db-unavailable" });
  }
});
```

```js
// Sentry на сервере
import * as Sentry from "@sentry/node";
Sentry.init({ dsn: process.env.SENTRY_DSN, environment: process.env.NODE_ENV, tracesSampleRate: 0.1 });

// в обработчике ошибок — отправить неожиданные ошибки
app.use((err, req, res, next) => {
  if (!(err instanceof AppError)) Sentry.captureException(err);
  next(err);
});
```

### Частые ошибки
- Узнавать о падении сайта от клиента.
- Health-check, который возвращает 200, даже когда приложение не может работать.
- Логи без контекста: «Ошибка!» — и всё.

### Мини-задание
Добавь `/healthz` и укажи его в настройках хостинга. Подключи бесплатный Sentry к API и фронтенду и вызови тестовую ошибку. Настрой UptimeRobot на проверку сайта каждые 5 минут с уведомлением в Telegram или на почту.

### На пальцах
Резервная копия — страховка: пока всё хорошо, кажется лишней тратой. Откат релиза — кнопка «вернуть как было», когда новая версия сломалась в пятницу вечером. Оба механизма нужно настроить и проверить заранее, а не искать их в момент пожара.

### Как это работает
**Резервные копии базы**:

- управляемые базы (Neon, Supabase, Render Postgres) делают копии сами; в Neon можно восстановить состояние на любую точку времени в пределах срока хранения;
- для своей базы — регулярный `pg_dump` по cron в отдельное хранилище (не на тот же сервер!);
- **проверка восстановления** — копия, из которой ни разу не восстанавливались, — это надежда, а не копия.

Правило 3-2-1: три копии, на двух разных носителях, одна — в другом месте.

**Откат релиза**:

- Render, Vercel, Railway хранят прошлые деплои — откат одной кнопкой («Rollback», «Redeploy»);
- или `git revert` проблемного коммита и обычный деплой;
- с Docker — запустить предыдущий тег образа, поэтому образы помечают версиями, а не только `latest`.

**Сложность — миграции базы.** Код откатить легко, схему — нет. Поэтому:

- миграции делают обратно совместимыми: сначала добавить колонку (старый код её не замечает), потом выкатить код, который её использует, и только потом, отдельным релизом, удалять старое;
- перед рискованной миграцией — свежая копия или ветка базы.

### Пример
```bash
# ручная копия и восстановление
pg_dump "$DATABASE_URL" --format=custom --file=backup-$(date +%F).dump
pg_restore --clean --if-exists --dbname="$RESTORE_DATABASE_URL" backup-2026-10-24.dump
```

```yaml
# ежедневный бэкап через GitHub Actions в облачное хранилище
on:
  schedule:
    - cron: "0 1 * * *"
jobs:
  backup:
    runs-on: ubuntu-latest
    steps:
      - run: sudo apt-get install -y postgresql-client
      - run: pg_dump "${{ secrets.DATABASE_URL }}" --format=custom --file=backup.dump
      - uses: actions/upload-artifact@v4
        with:
          name: db-backup-${{ github.run_id }}
          path: backup.dump
          retention-days: 14
```

```bash
# откат кода
git revert 3f2a1bc        # отменить проблемный коммит новым коммитом
git push                  # хостинг задеплоит исправленную версию
```

### Частые ошибки
- Резервные копии лежат на том же сервере, что и база.
- Ни разу не проверять восстановление.
- Миграция, удаляющая колонку, в одном релизе с кодом — откат кода не помогает, данные уже удалены.

### Мини-задание
Сделай `pg_dump` своей базы, создай в Neon новую ветку (или локальную базу) и восстанови в неё копию. Найди в панели своего хостинга кнопку отката деплоя и попробуй откатиться на прошлую версию.
