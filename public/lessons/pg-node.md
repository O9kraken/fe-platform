На продакшене при сотне пользователей Neon отвечает «too many connections», а каждый ответ задерживается на лишние 50 мс просто на открытие соединения. Соединения с базой — дорогой ресурс, и их держат в пуле.

### На пальцах
Драйвер `pg` — переводчик между Node.js и PostgreSQL. Pool — несколько заранее открытых телефонных линий с базой: не нужно каждый раз набирать номер и ждать соединения, свободная линия уже ждёт. Параметры `$1`, `$2` — пустые клеточки в бланке запроса, куда драйвер аккуратно впишет значения.

### Как это работает
>> `new Pool({ connectionString })` → `pool.query(sql, [id])` → `$1` подставляется безопасно → `rows`

- `npm install pg`.
- `new Pool({ connectionString })` — создать пул один раз на всё приложение.
- `pool.query(text, values)` — выполнить запрос. Возвращает объект с `rows` (массив строк-объектов) и `rowCount`.
- Значения передаются массивом вторым аргументом, а в тексте стоят `$1`, `$2`, ...
- `RETURNING *` в `INSERT`/`UPDATE` возвращает изменённые строки — не нужен второй запрос.

Пул держит несколько открытых соединений (по умолчанию до 10) и раздаёт их запросам.

Типы: PostgreSQL `integer` → JS `number`, `bigint` и `numeric` → строка (чтобы не потерять точность), `timestamptz` → `Date`, `jsonb` → объект.

?: Почему `bigint` и `numeric` приходят в JavaScript строкой, а не числом? || Обычное число JavaScript точно хранит целые только до 2^53. `bigint` бывает больше, а `numeric` хранит точные дробные. Если превратить их в `number`, можно молча потерять цифры, поэтому драйвер отдаёт строку и оставляет решение тебе.

### Пример
```js
export const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

projects.post("/", async (req, res) => {
  const { clientId, title, budget } = req.body;
  const result = pool.query(
    "INSERT INTO projects (client_id, title, budget) VALUES ($1, $2, $3) RETURNING *",
    [clientId, title, budget ?? null]
  );
  res.status(201).json(result.rows[0]);
});
```

?! Что вернёт этот маршрут, хотя проект в базу добавился? || Ошибку «Cannot read properties of undefined (reading '0')»: перед `pool.query` нет `await`, и в `result` лежит промис, у которого нет поля `rows`.

### Частые ошибки
- **`new Pool` внутри обработчика запроса** — тысячи соединений и падение базы.
- **Забыт `await`** — в ответ уходит промис или `undefined` вместо данных.
- **Ожидание числа из `bigint`/`numeric`** — приходит строка.

### Проверь себя
?? Что возвращает `pool.query`? || Промис с объектом результата: в `rows` — массив строк, в `rowCount` — количество затронутых строк.
?? Зачем `RETURNING *` в запросе `INSERT`? || Чтобы база сразу вернула вставленную строку со всеми полями, включая выданный id, без второго запроса.
?? Объясни своими словами, зачем нужен пул соединений. || Открывать соединение с базой долго, а их число ограничено. Пул заранее держит несколько открытых соединений и раздаёт их запросам по очереди, поэтому запросы быстрые, а база не перегружается.

Это SQL-инъекция, одна из самых старых и самых разрушительных уязвимостей. Она до сих пор в топе OWASP. Защита — одна привычка, которую нужно выработать с первого запроса.

### На пальцах
Склеивать SQL из строк — как дать незнакомцу бланк, где он сам дописывает текст приказа. Попросили имя, а он вписал: «Анна; и заодно выдайте мне ключи от сейфа». Параметры `$1` — бланк с защищённой клеточкой: что бы ни написали внутри, это будет только значение, а не новая команда.

### Как это работает
>> Ввод пользователя → склейка в SQL — инъекция → параметр `$1` — просто значение

SQL-инъекция — когда данные пользователя попадают прямо в текст запроса и меняют его смысл.

```js
// ❌ ОПАСНО
const sql = `SELECT * FROM users WHERE email = '${req.body.email}'`;
```

Защита:

- **Параметризованные запросы**: текст запроса и значения передаются в базу отдельно. База никогда не исполняет значение как код.
- ORM и построители запросов делают это автоматически.
- Параметрами нельзя подставить имена колонок и таблиц (например, для сортировки) — их выбирают из белого списка.
- Плюс — принцип наименьших прав: пользователь базы для приложения не должен уметь удалять таблицы.

?: Почему параметры `$1` защищают от инъекции, а ручное экранирование кавычек — плохо? || С параметрами текст запроса и значения едут в базу раздельно, и значение физически не может стать частью команды. Ручное экранирование — попытка угадать все опасные символы и кодировки; одна забытая — и защита пробита.

### Пример
```js
const email = "' OR '1'='1";
const sql = `SELECT id, email FROM users WHERE email = '${email}'`;
console.log(sql);
```

?! Какой SQL-запрос получится и что он вернёт? || `SELECT id, email FROM users WHERE email = '' OR '1'='1'`. Условие `'1'='1'` истинно для каждой строки, поэтому запрос вернёт всех пользователей. С параметром `$1` база искала бы email, буквально равный этой строке, — и не нашла бы ничего.

### Частые ошибки
- **Шаблонные строки с данными пользователя внутри SQL.**
- **Ручное «экранирование кавычек»** вместо параметров.
- **Имя колонки из запроса без белого списка** — например, для сортировки.

### Проверь себя
?? Что такое SQL-инъекция? || Уязвимость, при которой данные пользователя попадают прямо в текст SQL-запроса и меняют его смысл.
?? Как безопасно сделать сортировку по полю, которое выбирает пользователь? || Сопоставить значение из запроса с белым списком разрешённых колонок и подставить в SQL только значение из этого списка.
?? Объясни своими словами, как работают параметризованные запросы. || Текст запроса с метками `$1`, `$2` и сами значения передаются в базу отдельно. База подставляет значения как данные, и они никогда не выполняются как часть команды.

### На пальцах
Миграции — журнал ремонта дома: «15 января — добавили комнату "клиенты", 3 февраля — в комнате "проекты" сделали окно "статус"». У любого, кто строит копию дома (коллега, тестовый сервер, продакшен), есть один и тот же журнал, и дом получается одинаковым.

### Как это работает
>> `001_init.sql` → `002_add_status.sql` → скрипт применяет новые → схема одинакова везде

- Миграция — файл с изменением схемы: создать таблицу, добавить колонку, индекс.
- Файлы нумеруются по порядку: `001_create_clients.sql`, `002_create_projects.sql`, `003_add_status.sql`.
- В базе хранится служебная таблица с номерами уже применённых миграций.
- Команда «применить миграции» выполняет только новые — по порядку, каждую в транзакции.
- Миграции лежат в Git вместе с кодом и запускаются при деплое.

Правила:

- Уже применённую миграцию не редактируют — пишут новую.
- Изменения делают совместимыми: сначала добавить колонку, потом код, который её использует, потом удалить старую.
- Тестовые данные (seed) — отдельно от миграций.

Инструменты: node-pg-migrate, Knex, миграции Prisma и Drizzle. Простейший вариант можно написать самому.

?: Почему нельзя исправлять уже применённую миграцию? || На твоей базе, у коллег и на продакшене она уже выполнена и записана в служебную таблицу как готовая. Исправленный файл никто повторно не запустит, и схемы на разных машинах разойдутся. Исправление — всегда новая миграция.

### Пример
```text

  001_init.sql          ← применена
  002_projects.sql      ← применена
  003_add_status.sql    ← новая
```

```js

const files = (await readdir("migrations")).filter(f => f.endsWith(".sql")).sort();
for (const f of files) {
  if (done.has(f)) continue;
  // BEGIN, выполнить файл, записать имя в migrations, COMMIT
}
```

?! В таблице `migrations` записаны `001_init.sql` и `002_projects.sql`. Что сделает скрипт при запуске? А если в `003` есть ошибка? || Пропустит два применённых файла и выполнит только `003_add_status.sql`. Если в нём ошибка, транзакция откатится, запись в `migrations` не появится, и при следующем запуске скрипт снова попробует применить `003`.

### Частые ошибки
- **Схема меняется руками в панели базы** — у коллег и на продакшене она другая.
- **Редактирование уже применённой миграции.**
- **Колонка удаляется вместе с выкаткой кода**, который перестал её использовать, — старые экземпляры приложения падают во время деплоя.

### Проверь себя
?? Что такое миграция базы данных? || Файл с описанием одного изменения схемы, который применяется по порядку и записывается как выполненный.
?? Как скрипт миграций понимает, какие файлы уже применены? || По служебной таблице в базе, где хранятся имена выполненных миграций.
?? Объясни своими словами, зачем нужны миграции, если схему можно поменять в панели базы. || Чтобы изменения схемы хранились в Git вместе с кодом и одинаково применялись на любом компьютере и сервере. Ручные правки невозможно повторить и отследить.

### Ситуация
Заказ из трёх товаров. Сервер создаёт запись заказа, списывает остатки первого и второго товара — а третьего на складе не хватает, ошибка. В базе осталось: заказ без позиций и два товара, списанных в никуда. В SQL мы уже знаем ответ — транзакция. Но из кода с пулом соединений есть ловушка, на которой спотыкаются почти все.

### На пальцах
Транзакция из кода — то же «всё или ничего», только управляет ею твой сервер. Важная деталь: все команды транзакции должны идти по одной и той же телефонной линии с базой. Поэтому из пула берут одно соединение, делают на нём всю работу и возвращают обратно.

### Как это работает
>> `client = await pool.connect()` → `BEGIN` → запросы → `COMMIT` / `ROLLBACK` → `release()`

1. `const client = await pool.connect()` — взять одно соединение из пула.
2. `await client.query("BEGIN")`.
3. Все запросы транзакции — через этот `client`, а не через `pool.query`.
4. Успех — `COMMIT`, ошибка — `ROLLBACK`.
5. В `finally` — обязательно `client.release()`, иначе соединение не вернётся в пул.

Удобно написать обёртку `withTransaction(fn)`, чтобы не повторять этот шаблон.

?: Почему внутри транзакции нельзя использовать `pool.query`? || Каждый `pool.query` берёт из пула любое свободное соединение. `BEGIN` мог уйти по одному соединению, а следующие запросы — по другим, вне транзакции. Откатывать будет нечего, и вся защита исчезнет.

### Пример
```js
export async function withTransaction(fn) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const result = await fn(client);
    await client.query("COMMIT");
    return result;
  } catch (e) {
    await client.query("ROLLBACK");
    throw e;
  }
}
```

?! Пул рассчитан на 10 соединений. Что случится с приложением после десяти вызовов `withTransaction`? || Оно «зависнет»: в обёртке нет `finally { client.release() }`, и ни одно соединение не возвращается в пул. Одиннадцатый запрос будет бесконечно ждать свободную линию.

### Частые ошибки
- **`pool.query` вместо `client.query`** внутри транзакции.
- **Забыт `client.release()`** — пул истощается.
- **Внешние API (платёжка, почта) внутри открытой транзакции** — она надолго держит блокировки.

### Проверь себя
?? Как получить из пула одно соединение для транзакции? || `const client = await pool.connect()`.
?? Где обязательно возвращать соединение в пул и почему? || В блоке `finally` через `client.release()`, чтобы соединение вернулось и при успехе, и при ошибке.
?? Объясни своими словами, зачем обёртка `withTransaction`. || Чтобы не повторять в каждом маршруте шаблон с BEGIN, COMMIT, ROLLBACK и release и не забыть в нём что-то. Внутрь передаётся только полезная логика.

Задача сервера — перевести этот код в понятный ответ клиенту, а не показывать «ошибка 500».

### Как это работает
>> Ошибка базы → `err.code` `23505` — дубликат → 409 → `23503` — нет связанной записи

У ошибок PostgreSQL есть код в `err.code`:

| Код | Что случилось | Что ответить клиенту |
|---|---|---|
| `23505` | нарушена уникальность (`UNIQUE`) | 409 «Email уже занят» |
| `23503` | нарушен внешний ключ | 400 «Клиент не найден» или 409 «Нельзя удалить: есть связанные записи» |
| `23502` | `NULL` в колонке `NOT NULL` | 400 «Заполните поле» |
| `23514` | нарушен `CHECK` | 400 «Недопустимое значение» |
| `22P02` | неверный формат (текст вместо числа или uuid) | 400 «Неверный идентификатор» |

В объекте ошибки есть `err.constraint` — имя нарушенного ограничения и `err.detail` — подробности. Давай ограничениям понятные имена.

?: Почему ловить ошибку уникальности надёжнее, чем сначала проверять `SELECT`-ом, свободен ли email? || Между проверкой и вставкой другой пользователь может успеть зарегистрироваться с тем же email — оба увидят «свободно». Ограничение `UNIQUE` в базе срабатывает атомарно и не пропустит второго, как бы близко по времени ни пришли запросы.

### Пример
```js
export function mapPgError(err) {
  switch (err.code) {
    case "23505":
      return new HttpError(409, "Такая запись уже существует", "DUPLICATE");
    case "23503":
      return new HttpError(409, "Связанная запись не найдена или используется", "FK_VIOLATION");
    case "22P02":
      return new HttpError(400, "Неверный формат данных", "BAD_FORMAT");
    default:
      return err;
  }
}
```

?! Какой ответ получит клиент на `GET /api/projects/abc`, если колонка `id` числовая, а запрос `WHERE id = $1`? || PostgreSQL не сможет превратить `"abc"` в число и вернёт ошибку с кодом `22P02`. `mapPgError` превратит её в 400 «Неверный формат данных» вместо 500.

### Частые ошибки
- **`err.message` от базы клиенту** — там имена таблиц и детали схемы.
- **Уникальность только через предварительный `SELECT`** — гонка запросов.
- **Все ошибки базы как 500.**

### Проверь себя
?? Какой код ошибки PostgreSQL означает нарушение уникальности? || `23505`.
?? Какой HTTP-статус уместен, когда email уже занят? || 409 Conflict.
?? Объясни своими словами, зачем переводить коды ошибок базы в HTTP-ответы. || Чтобы клиент получал правильный статус и понятное сообщение, а не «500» с внутренними подробностями, которые пугают пользователя и выдают устройство базы.
