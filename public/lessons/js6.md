### Ситуация
Твой сайт на JavaScript просит данные у сервера на PHP, тот берёт их из базы на Python-скрипте, а мобильное приложение на Swift читает тот же ответ. Четыре разных языка — и все понимают друг друга. Секрет в общем формате, который выглядит почти как объект JavaScript, но с парой строгих правил, на которых все спотыкаются.

### На пальцах
JSON — общий язык для передачи данных, как стандартный бланк накладной. Сервер на Python, PHP или Node.js заполняет бланк, браузер его читает — и все понимают друг друга. По сути это запись объектов и массивов в виде текста, но со строгими правилами.

### Как это работает
>> Объект в JS → `JSON.stringify` → текст по сети → `JSON.parse` → объект

Правила JSON:

- Ключи всегда в двойных кавычках: `{"name": "Анна"}`.
- Строки только в двойных кавычках.
- Значения: строки, числа, `true`/`false`, `null`, массивы, объекты.
- Нельзя: функции, `undefined`, комментарии, лишнюю запятую в конце.

| Метод | Что делает |
|---|---|
| `JSON.stringify(значение)` | объект → строка (для отправки и сохранения) |
| `JSON.stringify(значение, null, 2)` | то же, но с отступами — удобно читать |
| `JSON.parse(строка)` | строка → объект (после получения) |

Даты в JSON превращаются в строки — после `parse` их надо обратно превратить в `Date`.

?: Почему у JSON такие строгие правила — двойные кавычки, никаких комментариев? || Чем проще и строже формат, тем легче написать для него парсер на любом языке и тем меньше разночтений. JSON намеренно минимален, чтобы одинаково читаться везде — от браузера до микроконтроллера.

### Пример
```js
const order = {
  id: 42,
  paid: false,
  comment: undefined,
  createdAt: new Date(2026, 9, 24),
};

const text = JSON.stringify(order);
const back = JSON.parse(text);

console.log("comment" in back);
console.log(typeof back.createdAt);
```

?! Что выведут две строки? || `false` — поле с `undefined` пропало при `stringify`. `string` — дата превратилась в строку вида `"2026-10-23T21:00:00.000Z"`, и чтобы снова получить дату, нужен `new Date(back.createdAt)`.

### Частые ошибки
- **Одинарные кавычки или комментарии** в `.json` файле — парсер упадёт.
- **Висячая запятая:** `{"a": 1,}` — ошибка.
- **«Unexpected token <»** при `JSON.parse` — сервер вернул HTML-страницу (обычно ошибку) вместо JSON. Смотри, что пришло, во вкладке Network.

### Проверь себя
?? Какие кавычки разрешены в JSON для ключей и строк? || Только двойные.
?? Что делает `JSON.stringify(obj, null, 2)`? || Превращает объект в строку JSON с отступами в 2 пробела, чтобы её было удобно читать.
?? Объясни своими словами, что такое JSON и зачем он нужен. || Текстовый формат записи данных — объектов и массивов. Его понимают все языки, поэтому через него обмениваются данными браузер, сервер и приложения.

### Ситуация
Ты пишешь `const users = fetch(url)` и выводишь `users` — в консоли загадочное `Promise {<pending>}`. Где данные? Они ещё в пути: сервер может отвечать полсекунды, а может пять. JavaScript не будет стоять и ждать, замораживая страницу, — он даёт тебе «квитанцию». Научимся по ней получать результат.

### На пальцах
Запрос на сервер — заказ в ресторане. Официант не стоит у столика, пока готовят: он берёт заказ и уходит, а ты получаешь номерок — промис. «Обещаю принести блюдо или сказать, что оно закончилось». `await` — «подожду номерок здесь, а потом продолжу». Пока ты ждёшь, весь ресторан (страница) продолжает работать.

### Как это работает
>> `fetch(url)` → Promise → `await` ответ → `await res.json()` → данные

- `fetch(url)` отправляет HTTP-запрос и сразу возвращает **промис** — объект «результат будет позже».
- Промис бывает в трёх состояниях: ожидание, выполнен (resolve), отклонён (reject).
- `await промис` — ждать результат. Писать `await` можно только внутри функции с `async` (или на верхнем уровне модуля).
- `fetch` работает в два шага: сначала приходят заголовки (`response`), потом тело читается отдельно — `await response.json()`.

Старый способ — цепочки `.then()`:

```js
fetch(url).then(r => r.json()).then(data => console.log(data));
```

`async/await` делает то же самое, но читается сверху вниз, как обычный код.

Несколько запросов параллельно: `await Promise.all([fetch(a), fetch(b)])`.

?: Почему у `fetch` два `await` — для ответа и для `json()`? || Сначала по сети приходят код и заголовки, и уже по ним можно понять, всё ли в порядке. Тело ответа может быть большим и приходить дольше, поэтому его чтение — отдельная асинхронная операция.

### Пример
```js
async function loadUsers() {
  console.log("1");
  const response = await fetch("https://jsonplaceholder.typicode.com/users");
  const users = await response.json();
  console.log("3:", users.length);
}

loadUsers();
console.log("2");
```

?! В каком порядке появятся «1», «2» и «3»? || 1, 2, 3. «1» печатается сразу при вызове. На `await` функция «засыпает», и выполняется остальной код — «2». Когда придут данные, функция продолжится и выведет «3: 10».

### Частые ошибки
- **Забыт `await`** — вместо данных `Promise {<pending>}`.
- **`await` в обычной функции без `async`** — синтаксическая ошибка.
- **Забыт второй `await` перед `response.json()`** — опять промис вместо данных.

### Проверь себя
?? Что сразу возвращает `fetch`? || Промис — обещание результата, который придёт позже.
?? Где можно использовать `await`? || Внутри функции, объявленной с `async`, или на верхнем уровне модуля.
?? Объясни своими словами, что такое промис. || Объект-обещание: «результат будет позже». Он либо выполнится с данными, либо отклонится с ошибкой, а код тем временем продолжает работать.

### Мини-задание

### Ситуация
Пользователь открыл приложение в метро без связи. Или сервер упал. Или страница удалена. Твой код уверенно делает `response.json()`, падает с непонятной ошибкой, и на экране остаётся белый лист. Пользователь думает, что сломалось всё. Хороший код ожидает, что запрос может не удаться, — и знает, что `fetch` сообщает о проблемах по-разному.

### На пальцах
Запрос может закончиться двумя разными бедами. Первая — официант вообще не дошёл до кухни: нет интернета, сервер выключен. Это ошибка сети, `fetch` её «бросает». Вторая — дошёл, а повар сказал «такого блюда нет» (404) или «у нас пожар» (500). Для `fetch` это успешный разговор, и проверить ответ — твоя задача через `response.ok`.

### Как это работает
>> `try` → запрос → `if (!res.ok) throw` → `catch` — показать ошибку

- `try { ... } catch (error) { ... }` — «попробуй, а если что-то сломалось — сделай вот это». Код после ошибки в `try` не выполняется, управление уходит в `catch`.
- `finally { ... }` — выполнится в любом случае: удобно убрать индикатор загрузки.
- `fetch` отклоняет промис **только** при сетевой ошибке.
- При ответах 404 и 500 промис выполняется, но `response.ok` равно `false`, а `response.status` содержит код.
- Правильный шаблон: проверить `ok` и самому бросить ошибку: `throw new Error(...)`.

`throw` можно использовать и для своих ошибок: «пустое поле», «нет прав».

?: Почему `fetch` не считает ответ 404 ошибкой? || С точки зрения сети всё прошло успешно: запрос дошёл, сервер ответил. 404 — это содержательный ответ «такого нет», и решать, ошибка это или нормальная ситуация, должен твой код. Иногда «не найдено» — вполне ожидаемый результат.

### Пример
```js
async function loadUser(id) {
  try {
    const response = await fetch(`https://jsonplaceholder.typicode.com/users/${id}`);
    if (!response.ok) {
      throw new Error(`Сервер ответил ${response.status}`);
    }
    const user = await response.json();
    console.log("Пользователь:", user.name);
  } catch (error) {
    console.error("Не получилось:", error.message);
  } finally {
    console.log("Запрос завершён");
  }
}

loadUser(9999);
```

?! Что появится в консоли для несуществующего пользователя 9999? || «Не получилось: Сервер ответил 404» и затем «Запрос завершён». Строка «Пользователь:» не выполнится: после `throw` управление сразу ушло в `catch`, а `finally` срабатывает всегда.

### Частые ошибки
- **Нет проверки `response.ok`** — код пытается читать `json()` у страницы ошибки.
- **Пустой `catch {}`**, который молча глотает ошибку, — потом невозможно понять, что сломалось.
- **Технический текст ошибки пользователю.** Ему нужно «Не удалось загрузить, попробуйте ещё раз», а подробности — в консоль.

### Проверь себя
?? В каком случае `fetch` сам отклоняет промис? || Только при сетевой ошибке: нет интернета, сервер недоступен, запрос заблокирован.
?? Как узнать, что сервер ответил ошибкой, например 404 или 500? || Проверить `response.ok` (будет `false`) или `response.status`.
?? Объясни своими словами, зачем нужен блок `finally`. || Он выполняется в любом случае — и после успеха, и после ошибки. Туда кладут то, что нужно сделать всегда, например скрыть индикатор загрузки.

### Ситуация
Ты делаешь админку для блога: показать посты, добавить новый, исправить опечатку в заголовке, удалить старый. Адрес везде один — `/api/posts`. Как сервер поймёт, чего ты хочешь? По «глаголу» запроса. А по трёхзначному коду ответа ты поймёшь, получилось ли, и что сказать пользователю.

### На пальцах
HTTP-метод — глагол в просьбе к серверу. GET — «покажи», POST — «добавь новое», PUT — «замени целиком», PATCH — «поправь вот это поле», DELETE — «удали». Код ответа — короткий ответ сервера: «готово», «создал», «не нашёл», «тебе нельзя», «у меня сломалось».

### Как это работает
>> `GET` — получить → `POST` — создать → `PATCH` — изменить → `DELETE` — удалить

| Метод | Смысл | Есть тело запроса | Пример |
|---|---|---|---|
| GET | получить | нет | `GET /api/posts` |
| POST | создать | да | `POST /api/posts` |
| PUT | заменить целиком | да | `PUT /api/posts/5` |
| PATCH | изменить часть | да | `PATCH /api/posts/5` |
| DELETE | удалить | обычно нет | `DELETE /api/posts/5` |

Коды, которые встречаются чаще всего:

| Код | Значение | Что показать пользователю |
|---|---|---|
| 200 | OK | данные |
| 201 | создано | «Сохранено» |
| 204 | готово, тела нет | «Удалено» |
| 400 | ошибка в запросе | что не так с формой |
| 401 | не вошёл | отправить на вход |
| 403 | нет прав | «Нет доступа» |
| 404 | не найдено | «Не найдено» |
| 429 | слишком много запросов | «Подождите немного» |
| 500 | ошибка сервера | «Что-то сломалось, попробуйте позже» |

В `fetch` метод передаётся во втором аргументе: `fetch(url, { method: "DELETE" })`.

?: Чем PUT отличается от PATCH, если оба что-то меняют? || PUT заменяет запись целиком: поля, которые ты не прислал, могут стереться. PATCH меняет только присланные поля, остальное не трогает. Чтобы поправить один заголовок, правильнее PATCH.

### Пример
```js
const API = "https://jsonplaceholder.typicode.com/posts";

const r = await fetch(`${API}/1`, {
  method: "PATCH",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ title: "Новый заголовок" }),
});

function messageFor(status) {
  if (status === 401) return "Войдите в аккаунт";
  if (status === 403) return "Нет доступа";
  if (status === 404) return "Не найдено";
  if (status >= 500) return "Сервер недоступен, попробуйте позже";
  return "Ошибка запроса";
}
console.log(messageFor(403), messageFor(503));
```

?! Что выведет последняя строка? || «Нет доступа» и «Сервер недоступен, попробуйте позже»: 503 больше или равно 500.

### Частые ошибки
- **Тело в GET-запросе** — `fetch` не позволит.
- **Нет заголовка `Content-Type: application/json`** при отправке JSON — сервер не поймёт тело.
- **Одно сообщение «Ошибка» на все случаи** вместо разных подсказок для 401, 404 и 500.

### Проверь себя
?? Какой метод используют, чтобы создать новую запись? || POST.
?? Что означают коды 401 и 403? || 401 — пользователь не вошёл в систему. 403 — вошёл, но прав на это действие нет.
?? Объясни своими словами, что такое HTTP-метод. || Глагол запроса, который говорит серверу, что сделать с ресурсом по адресу: получить, создать, заменить, изменить или удалить.

### Ситуация
Ты заходишь в интернет-магазин, а там пустой белый экран. Он грузится? Сломался? Товаров нет? Непонятно — и ты уходишь. Новички показывают только «счастливый путь»: данные пришли — нарисовал. А у любых данных с сервера есть ещё три состояния, и каждое нужно честно показать пользователю.

### На пальцах
Хороший интерфейс — как вежливый продавец: «Сейчас посмотрю на складе…», «Простите, не получилось, давайте ещё раз», «Этого товара пока нет», «Вот, пожалуйста». Он никогда не молчит, глядя в одну точку.

### Как это работает
>> Загрузка → ошибка или пусто или данные → у каждого свой экран

Любые данные с сервера проходят четыре состояния:

| Состояние | Что показать |
|---|---|
| Загрузка | спиннер или скелетон — серые заглушки на месте карточек |
| Ошибка | понятный текст и кнопку «Повторить» |
| Пусто | объяснение и действие: «Задач нет — создайте первую» |
| Данные | сам список |

Удобно хранить состояние в одной переменной `status` со значениями `"loading"`, `"error"`, `"empty"`, `"ready"` и рисовать интерфейс в зависимости от неё.

Мелочи, которые делают интерфейс приятным:

- Кнопку отправки блокируй на время запроса, чтобы не было двойных заказов.
- Если загрузка быстрая, спиннер может мигать. Показывай его с задержкой 200–300 мс.
- При ошибке сохраняй введённые данные формы.

?: Почему лучше одна переменная `status`, а не три отдельных флага `isLoading`, `isError`, `isEmpty`? || С тремя флагами легко получить невозможную комбинацию: одновременно «загрузка» и «ошибка», и на экране спиннер рядом с сообщением об ошибке. Одна переменная может быть только в одном состоянии за раз.

### Пример
```js
const box = document.querySelector("#box");

function render(status, posts = []) {
  if (status === "loading") box.textContent = "Загружаю…";
  if (status === "error") box.textContent = "Не удалось загрузить.";
  if (status === "empty") box.textContent = "Постов пока нет.";
  if (status === "ready") box.textContent = posts.map(p => p.title).join(", ");
}

async function load(url) {
  render("loading");
  try {
    const r = await fetch(url);
    if (!r.ok) throw new Error(r.status);
    const posts = await r.json();
    render(posts.length ? "ready" : "empty", posts);
  } catch {
    render("error");
  }
}

load("https://jsonplaceholder.typicode.com/posts?_limit=0");
```

?! Какой текст по очереди увидит пользователь для адреса с `_limit=0`? || Сначала «Загружаю…», затем «Постов пока нет.». Сервер вернул пустой массив, ответ успешный, поэтому это не ошибка, а состояние «пусто».

### Частые ошибки
- **Только «счастливый путь»** — данные, без загрузки, ошибки и пустоты.
- **Белый экран при ошибке** вместо сообщения.
- **Кнопка не блокируется на время запроса** — пользователь нажмёт пять раз и создаст пять заказов.

### Проверь себя
?? Назови четыре состояния загрузки данных. || Загрузка, ошибка, пусто, данные.
?? Что показать пользователю при ошибке загрузки? || Понятный текст без технических деталей и кнопку «Повторить».
?? Объясни своими словами, зачем блокировать кнопку отправки на время запроса. || Чтобы пользователь не нажал её несколько раз и не отправил одинаковые заказы или заявки повторно.
