### На пальцах
Большой проект в одном файле — как кухня, где все продукты, кастрюли и инструменты свалены в одну кучу. Модули — ящики с подписями: «специи», «посуда», «ножи». `export` — «из этого ящика можно брать вот это». `import` — «возьми из ящика специй соль».

### Как это работает
- Каждый файл — отдельный модуль со своими переменными. Снаружи видно только то, что экспортировали.
- **Именованный экспорт** — сколько угодно в файле: `export function formatPrice() {}`, импорт по точному имени в фигурных скобках: `import { formatPrice } from "./utils.js"`.
- **Экспорт по умолчанию** — один на файл: `export default function App() {}`, импорт под любым именем без скобок: `import App from "./App.js"`.
- Переименовать при импорте: `import { formatPrice as fp } from ...`.
- Импорт из npm-пакетов пишется без пути: `import dayjs from "dayjs"`.
- В браузере без сборщика модули подключают так: `<script type="module" src="main.js">`, а в путях обязательно указывают расширение `.js`.

Модули выполняются один раз, даже если их импортировали из десяти мест.

### Пример
```js
// utils/format.js
export function formatPrice(value) {
  return value.toLocaleString("ru-RU") + " ₽";
}
export const VAT = 0.2;
```

```js
// api/products.js
export default async function getProducts() {
  const r = await fetch("/api/products");
  return r.json();
}
```

```js
// main.js
import getProducts from "./api/products.js";
import { formatPrice, VAT } from "./utils/format.js";

const products = await getProducts();
console.log(products.map(p => formatPrice(p.price * (1 + VAT))));
```

```html
<script type="module" src="main.js"></script>
```

### Частые ошибки
- Путать скобки: экспорт по умолчанию импортировать как `{ getProducts }` — получишь `undefined`.
- Забыть `type="module"` у тега script — ошибка «Cannot use import statement outside a module».
- Открывать страницу с модулями двойным кликом (`file://`) — браузер их заблокирует. Нужен локальный сервер (Live Server, Vite).

### Мини-задание
Разнеси код списка задач на три модуля: `storage.js` (загрузка и сохранение в localStorage), `render.js` (отрисовка) и `main.js` (обработчики событий). Подключи через `type="module"` и проверь в Live Server.

### На пальцах
npm — магазин готовых деталей для программ: календари, графики, библиотеки для дат. Вместо того чтобы вытачивать деталь самому, ты пишешь `npm install` — и деталь доставлена. `package.json` — накладная проекта: какие детали нужны и какими командами проект собирается и запускается.

### Как это работает
npm устанавливается вместе с Node.js (nodejs.org, версия LTS). Проверка: `node -v` и `npm -v` в терминале.

| Команда | Что делает |
|---|---|
| `npm init -y` | создать `package.json` |
| `npm install dayjs` | поставить пакет и записать в `dependencies` |
| `npm install -D prettier` | поставить инструмент разработки в `devDependencies` |
| `npm install` | поставить всё по списку из `package.json` |
| `npm run dev` | запустить скрипт `dev` |
| `npm uninstall dayjs` | удалить пакет |

- `dependencies` — то, что нужно приложению в работе.
- `devDependencies` — инструменты для разработки: сборщик, линтер, тесты.
- `package-lock.json` — точные версии всех пакетов. Его коммитят, чтобы у всех стояло одно и то же.
- `scripts` — короткие имена для длинных команд.

Версия `"^1.11.10"` значит: «1.11.10 или новее, но без смены первой цифры» — обновления без ломающих изменений.

### Пример
```bash
mkdir date-demo && cd date-demo
npm init -y
npm install dayjs
```

```json
{
  "name": "date-demo",
  "type": "module",
  "scripts": {
    "start": "node index.js"
  },
  "dependencies": {
    "dayjs": "^1.11.13"
  }
}
```

```js
// index.js
import dayjs from "dayjs";
console.log(dayjs().add(7, "day").format("DD.MM.YYYY"));
```

```bash
npm start
```

### Частые ошибки
- Ставить пакеты глобально (`-g`) без нужды — у коллег их не будет.
- Удалить `package-lock.json` «потому что мешает» — версии начнут различаться.
- Ставить пакет ради одной строчки кода. Каждая зависимость — чужой код, который нужно обновлять.

### Мини-задание
Создай проект, установи `dayjs`, напиши скрипт, который выводит, сколько дней осталось до Нового года. Добавь команду `start` в `scripts` и запусти через `npm start`.

### На пальцах
`node_modules` — склад со всеми деталями, которые скачал npm. Он огромный — сотни мегабайт, и его в любой момент можно собрать заново по накладной `package.json`. Возить склад с собой (класть в Git) бессмысленно. `.gitignore` — список «это не упаковывать».

### Как это работает
- После `npm install` появляется папка `node_modules` со всеми пакетами и их зависимостями. Даже маленький проект на React — это тысячи файлов.
- Её не коммитят: она тяжёлая, зависит от операционной системы и восстанавливается командой `npm install`.
- `.gitignore` — текстовый файл в корне репозитория. Каждая строка — шаблон того, что Git должен игнорировать.

Что обычно добавляют в `.gitignore`:

```text
node_modules/
dist/
.env
.env.local
*.log
.DS_Store
.vscode/
```

- `dist/` или `build/` — результат сборки, его делают заново.
- `.env` — файлы с секретами.
- `.DS_Store` — служебные файлы macOS.

Важно: `.gitignore` не действует на файлы, которые уже попали в Git. Если `node_modules` уже закоммичен, его нужно убрать из индекса: `git rm -r --cached node_modules`.

### Пример
```bash
# создать .gitignore сразу при создании проекта
echo "node_modules/" >> .gitignore
echo ".env" >> .gitignore
git add .gitignore
git commit -m "chore: добавить .gitignore"

# если node_modules уже попал в репозиторий
git rm -r --cached node_modules
git commit -m "chore: убрать node_modules из репозитория"
```

### Частые ошибки
- Закоммитить `node_modules` — репозиторий весит гигабайт, а GitHub ругается на размер.
- Добавить `.env` в `.gitignore` после того, как он уже отправлен на GitHub. Секрет утёк — ключ нужно перевыпустить.
- Игнорировать `package-lock.json`. Его как раз нужно коммитить.

### Мини-задание
Проверь свой проект через `git status`: нет ли в списке `node_modules` или `.env`. Создай правильный `.gitignore`. Затем удали папку `node_modules` и восстанови её командой `npm install`.

### На пальцах
Vite — готовая мастерская для современного фронтенда. Раньше нужно было самому собирать верстак, подключать станки и настраивать каждый винтик. Vite за одну команду даёт всё: сервер для разработки, мгновенное обновление, поддержку модулей, TypeScript и React.

### Как это работает
1. `npm create vite@latest my-app` — мастер спросит фреймворк (Vanilla, React, Vue…) и язык (JavaScript или TypeScript).
2. `cd my-app` → `npm install` → `npm run dev`.
3. Откроется адрес `http://localhost:5173`. Сохраняешь файл — страница обновляется мгновенно, часто даже без перезагрузки.

Структура проекта Vanilla:

```text
my-app/
├── index.html        ← точка входа, лежит в корне
├── package.json
├── public/           ← файлы «как есть»: favicon, robots.txt
└── src/
    ├── main.js       ← подключается из index.html
    └── style.css
```

Что умеет Vite из коробки:

- `import` из npm-пакетов прямо в браузерном коде;
- импорт CSS прямо в JS: `import "./style.css"`;
- импорт картинок: `import logo from "./logo.svg"` — получишь правильный путь;
- переменные окружения из `.env` с префиксом `VITE_`.

### Пример
```bash
npm create vite@latest todo-app -- --template vanilla
cd todo-app
npm install
npm run dev
```

```js
// src/main.js
import "./style.css";
import dayjs from "dayjs";

document.querySelector("#app").innerHTML = `
  <h1>Сегодня ${dayjs().format("DD.MM.YYYY")}</h1>
`;
```

### Частые ошибки
- Открыть `index.html` двойным кликом вместо `npm run dev` — ничего не заработает.
- Искать сайт на порту 5500 по привычке Live Server — у Vite порт 5173, его пишут в терминале.
- Закрыть терминал с запущенным `npm run dev` — сервер остановится.

### Мини-задание
Создай проект Vite с шаблоном vanilla, перенеси в него свой список задач с модулями из прошлых пунктов, установи `dayjs` и выведи дату создания у каждой задачи.

### На пальцах
`npm run dev` — репетиция: актёры играют в рабочей одежде, режиссёр сразу останавливает и поправляет. `npm run build` — премьера: всё отглажено, лишнее убрано, декорации собраны. Зрителям (пользователям) показывают только премьеру.

### Как это работает
| | `npm run dev` | `npm run build` |
|---|---|---|
| Цель | удобство разработки | скорость у пользователя |
| Результат | сервер в памяти, файлов нет | папка `dist/` с готовыми файлами |
| Код | как написан, с картами для отладки | сжат, объединён, лишнее удалено |
| Обновление | мгновенно при сохранении | заново по команде |

Что делает сборка:

- объединяет сотни модулей в несколько файлов;
- минифицирует — убирает пробелы, комментарии, сокращает имена;
- удаляет неиспользуемый код (tree-shaking);
- добавляет к именам файлов хеш (`index-a1b2c3.js`), чтобы браузер не брал старую версию из кеша.

`npm run preview` — запустить собранный `dist/` локально и проверить перед деплоем.

Папку `dist/` загружают на хостинг. Vercel, Netlify и GitHub Pages умеют сами запускать `npm run build` и брать оттуда файлы.

### Пример
```bash
npm run build
# vite v5 building for production...
# dist/index.html                  0.46 kB
# dist/assets/index-4f2a9c1b.css   1.20 kB
# dist/assets/index-8d7e6f5a.js   12.31 kB │ gzip: 4.90 kB

npm run preview
# ➜ Local: http://localhost:4173/
```

### Частые ошибки
- Деплоить исходники вместо `dist/`.
- Не проверить сборку перед деплоем: в dev всё работает, а в build ломаются пути или переменные окружения.
- Коммитить `dist/` в Git — его генерируют заново.

### Мини-задание
Собери свой проект через `npm run build`, посмотри размеры файлов в `dist/`, открой минифицированный JS и сравни с исходником. Запусти `npm run preview` и проверь, что всё работает.

### На пальцах
ESLint — внимательный редактор, который читает код и говорит: «тут переменная не используется», «тут, похоже, опечатка», «здесь забыли await». Prettier — корректор вёрстки: выравнивает отступы и кавычки, чтобы весь код выглядел одинаково. Первый ловит ошибки смысла, второй — оформление.

### Как это работает
- **ESLint** анализирует код по правилам и находит проблемы до запуска: неиспользуемые переменные, необъявленные имена, сравнение через `==`, опасные конструкции. Часть проблем умеет исправлять сам.
- **Prettier** не спорит о стиле: у него почти нет настроек. Он переписывает форматирование целиком — отступы, переносы, кавычки, точки с запятой.
- Вместе они не конфликтуют, если ESLint не пытается проверять форматирование (в современных конфигурациях так по умолчанию).

Установка в проект:

```bash
npm install -D eslint prettier
npx eslint --init          # мастер создаст eslint.config.js
```

Расширения ESLint и Prettier для VS Code подсвечивают проблемы прямо в редакторе и исправляют при сохранении. Проекты на Vite с React уже содержат настроенный ESLint.

### Пример
```json
{
  "scripts": {
    "lint": "eslint .",
    "format": "prettier --write ."
  }
}
```

```js
// ESLint подсветит:
const unused = 5;              // 'unused' is assigned a value but never used
if (count == 0) {}             // Expected '===' and instead saw '=='
console.log(usr.name);         // 'usr' is not defined — опечатка в имени
```

Файл `.prettierrc` с парой настроек:

```json
{ "singleQuote": false, "semi": true, "printWidth": 100 }
```

### Частые ошибки
- Отключать правило ESLint каждый раз, когда оно ругается, вместо того чтобы разобраться.
- Разные настройки форматирования у членов команды — каждый коммит превращается в «переформатировал весь файл».
- Не запускать линтер перед коммитом — проблемы попадают в репозиторий.

### Мини-задание
Подключи ESLint и Prettier к своему проекту на Vite, добавь скрипты `lint` и `format`. Нарочно напиши неиспользуемую переменную и сравнение через `==`, посмотри, что скажет `npm run lint`, и исправь.
