### Ситуация
Твой `app.js` разросся до 900 строк: загрузка данных, отрисовка, обработчики, форматирование цен, работа с хранилищем — всё вперемешку. Чтобы найти функцию, ты листаешь пять минут, а изменение в одном месте ломает другое. Профессиональные проекты из одного файла не состоят — их делят на модули.

### На пальцах
Большой проект в одном файле — кухня, где продукты, кастрюли и инструменты свалены в одну кучу. Модули — ящики с подписями: «специи», «посуда», «ножи». `export` — «из этого ящика можно брать вот это». `import` — «возьми из ящика специй соль».

### Как это работает
>> `export function f` в модуле → `import { f } from './m.js'` → код разложен по файлам

- Каждый файл — отдельный модуль со своими переменными. Снаружи видно только то, что экспортировали.
- **Именованный экспорт** — сколько угодно в файле: `export function formatPrice() {}`, импорт по точному имени в фигурных скобках: `import { formatPrice } from "./utils.js"`.
- **Экспорт по умолчанию** — один на файл: `export default function App() {}`, импорт под любым именем без скобок: `import App from "./App.js"`.
- Переименовать при импорте: `import { formatPrice as fp } from ...`.
- Импорт из npm-пакетов пишется без пути: `import dayjs from "dayjs"`.
- В браузере без сборщика: `<script type="module" src="main.js">`, а в путях обязательно расширение `.js`.

Модули выполняются один раз, даже если их импортировали из десяти мест.

?: Почему переменные одного модуля не видны в другом без экспорта? || Каждый модуль — своя область видимости. Это защищает от случайных конфликтов имён: две переменные `count` в разных файлах никогда не перепутаются. Наружу выходит только то, что ты осознанно отдал через `export`.

### Пример
```js
// utils/format.js
export function formatPrice(value) {
  return value.toLocaleString("ru-RU") + " ₽";
}

// api/products.js
export default async function getProducts() {
  const r = await fetch("/api/products");
  return r.json();
}

// main.js
import { getProducts } from "./api/products.js";
import { formatPrice } from "./utils/format.js";
```

?! Что окажется в `getProducts` в `main.js` и почему? || Ошибка импорта (или `undefined`, в зависимости от среды): в `products.js` функция экспортирована по умолчанию, а импортируется как именованная в фигурных скобках. Правильно: `import getProducts from "./api/products.js"`.

### Частые ошибки
- **Путаница со скобками:** экспорт по умолчанию импортируют как `{ getProducts }`.
- **Нет `type="module"`** у тега script — ошибка «Cannot use import statement outside a module».
- **Открытие страницы двойным кликом** (`file://`) — браузер заблокирует модули. Нужен локальный сервер (Live Server, Vite).

### Проверь себя
?? Чем именованный экспорт отличается от экспорта по умолчанию? || Именованных может быть много, импортируются по точному имени в `{ }`. Экспорт по умолчанию один на файл, импортируется без скобок под любым именем.
?? Что нужно добавить к тегу `script`, чтобы работали `import` и `export` в браузере? || `type="module"`.
?? Объясни своими словами, зачем делить код на модули. || Чтобы каждый файл отвечал за одну вещь: так код легче найти, понять и менять, а имена в разных файлах не конфликтуют.

### На пальцах
npm — магазин готовых деталей для программ: календари, графики, библиотеки для дат. Вместо того чтобы вытачивать деталь самому, пишешь `npm install` — и деталь доставлена. `package.json` — накладная проекта: какие детали нужны и какими командами проект собирается и запускается.

### Как это работает
>> `npm init` → `package.json` → `npm install пакет` → `npm run dev` из `scripts`

npm устанавливается вместе с Node.js (nodejs.org, версия LTS). Проверка: `node -v` и `npm -v` в терминале.

| Команда | Что делает |
|---|---|
| `npm init -y` | создать `package.json` |
| `npm install dayjs` | поставить пакет и записать в `dependencies` |
| `npm install -D prettier` | поставить инструмент разработки в `devDependencies` |
| `npm install` | поставить всё по списку из `package.json` |
| `npm run dev` | запустить скрипт `dev` |
| `npm uninstall dayjs` | удалить пакет |

- `dependencies` — то, что нужно приложению в работе.
- `devDependencies` — инструменты для разработки: сборщик, линтер, тесты.
- `package-lock.json` — точные версии всех пакетов. Его коммитят, чтобы у всех стояло одно и то же.
- `scripts` — короткие имена для длинных команд.

Версия `"^1.11.10"` значит: «1.11.10 или новее, но без смены первой цифры».

?: Зачем коммитить `package-lock.json`, если в `package.json` уже есть список пакетов? || В `package.json` указан диапазон версий (`^1.11.10`), и через месяц `npm install` может поставить другую версию — у тебя одна, у коллеги другая, на сервере третья. Lock-файл фиксирует точные версии всего дерева зависимостей, и у всех стоит одно и то же.

### Пример
```json

    "start": "node index.js",
    "dev": "node --watch index.js"
  },
  "dependencies": {
    "dayjs": "^1.11.13"
  }
}
```

?! Какой командой запустить скрипт `dev` и почему для `start` подходит более короткая форма? || `npm run dev`. Для нескольких стандартных имён, включая `start` и `test`, npm разрешает писать без `run`: `npm start`. Для остальных скриптов `run` обязателен.

- **Глобальная установка (`-g`) без нужды** — у коллег этих пакетов не будет.

### На пальцах
`node_modules` — склад со всеми деталями, которые скачал npm. Он огромный — сотни мегабайт — и его в любой момент можно собрать заново по накладной `package.json`. Возить склад с собой (класть в Git) бессмысленно. `.gitignore` — список «это не упаковывать».

### Как это работает
>> `npm install` → `node_modules` → `.gitignore` → в Git только `package.json` и lock

- После `npm install` появляется папка `node_modules` со всеми пакетами и их зависимостями. Даже маленький проект на React — тысячи файлов.
- Её не коммитят: она тяжёлая, зависит от операционной системы и восстанавливается командой `npm install`.
- `.gitignore` — текстовый файл в корне репозитория. Каждая строка — шаблон того, что Git должен игнорировать.

Что обычно добавляют в `.gitignore`:

```text
node_modules/
dist/
.env
.env.local
*.log
.DS_Store
```

- `dist/` или `build/` — результат сборки, его делают заново.
- `.env` — файлы с секретами.
- `.DS_Store` — служебные файлы macOS.

?: Почему `.gitignore` не помогает, если файл уже был закоммичен? || `.gitignore` говорит Git только «не начинай следить за такими файлами». За файлами, которые уже в истории, Git продолжает следить. Их нужно явно убрать из индекса: `git rm -r --cached node_modules`.

### Пример
```bash
git init
npm install dayjs
git add .
git commit -m "start"
echo "node_modules/" >> .gitignore
git status
```

?! Пропадёт ли `node_modules` из репозитория после добавления строчки в `.gitignore`? || Нет. Папка уже попала в первый коммит, и Git продолжит её отслеживать. Нужно `git rm -r --cached node_modules` и новый коммит. А правильнее — создать `.gitignore` до первого `git add`.

### Частые ошибки
- **Закоммиченный `node_modules`** — репозиторий весит гигабайт.
- **`.env` в `.gitignore` после отправки на GitHub.** Секрет уже утёк — ключ нужно перевыпустить, а не просто удалить файл.
- **Игнорировать `package-lock.json`.** Его как раз нужно коммитить.

### Проверь себя
?? Почему папку `node_modules` не кладут в Git? || Она огромная, зависит от системы и полностью восстанавливается командой `npm install` по `package.json`.
?? Как убрать из Git папку, которая уже была закоммичена? || `git rm -r --cached имя_папки`, добавить её в `.gitignore` и сделать коммит.
?? Объясни своими словами, что делать, если `.env` с ключом попал на GitHub. || Считать ключ скомпрометированным: перевыпустить его в сервисе, а потом убрать файл из репозитория и добавить в `.gitignore`.

Что умеет Vite из коробки:

- `import` из npm-пакетов прямо в браузерном коде;

### Ситуация
В режиме разработки твой сайт — это сотни отдельных модулей с комментариями и пробелами. У пользователя на мобильном интернете он бы грузился полминуты. Перед публикацией код «упаковывают»: сжимают, склеивают, выкидывают лишнее. И именно на этом шаге всплывают ошибки, которых в разработке не было.

### На пальцах
`npm run dev` — репетиция: актёры играют в рабочей одежде, режиссёр сразу останавливает и поправляет. `npm run build` — премьера: всё отглажено, лишнее убрано, декорации собраны. Зрителям (пользователям) показывают только премьеру.

### Как это работает
>> `npm run dev` — быстрый сервер → правки сразу → `npm run build` → оптимизированная папка `dist`

| | `npm run dev` | `npm run build` |
|---|---|---|
| Цель | удобство разработки | скорость у пользователя |
| Результат | сервер в памяти, файлов нет | папка `dist/` с готовыми файлами |
| Код | как написан, с картами для отладки | сжат, объединён, лишнее удалено |
| Обновление | мгновенно при сохранении | заново по команде |

Что делает сборка:

- объединяет сотни модулей в несколько файлов;
- минифицирует — убирает пробелы, комментарии, сокращает имена;
- удаляет неиспользуемый код (tree-shaking);
- добавляет к именам файлов хеш (`index-a1b2c3.js`), чтобы браузер не брал старую версию из кеша.

`npm run preview` — запустить собранный `dist/` локально и проверить перед деплоем.

?: Зачем к именам собранных файлов добавляют хеш вроде `index-a1b2c3.js`? || Браузеры надолго кешируют JS и CSS. Если имя файла не меняется, после обновления сайта пользователь получит старую версию из кеша. Хеш зависит от содержимого: изменился код — изменилось имя, и браузер скачает свежий файл.

### Пример
```bash
npm run build
# dist/index.html                  0.46 kB
# dist/assets/index-4f2a9c1b.css   1.20 kB
# dist/assets/index-8d7e6f5a.js   12.31 kB │ gzip: 4.90 kB

npm run preview
```

?! Ты поменял одну строку в `main.js` и снова запустил `npm run build`. Какое из имён файлов изменится? || Имя JS-файла: хеш `8d7e6f5a` станет другим, потому что изменилось содержимое. Имя CSS-файла останется прежним, если стили не менялись.

### Частые ошибки
- **Деплой исходников** вместо `dist/`.
- **Нет проверки сборки перед деплоем:** в dev всё работает, а в build ломаются пути или переменные окружения. Для этого и нужен `npm run preview`.
- **`dist/` в Git** — его генерируют заново.

### Проверь себя
?? Что появляется после `npm run build`? || Папка `dist/` с готовыми, сжатыми и объединёнными файлами для публикации.
?? Как проверить собранную версию локально перед деплоем? || `npm run preview`.
?? Объясни своими словами разницу между `npm run dev` и `npm run build`. || `dev` запускает удобный сервер для разработки с мгновенным обновлением. `build` готовит оптимизированные файлы для реальных пользователей.

### Ситуация
Ты час ищешь, почему не работает фильтр, а оказывается — опечатка: `usr` вместо `user`. В команде из пяти человек каждый ставит отступы по-своему, и каждый коммит выглядит как «переписал весь файл». Обе проблемы решают два инструмента, которые работают прямо в редакторе — пока ты печатаешь.

### На пальцах
ESLint — внимательный редактор, который читает код и говорит: «тут переменная не используется», «тут, похоже, опечатка», «здесь забыли await». Prettier — корректор вёрстки: выравнивает отступы и кавычки, чтобы весь код выглядел одинаково. Первый ловит ошибки смысла, второй — оформление.

### Как это работает
>> Пишешь код → ESLint находит ошибки → Prettier выравнивает → сохранение — и чисто

- **ESLint** анализирует код по правилам и находит проблемы до запуска: неиспользуемые переменные, необъявленные имена, сравнение через `==`, опасные конструкции. Часть проблем исправляет сам.
- **Prettier** почти не имеет настроек: переписывает форматирование целиком — отступы, переносы, кавычки, точки с запятой.
- Вместе они не конфликтуют, если ESLint не проверяет форматирование (в современных конфигурациях так по умолчанию).

```bash
npm install -D eslint prettier

```

Расширения ESLint и Prettier для VS Code подсвечивают проблемы в редакторе и исправляют при сохранении. Проекты на Vite с React уже содержат настроенный ESLint.

?: Почему у Prettier так мало настроек — разве это не минус? || Это сделано специально, чтобы закончить споры о стиле. Когда настраивать почти нечего, команда не тратит время на обсуждение кавычек и отступов, а весь код автоматически выглядит одинаково.

### Пример
```json
{
  "scripts": {
    "lint": "eslint .",
    "format": "prettier --write ."
  }
}
```

```js
const unused = 5;
if (count == 0) {}
console.log(usr.name);
```

?! Какие три проблемы подсветит ESLint в этом коде? || `unused` объявлена, но не используется. `==` вместо `===` (если включено правило eqeqeq). `usr` не объявлена — скорее всего, опечатка в `user`.

### Частые ошибки
- **Отключать правило каждый раз**, когда ESLint ругается, вместо того чтобы разобраться.
- **Разные настройки форматирования** у членов команды — каждый коммит превращается в «переформатировал весь файл».
- **Линтер не запускается перед коммитом** — проблемы попадают в репозиторий.

### Проверь себя
?? Чем ESLint отличается от Prettier? || ESLint ищет ошибки и опасные места в логике кода. Prettier только приводит форматирование к единому виду.
?? Как ESLint помогает поймать опечатку в имени переменной? || Он сообщает, что переменная не объявлена (`is not defined`), ещё до запуска программы.
?? Объясни своими словами, зачем команде единый форматтер. || Чтобы весь код выглядел одинаково, а в истории изменений были видны реальные правки, а не перестановка пробелов и кавычек.

### Мини-задание
Подключи ESLint и Prettier к своему проекту на Vite, добавь скрипты `lint` и `format`. Нарочно напиши неиспользуемую переменную и сравнение через `==`, посмотри, что скажет `npm run lint`, и исправь.
