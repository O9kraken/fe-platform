### На пальцах
`CREATE TABLE` — нарисовать бланк с графами и правилами заполнения. `NOT NULL` — «графа обязательна». `DEFAULT` — «если не заполнили, пишем вот это». `UNIQUE` — «такое значение может быть только у одной строки». `CHECK` — «значение должно удовлетворять условию». Правила в самой базе — последний рубеж: даже если в коде ошибка, мусор в таблицу не попадёт.

### Как это работает
```sql
CREATE TABLE имя (
  колонка тип ограничения,
  ...
);
```

| Ограничение | Пример | Значение |
|---|---|---|
| `PRIMARY KEY` | `id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY` | уникальный идентификатор |
| `NOT NULL` | `title text NOT NULL` | обязательное поле |
| `DEFAULT` | `status text NOT NULL DEFAULT 'new'` | значение по умолчанию |
| `UNIQUE` | `email text UNIQUE` | без повторов |
| `CHECK` | `CHECK (budget >= 0)` | условие |
| `REFERENCES` | `client_id integer REFERENCES clients(id)` | внешний ключ |

- Изменить таблицу: `ALTER TABLE ... ADD COLUMN`, `DROP COLUMN`, `ADD CONSTRAINT`.
- Удалить: `DROP TABLE` — навсегда, вместе с данными.

### Как это работает
```sql
client_id integer NOT NULL REFERENCES clients(id) ON DELETE CASCADE
```

| Правило | Что происходит при удалении клиента |
|---|---|
| `NO ACTION` / `RESTRICT` (по умолчанию) | удалить нельзя, пока есть проекты — ошибка |
| `CASCADE` | проекты удалятся вместе с клиентом |
| `SET NULL` | у проектов `client_id` станет `NULL` (колонка должна разрешать NULL) |
| `SET DEFAULT` | подставится значение по умолчанию |

Как выбирать:

- **CASCADE** — когда дочерние записи не имеют смысла без родителя: задачи проекта, позиции заказа, комментарии к посту.
- **RESTRICT** — когда удаление родителя должно быть осознанным: клиент с оплаченными проектами, категория с товарами.
- **SET NULL** — когда связь необязательная: задача без исполнителя после удаления сотрудника.

Часто вместо физического удаления используют «мягкое»: колонка `deleted_at` — запись прячется, но остаётся для истории и отчётов.

### На пальцах
Один-ко-многим — мама и дети: у мамы много детей, у ребёнка одна мама. Ссылка хранится у ребёнка: «моя мама — № 3». Многие-ко-многим — ученики и кружки: ученик ходит в несколько кружков, в кружке много учеников. Тут нужна отдельная тетрадь записи «кто в какой кружок записан» — связующая таблица.

### Как это работает
**Один-ко-многим** (самая частая связь):

- клиент → проекты, проект → задачи, пользователь → заказы;
- внешний ключ в таблице «многих»: `projects.client_id`.

**Многие-ко-многим**:

- проекты ↔ сотрудники, статьи ↔ теги, студенты ↔ курсы;
- создаётся связующая таблица с двумя внешними ключами;
- первичный ключ — пара этих колонок, чтобы одну и ту же связь нельзя было добавить дважды;
- в связующую таблицу можно положить данные о самой связи: роль сотрудника в проекте, дату записи на курс.

**Один-к-одному** — редкий случай: пользователь и его профиль. Внешний ключ с `UNIQUE`.

- одни и те же данные повторяются в разных строках (имя и телефон клиента в каждом проекте);

### На пальцах
Индекс — алфавитный указатель в конце толстой книги. Без него, чтобы найти упоминания слова «транзакция», нужно пролистать все 800 страниц. С ним — открыть указатель на букву «Т» и сразу перейти на нужные страницы. Но указатель нужно обновлять при каждой правке книги, и он занимает место.

### Как это работает
- `CREATE INDEX имя ON таблица (колонка)` — создать индекс (обычно B-дерево).
- Первичный ключ и `UNIQUE` создают индекс автоматически.
- Индекс ускоряет: поиск по `=`, диапазоны (`>`, `BETWEEN`), `ORDER BY` по индексированной колонке, `JOIN` по внешнему ключу.
- Составной индекс `(client_id, created_at)` работает для запросов по `client_id` и по `client_id + created_at`, но не по одному `created_at`. Порядок колонок важен.

Когда индекс не поможет:

- `LIKE '%слово%'` — шаблон начинается с `%`;
- функция над колонкой: `WHERE lower(email) = ...` (нужен индекс по выражению `lower(email)`);
- маленькие таблицы — перебор быстрее;
- колонки с двумя-тремя значениями (например, `boolean`) — индекс почти бесполезен.

Цена индексов: каждый `INSERT`, `UPDATE`, `DELETE` обновляет все индексы таблицы; они занимают место на диске.

Что индексировать в первую очередь: внешние ключи (PostgreSQL не делает это сам), колонки частых фильтров и сортировок, поля для поиска (email, slug).

?: Почему составной индекс `(client_id, created_at)` не помогает при поиске только по `created_at`? || Индекс отсортирован сначала по `client_id`, а уже внутри каждого клиента — по дате. Как телефонная книга, отсортированная по фамилии, а потом по имени: найти всех «Анн» без фамилии можно только перебором всей книги.

### Пример
```sql
CREATE INDEX payments_project_date_idx ON payments (project_id, paid_at);

SELECT * FROM payments WHERE project_id = 3 AND paid_at >= '2026-07-01';
SELECT * FROM payments WHERE paid_at >= '2026-07-01';
SELECT * FROM users WHERE lower(email) = 'anna@mail.ru';
```

?! Какие из трёх запросов смогут использовать индексы, если на `users` есть только обычный индекс по `email`? || Первый — да, составной индекс подходит полностью. Второй — нет, фильтр только по второй колонке индекса. Третий — нет: функция `lower()` над колонкой мешает обычному индексу, нужен индекс по выражению `lower(email)`.

### Частые ошибки
- **Индекс на каждую колонку «на всякий случай».**
- **Нет индексов на внешние ключи** — `JOIN` и удаление родителя медленные.

### Ситуация
Клиент оплатил проект. Сервер записывает платёж и затем меняет статус проекта на «в работе». Между этими двумя запросами сервер перезапустился. Итог: платёж есть, а проект по-прежнему «ждёт оплаты», менеджер звонит клиенту с напоминанием, клиент в ярости. Связанные изменения должны происходить вместе — или не происходить вовсе.

### На пальцах
Перевод денег — две операции: списать у Ани и зачислить Борису. Если после списания свет погас, деньги не должны исчезнуть. Транзакция — «всё или ничего»: либо обе операции произошли, либо ни одной. `BEGIN` — начать, `COMMIT` — подтвердить, `ROLLBACK` — отменить всё, будто ничего не было.

### Как это работает
```sql
BEGIN;
  ...несколько команд...
COMMIT;      -- или ROLLBACK;
```

Свойства транзакций (ACID):

- **Atomicity** — атомарность: всё или ничего.
- **Consistency** — согласованность: после транзакции все ограничения (`CHECK`, внешние ключи) соблюдены.
- **Isolation** — изоляция: параллельные транзакции не видят «полуготовые» изменения друг друга.
- **Durability** — надёжность: подтверждённое не пропадёт даже при сбое.

Если внутри транзакции произошла ошибка, в PostgreSQL вся транзакция помечается как неудачная, и её нужно откатить.

Конкурентный доступ: если два запроса одновременно меняют одну строку (последний билет на концерт), используют `SELECT ... FOR UPDATE` или атомарные обновления вида `UPDATE ... SET stock = stock - 1 WHERE stock > 0`.

?: Почему проверка «есть ли товар» и списание двумя отдельными запросами — ошибка? || Между проверкой и списанием другой покупатель может успеть купить последний товар. Оба увидят «остаток 1», оба спишут — и остаток станет −1. Атомарный `UPDATE ... WHERE stock > 0` проверяет и меняет за один шаг.

### Пример
```sql
-- на счету Ани 1000, у Бориса 0; CHECK (balance >= 0)
BEGIN;
UPDATE accounts SET balance = balance + 1500 WHERE owner = 'Борис';
UPDATE accounts SET balance = balance - 1500 WHERE owner = 'Аня';
COMMIT;
```

?! Чем закончится перевод 1500 рублей и сколько денег будет у каждого после? || Второй `UPDATE` нарушит `CHECK`: у Ани стало бы −500. Транзакция станет неудачной, `COMMIT` превратится в откат — и первое начисление Борису тоже отменится. У Ани 1000, у Бориса 0, как до начала.

### Частые ошибки
- **Связанные изменения отдельными запросами** без транзакции.
- **Долгая транзакция** (например, ожидание внешнего API внутри) — блокируются строки для других.
- **Проверка остатка и списание двумя запросами** — гонка за последний товар.
