### На пальцах
`CREATE TABLE` — нарисовать бланк с графами и правилами заполнения. `NOT NULL` — «графа обязательна». `DEFAULT` — «если не заполнили, пишем вот это». `UNIQUE` — «такое значение может быть только у одной строки». `CHECK` — «значение должно удовлетворять условию». Правила в самой базе — последний рубеж: даже если в коде ошибка, мусор в таблицу не попадёт.

### Как это работает
```sql
CREATE TABLE имя (
  колонка тип ограничения,
  ...
);
```

| Ограничение | Пример | Значение |
|---|---|---|
| `PRIMARY KEY` | `id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY` | уникальный идентификатор |
| `NOT NULL` | `title text NOT NULL` | обязательное поле |
| `DEFAULT` | `status text NOT NULL DEFAULT 'new'` | значение по умолчанию |
| `UNIQUE` | `email text UNIQUE` | без повторов |
| `CHECK` | `CHECK (budget >= 0)` | условие |
| `REFERENCES` | `client_id integer REFERENCES clients(id)` | внешний ключ |

- `created_at timestamptz NOT NULL DEFAULT now()` — время создания проставится само.
- Список допустимых значений: `CHECK (status IN ('new', 'active', 'done'))`.
- Изменить таблицу: `ALTER TABLE ... ADD COLUMN`, `DROP COLUMN`, `ADD CONSTRAINT`.
- Удалить: `DROP TABLE` — навсегда, вместе с данными.

### Пример
```sql
CREATE TABLE clients (
  id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text NOT NULL CHECK (length(name) BETWEEN 2 AND 100),
  email      text UNIQUE,
  city       text,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE projects (
  id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  client_id  integer NOT NULL REFERENCES clients(id),
  title      text NOT NULL,
  budget     integer CHECK (budget >= 0),
  status     text NOT NULL DEFAULT 'new' CHECK (status IN ('new', 'active', 'paused', 'done')),
  created_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO clients (name, email) VALUES ('Кофейня «Зерно»', 'zerno@mail.ru');
INSERT INTO projects (client_id, title, budget) VALUES (1, 'Лендинг', 45000);  -- status = 'new' сам
INSERT INTO projects (client_id, title, budget) VALUES (1, 'Сайт', -5);       -- ❌ нарушен CHECK
```

### Частые ошибки
- Все колонки без `NOT NULL` — в таблице появляются «полупустые» строки.
- Проверять допустимые значения только в коде приложения.
- `DROP TABLE` на боевой базе «чтобы пересоздать».

### На пальцах
Внешний ключ — нитка, связывающая две карточки: проект привязан к клиенту. Что делать с проектами, если клиента удалили? Варианты, как с вещами уехавшего соседа: запретить удаление, пока вещи на месте (`RESTRICT`); выбросить вещи вместе с ним (`CASCADE`); оставить вещи, но стереть имя хозяина (`SET NULL`).

### Как это работает
```sql
client_id integer NOT NULL REFERENCES clients(id) ON DELETE CASCADE
```

| Правило | Что происходит при удалении клиента |
|---|---|
| `NO ACTION` / `RESTRICT` (по умолчанию) | удалить нельзя, пока есть проекты — ошибка |
| `CASCADE` | проекты удалятся вместе с клиентом |
| `SET NULL` | у проектов `client_id` станет `NULL` (колонка должна разрешать NULL) |
| `SET DEFAULT` | подставится значение по умолчанию |

Аналогично `ON UPDATE` — при изменении первичного ключа (на практике id не меняют).

Как выбирать:

- **CASCADE** — когда дочерние записи не имеют смысла без родителя: задачи проекта, позиции заказа, комментарии к посту.
- **RESTRICT** — когда удаление родителя должно быть осознанным: клиент с оплаченными проектами, категория с товарами.
- **SET NULL** — когда связь необязательная: задача без исполнителя после удаления сотрудника.

Часто вместо физического удаления используют «мягкое»: колонка `deleted_at` — запись прячется, но остаётся для истории и отчётов.

### Пример
```sql
CREATE TABLE tasks (
  id          integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  project_id  integer NOT NULL REFERENCES projects(id) ON DELETE CASCADE,   -- без проекта задач нет
  assignee_id integer REFERENCES users(id) ON DELETE SET NULL,              -- сотрудник ушёл — задача осталась
  title       text NOT NULL
);

CREATE TABLE payments (
  id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  project_id integer NOT NULL REFERENCES projects(id) ON DELETE RESTRICT,   -- проект с платежами не удалить
  amount     integer NOT NULL CHECK (amount > 0)
);

DELETE FROM projects WHERE id = 1;
-- если есть платежи: ❌ update or delete on table "projects" violates foreign key constraint
-- если только задачи: задачи удалятся вместе с проектом
```

### Частые ошибки
- `CASCADE` везде — одно неосторожное удаление клиента стирает проекты, платежи и историю.
- `SET NULL` на колонке с `NOT NULL` — ошибка при удалении.
- Не думать о правиле вообще и удивляться ошибке при удалении.

### На пальцах
Один-ко-многим — мама и дети: у мамы много детей, у ребёнка одна мама. Ссылка хранится у ребёнка: «моя мама — № 3». Многие-ко-многим — ученики и кружки: ученик ходит в несколько кружков, в кружке много учеников. Тут нужна отдельная тетрадь записи «кто в какой кружок записан» — связующая таблица.

### Как это работает
**Один-ко-многим** (самая частая связь):

- клиент → проекты, проект → задачи, пользователь → заказы;
- внешний ключ в таблице «многих»: `projects.client_id`.

**Многие-ко-многим**:

- проекты ↔ сотрудники, статьи ↔ теги, студенты ↔ курсы;
- создаётся связующая таблица с двумя внешними ключами;
- первичный ключ — пара этих колонок, чтобы одну и ту же связь нельзя было добавить дважды;
- в связующую таблицу можно положить данные о самой связи: роль сотрудника в проекте, дату записи на курс.

**Один-к-одному** — редкий случай: пользователь и его профиль. Внешний ключ с `UNIQUE`.

### Пример
```sql
CREATE TABLE employees (
  id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL
);

-- многие-ко-многим: кто работает над каким проектом и в какой роли
CREATE TABLE project_members (
  project_id  integer REFERENCES projects(id) ON DELETE CASCADE,
  employee_id integer REFERENCES employees(id) ON DELETE CASCADE,
  role        text NOT NULL DEFAULT 'developer',
  PRIMARY KEY (project_id, employee_id)
);

INSERT INTO project_members (project_id, employee_id, role) VALUES (1, 1, 'designer'), (1, 2, 'developer'), (2, 2, 'lead');

-- команда проекта 1
SELECT e.name, pm.role
FROM project_members pm
JOIN employees e ON e.id = pm.employee_id
WHERE pm.project_id = 1;

-- проекты сотрудника 2
SELECT p.title, pm.role
FROM project_members pm
JOIN projects p ON p.id = pm.project_id
WHERE pm.employee_id = 2;
```

### Частые ошибки
- Хранить список id через запятую в одной колонке: `members = '1,2,5'` — по нему невозможно нормально искать и соединять.
- Связующая таблица без составного первичного ключа — одну связь добавляют дважды.
- Делать многие-ко-многим там, где на самом деле один-ко-многим.

### На пальцах
Нормализация — правило «каждый факт записан ровно в одном месте». Если адрес клиента записан в каждом его заказе, то при переезде клиента придётся исправлять сотню заказов — и где-нибудь обязательно забудешь. Лучше записать адрес один раз в карточке клиента, а заказы будут на неё ссылаться.

### Как это работает
Признаки, что схему нужно нормализовать:

- одни и те же данные повторяются в разных строках (имя и телефон клиента в каждом проекте);
- в одной ячейке несколько значений через запятую;
- колонки с номерами: `phone1`, `phone2`, `phone3`;
- при изменении одного факта приходится обновлять много строк.

Что делать:

1. Повторяющиеся данные — в отдельную таблицу, ссылаться по id.
2. Несколько значений — в отдельную таблицу «один-ко-многим».
3. Нумерованные колонки — тоже в отдельную таблицу.

Здравый смысл важнее теории. Иногда данные сознательно дублируют (денормализуют):

- **снимок на момент события**: цена товара в заказе хранится в самом заказе — если цена в каталоге изменится, старые заказы не должны поменяться;
- **ради скорости**: счётчик комментариев у поста, чтобы не считать их при каждом показе (но тогда нужно аккуратно его обновлять).

### Пример
Плохо — одна большая таблица:

```text
orders: id | client_name | client_phone | client_city | items                 | total
        1  | Анна        | +7999...     | Москва      | "Чай x2, Кофе x1"     | 1050
        2  | Анна        | +7999...     | Москва      | "Кофе x3"             | 1350
```

Хорошо — нормализованная схема:

```sql
CREATE TABLE clients (id integer PRIMARY KEY, name text NOT NULL, phone text, city text);
CREATE TABLE products (id integer PRIMARY KEY, title text NOT NULL, price integer NOT NULL);
CREATE TABLE orders (id integer PRIMARY KEY, client_id integer REFERENCES clients(id), created_at timestamptz DEFAULT now());
CREATE TABLE order_items (
  order_id   integer REFERENCES orders(id) ON DELETE CASCADE,
  product_id integer REFERENCES products(id),
  qty        integer NOT NULL CHECK (qty > 0),
  price      integer NOT NULL,          -- снимок цены на момент заказа — осознанное дублирование
  PRIMARY KEY (order_id, product_id)
);
```

### Частые ошибки
- Хранить список товаров заказа текстом.
- Не хранить цену в позиции заказа и пересчитывать старые заказы по новым ценам.
- Нормализовать до абсурда: отдельная таблица для каждого поля.

### На пальцах
Индекс — алфавитный указатель в конце толстой книги. Без него, чтобы найти упоминания слова «транзакция», нужно пролистать все 800 страниц. С ним — открыть указатель на букву «Т» и сразу перейти на нужные страницы. Но указатель нужно обновлять при каждой правке книги, и он занимает место.

### Как это работает
- `CREATE INDEX имя ON таблица (колонка)` — создать индекс (обычно B-дерево).
- Первичный ключ и `UNIQUE` создают индекс автоматически.
- Индекс ускоряет: поиск по `=`, диапазоны (`>`, `BETWEEN`), `ORDER BY` по индексированной колонке, `JOIN` по внешнему ключу.
- Составной индекс `(client_id, created_at)` работает для запросов по `client_id` и по `client_id + created_at`, но не по одному `created_at`. Порядок колонок важен.

Когда индекс не поможет:

- `LIKE '%слово%'` — шаблон начинается с `%`;
- функция над колонкой: `WHERE lower(email) = ...` (нужен индекс по выражению `lower(email)`);
- маленькие таблицы — перебор быстрее;
- колонки с двумя-тремя значениями (например, `boolean`) — индекс почти бесполезен.

Цена индексов:

- каждый `INSERT`, `UPDATE`, `DELETE` обновляет все индексы таблицы — запись медленнее;
- занимают место на диске.

Что индексировать в первую очередь: внешние ключи (PostgreSQL не делает это сам), колонки частых фильтров и сортировок, поля для поиска (email, slug).

### Пример
```sql
-- внешние ключи — почти всегда
CREATE INDEX projects_client_id_idx ON projects (client_id);
CREATE INDEX payments_project_id_idx ON payments (project_id);

-- уникальный поиск без учёта регистра
CREATE UNIQUE INDEX users_email_lower_idx ON users (lower(email));
SELECT * FROM users WHERE lower(email) = lower('Anna@Mail.ru');   -- использует индекс

-- частый запрос: платежи проекта за период, по дате
CREATE INDEX payments_project_date_idx ON payments (project_id, paid_at);
SELECT * FROM payments WHERE project_id = 3 AND paid_at >= '2026-07-01' ORDER BY paid_at;
```

### Частые ошибки
- Индекс на каждую колонку «на всякий случай».
- Забыть индексы на внешние ключи — `JOIN` и удаление родителя медленные.
- Неправильный порядок колонок в составном индексе.

### На пальцах
Перевод денег — две операции: списать у Ани и зачислить Борису. Если после списания свет погас, деньги не должны исчезнуть. Транзакция — «всё или ничего»: либо обе операции произошли, либо ни одной. `BEGIN` — начать, `COMMIT` — подтвердить, `ROLLBACK` — отменить всё, будто ничего не было.

### Как это работает
```sql
BEGIN;
  ...несколько команд...
COMMIT;      -- или ROLLBACK;
```

Свойства транзакций (ACID):

- **Atomicity** — атомарность: всё или ничего.
- **Consistency** — согласованность: после транзакции все ограничения (`CHECK`, внешние ключи) соблюдены.
- **Isolation** — изоляция: параллельные транзакции не видят «полуготовые» изменения друг друга.
- **Durability** — надёжность: подтверждённое не пропадёт даже при сбое.

Если внутри транзакции произошла ошибка, в PostgreSQL вся транзакция помечается как неудачная, и её нужно откатить.

Когда нужна транзакция: всякий раз, когда несколько изменений должны произойти вместе — заказ и его позиции, перевод денег, создание пользователя и его профиля, списание остатка и создание брони.

Конкурентный доступ: если два запроса одновременно меняют одну строку (последний билет на концерт), используют блокировку `SELECT ... FOR UPDATE` или атомарные обновления вида `UPDATE ... SET stock = stock - 1 WHERE stock > 0`.

### Пример
```sql
-- оплата проекта: записать платёж и перевести проект в работу
BEGIN;
INSERT INTO payments (project_id, amount, paid_at) VALUES (3, 40000, '2026-10-24');
UPDATE projects SET status = 'active' WHERE id = 3;
COMMIT;

-- передумали посередине
BEGIN;
DELETE FROM payments WHERE project_id = 3;
ROLLBACK;                       -- платежи на месте

-- атомарное списание остатка без гонок
UPDATE products SET stock = stock - 1 WHERE id = 7 AND stock > 0;
-- если обновилось 0 строк — товар закончился
```

### Частые ошибки
- Выполнять связанные изменения отдельными запросами без транзакции.
- Открыть транзакцию и долго держать её (например, ждать ответа внешнего API внутри) — блокируются строки для других.
- Проверка «есть ли остаток» и списание двумя запросами — между ними кто-то успеет купить последний товар.
