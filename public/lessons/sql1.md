### На пальцах
База данных — шкаф с таблицами, как в Excel, только строже. Таблица — один лист: «Клиенты». Колонка — графа: «Имя», «Город». Строка — одна запись: конкретный клиент. Тип данных — правило для графы: в «Бюджет» можно писать только числа, а в «Дату» — только даты. Excel простит что угодно, база — нет, и в этом её сила.

### Как это работает
В курсе используется учебная база студии из трёх таблиц:

| Таблица | Колонки |
|---|---|
| `clients` | `id`, `name`, `city`, `created_at` |
| `projects` | `id`, `client_id`, `title`, `type`, `budget`, `status` |
| `payments` | `id`, `project_id`, `amount`, `paid_at` |

Основные типы в PostgreSQL:

| Тип | Что хранит |
|---|---|
| `integer`, `bigint` | целые числа |
| `numeric(12,2)` | точные дробные — деньги |
| `text`, `varchar(100)` | строки |
| `boolean` | `true` / `false` |
| `date`, `timestamptz` | дата, дата и время с часовым поясом |
| `uuid` | уникальный идентификатор |
| `jsonb` | JSON-документ |

- У каждой таблицы есть первичный ключ — колонка `id`, уникальная для каждой строки.
- `NULL` — «значение неизвестно». Это не ноль и не пустая строка.
- SQL — язык запросов к базе. Ключевые слова принято писать заглавными: `SELECT`, `FROM`, `WHERE` — так проще читать, но база понимает и строчные.

В «Песочнице» этого курса есть режим SQL с этой базой — все примеры можно запускать.

### Пример
```sql
-- что лежит в таблицах
SELECT * FROM clients;
SELECT * FROM projects;
SELECT * FROM payments;
```

### Частые ошибки
- Хранить деньги в `real`/`float` — копейки «уплывают». Используй `numeric` или целые копейки.
- Хранить дату строкой «15.01.2026» — по ней нельзя нормально сортировать и считать.
- Путать `NULL` с нулём: проект без бюджета и проект с бюджетом 0 — разные вещи.

### На пальцах
`SELECT ... FROM` — просьба архивариусу: «Принесите из шкафа "Проекты" графы "Название" и "Бюджет"». Звёздочка `*` — «принесите все графы». `AS` — наклейка с новым названием на графу в ответе: «назовите это "Сумма со скидкой"».

### Как это работает
```sql
SELECT колонки FROM таблица;
```

- `SELECT *` — все колонки. Удобно для просмотра, но в коде приложения перечисляй нужные: меньше данных и понятнее.
- Колонки через запятую: `SELECT title, budget FROM projects`.
- `AS` — псевдоним для колонки в ответе: `budget AS "Бюджет"`. Двойные кавычки — если в имени пробелы или русские буквы.
- Псевдоним для таблицы — короткое имя, удобно в длинных запросах: `FROM projects AS p` или просто `FROM projects p`, дальше `p.title`.
- Можно выбирать выражения: `budget * 1.2`, `upper(title)`, `'текст'`.
- Строки — в одинарных кавычках: `'Москва'`. Двойные — для имён колонок.

### Пример
```sql
SELECT title, budget FROM projects;

SELECT
  p.title  AS "Проект",
  p.budget AS "Бюджет",
  p.budget * 1.2 AS "С НДС"
FROM projects AS p;

SELECT name, city, 'клиент' AS role FROM clients;
```

### Частые ошибки
- Двойные кавычки для строк: `WHERE city = "Москва"` — PostgreSQL решит, что это имя колонки.
- Запятая после последней колонки перед `FROM`.
- `SELECT *` в коде приложения — при добавлении колонки в таблицу запрос начнёт возвращать лишнее.

### На пальцах
`WHERE` — фильтр, как в интернет-магазине: «только город Москва», «цена от 50 до 100 тысяч», «название начинается на "Сайт"», «без указанного бюджета». База перебирает строки и оставляет те, для которых условие истинно.

### Как это работает
| Оператор | Пример | Значение |
|---|---|---|
| `=`, `<>` | `status = 'done'` | равно, не равно |
| `>`, `<`, `>=`, `<=` | `budget >= 100000` | сравнение |
| `IN (...)` | `city IN ('Москва', 'Казань')` | одно из списка |
| `BETWEEN a AND b` | `budget BETWEEN 50000 AND 100000` | диапазон включительно |
| `LIKE` | `title LIKE 'Сайт%'` | по шаблону: `%` — любые символы, `_` — один символ |
| `ILIKE` | `title ILIKE '%кофе%'` | то же без учёта регистра (PostgreSQL) |
| `IS NULL`, `IS NOT NULL` | `budget IS NULL` | значение отсутствует |

Условия объединяют через `AND`, `OR`, `NOT`. `AND` выполняется раньше `OR` — ставь скобки, чтобы не ошибиться.

`NULL` нельзя сравнить через `=`: `budget = NULL` никогда не истинно. Только `IS NULL`.

### Пример
```sql
-- активные проекты дороже 100 тысяч
SELECT title, budget FROM projects
WHERE status = 'active' AND budget > 100000;

-- клиенты из Москвы и Казани
SELECT name, city FROM clients
WHERE city IN ('Москва', 'Казань');

-- проекты, где упоминается «сайт» в любом регистре
SELECT title FROM projects WHERE title LIKE '%айт%';

-- проекты без бюджета
SELECT title FROM projects WHERE budget IS NULL;

-- скобки важны: (лендинги ИЛИ сайты) И активные
SELECT title, type FROM projects
WHERE (type = 'landing' OR type = 'site') AND status = 'active';
```

### Частые ошибки
- `WHERE budget = NULL` — ничего не найдёт.
- Забыть скобки при смешивании `AND` и `OR`.
- `LIKE '%текст%'` по большой таблице — медленно, обычный индекс не помогает (для поиска есть полнотекстовые индексы).

### На пальцах
`ORDER BY` — расставить карточки по порядку: по алфавиту, по сумме, по дате. `LIMIT` — «дайте мне первые пять». `OFFSET` — «пропустите первые десять» — так делают постраничный вывод: страница 3 — пропустить 20, взять 10.

### Как это работает
- `ORDER BY колонка` — по возрастанию (`ASC` можно не писать).
- `ORDER BY колонка DESC` — по убыванию.
- Несколько колонок: `ORDER BY status, budget DESC` — сначала по статусу, внутри — по бюджету.
- `NULLS LAST` / `NULLS FIRST` — куда ставить пустые значения (в PostgreSQL при `DESC` они по умолчанию первые).
- `LIMIT n` — не больше n строк.
- `OFFSET m` — пропустить m строк.
- Без `ORDER BY` порядок строк не гарантирован. `LIMIT` без сортировки возвращает «какие-то» строки.

Пагинация: страница `page`, размер `size` → `LIMIT size OFFSET (page - 1) * size`. На очень больших таблицах `OFFSET` медленный — тогда используют «курсор»: `WHERE id > последний_id ORDER BY id LIMIT 20`.

### Пример
```sql
-- три самых дорогих проекта
SELECT title, budget FROM projects
ORDER BY budget DESC NULLS LAST
LIMIT 3;

-- клиенты по алфавиту, вторая страница по 2
SELECT name FROM clients
ORDER BY name
LIMIT 2 OFFSET 2;

-- сначала активные, внутри по убыванию бюджета
SELECT title, status, budget FROM projects
ORDER BY status, budget DESC;
```

### Частые ошибки
- `LIMIT` без `ORDER BY` — каждый раз может приходить разное.
- Не учесть `NULL` при сортировке — проекты без бюджета оказываются «самыми дорогими».
- Сортировка по неуникальной колонке при пагинации — записи «скачут» между страницами. Добавь второй ключ: `ORDER BY budget DESC, id`.

### На пальцах
`DISTINCT` — убрать повторы: из списка городов всех клиентов получить список уникальных городов. Вычисляемая колонка — графа, которой нет в таблице, но её можно посчитать на лету: «бюджет с НДС», «год из даты», «полное название».

### Как это работает
- `SELECT DISTINCT city FROM clients` — каждое значение по одному разу.
- `DISTINCT` по нескольким колонкам убирает повторы сочетаний.
- Вычисления в `SELECT`:
  - арифметика: `budget * 1.2`, `amount / 100`;
  - строки: `upper(name)`, `length(title)`, склейка `name || ' (' || city || ')'`;
  - даты: `extract(year from paid_at)`, `now() - created_at`;
  - условия: `CASE WHEN ... THEN ... ELSE ... END`;
  - замена NULL: `COALESCE(budget, 0)`.
- Вычисляемой колонке почти всегда дают псевдоним через `AS`.

`CASE` — «если/иначе» прямо в запросе: удобно превратить коды в понятные подписи или разбить на категории.

### Пример
```sql
SELECT DISTINCT city FROM clients ORDER BY city;

SELECT
  title,
  COALESCE(budget, 0) AS budget,
  COALESCE(budget, 0) * 1.2 AS with_vat,
  CASE
    WHEN budget IS NULL THEN 'не оценён'
    WHEN budget >= 100000 THEN 'крупный'
    ELSE 'обычный'
  END AS size
FROM projects;

SELECT name || ' — ' || COALESCE(city, 'город не указан') AS label FROM clients;
```

### Частые ошибки
- `DISTINCT` как «лекарство» от дублей после неправильного `JOIN` — лучше исправить сам `JOIN`.
- Арифметика с `NULL` даёт `NULL`: `NULL * 1.2 = NULL`. Используй `COALESCE`.
- Использовать псевдоним из `SELECT` в `WHERE` того же запроса — не сработает (почему — в следующем пункте).

### На пальцах
SQL-запрос читается сверху вниз, но выполняется в другом порядке — как рецепт, где «подать к столу» написано в начале. Сначала база берёт нужные таблицы (`FROM`), потом выкидывает лишние строки (`WHERE`), потом группирует, потом выбирает колонки и считает выражения (`SELECT`), потом сортирует и обрезает.

### Как это работает
Логический порядок выполнения:

1. `FROM` и `JOIN` — какие таблицы и как соединить.
2. `WHERE` — отфильтровать строки.
3. `GROUP BY` — сгруппировать.
4. `HAVING` — отфильтровать группы.
5. `SELECT` — вычислить колонки и псевдонимы.
6. `DISTINCT` — убрать повторы.
7. `ORDER BY` — отсортировать.
8. `LIMIT` / `OFFSET` — обрезать.

Что из этого следует:

- Псевдоним из `SELECT` **нельзя** использовать в `WHERE` — когда выполняется `WHERE`, `SELECT` ещё не случился.
- Псевдоним **можно** использовать в `ORDER BY` — он выполняется после `SELECT`.
- Агрегаты (`SUM`, `COUNT`) нельзя в `WHERE`, только в `HAVING` — группы появляются после `WHERE`.

### Пример
```sql
-- ❌ ошибка: column "with_vat" does not exist
SELECT title, budget * 1.2 AS with_vat FROM projects
WHERE with_vat > 100000;

-- ✅ повтори выражение в WHERE
SELECT title, budget * 1.2 AS with_vat FROM projects
WHERE budget * 1.2 > 100000
ORDER BY with_vat DESC;           -- а здесь псевдоним работает

-- ✅ или оберни в подзапрос
SELECT * FROM (
  SELECT title, budget * 1.2 AS with_vat FROM projects
) t
WHERE with_vat > 100000;
```

### Частые ошибки
- Псевдоним в `WHERE`.
- `WHERE SUM(amount) > 100000` вместо `HAVING`.
- Думать, что `LIMIT` ускоряет сложный запрос: сначала всё равно выполняются все предыдущие шаги (хотя оптимизатор иногда помогает).

### Мини-задание
