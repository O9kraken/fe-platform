### Ситуация
Студия ведёт клиентов и проекты в Excel. Один менеджер пишет в колонке «Бюджет» «30 тыс.», другой — «30000», третий — «уточнить». Дата где-то «15.01», где-то «январь». Посчитать выручку за квартал невозможно без часа ручной чистки. База данных не даст записать такой хаос с самого начала — и именно поэтому на ней держится любой серьёзный продукт.

### На пальцах
База данных — шкаф с таблицами, как в Excel, только строже. Таблица — один лист: «Клиенты». Колонка — графа: «Имя», «Город». Строка — одна запись: конкретный клиент. Тип данных — правило для графы: в «Бюджет» можно писать только числа, в «Дату» — только даты. Excel простит что угодно, база — нет, и в этом её сила.

### Как это работает
В курсе используется учебная база студии из трёх таблиц:

| Таблица | Колонки |
|---|---|
| `clients` | `id`, `name`, `city`, `created_at` |
| `projects` | `id`, `client_id`, `title`, `type`, `budget`, `status` |
| `payments` | `id`, `project_id`, `amount`, `paid_at` |

Основные типы в PostgreSQL:

| Тип | Что хранит |
|---|---|
| `integer`, `bigint` | целые числа |
| `numeric(12,2)` | точные дробные — деньги |
| `text`, `varchar(100)` | строки |
| `boolean` | `true` / `false` |
| `date`, `timestamptz` | дата, дата и время с часовым поясом |
| `uuid` | уникальный идентификатор |
| `jsonb` | JSON-документ |

- У каждой таблицы есть первичный ключ — колонка `id`, уникальная для каждой строки.
- `NULL` — «значение неизвестно». Это не ноль и не пустая строка.
- SQL — язык запросов к базе. Ключевые слова принято писать заглавными: `SELECT`, `FROM`, `WHERE` — так проще читать, но база понимает и строчные.

В «Песочнице» этого курса есть режим SQL с этой базой — все примеры можно запускать.

?: Почему дату лучше хранить в колонке типа `date`, а не строкой «15.01.2026»? || Строки сортируются по буквам: «02.03.2026» окажется раньше «15.01.2026», хотя это март. С типом `date` база правильно сортирует, считает разницу между датами и не даст записать «32.13.2026».

### Пример
```sql
SELECT * FROM clients;
SELECT * FROM projects;
SELECT * FROM payments;
```

?! В таблице `projects` есть проект с бюджетом `NULL` и проект с бюджетом `0`. Чем они отличаются по смыслу? || `NULL` — бюджет неизвестен, его ещё не оценили. `0` — бюджет точно известен и равен нулю, например бесплатная работа. Для базы это разные значения, и в расчётах они ведут себя по-разному.

### Частые ошибки
- **Деньги в `real`/`float`** — копейки «уплывают». Используй `numeric` или целые копейки.
- **Дата строкой «15.01.2026»** — по ней нельзя нормально сортировать и считать.
- **`NULL` и ноль — одно и то же.** Проект без бюджета и проект с бюджетом 0 — разные вещи.

### Проверь себя
?? Что такое первичный ключ? || Колонка (обычно `id`), значение которой уникально для каждой строки и по которому строку однозначно находят.
?? Какой тип PostgreSQL подходит для денег? || `numeric` с точностью, например `numeric(12,2)`, или целое число копеек.
?? Объясни своими словами, чем таблица в базе данных строже таблицы Excel. || У каждой колонки есть тип, и база не даст записать в неё значение не того типа. Поэтому данные всегда в одном формате, и их можно надёжно сортировать и считать.

А в приложении тот же `SELECT *` начинает тянуть по сети тяжёлую колонку с описанием, добавленную вчера. Умение выбрать ровно нужное — первый шаг в SQL.

### На пальцах
`SELECT ... FROM` — просьба архивариусу: «Принесите из шкафа "Проекты" графы "Название" и "Бюджет"». Звёздочка `*` — «принесите все графы». `AS` — наклейка с новым названием на графу в ответе: «назовите это "Сумма со скидкой"».

### Как это работает
```sql
SELECT колонки FROM таблица;
```

- `SELECT *` — все колонки. Удобно для просмотра, но в коде приложения перечисляй нужные.
- Колонки через запятую: `SELECT title, budget FROM projects`.
- `AS` — псевдоним для колонки в ответе: `budget AS "Бюджет"`. Двойные кавычки — если в имени пробелы или русские буквы.
- Псевдоним для таблицы: `FROM projects AS p` или `FROM projects p`, дальше `p.title`.
- Можно выбирать выражения: `budget * 1.2`, `upper(title)`, `'текст'`.
- Строки — в одинарных кавычках: `'Москва'`. Двойные — для имён колонок.

?: Почему в SQL строки пишут в одинарных кавычках, а двойные оставляют для имён? || Так устроен стандарт SQL: двойные кавычки означают идентификатор — имя колонки или таблицы, особенно с пробелами или заглавными буквами. Поэтому `"Москва"` база попытается найти как колонку с таким именем.

### Пример
```sql
SELECT name, city FROM clients WHERE city = "Москва";
```

?! Что ответит PostgreSQL на этот запрос? || Ошибку `column "Москва" does not exist`: в двойных кавычках база ищет колонку с таким именем. Строку нужно писать в одинарных кавычках: `city = 'Москва'`.

### Частые ошибки
- **Двойные кавычки для строк** — PostgreSQL решит, что это имя колонки.
- **Запятая после последней колонки** перед `FROM` — синтаксическая ошибка.
- **`SELECT *` в коде приложения** — при добавлении колонки запрос начнёт возвращать лишнее.

### Ситуация
Директор студии спрашивает: «Какие у нас активные проекты дороже ста тысяч?», «Кто из клиентов в Москве или Казани?», «У каких проектов до сих пор не указан бюджет?». Пролистывать таблицу глазами — долго и неточно. `WHERE` отвечает на любой такой вопрос одной строкой — если знать одну ловушку с пустыми значениями.

### На пальцах
`WHERE` — фильтр, как в интернет-магазине: «только город Москва», «цена от 50 до 100 тысяч», «название начинается на "Сайт"», «без указанного бюджета». База перебирает строки и оставляет те, для которых условие истинно.

### Как это работает
| Оператор | Пример | Значение |
|---|---|---|
| `=`, `<>` | `status = 'done'` | равно, не равно |
| `>`, `<`, `>=`, `<=` | `budget >= 100000` | сравнение |
| `IN (...)` | `city IN ('Москва', 'Казань')` | одно из списка |
| `BETWEEN a AND b` | `budget BETWEEN 50000 AND 100000` | диапазон включительно |
| `LIKE` | `title LIKE 'Сайт%'` | шаблон: `%` — любые символы, `_` — один символ |
| `ILIKE` | `title ILIKE '%кофе%'` | то же без учёта регистра (PostgreSQL) |
| `IS NULL`, `IS NOT NULL` | `budget IS NULL` | значение отсутствует |

Условия объединяют через `AND`, `OR`, `NOT`. `AND` выполняется раньше `OR` — ставь скобки.

`NULL` нельзя сравнить через `=`: `budget = NULL` никогда не истинно. Только `IS NULL`.

?: Почему `budget = NULL` никогда не истинно? || `NULL` значит «неизвестно». На вопрос «равно ли неизвестное значение неизвестному?» честный ответ — «неизвестно», а не «да». Поэтому сравнение с `NULL` даёт `NULL`, и строка не проходит фильтр. Для проверки есть отдельный оператор `IS NULL`.

### Пример
```sql
SELECT title, type, status FROM projects
WHERE type = 'landing' OR type = 'site' AND status = 'active';
```

?! Какие проекты вернёт этот запрос? Совпадает ли это с задумкой «активные лендинги и сайты»? || Все лендинги — в любом статусе — плюс только активные сайты. `AND` выполняется раньше `OR`, и условие читается как `type = 'landing' OR (type = 'site' AND status = 'active')`. Нужны скобки: `(type = 'landing' OR type = 'site') AND status = 'active'`.

### Частые ошибки
- **`WHERE budget = NULL`** — ничего не найдёт.
- **Нет скобок** при смешивании `AND` и `OR`.
- **`LIKE '%текст%'` по большой таблице** — медленно, обычный индекс не помогает.

### Проверь себя
?? Как найти строки, где значение в колонке отсутствует? || `WHERE колонка IS NULL`.
?? Чем `LIKE` отличается от `ILIKE` в PostgreSQL? || `LIKE` учитывает регистр букв, `ILIKE` — нет.
?? Объясни своими словами, что выберет условие `budget BETWEEN 50000 AND 100000`. || Строки, где бюджет от 50 000 до 100 000 включительно, то есть обе границы тоже подходят.

### Ситуация
На главной админки нужен блок «Три самых дорогих проекта». Ты пишешь `ORDER BY budget DESC LIMIT 3` — и первыми оказываются проекты вообще без бюджета. Переключаешь страницы списка клиентов — и одна и та же компания появляется на второй и на третьей странице. Сортировка и пагинация кажутся простыми, но в них прячутся неочевидные правила.

### На пальцах
`ORDER BY` — расставить карточки по порядку: по алфавиту, по сумме, по дате. `LIMIT` — «дайте мне первые пять». `OFFSET` — «пропустите первые десять» — так делают постраничный вывод: страница 3 — пропустить 20, взять 10.

### Как это работает
- `ORDER BY колонка` — по возрастанию (`ASC` можно не писать).
- `ORDER BY колонка DESC` — по убыванию.
- Несколько колонок: `ORDER BY status, budget DESC` — сначала по статусу, внутри — по бюджету.
- `NULLS LAST` / `NULLS FIRST` — куда ставить пустые значения (в PostgreSQL при `DESC` они по умолчанию первые).
- `LIMIT n` — не больше n строк.
- `OFFSET m` — пропустить m строк.
- Без `ORDER BY` порядок строк не гарантирован.

Пагинация: страница `page`, размер `size` → `LIMIT size OFFSET (page - 1) * size`. На очень больших таблицах `OFFSET` медленный — тогда используют «курсор»: `WHERE id > последний_id ORDER BY id LIMIT 20`.

?: Почему записи «скачут» между страницами при сортировке только по бюджету? || Если у нескольких проектов одинаковый бюджет, их взаимный порядок не определён, и база может каждый раз расставлять их по-разному. Второй уникальный ключ сортировки, например `id`, делает порядок однозначным.

### Пример
```sql
SELECT title, budget FROM projects
ORDER BY budget DESC
LIMIT 3;
```

?! В таблице есть проекты с `budget = NULL`. Попадут ли они в «тройку самых дорогих» и как это исправить? || Попадут, и даже первыми: в PostgreSQL при `DESC` пустые значения по умолчанию идут в начале. Нужно `ORDER BY budget DESC NULLS LAST` или отфильтровать `WHERE budget IS NOT NULL`.

### Частые ошибки
- **`LIMIT` без `ORDER BY`** — каждый раз может приходить разное.
- **Не учтён `NULL` при сортировке** — проекты без бюджета оказываются «самыми дорогими».
- **Сортировка по неуникальной колонке при пагинации** — добавь второй ключ: `ORDER BY budget DESC, id`.

### Проверь себя
?? Как получить вторую страницу по 10 записей? || `LIMIT 10 OFFSET 10`.
?? Что делает `NULLS LAST`? || Ставит строки с пустым значением в конец результата сортировки.
?? Объясни своими словами, почему `LIMIT` без `ORDER BY` — плохая идея. || Без сортировки база не обещает никакого порядка, поэтому «первые пять» могут каждый раз оказываться разными строками.

### Ситуация
Нужен выпадающий список городов для фильтра клиентов — а `SELECT city FROM clients` возвращает «Москва» двадцать раз. Отчёт должен показывать бюджет с НДС и категорию проекта «крупный / обычный», которых нет в таблице. А у проектов без бюджета в колонке «с НДС» пусто вместо нуля. Всё это решается прямо в запросе, без кода на сервере.

### На пальцах
`DISTINCT` — убрать повторы: из списка городов всех клиентов получить список уникальных городов. Вычисляемая колонка — графа, которой нет в таблице, но её можно посчитать на лету: «бюджет с НДС», «год из даты», «полное название».

### Как это работает
- `SELECT DISTINCT city FROM clients` — каждое значение по одному разу.
- `DISTINCT` по нескольким колонкам убирает повторы сочетаний.
- Вычисления в `SELECT`:
  - арифметика: `budget * 1.2`, `amount / 100`;
  - строки: `upper(name)`, `length(title)`, склейка `name || ' (' || city || ')'`;
  - даты: `extract(year from paid_at)`, `now() - created_at`;
  - условия: `CASE WHEN ... THEN ... ELSE ... END`;
  - замена NULL: `COALESCE(budget, 0)`.
- Вычисляемой колонке почти всегда дают псевдоним через `AS`.

?: Почему `NULL * 1.2` даёт `NULL`, а не ноль? || Неизвестное число, умноженное на 1,2, — по-прежнему неизвестное число. SQL не угадывает вместо тебя, что «неизвестно» значит «ноль». Если нужен ноль, говорят явно: `COALESCE(budget, 0)`.

### Пример
```sql
SELECT
  title,
  CASE
    WHEN budget >= 100000 THEN 'крупный'
    WHEN budget IS NULL THEN 'не оценён'
    ELSE 'обычный'
  END AS size
FROM projects;
```

?! Какую категорию получат проекты с бюджетом 150 000, 30 000 и `NULL`? || 150 000 — «крупный», 30 000 — «обычный», `NULL` — «не оценён». Сравнение `NULL >= 100000` не истинно, поэтому первая ветка пропускается, и срабатывает проверка `IS NULL`.

### Частые ошибки
- **`DISTINCT` как «лекарство» от дублей** после неправильного `JOIN` — лучше исправить сам `JOIN`.
- **Арифметика с `NULL`** даёт `NULL`. Используй `COALESCE`.
- **Псевдоним из `SELECT` в `WHERE`** того же запроса — не сработает (почему — в следующем пункте).

### Проверь себя
?? Как получить список уникальных городов клиентов? || `SELECT DISTINCT city FROM clients`.
?? Что делает `COALESCE(budget, 0)`? || Возвращает `budget`, а если он `NULL` — возвращает 0.
?? Объясни своими словами, для чего нужен `CASE` в запросе. || Чтобы прямо в SQL выбрать значение по условиям — например, превратить числа в понятные категории или коды в подписи.

### Ситуация
Ты пишешь `SELECT budget * 1.2 AS with_vat FROM projects WHERE with_vat > 100000` — и база отвечает «column with_vat does not exist». Как не существует? Вот же она, в той же строке! Чтобы понять, нужно знать секрет SQL: запрос выполняется совсем не в том порядке, в каком написан. Это частый вопрос на собеседованиях.

### На пальцах
SQL-запрос читается сверху вниз, но выполняется в другом порядке — как рецепт, где «подать к столу» написано в начале. Сначала база берёт нужные таблицы (`FROM`), потом выкидывает лишние строки (`WHERE`), потом группирует, потом выбирает колонки и считает выражения (`SELECT`), потом сортирует и обрезает.

### Как это работает
Логический порядок выполнения:

1. `FROM` и `JOIN` — какие таблицы и как соединить.
2. `WHERE` — отфильтровать строки.
3. `GROUP BY` — сгруппировать.
4. `HAVING` — отфильтровать группы.
5. `SELECT` — вычислить колонки и псевдонимы.
6. `DISTINCT` — убрать повторы.
7. `ORDER BY` — отсортировать.
8. `LIMIT` / `OFFSET` — обрезать.

Что из этого следует:

- Псевдоним из `SELECT` **нельзя** использовать в `WHERE` — когда выполняется `WHERE`, `SELECT` ещё не случился.
- Псевдоним **можно** использовать в `ORDER BY` — он выполняется после `SELECT`.
- Агрегаты (`SUM`, `COUNT`) нельзя в `WHERE`, только в `HAVING` — группы появляются после `WHERE`.

?: Почему агрегат вроде `SUM(amount)` нельзя использовать в `WHERE`? || `WHERE` работает с отдельными строками до группировки, а сумма появляется только после `GROUP BY`. На этапе `WHERE` считать ещё нечего. Для условий по группам есть `HAVING`, который выполняется после группировки.

### Пример
```sql
SELECT title, budget * 1.2 AS with_vat FROM projects
WHERE budget * 1.2 > 100000
ORDER BY with_vat DESC;
```

?! Сработает ли этот запрос, хотя `with_vat` используется в `ORDER BY`? || Да. В `WHERE` выражение повторено полностью, а `ORDER BY` выполняется после `SELECT` и уже знает псевдоним `with_vat`.

### Частые ошибки
- **Псевдоним в `WHERE`.**
- **`WHERE SUM(amount) > 100000`** вместо `HAVING`.
- **Вера, что `LIMIT` ускоряет сложный запрос:** все предыдущие шаги всё равно выполняются (хотя оптимизатор иногда помогает).

### Проверь себя
?? В каком порядке логически выполняются `SELECT`, `WHERE` и `ORDER BY`? || Сначала `WHERE`, затем `SELECT`, затем `ORDER BY`.
?? Где можно использовать псевдоним колонки из `SELECT`, а где нельзя? || Можно в `ORDER BY`, нельзя в `WHERE`, `GROUP BY` (в стандарте) и `HAVING` того же запроса.
?? Объясни своими словами, как обойти запрет на псевдоним в `WHERE`. || Повторить выражение целиком в `WHERE` или обернуть запрос в подзапрос, а фильтровать по псевдониму уже во внешнем запросе.

### Мини-задание
Напиши запрос, который выводит проекты с бюджетом с НДС больше 100 000 и сортирует по этому значению, двумя способами: повтором выражения и через подзапрос. Объясни себе, почему первоначальный вариант с псевдонимом в `WHERE` не работает.
