### На пальцах
Проверка машины на заводе: сначала по отдельности проверяют каждую деталь — болты, свечи, тормозные колодки (быстро и дёшево, их тысячи). Потом узлы целиком — двигатель, тормозную систему (дольше). И в конце пара тест-драйвов на трассе (долго и дорого). Это и есть пирамида тестов: много мелких внизу, мало больших вверху.

### Как это работает
| Уровень | Что проверяет | Скорость | Сколько |
|---|---|---|---|
| Unit | одну функцию или маленький компонент изолированно | миллисекунды | много |
| Интеграционные | несколько частей вместе: форма + валидация + запрос | секунды | средне |
| E2E (end-to-end) | весь сценарий в настоящем браузере: зайти, найти, купить | десятки секунд | мало, только ключевые |

Почему не только e2e: они медленные, хрупкие (поменял текст кнопки — тест упал) и при падении плохо показывают, где именно ошибка.

Почему не только unit: можно идеально протестировать все детали, но не заметить, что они не стыкуются друг с другом.

Что тестировать в первую очередь:

- чистые функции с логикой: расчёт цены, форматирование, валидация;
- критичные сценарии: вход, оформление заказа, оплата;
- места, где уже были баги — чтобы они не вернулись.

Не нужно стремиться к 100% покрытию. Тесты должны давать уверенность, что важное работает.

### Пример
```text
            /\
           /e2e\         ← «пользователь оформил заказ» (2–5 тестов)
          /------\
         / интегр.\      ← «форма заказа показывает ошибки и отправляет данные»
        /----------\
       /    unit    \    ← formatPrice, calcDiscount, validatePhone (десятки)
      /--------------\
```

### Частые ошибки
- Писать только e2e и ждать прогона по 20 минут.
- Тестировать детали реализации (внутреннее состояние), а не поведение — тесты ломаются от любого рефакторинга.
- Откладывать тесты «на потом» — потом их не пишут никогда.

### Мини-задание
Возьми свой учебный проект и распиши пирамиду: какие функции стоит покрыть unit-тестами, какие компоненты — интеграционными, и какие два сценария — e2e.

### На пальцах
Unit-тест — проверка одной детали на стенде: подали на вход известные значения и сравнили результат с ожидаемым. «Если цена 1000 и скидка 15% — должно получиться 850». Vitest — сам стенд: запускает все проверки за секунду и показывает, какие прошли, а какие нет.

### Как это работает
1. `npm install -D vitest`
2. В `package.json`: `"test": "vitest"`.
3. Тесты кладут рядом с кодом в файлы `*.test.ts`.
4. `npm test` — запуск в режиме наблюдения: тесты перезапускаются при сохранении.

Структура теста:

- `describe("что тестируем", () => { ... })` — группа.
- `it("что должно происходить", () => { ... })` (или `test`) — один тест.
- `expect(значение).toBe(ожидаемое)` — проверка.

Основные проверки:

| Проверка | Для чего |
|---|---|
| `toBe(x)` | строгое равенство примитивов |
| `toEqual(obj)` | глубокое равенство объектов и массивов |
| `toThrow()` | функция бросает ошибку |
| `toContain(x)` | массив или строка содержит |
| `toBeNull()`, `toBeUndefined()` | пустые значения |
| `.not.toBe(x)` | отрицание |

Хорошее правило для каждого теста — три шага: подготовить данные, выполнить действие, проверить результат (Arrange, Act, Assert).

### Пример
```ts
// src/utils/price.ts
export function applyDiscount(price: number, percent: number): number {
  if (percent < 0 || percent > 100) throw new Error("Скидка от 0 до 100");
  return Math.round(price * (1 - percent / 100));
}

export function formatPrice(n: number): string {
  return n.toLocaleString("ru-RU") + " ₽";
}
```

```ts
// src/utils/price.test.ts
import { describe, it, expect } from "vitest";
import { applyDiscount, formatPrice } from "./price";

describe("applyDiscount", () => {
  it("считает скидку", () => {
    expect(applyDiscount(1000, 15)).toBe(850);
  });
  it("без скидки цена не меняется", () => {
    expect(applyDiscount(1000, 0)).toBe(1000);
  });
  it("не принимает скидку больше 100%", () => {
    expect(() => applyDiscount(1000, 150)).toThrow();
  });
});

describe("formatPrice", () => {
  it("добавляет пробелы и знак рубля", () => {
    expect(formatPrice(1500)).toMatch(/1\s500 ₽/);
  });
});
```

### Частые ошибки
- Один огромный тест, проверяющий всё подряд — при падении непонятно, что сломалось.
- `toBe` для объектов: `expect({a: 1}).toBe({a: 1})` упадёт, нужен `toEqual`.
- Не проверить, что тест вообще умеет падать: временно сломай код и убедись, что тест покраснел.

### Мини-задание
Напиши функцию `pluralize(n, ["товар", "товара", "товаров"])` и не меньше шести тестов: 1, 2, 5, 11, 21, 104. Сначала напиши тесты, потом реализацию, пока все не станут зелёными. Потренируйся в задачах «Свой expect» этого урока.

### На пальцах
Тестировать компонент можно двумя способами: «залезть под капот и проверить, что переменная isOpen стала true» или «сесть за руль как обычный водитель и проверить, что дверь открылась». React Testing Library заставляет тестировать вторым способом — так, как пользователь видит и нажимает.

### Как это работает
Установка для Vite: `npm install -D @testing-library/react @testing-library/user-event @testing-library/jest-dom jsdom`, в `vite.config.ts` — `test: { environment: "jsdom" }`.

Главные функции:

- `render(<Компонент />)` — нарисовать компонент в тестовом DOM.
- `screen.getByRole("button", { name: "Отправить" })` — найти элемент так, как его найдёт скринридер: по роли и доступному имени.
- `userEvent.setup()` + `await user.click(...)`, `await user.type(input, "текст")` — действия как у живого пользователя.
- `expect(el).toBeInTheDocument()`, `toBeDisabled()`, `toHaveTextContent()` — проверки из jest-dom.

Приоритет поиска:

1. `getByRole` — кнопки, ссылки, заголовки, поля по `label`.
2. `getByLabelText` — поля формы.
3. `getByText` — обычный текст.
4. `getByTestId` — только если ничего другое не подходит.

Варианты: `getBy...` — элемент должен быть (иначе ошибка), `queryBy...` — может отсутствовать (вернёт null), `findBy...` — подождать появления (для асинхронного).

Бонус: если элемент не находится по роли, значит, он недоступен и для людей со скринридером.

### Пример
```tsx
// Counter.tsx
import { useState } from "react";
export function Counter() {
  const [n, setN] = useState(0);
  return (
    <>
      <p>Счёт: {n}</p>
      <button onClick={() => setN(n + 1)}>Добавить</button>
      <button onClick={() => setN(0)} disabled={n === 0}>Сбросить</button>
    </>
  );
}
```

```tsx
// Counter.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import "@testing-library/jest-dom/vitest";
import { it, expect } from "vitest";
import { Counter } from "./Counter";

it("увеличивает счёт и сбрасывает его", async () => {
  const user = userEvent.setup();
  render(<Counter />);

  const reset = screen.getByRole("button", { name: "Сбросить" });
  expect(reset).toBeDisabled();

  await user.click(screen.getByRole("button", { name: "Добавить" }));
  await user.click(screen.getByRole("button", { name: "Добавить" }));
  expect(screen.getByText("Счёт: 2")).toBeInTheDocument();

  await user.click(reset);
  expect(screen.getByText("Счёт: 0")).toBeInTheDocument();
});
```

### Частые ошибки
- Искать по классам и `data-testid` везде — тест не проверяет доступность и ломается от смены вёрстки.
- Забыть `await` перед `user.click` — проверка срабатывает раньше обновления.
- Проверять внутреннее состояние компонента вместо того, что видно на экране.

### Мини-задание

### На пальцах
E2E-тест — тайный покупатель-робот. Он открывает настоящий браузер, заходит на сайт, ищет товар, кладёт в корзину и оформляет заказ. Если на любом шаге что-то сломалось — сразу сигнал. Playwright — агентство, которое нанимает таких роботов и записывает видео их походов.

### Как это работает
1. `npm init playwright@latest` — установит Playwright, браузеры и создаст пример теста.
2. Тесты пишутся в папке `tests/` в файлах `*.spec.ts`.
3. `npx playwright test` — запуск. `npx playwright test --ui` — наглядный режим с пошаговым просмотром.
4. `npx playwright codegen http://localhost:5173` — записывает твои клики и генерирует код теста.

Основное API:

- `await page.goto("/")` — открыть страницу.
- `page.getByRole("button", { name: "Купить" })` — найти элемент, как в Testing Library.
- `await locator.click()`, `await locator.fill("текст")` — действия.
- `await expect(locator).toBeVisible()`, `toHaveText(...)`, `toHaveURL(...)` — проверки. Они сами ждут, пока условие выполнится (до 5 секунд), поэтому `sleep` не нужен.

В `playwright.config.ts` можно указать `webServer`, чтобы перед тестами автоматически запускался твой dev-сервер.

### Пример
```ts
// tests/checkout.spec.ts
import { test, expect } from "@playwright/test";

test("пользователь находит товар и кладёт его в корзину", async ({ page }) => {
  await page.goto("http://localhost:5173/");

  await page.getByRole("searchbox", { name: "Поиск" }).fill("кроссовки");
  await page.getByRole("link", { name: /Кроссовки Run/ }).click();
  await expect(page).toHaveURL(/\/product\//);

  await page.getByRole("button", { name: "В корзину" }).click();
  await expect(page.getByRole("link", { name: /Корзина \(1\)/ })).toBeVisible();

  await page.getByRole("link", { name: /Корзина/ }).click();
  await expect(page.getByRole("heading", { name: "Корзина" })).toBeVisible();
  await expect(page.getByText("Кроссовки Run")).toBeVisible();
});
```

### Частые ошибки
- Писать e2e на каждую мелочь — набор становится медленным и хрупким.
- `await page.waitForTimeout(3000)` вместо проверок, которые ждут сами.
- Зависимость от реальных данных, которые меняются: сегодня товар есть, завтра продан.

### На пальцах
Тестировать только «правильный» путь — как проверять дверной замок только родным ключом. Взломщик придёт с отвёрткой, а ребёнок — с ключом от другой двери. Негативные сценарии проверяют, что программа ведёт себя достойно, когда что-то идёт не так: неверный ввод, нет сети, пустой ответ, нет прав.

### Как это работает
Что проверить почти в любой фиче:

| Ситуация | Что должно быть |
|---|---|
| Пустая форма | сообщения у обязательных полей, отправки нет |
| Неверный формат (email, телефон) | понятное сообщение у поля |
| Сервер ответил 400 | ошибки показаны у нужных полей |
| Сервер ответил 500 или нет сети | общее сообщение и кнопка «Повторить», введённые данные не потеряны |
| Пустой список | понятная заглушка, а не пустота |
| Нет прав (401/403) | переход на вход или сообщение «Нет доступа» |
| Двойной клик по «Оплатить» | один запрос, кнопка заблокирована |
| Очень длинный текст | вёрстка не ломается |

Ответы сервера в тестах подменяют: в unit- и интеграционных — через моки (`vi.fn`, MSW), в Playwright — через `page.route`.

### Пример
```ts
// Playwright: сервер «упал»
import { test, expect } from "@playwright/test";

test("при ошибке сервера показываем сообщение и сохраняем ввод", async ({ page }) => {
  await page.route("**/api/lead", route => route.fulfill({ status: 500, body: "{}" }));
  await page.goto("http://localhost:5173/contacts");

  await page.getByLabel("Имя").fill("Анна");
  await page.getByLabel("Телефон").fill("+7 999 123-45-67");
  await page.getByRole("button", { name: "Отправить" }).click();

  await expect(page.getByRole("alert")).toHaveText(/Не удалось отправить/);
  await expect(page.getByLabel("Имя")).toHaveValue("Анна");
});

test("пустую форму не отправляем", async ({ page }) => {
  let sent = false;
  await page.route("**/api/lead", route => { sent = true; return route.fulfill({ status: 200, body: "{}" }); });
  await page.goto("http://localhost:5173/contacts");
  await page.getByRole("button", { name: "Отправить" }).click();
  await expect(page.getByText("Введите имя")).toBeVisible();
  expect(sent).toBe(false);
});
```

### Частые ошибки
- Тестировать только «счастливый путь».
- При ошибке очищать форму — пользователь теряет введённое.
- Проверять, что «что-то показалось», а не конкретное сообщение.

### Мини-задание
Для формы обратной связи своего проекта напиши три негативных теста: пустая форма, неверный email, ошибка сервера 500. Убедись, что во всех случаях пользователь понимает, что произошло.
