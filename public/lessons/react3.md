### Ситуация
Компонент `UserCard` должен загрузить пользователя с сервера. Ты пишешь `fetch` прямо в теле компонента — и вкладка Network заполняется сотнями одинаковых запросов: каждый ответ меняет состояние, состояние вызывает отрисовку, отрисовка — новый запрос. Действия «снаружи» компонента нужно запускать в специальном месте и в нужный момент.

### На пальцах
Компонент рисует интерфейс, но иногда нужно сделать что-то «снаружи»: сходить на сервер, запустить таймер, поменять заголовок вкладки. `useEffect` — записка «после того как нарисуешь, сделай ещё вот это». Массив зависимостей — условие: «и повторяй, только когда изменится вот это».

### Как это работает
```tsx
useEffect(() => {
  // побочный эффект
  return () => { /* очистка, необязательно */ };
}, [зависимости]);
```

| Зависимости | Когда запускается |
|---|---|
| нет массива | после каждой отрисовки |
| `[]` | один раз после первой отрисовки |
| `[id]` | после первой и каждый раз, когда изменился `id` |

- В зависимости перечисляют все значения из компонента, которые используются внутри эффекта: props, состояние, функции. ESLint-правило `react-hooks/exhaustive-deps` подскажет, если что-то забыл.
- Эффект запускается после отрисовки — экран не блокируется.
- В режиме разработки со `StrictMode` эффект запускается дважды: так React проверяет, что очистка написана правильно.

Сама функция эффекта не может быть `async`. Создай внутри async-функцию и вызови её.

?: Почему функцию эффекта нельзя сделать `async`? || Async-функция всегда возвращает промис, а React ждёт от эффекта либо ничего, либо функцию очистки. Промис он не поймёт, и очистка не сработает. Поэтому async-функцию объявляют внутри эффекта и вызывают.

### Пример
```tsx
import { useEffect, useState } from "react";

export function UserCard({ id }: { id: number }) {
  const [user, setUser] = useState<{ name: string } | null>(null);

  useEffect(() => {
    async function load() {
      const r = await fetch(`https://jsonplaceholder.typicode.com/users/${id}`);
      setUser(await r.json());
    }
    load();
  }, []);

  return <p>{user ? user.name : "Загрузка…"}</p>;
}
```

?! Родитель меняет проп `id` с 1 на 2. Что покажет карточка? || По-прежнему пользователя 1. В массиве зависимостей пусто, поэтому эффект выполнился один раз и при смене `id` не перезапускается. Нужно `[id]`.

### Частые ошибки
- **Нет массива зависимостей и `setState` внутри** — бесконечный цикл: отрисовка → эффект → обновление → отрисовка.
- **Забытая зависимость:** эффект использует `id`, а в массиве его нет — данные не обновляются.
- **`useEffect(async () => ...)`** — так нельзя.

### Проверь себя
?? Когда запускается эффект с пустым массивом зависимостей? || Один раз — после первой отрисовки компонента.
?? Что нужно перечислять в массиве зависимостей? || Все значения из компонента, которые используются внутри эффекта: props, состояние, функции.
?? Объясни своими словами, зачем нужен `useEffect`. || Чтобы после отрисовки синхронизировать компонент с внешним миром: загрузить данные, запустить таймер, подписаться на событие — и повторять это только при изменении нужных значений.

### Ситуация
Пользователь быстро щёлкает: «Пост 1», «Пост 2», «Пост 3». Ответ на первый запрос пришёл последним — и на экране висит заголовок первого поста, хотя выбран третий. ### На пальцах
Ты запустил таймер на плите и ушёл из кухни насовсем — таймер будет пищать в пустой комнате. Функция очистки — «уходя, выключи за собой»: останови таймер, отпишись от событий, отмени запрос, который уже не нужен. `AbortController` — кнопка «отмена» для запроса `fetch`.

### Как это работает
- Если эффект возвращает функцию, React вызовет её перед следующим запуском эффекта и когда компонент исчезнет с экрана.
- Что обязательно чистить: `setInterval`/`setTimeout`, `addEventListener` на `window`/`document`, подписки (WebSocket), незавершённые запросы.

`AbortController`:

1. `const controller = new AbortController()`
2. `fetch(url, { signal: controller.signal })`
3. В очистке: `controller.abort()` — запрос прерывается, `fetch` бросает ошибку `AbortError`, её нужно игнорировать.

?: Как отмена запроса решает «гонку запросов»? || При смене `id` React сначала вызывает очистку старого эффекта — и устаревший запрос отменяется, его ответ уже не попадёт в состояние. На экран может попасть только ответ на последний, актуальный запрос.

### Пример
```tsx
import { useEffect, useState } from "react";

export function Clock() {
  const [now, setNow] = useState(new Date());
  useEffect(() => {
    const t = setInterval(() => setNow(new Date()), 1000);
    return () => clearInterval(t);
  }, []);
  return <p>{now.toLocaleTimeString("ru-RU")}</p>;
}

export function Post({ id }: { id: number }) {
  const [title, setTitle] = useState("");
  useEffect(() => {
    const controller = new AbortController();
    fetch(`https://jsonplaceholder.typicode.com/posts/${id}`, { signal: controller.signal })
      .then(r => r.json())
      .then(p => setTitle(p.title))
      .catch(e => { if (e.name !== "AbortError") console.error(e); });
    return () => controller.abort();
  }, [id]);
  return <h2>{title}</h2>;
}
```

?! Компонент `Clock` показали, скрыли и снова показали пять раз. Сколько таймеров будет работать в итоге? А если убрать `return () => clearInterval(t)`? || С очисткой — один: при каждом скрытии таймер останавливается. Без очистки — пять, и все они продолжают тикать, обновляя состояние давно исчезнувших компонентов.

### Частые ошибки
- **`setInterval` без очистки** — таймеры копятся.
- **`window.addEventListener("resize", ...)` без `removeEventListener`** в очистке.
- **Показ пользователю `AbortError`** — это нормальная отмена, а не сбой.

### Проверь себя
?? Когда React вызывает функцию очистки эффекта? || Перед каждым повторным запуском эффекта и когда компонент исчезает с экрана.
?? Как отменить запрос `fetch`? || Передать в него `signal` от `AbortController` и вызвать `controller.abort()`.
?? Объясни своими словами, что такое гонка запросов. || Несколько запросов выполняются одновременно, и ответы приходят не в том порядке. Если не отменять устаревшие, на экране может оказаться результат старого запроса вместо нового.

### Ситуация
Ты открываешь приложение доставки, а там пустой экран. Секунду, две, три. Пользователь не знает: грузится, сломалось или ресторанов нет? Компонент с загрузкой данных, который показывает только «счастливый» результат, — самая частая причина плохого впечатления от приложения. Соберём правильный шаблон один раз и будем им пользоваться.

### На пальцах
Ты заказал пиццу. Важны три вопроса: «уже везут?», «что-то пошло не так?» и «вот она!». Хороший компонент с загрузкой данных отвечает на все три, а не просто показывает пустоту, пока ждёт.

### Как это работает
Для запроса держат три части состояния: данные, загружается ли и ошибку. Или одну переменную со статусом.

Порядок в эффекте:

1. Перед запросом: `loading = true`, ошибку сбросить.
2. `fetch` в `try`, проверить `response.ok`.
3. Успех — положить данные.
4. Ошибка — положить понятное сообщение.
5. В `finally` — `loading = false`.

В отрисовке сначала обрабатывают особые случаи ранним `return`: загрузка, ошибка, пустой список — и в конце основной вид.

Кнопка «Повторить» — хранить счётчик попыток в состоянии и добавить его в зависимости эффекта.

?: Как счётчик попыток в зависимостях заставляет эффект перезапуститься? || Эффект перезапускается, когда меняется любая из его зависимостей. Кнопка «Повторить» увеличивает `attempt` на 1, React видит новое значение в массиве зависимостей и запускает загрузку заново.

### Пример
```tsx
const [posts, setPosts] = useState<Post[]>([]);
const [loading, setLoading] = useState(false);
const [error, setError] = useState<string | null>(null);

useEffect(() => {
  let ignore = false;
  async function load() {
    setLoading(true);
    try {
      const r = await fetch("https://jsonplaceholder.typicode.com/posts?_limit=5");
      if (!r.ok) throw new Error(`Ошибка ${r.status}`);
      const data = await r.json();
      if (!ignore) setPosts(data);
    } catch {
      if (!ignore) setError("Не удалось загрузить посты");
    } finally {
      if (!ignore) setLoading(false);
    }
  }
  load();
  return () => { ignore = true; };
}, []);

if (loading) return <p>Загрузка…</p>;
if (error) return <p>{error}</p>;
if (posts.length === 0) return <p>Постов пока нет</p>;
```

?! Что пользователь увидит в самый первый момент, до запуска эффекта? || «Постов пока нет» — на долю секунды. Начальное `loading = false`, а постов ещё нет, и срабатывает проверка на пустой список. Потом мелькнёт «Загрузка…». Начальное значение `loading` должно быть `true`.

### Частые ошибки
- **Ошибку не сбрасывают перед повтором** — сообщение «висит» поверх новых данных.
- **Начальное `loading = false`** — мелькает «пусто», как в примере.
- **Нет проверки `response.ok`.**

### Проверь себя
?? Какие три части состояния нужны для загрузки данных? || Данные, флаг загрузки и ошибка (или одна переменная со статусом).
?? В каком порядке проверять состояния при отрисовке? || Сначала загрузка, затем ошибка, затем пустой результат и только в конце основной вид.
?? Объясни своими словами, зачем в примере переменная `ignore`. || Чтобы ответ устаревшего запроса не записался в состояние после того, как компонент исчез или эффект перезапустился.

### Ситуация
У тебя пять компонентов, которые грузят данные, и в каждом одни и те же 25 строк: три состояния, `fetch`, отмена, проверка `ok`. Нашёл баг в обработке ошибок — исправляй в пяти местах. Логику с хуками можно вынести в свою функцию так же, как обычный код выносят в обычную функцию.

### На пальцах
Кастомный хук — вынести повторяющийся ритуал в свою «кнопку»: `useFetch(url)`. Нажал — получил данные, загрузку и ошибку. Как готовая смесь для блинов вместо того, чтобы каждый раз отмерять муку.

### Как это работает
- Кастомный хук — обычная функция, имя которой начинается с `use` и внутри которой вызываются другие хуки.
- Он ничего не рисует, а возвращает данные и функции.
- Каждый компонент, вызвавший хук, получает собственное независимое состояние.
- Правила хуков действуют и для кастомных: вызывать на верхнем уровне компонента или другого хука.

Хорошие кандидаты: загрузка данных, `localStorage`, размер окна, таймер, дебаунс ввода.

С generic в TypeScript хук знает тип данных: `useFetch<Post[]>(url)`.

?: Почему имя хука обязательно начинается с `use`? || По этому префиксу React и ESLint понимают, что внутри вызываются хуки, и проверяют правила: не в условиях, не в циклах. Без префикса проверки не сработают, и ошибки будет трудно найти.

### Пример
```tsx
export function useFetch<T>(url: string) {
  const [data, setData] = useState<T | null>(null);
  const [error, setError] = useState<string | null>(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    const controller = new AbortController();
    setLoading(true);
    setError(null);
    fetch(url, { signal: controller.signal })
      .then(r => { if (!r.ok) throw new Error(`Ошибка ${r.status}`); return r.json(); })
      .then(setData)
      .catch(e => { if (e.name !== "AbortError") setError(e.message); })
      .finally(() => setLoading(false));
    return () => controller.abort();
  }, [url]);

  return { data, error, loading };
}

// в двух разных компонентах
const a = useFetch<User[]>("/api/users");
const b = useFetch<User[]>("/api/users");
```

?! Сколько запросов к `/api/users` уйдёт, если оба компонента на странице? Общие ли у них данные? || Два запроса, и у каждого компонента своя копия данных. Кастомный хук делит логику, а не состояние. Для общего кеша есть TanStack Query.

### Частые ошибки
- **Имя без `use`** — ESLint не проверит правила хуков.
- **Ожидание, что два компонента с `useFetch` делят данные.** У каждого свои.
- **Объект, создаваемый на каждой отрисовке, в зависимостях** — эффект срабатывает постоянно.

### Проверь себя
?? Что такое кастомный хук? || Функция с именем на `use`, внутри которой вызываются другие хуки. Она возвращает данные и функции, а не разметку.
?? Делят ли два компонента общее состояние, если вызывают один и тот же кастомный хук? || Нет, каждый вызов создаёт своё независимое состояние.
?? Объясни своими словами, зачем выносить логику в кастомный хук. || Чтобы не повторять одинаковый код с состоянием и эффектами в разных компонентах, а исправлять и улучшать его в одном месте.

### Ситуация
Освоив `useEffect`, новички начинают прогонять через него всё: «изменилось имя — в эффекте посчитаю полное имя», «нажали кнопку — поставлю флаг, а эффект отправит форму». Компонент рисуется по два-три раза, логика расползается по цепочке эффектов, баги не найти. Половина эффектов в учебных проектах просто не нужна.

### На пальцах
`useEffect` — запасной выход, а не главная дверь. Пропускать через него обычные вычисления — всё равно что звонить себе на телефон, чтобы напомнить о том, что держишь в руке.

### Как это работает
Эффект нужен для синхронизации с внешним миром: сервер, таймеры, браузерные API, сторонние библиотеки. Если внешнего мира нет — скорее всего, эффект не нужен.

| Задача | Вместо эффекта |
|---|---|
| Значение, вычисляемое из props и состояния | посчитать прямо в теле компонента |
| Тяжёлое вычисление | `useMemo` |
| Реакция на действие пользователя | код в обработчике события |
| Сбросить состояние при смене пропа | `key` у компонента |
| Отправить аналитику при клике | в обработчике клика |

Признак лишнего эффекта: внутри только `setState` на основе других состояний или props.

?: Почему вычисляемое значение лучше считать прямо в теле компонента, а не хранить в состоянии? || Компонент и так перерисовывается при изменении исходных данных, и вычисление выполнится заново. Отдельное состояние с эффектом даёт лишнюю отрисовку, а на мгновение показывает устаревшее значение.

### Пример
```tsx
const [first, setFirst] = useState("Анна");
const [last, setLast] = useState("Смирнова");
const [full, setFull] = useState("");
useEffect(() => { setFull(`${first} ${last}`); }, [first, last]);
console.log("render", full);
```

?! Сколько раз выполнится `console.log` при первом показе компонента и что он выведет? || Два раза: первый — с пустой строкой (эффект ещё не сработал), второй — «Анна Смирнова» после `setFull`. С простым `const full = \`${first} ${last}\`` была бы одна отрисовка сразу с правильным значением.

### Частые ошибки
- **Отфильтрованный список в состоянии, обновляемый эффектом.** Фильтруй прямо при отрисовке.
- **Цепочки эффектов:** один меняет состояние, другой реагирует, третий — на второй.
- **Сброс формы эффектом при смене `userId`** вместо `<Form key={userId} />`.

### Проверь себя
?? Для чего на самом деле нужен `useEffect`? || Для синхронизации с внешним миром: сервером, таймерами, браузерными API, сторонними библиотеками.
?? Куда поместить код, который должен выполниться при клике? || В обработчик события клика, а не в эффект.
?? Объясни своими словами, как понять, что эффект лишний. || Если внутри него только `setState`, вычисленный из других props или состояния, и нет обращения к внешнему миру — значение можно посчитать прямо при отрисовке.
