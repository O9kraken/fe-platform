### На пальцах
Ресторан работает потому, что у каждого своя роль: официант принимает заказ и приносит блюдо (маршрут), повар решает, как готовить (сервис), кладовщик знает, где лежат продукты (репозиторий). Если официант сам бегает в подвал и жарит котлеты — бардак. Слои — то же разделение обязанностей в коде сервера.

### Как это работает
| Слой | Отвечает за | Не знает о |
|---|---|---|
| **Маршрут (controller)** | HTTP: разобрать запрос, вызвать сервис, вернуть статус и JSON | SQL, бизнес-правилах |
| **Сервис** | бизнес-правила: «нельзя закрыть проект без оплаты», «скидка постоянным клиентам» | HTTP (`req`, `res`) и SQL |
| **Репозиторий** | доступ к данным: SQL или ORM-запросы | HTTP, бизнес-правилах |

Зависимости идут в одну сторону: маршрут → сервис → репозиторий.

Зачем:

- бизнес-правила в одном месте, их легко найти и протестировать без HTTP и базы;
- можно сменить базу или ORM, переписав только репозитории;
- один сервис можно вызвать из маршрута, из фонового задания и из скрипта.

Для небольшого проекта не нужно строить «энтерпрайз»: достаточно вынести SQL из маршрутов и держать правила в сервисах.

### Пример
```js
// repositories/projects.js — только данные
export const projectsRepo = {
  findById: (id) => q("SELECT * FROM projects WHERE id = $1", [id]).then(r => r.rows[0]),
  paidSum: (id) => q("SELECT COALESCE(SUM(amount), 0)::int AS s FROM payments WHERE project_id = $1", [id]).then(r => r.rows[0].s),
  setStatus: (id, status) => q("UPDATE projects SET status = $2 WHERE id = $1 RETURNING *", [id, status]).then(r => r.rows[0]),
};
```

```js
// services/projects.js — бизнес-правила
import { projectsRepo } from "../repositories/projects.js";
import { HttpError } from "../errors.js";

export async function closeProject(id, user) {
  const project = await projectsRepo.findById(id);
  if (!project || project.owner_id !== user.id) throw new HttpError(404, "Проект не найден");
  const paid = await projectsRepo.paidSum(id);
  if (paid < project.budget) throw new HttpError(409, "Нельзя закрыть проект без полной оплаты");
  return projectsRepo.setStatus(id, "done");
}
```

```js
// routes/projects.js — только HTTP
router.post("/:id/close", requireUser, wrap(async (req, res) => {
  res.json(await closeProject(Number(req.params.id), req.user));
}));
```

### Частые ошибки
- SQL и бизнес-правила прямо в обработчиках маршрутов.
- Сервис принимает `req` и `res` — его нельзя вызвать вне HTTP.
- Десять слоёв абстракций для CRUD из трёх таблиц.

### Мини-задание
Выбери в своём API одну операцию с бизнес-правилом и разнеси её по трём слоям. Напиши unit-тест сервиса, подменив репозиторий заглушкой.

### На пальцах
Если каждый сотрудник сам решает, как отвечать на жалобы, клиенты получают то вежливое письмо, то грубость, то технические подробности склада. Свои классы ошибок — стандартные бланки отказов («не найдено», «нет прав», «конфликт»), а единый обработчик — один отдел, который по бланку формирует правильный ответ.

### Как это работает
1. Базовый класс `AppError` (или `HttpError`) со статусом и машиночитаемым кодом.
2. Наследники под типовые случаи: `NotFoundError`, `ForbiddenError`, `ConflictError`, `ValidationError`.
3. Сервисы бросают эти ошибки, не думая о HTTP-деталях ответа.
4. Единый обработчик в конце приложения:
   - свои ошибки → их статус и сообщение;
   - ошибки базы с известными кодами → понятные ответы;
   - всё остальное → 500 с общим текстом и полная запись в лог.

Отделяй **ожидаемые** ошибки (неверные данные, нет прав — это нормальная работа) от **неожиданных** (баги, база недоступна). Первые — понятный ответ клиенту, вторые — 500 и внимание разработчиков (лог, алерт в Sentry).

### Пример
```js
// src/errors.js
export class AppError extends Error {
  constructor(status, message, code, details) {
    super(message);
    this.status = status;
    this.code = code;
    this.details = details;
  }
}
export class NotFoundError extends AppError {
  constructor(what = "Ресурс") { super(404, `${what} не найден`, "NOT_FOUND"); }
}
export class ForbiddenError extends AppError {
  constructor() { super(403, "Нет прав на это действие", "FORBIDDEN"); }
}
export class ValidationError extends AppError {
  constructor(fields) { super(400, "Проверьте данные", "VALIDATION", fields); }
}
```

```js
// src/app.js — последний middleware
app.use((err, req, res, next) => {
  if (err instanceof AppError) {
    return res.status(err.status).json({ error: err.message, code: err.code, fields: err.details });
  }
  req.log?.error({ err, path: req.path }, "Необработанная ошибка");
  res.status(500).json({ error: "Внутренняя ошибка сервера", code: "INTERNAL" });
});
```

```js
// в сервисе
if (!project) throw new NotFoundError("Проект");
```

### Частые ошибки
- `throw "строка"` вместо объекта ошибки — теряется стек.
- Отдавать клиенту `err.message` любой ошибки.
- Ловить ошибку, ничего не делать и продолжать работу как ни в чём не бывало.

### Мини-задание
Заведи в своём API иерархию ошибок из 4–5 классов и перепиши сервисы на их использование. Проверь, что неожиданная ошибка (например, опечатка в SQL) даёт клиенту только общий текст. Потренируйся в задаче «Единая обработка ошибок».

### На пальцах
Конфигурация через окружение — один и тот же автомобиль, в который в разных городах заливают разное топливо и вставляют разные ключи. Код не меняется между ноутбуком, тестовым сервером и продакшеном — меняются только переменные. И все настройки собраны в одном месте, а не разбросаны по файлам.

### Как это работает
Правила (из методологии «12 факторов»):

- всё, что отличается между окружениями, — в переменных окружения: адреса баз, ключи, порты, адрес фронтенда, уровень логов;
- код читает переменные **в одном модуле** `config.js`, проверяет их при старте и экспортирует готовый объект;
- остальной код импортирует `config`, а не обращается к `process.env` повсюду;
- если чего-то не хватает или значение неверное — сервер не стартует и пишет понятную ошибку;
- значения по умолчанию — только для безопасных настроек (порт, уровень логов), не для секретов.

Проверять удобно zod-схемой: она же приводит типы (строка → число, строка → boolean).

### Пример
```js
// src/config.js
import { z } from "zod";

const schema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  DATABASE_URL: z.string().url().refine(u => u.startsWith("postgres"), "Нужна строка PostgreSQL"),
  JWT_SECRET: z.string().min(32, "JWT_SECRET слишком короткий"),
  CORS_ORIGINS: z.string().default("http://localhost:5173"),
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
});

const parsed = schema.safeParse(process.env);
if (!parsed.success) {
  console.error("Ошибка конфигурации:", parsed.error.flatten().fieldErrors);
  process.exit(1);
}

const env = parsed.data;
export const config = {
  isProd: env.NODE_ENV === "production",
  port: env.PORT,
  databaseUrl: env.DATABASE_URL,
  jwtSecret: env.JWT_SECRET,
  corsOrigins: env.CORS_ORIGINS.split(",").map(s => s.trim()),
  logLevel: env.LOG_LEVEL,
};
```

```js
// в остальном коде
import { config } from "./config.js";
app.listen(config.port);
```

### Частые ошибки
- `process.env.SOMETHING` в двадцати файлах.
- Значение по умолчанию для секрета: `JWT_SECRET || "secret"` — продакшен случайно запускается с известным ключом.
- Проверять переменные «когда понадобятся» — сервер падает через час работы.

### Мини-задание
Сделай модуль `config.js` с zod-схемой для всех переменных своего API и замени все обращения к `process.env`. Запусти сервер без `DATABASE_URL` и с коротким `JWT_SECRET` и посмотри сообщения. Потренируйся в задаче «Проверка окружения при запуске».

### На пальцах
Логи — бортовой журнал корабля. Когда что-то случилось ночью, капитан утром открывает журнал и видит: в 03:12 — запрос такой-то, в 03:12 — ошибка базы, в 03:13 — повтор. Уровни — пометки важности: «для отладки», «для сведения», «внимание», «авария». Структурированные логи — журнал не свободным текстом, а таблицей, по которой легко искать.

### Как это работает
Уровни:

| Уровень | Когда |
|---|---|
| `debug` | подробности для отладки, в продакшене обычно выключены |
| `info` | важные события: сервер запущен, пользователь зарегистрировался, заказ оплачен |
| `warn` | что-то необычное, но работа продолжается: повторная попытка, медленный запрос |
| `error` | ошибка, требующая внимания: необработанное исключение, недоступен сервис |

Структурированный лог — JSON-строка с полями, а не просто текст:

```json
{"level":"info","time":"2026-10-24T12:00:00Z","reqId":"a1b2","method":"POST","path":"/api/orders","status":201,"ms":42,"userId":17}
```

Такие логи можно фильтровать и искать в сервисах логов (Grafana Loki, Better Stack, логи Render): «все ошибки пользователя 17 за час».

Что писать в каждую строку: время, уровень, сообщение, id запроса (чтобы связать все строки одного запроса), пользователь, путь, статус, длительность.

Чего не писать никогда: пароли, токены, номера карт, полные персональные данные.

Популярная библиотека — **pino**: быстрая, пишет JSON, умеет скрывать указанные поля (`redact`).

### Пример
```js
import pino from "pino";
import pinoHttp from "pino-http";
import { randomUUID } from "node:crypto";

export const logger = pino({
  level: process.env.LOG_LEVEL ?? "info",
  redact: ["req.headers.authorization", "req.headers.cookie", "*.password"],
});

app.use(pinoHttp({ logger, genReqId: () => randomUUID() }));   // строка на каждый запрос

app.post("/api/orders", wrap(async (req, res) => {
  const order = await createOrder(req.body, req.user);
  req.log.info({ orderId: order.id, total: order.total }, "Заказ создан");
  res.status(201).json(order);
}));
```

### Частые ошибки
- `console.log("тут")`, `console.log(data)` без контекста — по таким логам ничего не найти.
- Логировать тело запроса целиком вместе с паролем.
- Всё на уровне `error` или всё на уровне `info` — важное тонет в шуме.

### Мини-задание
Подключи pino и pino-http к своему API, настрой `redact` для пароля и cookie. Создай ошибку в одном маршруте и найди в логах все строки этого запроса по его id.

### На пальцах
Структура папок — план склада. В маленькой кладовке можно сложить всё на одну полку. На большом складе нужны секции: «обувь», «одежда», «электроника», и в каждой — свои стеллажи. Новый сотрудник должен находить нужную коробку, не спрашивая.

### Как это работает
Два популярных подхода.

**По слоям** — просто и понятно для небольших API:

```text
src/
├── index.js           ← запуск сервера
├── app.js             ← express, middleware, роутеры
├── config.js
├── db.js
├── errors.js
├── middleware/        ← auth, validate, rateLimit
├── routes/            ← projects.js, clients.js, auth.js
├── services/          ← бизнес-правила
└── repositories/      ← SQL
```

**По модулям (фичам)** — лучше растёт, всё про одну сущность рядом:

```text
src/
├── app.js
├── config.js
├── shared/            ← db, errors, logger, middleware
└── modules/
    ├── projects/
    │   ├── projects.routes.js
    │   ├── projects.service.js
    │   ├── projects.repo.js
    │   ├── projects.schema.js     ← zod-схемы
    │   └── projects.test.js
    ├── clients/
    └── auth/
```

Плюс в корне: `migrations/`, `scripts/` (migrate, seed), `tests/` (общие хелперы и интеграционные тесты), `.env.example`, `Dockerfile`, `README.md`.

Начни с «по слоям». Когда файлов в папке `services` становится больше 10–15, переходи на модули.

### Пример
```js
// src/modules/projects/projects.routes.js
import { Router } from "express";
import { requireUser } from "../../shared/middleware/auth.js";
import { validate } from "../../shared/middleware/validate.js";
import { createProjectSchema } from "./projects.schema.js";
import * as service from "./projects.service.js";

export const projectsRouter = Router();
projectsRouter.use(requireUser);
projectsRouter.get("/", async (req, res) => res.json(await service.list(req.user)));
projectsRouter.post("/", validate(createProjectSchema), async (req, res) => {
  res.status(201).json(await service.create(req.body, req.user));
});
```

### Частые ошибки
- Всё в одном `index.js` на тысячу строк.
- Смешивать подходы: часть кода по слоям, часть по модулям.
- Модуль импортирует внутренности другого модуля напрямую вместо его сервиса.

### Мини-задание
Перестрой свой API по одному из подходов. Нарисуй в README дерево папок с пояснением, что где лежит. Проверь, что все тесты проходят после переезда.

### На пальцах
Монолит — один большой ресторан, где кухня, зал и склад под одной крышей. Микросервисы — сеть отдельных заведений: одно только печёт, другое только жарит, третье только доставляет, и они созваниваются по телефону. Сеть гибче на огромных масштабах, но для одного кафе на 30 мест строить её — безумие: больше времени уйдёт на телефонные звонки, чем на готовку.

### Как это работает
| | Монолит | Микросервисы |
|---|---|---|
| Что это | одно приложение, одна база | много маленьких сервисов, у каждого своя база |
| Деплой | один | у каждого свой |
| Общение частей | вызов функции | по сети: HTTP, очереди |
| Ошибки на стыках | редко | сеть может упасть в любой момент |
| Отладка | один лог, один процесс | трассировка запроса через несколько сервисов |
| Нужно команде | 1–10 человек | много команд, каждой свой сервис |

Почему начинают с монолита:

- быстрее разрабатывать и менять: всё в одном репозитории, рефакторинг — простое переименование;
- транзакции работают сами — в микросервисах согласованность данных между базами становится отдельной сложной задачей;
- проще деплой, мониторинг, тесты;
- пока продукт ищет себя, границы между частями всё время сдвигаются — в микросервисах каждая такая правка болезненна.

Хороший путь — **модульный монолит**: одно приложение, но с чёткими модулями и границами между ними. Если когда-нибудь действительно понадобится, модуль можно вынести в отдельный сервис.

Причины выделять сервис: сильно разная нагрузка (обработка видео), отдельная команда, другой язык или требования к надёжности.

### Пример
```text
Модульный монолит студии:

studio-api (один процесс, одна база PostgreSQL)
├── modules/auth       ← вход, роли
├── modules/clients
├── modules/projects   ← использует clients через его сервис, а не через таблицы
├── modules/billing    ← платежи
└── jobs/              ← фоновые задачи (письма, отчёты) — тот же код, отдельный процесс
```

### Частые ошибки
- Начинать учебный или стартап-проект с пяти микросервисов и Kubernetes.
- Монолит без внутренних границ — «большой комок грязи», где всё зависит от всего.
- Микросервисы с общей базой данных — сложности обоих подходов без плюсов.

### Мини-задание
Нарисуй схему модулей своего проекта как модульного монолита: какие модули, какие зависимости между ними. Найди место, где один модуль лезет напрямую в таблицы другого, и замени на вызов его сервиса.
