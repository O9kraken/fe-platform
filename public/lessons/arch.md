### Ситуация
Обработчик `POST /api/projects/:id/close` занимает 80 строк: разбор запроса, три SQL-запроса, проверка оплаты, отправка письма, формирование ответа. Теперь то же самое нужно сделать из фонового скрипта — и приходится копировать, потому что логика намертво спаяна с `req` и `res`. Протестировать правило «нельзя закрыть без оплаты» без запуска сервера и базы невозможно. Разделение на слои решает это.

### На пальцах
Ресторан работает потому, что у каждого своя роль: официант принимает заказ и приносит блюдо (маршрут), повар решает, как готовить (сервис), кладовщик знает, где лежат продукты (репозиторий). Если официант сам бегает в подвал и жарит котлеты — бардак. Слои — то же разделение обязанностей в коде сервера.

### Как это работает
>> Маршрут — HTTP → сервис — бизнес-правила → репозиторий — SQL

| Слой | Отвечает за | Не знает о |
|---|---|---|
| **Маршрут (controller)** | HTTP: разобрать запрос, вызвать сервис, вернуть статус и JSON | SQL, бизнес-правилах |
| **Сервис** | бизнес-правила: «нельзя закрыть проект без оплаты», «скидка постоянным клиентам» | HTTP (`req`, `res`) и SQL |
| **Репозиторий** | доступ к данным: SQL или ORM-запросы | HTTP, бизнес-правилах |

Зависимости идут в одну сторону: маршрут → сервис → репозиторий.

Зачем:

- бизнес-правила в одном месте, их легко найти и протестировать без HTTP и базы;
- можно сменить базу или ORM, переписав только репозитории;
- один сервис можно вызвать из маршрута, из фонового задания и из скрипта.

Для небольшого проекта не нужно строить «энтерпрайз»: достаточно вынести SQL из маршрутов и держать правила в сервисах.

?: Почему сервис не должен принимать `req` и `res`? || Тогда его можно вызвать только из HTTP-обработчика. Фоновая задача, скрипт или тест не имеют `req` и `res` и не смогут использовать ту же логику. Сервис должен получать обычные данные и возвращать результат или бросать ошибку.

### Частые ошибки
- **SQL и бизнес-правила прямо в обработчиках маршрутов.**
- **Сервис принимает `req` и `res`** — его нельзя вызвать вне HTTP.
- **Десять слоёв абстракций** для CRUD из трёх таблиц.

?? В каком направлении идут зависимости между слоями? || Маршрут → сервис → репозиторий; нижние слои ничего не знают о верхних.
?? Объясни своими словами главную пользу разделения на слои. || Бизнес-правила лежат в одном месте, их можно тестировать и переиспользовать без HTTP и базы, а замена базы или фреймворка затрагивает только свой слой.

В одном месте сервиса ты пишешь `throw new Error("not found")`, в другом — `throw "нет прав"`, в третьем — `return null`, и маршрут гадает, что это значит. В результате клиент то получает 500 на «не найдено», то видит текст ошибки базы. Нужен общий язык ошибок: сервис говорит, что случилось, а один обработчик решает, как об этом сообщить.

### На пальцах
Если каждый сотрудник сам решает, как отвечать на жалобы, клиенты получают то вежливое письмо, то грубость, то технические подробности склада. Свои классы ошибок — стандартные бланки отказов («не найдено», «нет прав», «конфликт»), а единый обработчик — один отдел, который по бланку формирует правильный ответ.

### Как это работает
>> `throw new HttpError(404, …)` → ошибка летит вверх → единый обработчик → ответ клиенту

1. Базовый класс `AppError` (или `HttpError`) со статусом и машиночитаемым кодом.
2. Наследники под типовые случаи: `NotFoundError`, `ForbiddenError`, `ConflictError`, `ValidationError`.
3. Сервисы бросают эти ошибки, не думая о деталях ответа.
4. Единый обработчик в конце приложения:
   - свои ошибки → их статус и сообщение;
   - ошибки базы с известными кодами → понятные ответы;
   - всё остальное → 500 с общим текстом и полная запись в лог.

Отделяй **ожидаемые** ошибки (неверные данные, нет прав — это нормальная работа) от **неожиданных** (баги, база недоступна). Первые — понятный ответ клиенту, вторые — 500 и внимание разработчиков (лог, алерт в Sentry).

?: Почему `throw "строка"` хуже, чем `throw new Error(...)`? || У строки нет стека вызовов: в логе будет только текст, без указания, где именно возникла ошибка. Кроме того, проверка `err instanceof AppError` не сработает, и обработчик не сможет отличить ожидаемую ошибку от бага.

### Пример
```js
export class AppError extends Error {
  constructor(status, message, code) {
    super(message);
    this.status = status;
    this.code = code;
  }
}
export class NotFoundError extends AppError {
  constructor(what = "Ресурс") { super(404, `${what} не найден`, "NOT_FOUND"); }
}

app.use((err, req, res, next) => {
  if (err instanceof AppError) {
    return res.status(err.status).json({ error: err.message, code: err.code });
  }
  req.log?.error({ err, path: req.path }, "Необработанная ошибка");
  res.status(500).json({ error: "Внутренняя ошибка сервера", code: "INTERNAL" });
});
```

?! Сервис бросил `new NotFoundError("Проект")`, а в другом месте — `TypeError` из-за опечатки. Какие ответы получит клиент и что попадёт в лог? || На `NotFoundError` — 404 «Проект не найден» с кодом `NOT_FOUND`, в лог ничего особенного: это ожидаемая ситуация. На `TypeError` — 500 «Внутренняя ошибка сервера», а полные подробности со стеком уйдут в лог для разработчиков.

### Частые ошибки
- **`throw "строка"`** вместо объекта ошибки — теряется стек.
- **`err.message` любой ошибки клиенту.**
- **Поймать ошибку и молча продолжить** как ни в чём не бывало.

### Проверь себя
?? Чем ожидаемые ошибки отличаются от неожиданных? || Ожидаемые — часть нормальной работы: неверные данные, нет прав, не найдено; клиент получает понятный ответ. Неожиданные — баги и сбои; клиент получает 500, а разработчики — подробности в логах.
?? Зачем делать наследников вроде `NotFoundError` от общего `AppError`? || Чтобы сервисы бросали понятные ошибки без деталей HTTP, а один обработчик по `instanceof AppError` превращал их в правильный статус и ответ.
?? Объясни своими словами, что даёт единый обработчик ошибок. || Все ошибки во всём приложении превращаются в ответы одного формата, технические детали не утекают к клиенту, а неожиданные сбои гарантированно попадают в лог.

### Ситуация
В двадцати файлах разбросаны обращения к `process.env`: где-то с запасным значением, где-то без, где-то `Number(process.env.PORT)`, а где-то строкой. На продакшене сервер работает час, а потом падает на запросе, которому понадобилась переменная, которую забыли задать. В другом месте `JWT_SECRET || "secret"` — и продакшен годами подписывал сессии ключом, который знает каждый.

### На пальцах
Конфигурация через окружение — один и тот же автомобиль, в который в разных городах заливают разное топливо и вставляют разные ключи. Код не меняется между ноутбуком, тестовым сервером и продакшеном — меняются только переменные. И все настройки собраны в одном месте, а не разбросаны по файлам.

### Как это работает
>> `process.env` → проверка zod при старте → объект `config` → везде импорт из одного места

Правила (из методологии «12 факторов»):

- всё, что отличается между окружениями, — в переменных окружения: адреса баз, ключи, порты, адрес фронтенда, уровень логов;
- код читает переменные **в одном модуле** `config.js`, проверяет их при старте и экспортирует готовый объект;
- остальной код импортирует `config`, а не обращается к `process.env` повсюду;
- если чего-то не хватает или значение неверное — сервер не стартует и пишет понятную ошибку;
- значения по умолчанию — только для безопасных настроек (порт, уровень логов), не для секретов.

Проверять удобно zod-схемой: она же приводит типы (строка → число, строка → boolean).

?: Почему опасно задавать секрету значение по умолчанию, например `JWT_SECRET || "secret"`? || Если на продакшене забудут задать переменную, сервер не упадёт, а молча запустится с известным всем ключом. Любой сможет подделать токены и войти как администратор. Без значения по умолчанию сервер просто не стартует — ошибку заметят сразу.

### Пример
```js
const schema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32, "JWT_SECRET слишком короткий"),
});

const parsed = schema.safeParse(process.env);
if (!parsed.success) {
  console.error("Ошибка конфигурации:", parsed.error.flatten().fieldErrors);
  process.exit(1);
}
```

?! Сервер запускают с переменными `PORT=abc` и `JWT_SECRET=dev`, а `DATABASE_URL` не задан. Что произойдёт? || Сервер не стартует и выведет все три проблемы сразу: `PORT` не превращается в число, `JWT_SECRET` короче 32 символов, `DATABASE_URL` отсутствует. Процесс завершится с кодом 1 — деплой упадёт до того, как пользователи что-то увидят.

### Частые ошибки
- **`process.env.SOMETHING` в двадцати файлах.**
- **Значение по умолчанию для секрета** — продакшен случайно запускается с известным ключом.
- **Проверка переменных «когда понадобятся»** — сервер падает через час работы.

### Проверь себя
?? Где в коде должны читаться переменные окружения? || В одном модуле конфигурации, который проверяет их при старте и экспортирует готовый объект для остального кода.
?? Для каких настроек допустимы значения по умолчанию? || Только для безопасных, вроде порта или уровня логов, — не для секретов и адресов боевых сервисов.
?? Объясни своими словами, зачем проверять конфигурацию при старте приложения. || Чтобы ошибка в настройках обнаружилась сразу и понятно, а не через час работы на случайном запросе, и чтобы сломанная конфигурация не попала к пользователям.

### Ситуация
Ночью у пользователя не оформился заказ. Утром ты открываешь логи Render и видишь тысячи строк: «тут», «data:», `[object Object]`, «ошибка». Какая из них относится к этому заказу? Непонятно. Логи пишут для того человека, который будет разбираться в аварии в три часа ночи, — то есть для тебя, и им нужна структура.

### На пальцах
Логи — бортовой журнал корабля. Когда что-то случилось ночью, капитан утром открывает журнал и видит: в 03:12 — запрос такой-то, в 03:12 — ошибка базы, в 03:13 — повтор. Уровни — пометки важности: «для отладки», «для сведения», «внимание», «авария». Структурированные логи — журнал не свободным текстом, а таблицей, по которой легко искать.

### Как это работает
>> `debug` → `info` → `warn` → `error` → JSON-строки с полями → поиск по логам

| Уровень | Когда |
|---|---|
| `debug` | подробности для отладки, в продакшене обычно выключены |
| `info` | важные события: сервер запущен, пользователь зарегистрировался, заказ оплачен |
| `warn` | что-то необычное, но работа продолжается: повторная попытка, медленный запрос |
| `error` | ошибка, требующая внимания: необработанное исключение, недоступен сервис |

Структурированный лог — JSON-строка с полями, а не просто текст:

```json
{"level":"info","time":"2026-10-24T12:00:00Z","reqId":"a1b2","method":"POST","path":"/api/orders","status":201,"ms":42,"userId":17}
```

Такие логи можно фильтровать и искать в сервисах логов: «все ошибки пользователя 17 за час».

Что писать в каждую строку: время, уровень, сообщение, id запроса (чтобы связать все строки одного запроса), пользователь, путь, статус, длительность.

Чего не писать никогда: пароли, токены, номера карт, полные персональные данные.

Популярная библиотека — **pino**: быстрая, пишет JSON, умеет скрывать указанные поля (`redact`).

?: Зачем каждому запросу уникальный id в логах? || Сервер обрабатывает сотни запросов одновременно, и их строки перемешиваются. По id запроса можно отфильтровать все строки одной истории — от прихода запроса до ошибки — и восстановить, что именно произошло.

### Пример
```js
export const logger = pino({
  level: process.env.LOG_LEVEL ?? "info",
  redact: ["req.headers.authorization", "req.headers.cookie"],
});

app.post("/api/auth/register", (req, res) => {
  req.log.info({ body: req.body }, "Регистрация");
  // ...
});
```

?! Что окажется в логах при каждой регистрации и почему это проблема? || Тело запроса целиком, включая пароль пользователя открытым текстом. Логи читает много людей и сервисов, они хранятся долго. Нужно логировать только нужные поля (email, id) или добавить `*.password` в `redact`.

### Частые ошибки
- **`console.log("тут")`, `console.log(data)` без контекста** — по таким логам ничего не найти.
- **Тело запроса целиком вместе с паролем.**
- **Всё на уровне `error` или всё на `info`** — важное тонет в шуме.

### Проверь себя
?? Назови четыре уровня логов и когда используется каждый. || `debug` — подробности для отладки, `info` — важные события, `warn` — необычное, но не критичное, `error` — ошибки, требующие внимания.
?? Чем структурированный лог лучше обычного текста? || Он записан в JSON с полями, поэтому его легко фильтровать и искать по значениям: пользователю, пути, статусу, id запроса.
?? Объясни своими словами, что нельзя писать в логи и почему. || Пароли, токены, номера карт и персональные данные. Логи хранятся долго и доступны многим людям и сервисам, поэтому любой секрет там — утечка.

Новый разработчик открывает твой API: 40 файлов в одной папке `src`, где `projects.js` — это маршруты, а `project.js` — запросы к базе, и непонятно, где правила. Он полдня ищет, где проверяется оплата. Хорошая структура папок отвечает на вопрос «где это лежит?» без единого вопроса коллегам.

### На пальцах
Структура папок — план склада. В маленькой кладовке можно сложить всё на одну полку. На большом складе нужны секции: «обувь», «одежда», «электроника», и в каждой — свои стеллажи. Новый сотрудник должен находить нужную коробку, не спрашивая.

### Как это работает
>> `routes/` → `services/` → `repositories/` → `config` и `errors` отдельно

**По слоям** — просто и понятно для небольших API:

```text
src/
├── index.js           ← запуск сервера
├── app.js             ← express, middleware, роутеры
├── config.js
├── db.js
├── errors.js
├── middleware/        ← auth, validate, rateLimit
├── routes/            ← projects.js, clients.js, auth.js
├── services/          ← бизнес-правила
└── repositories/      ← SQL
```

**По модулям (фичам)** — лучше растёт, всё про одну сущность рядом:

```text
src/
├── app.js
├── config.js
├── shared/            ← db, errors, logger, middleware
└── modules/
    ├── projects/
    │   ├── projects.routes.js
    │   ├── projects.service.js
    │   ├── projects.repo.js
    │   ├── projects.schema.js
    │   └── projects.test.js
    ├── clients/
    └── auth/
```

Плюс в корне: `migrations/`, `scripts/` (migrate, seed), `tests/`, `.env.example`, `Dockerfile`, `README.md`.

Начни с «по слоям». Когда файлов в папке `services` становится больше 10–15, переходи на модули.

?: Почему один модуль не должен лезть во внутренности другого, например в его репозиторий? || Тогда модули срастаются: изменишь таблицу проектов — сломаются клиенты, биллинг и всё, что напрямую читает её. Если общение идёт только через сервис модуля, внутренности можно менять свободно, пока сохраняется его публичный интерфейс.

### Пример

### Ситуация
На собеседовании тебя спрашивают: «Монолит или микросервисы?» Хочется ответить «микросервисы» — звучит современно, как у Netflix и Uber. А потом выясняется, что у стартапа из трёх разработчиков пять микросервисов, Kubernetes и половина времени уходит на то, чтобы они договорились друг с другом по сети. Правильный ответ почти всегда начинается со слов «зависит от…».

### На пальцах
Монолит — один большой ресторан, где кухня, зал и склад под одной крышей. Микросервисы — сеть отдельных заведений: одно только печёт, другое только жарит, третье только доставляет, и они созваниваются по телефону. Сеть гибче на огромных масштабах, но для одного кафе на 30 мест строить её — безумие: больше времени уйдёт на звонки, чем на готовку.

### Как это работает
>> Монолит: один деплой → растёт команда и нагрузка → выделить сервис по необходимости

| | Монолит | Микросервисы |
|---|---|---|
| Что это | одно приложение, одна база | много маленьких сервисов, у каждого своя база |
| Деплой | один | у каждого свой |
| Общение частей | вызов функции | по сети: HTTP, очереди |
| Ошибки на стыках | редко | сеть может упасть в любой момент |
| Отладка | один лог, один процесс | трассировка запроса через несколько сервисов |
| Нужно команде | 1–10 человек | много команд, каждой свой сервис |

Почему начинают с монолита:

- быстрее разрабатывать и менять: всё в одном репозитории, рефакторинг — простое переименование;
- транзакции работают сами — в микросервисах согласованность данных между базами становится отдельной сложной задачей;
- проще деплой, мониторинг, тесты;
- пока продукт ищет себя, границы между частями всё время сдвигаются.

Хороший путь — **модульный монолит**: одно приложение, но с чёткими модулями и границами. Если понадобится, модуль можно вынести в отдельный сервис.

Причины выделять сервис: сильно разная нагрузка (обработка видео), отдельная команда, другой язык или требования к надёжности.

?: Почему транзакции становятся сложной задачей в микросервисах? || В монолите заказ и списание со склада — одна транзакция в одной базе: всё или ничего. В микросервисах это две разные базы в разных сервисах, и общей транзакции нет. Если второй сервис упал после первого, нужно отдельно придумывать откат и согласование.

### Пример
```text
Стартап: 3 разработчика, продукт меняется каждую неделю.
Сервисы: auth, clients, projects, billing, notifications — каждый со своей базой,
общаются по HTTP, деплоятся в Kubernetes.
```

?! Какие проблемы, скорее всего, будут у этой команды и что бы ты предложил на собеседовании? || Каждое изменение затрагивает несколько сервисов и требует согласованного деплоя; сетевые сбои между сервисами; нет общих транзакций; много времени на инфраструктуру вместо продукта. Предложить модульный монолит с чёткими границами — а выносить в отдельный сервис только то, что действительно этого требует, например тяжёлые уведомления.

### Частые ошибки
- **Учебный или стартап-проект с пятью микросервисами и Kubernetes.**
- **Монолит без внутренних границ** — «большой комок грязи», где всё зависит от всего.
- **Микросервисы с общей базой данных** — сложности обоих подходов без плюсов.

### Проверь себя
?? Чем монолит отличается от микросервисов? || Монолит — одно приложение с одной базой и одним деплоем. Микросервисы — много отдельных сервисов со своими базами и деплоями, которые общаются по сети.
?? Что такое модульный монолит? || Одно приложение, разделённое внутри на модули с чёткими границами, которые общаются только через публичные интерфейсы друг друга.
?? Объясни своими словами, когда действительно стоит выделять микросервис. || Когда у части системы сильно отличается нагрузка, её развивает отдельная команда, нужен другой язык или особые требования к надёжности, — и выгода перевешивает сложность сетевого взаимодействия.
