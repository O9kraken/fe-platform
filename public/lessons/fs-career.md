### Как это работает
>> Почему перерисовался → где хранить данные → как измерить → как ускорить

**Рендер React**:

- компонент перерисовывается при изменении своего состояния, при перерисовке родителя и при изменении контекста, который он читает;
- React сравнивает новое дерево с предыдущим и обновляет в DOM только различия;
- `key` в списках помогает понять, какие элементы те же;
- лишние перерисовки уменьшают: опускают состояние ниже по дереву, разделяют контексты, используют `memo`, `useMemo`, `useCallback` — но только там, где это измеримо помогает.

**Состояние**:

- локальное (`useState`) — открыто ли меню, ввод в поле;
- общее для ветки — подъём состояния или Context;
- глобальное клиентское — Zustand или Context + useReducer;
- серверное — TanStack Query или серверные компоненты: кеш, повторы, инвалидация;
- состояние в адресе — фильтры, страница, вкладка: можно поделиться ссылкой.

**Производительность**:

- Core Web Vitals: LCP, INP, CLS — что измеряют и как улучшить;
- код-сплиттинг и ленивая загрузка, оптимизация картинок и шрифтов;
- длинные списки — виртуализация;
- инструменты: Lighthouse, вкладка Performance, React DevTools Profiler.

?: Почему серверные данные не стоит класть в глобальный стор вроде Zustand? || Это копия данных сервера, и её приходится вручную загружать, обновлять после изменений и считать устаревшей. TanStack Query делает это сам: кеширует, повторяет запросы, перезагружает после мутаций. Глобальный стор оставляют для чисто клиентского состояния.

### Как это работает
>> Аутентификация → авторизация → `WHERE id = $1 AND user_id = $2` → 404 для чужого

**HTTP**: методы и идемпотентность, коды (200/201/204, 400/401/403/404/409/422, 500), заголовки, cookie и их флаги, CORS и почему это не защита сервера, кеширование (`Cache-Control`, `ETag`).

### На пальцах
«Что происходит, когда вводишь адрес в браузере?» — любимый вопрос, потому что ответ проходит через всё, что ты изучил: сеть, сервер, базу, фронтенд. Это как рассказать путь письма от почтового ящика до адресата и обратно со всеми сортировочными пунктами. Чем подробнее и стройнее — тем лучше.

### Как это работает
>> DNS → TCP и TLS → HTTP-запрос → сервер и база → ответ → DOM, CSSOM, отрисовка

Полный ответ по шагам:

1. **Разбор адреса** — браузер выделяет протокол, домен, путь, параметры. Если это не адрес — отправляет в поиск.
2. **Кеши** — браузер проверяет, нет ли страницы или DNS-записи в кеше.
3. **DNS** — домен превращается в IP: кеш браузера → ОС → DNS-резолвер провайдера → корневые серверы → серверы зоны `.ru` → авторитетный сервер домена.
4. **TCP-соединение** с сервером на порту 443 (тройное рукопожатие).
5. **TLS** — проверка сертификата и договорённость о ключах шифрования.
6. **HTTP-запрос** — `GET /path` с заголовками (Host, cookie, Accept).
7. **На стороне сервера**: CDN или балансировщик → веб-сервер или Node.js-приложение → middleware (логирование, сессия, CORS) → маршрут → сервис → база (запрос, индексы) → формирование ответа.
8. **HTTP-ответ** — код, заголовки (`Content-Type`, `Cache-Control`, `Set-Cookie`), тело.
9. **Разбор HTML** — построение DOM; по пути находятся CSS, JS, картинки, шрифты — для каждого новые запросы (часто параллельно, по HTTP/2).
10. **CSS** → CSSOM; DOM + CSSOM → дерево отрисовки → **layout** (расчёт размеров и позиций) → **paint** (отрисовка) → **composite** (слои).
11. **JavaScript** — `defer`-скрипты выполняются после разбора HTML; фреймворк «оживляет» страницу (гидратация), навешивает обработчики, делает запросы к API за данными.
12. **Дальше** — события пользователя, новые запросы к API, перерисовки.

На собеседовании можно начать с короткой версии из шести-семи пунктов и углубиться туда, куда спросят.

?: Зачем нужен шаг TLS, если TCP-соединение уже установлено? || TCP только доставляет байты, но не шифрует их и не доказывает, что на том конце настоящий сайт. TLS проверяет сертификат (что это действительно studio.ru) и договаривается о ключах, чтобы никто по пути не прочитал и не подменил пароли и cookie.

Лайв-кодинг: «Сгруппируйте заказы по статусу». Ты молча пишешь 15 минут, интервьюер смотрит в тишине, в конце код падает на пустом массиве. Задача была решаемой, но интервьюер так и не понял, как ты думаешь. На лайв-кодинге рассуждения вслух важнее идеального кода с первой попытки.

### На пальцах
Тестовое задание — показать, как ты работаешь, когда никто не смотрит. Лайв-кодинг — показать, как ты думаешь, когда смотрят. В первом важен результат и порядок, во втором — рассуждения вслух: интервьюеру интереснее, как ты ищешь решение, чем идеальный код с первой попытки.

### Как это работает
>> Повторить задачу → план вслух → простое решение → проверить граничные случаи

**Тестовое для fullstack** обычно: маленькое приложение с фронтом и API (список с CRUD, авторизация, фильтры). Чек-лист:

- работающий фронт и бэк, запуск одной командой (Docker Compose — плюс);
- валидация на обеих сторонах, единый формат ошибок, состояния загрузки и ошибок в интерфейсе;
- права доступа, если есть пользователи;
- несколько тестов API и, по возможности, один e2e;
- README: запуск, решения, что не успел;
- деплой — серьёзный плюс;
- аккуратная история коммитов.

**Лайв-кодинг**:

1. Повтори задачу своими словами, уточни входные данные и граничные случаи.
2. Расскажи план до того, как писать код.
3. Начни с простого рабочего решения, потом улучшай.
4. Думай вслух: «здесь проверю пустой массив», «тут сложность O(n²), можно через Map».
5. Проверь на примерах, включая граничные.
6. Застрял — скажи, что рассматриваешь, и попроси подсказку. Это нормально.

Типичные задачи: работа с массивами и объектами (группировка, поиск дублей), строки, простые алгоритмы со счётчиками и `Map`, промисы (`Promise.all`, повтор с задержкой), маленький компонент React с состоянием, SQL-запрос.

?: Почему сначала пишут простое рабочее решение, а не сразу оптимальное? || Рабочее решение — уже результат: его можно проверить на примерах и потом улучшать. Погоня за идеалом с первой попытки часто заканчивается тем, что к концу времени нет никакого работающего кода.

### Пример

```js
// Лайв-кодинг: сгруппировать заказы по статусу и посчитать сумму в каждой группе
// Рассуждение вслух: «Пройду один раз по массиву, буду накапливать в объекте.
// Граничные случаи: пустой массив → пустой объект; сумма может быть строкой — приведу к числу».

function groupTotals(orders) {
  const result = {};
  for (const { status, total } of orders) {
    result[status] ??= { count: 0, sum: 0 };
    result[status].count += 1;
    result[status].sum += Number(total) || 0;
  }
  return result;
}

console.log(groupTotals([
  { status: "paid", total: 1500 },
  { status: "new", total: "800" },
  { status: "paid", total: 700 },
]));
```

?! Что выведет `console.log`? А что вернёт `groupTotals([{ status: "new", total: "abc" }])`? || `{ paid: { count: 2, sum: 2200 }, new: { count: 1, sum: 800 } }` — строка `"800"` приведена к числу. Во втором случае — `{ new: { count: 1, sum: 0 } }`: `Number("abc")` даёт `NaN`, а `NaN || 0` — это 0.

- **Молча писать код 15 минут.**
- **Пытаться сразу написать идеальное решение** и не написать никакого.
- **Красивый фронт в тестовом** без обработки ошибок и проверки прав на бэке.

### Проверь себя
?? Что сделать в первую очередь на лайв-кодинге? || Повторить задачу своими словами и уточнить входные данные и граничные случаи.
?? Что входит в чек-лист fullstack-тестового? || Работающий фронт и бэк с простым запуском, валидация на обеих сторонах, состояния ошибок, права, тесты, README, деплой, аккуратные коммиты.

### Ситуация
Финальный проект задеплоен, резюме готово, а ты всё ещё думаешь: «Вот доделаю ещё одну фичу — и начну откликаться». Проходит месяц. Первую работу находят не те, кто дольше готовился, а те, кто начал откликаться и учиться на каждом собеседовании. У тебя уже есть то, чего нет у многих новичков: опыт с реальными клиентами.

### На пальцах
Поиск первой работы fullstack-разработчиком — как искать арендаторов для нового помещения: чем больше точек, где о тебе узнают, тем быстрее найдётся подходящий. Площадки вакансий, стажировки, студии, знакомые, бывшие заказчики — у тебя уже есть то, чего нет у многих новичков: опыт с реальными клиентами.

### Как это работает
>> Отклики каждый день → собеседования → записать вопросы → повторить → снова отклики

Где искать:

- **hh.ru** и **Хабр Карьера** — подписки на «Junior Fullstack», «Junior Node.js», «Junior React», «JavaScript стажёр», фильтр по удалёнке.
- **Стажировки** крупных компаний (Яндекс, Т-Банк, Сбер, VK, Ozon, Авито, Kaspersky) — отбор сложный, но это сильный старт. Следи за сроками набора.
- **Веб-студии и агентства** — им особенно ценны fullstack-разработчики, которые понимают и сайты на CMS, и современный стек, и общение с заказчиком. Твой опыт с WordPress и SEO здесь — прямое преимущество.
- **Стартапы и небольшие продуктовые компании** — чаще берут универсальных разработчиков.
- **Telegram-каналы и чаты** с вакансиями для джунов и по стеку.
- **Нетворкинг** — митапы, профессиональные сообщества, знакомые разработчики, рекомендации.
- **Свои заказчики** — предложить разработку сервиса или личного кабинета клиентам, с которыми уже работал: это и опыт, и проект в портфолио.

Тактика:

- 5–10 персональных откликов в день, таблица откликов;
- разбор каждого собеседования: что спросили, на что не ответил;
- параллельно — улучшать финальный проект по обратной связи;
- откликаться при совпадении требований на 60–70%.

?: Почему стоит откликаться, даже если подходишь под требования на 60–70%? || Требования в вакансиях часто — список пожеланий, а не жёсткий фильтр. Компании регулярно берут кандидатов без части пунктов, если видят, что они быстро учатся. Не откликнувшись, ты отказываешь себе сам — вместо работодателя.
