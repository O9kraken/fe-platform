### Ситуация
Ты выкатил сайт, и через неделю приходит отчёт об ошибке: «Cannot read properties of undefined (reading 'price')». Где-то в коде вместо товара пришло «ничего», и узнал ты об этом от пользователя. TypeScript ловит такие ошибки ещё в редакторе — красной волнистой линией, до того как код вообще запустится. Поэтому его спрашивают почти в каждой вакансии.

### На пальцах
JavaScript — разговор без договорённостей: тебе могут дать вместо числа строку, и узнаешь ты об этом, только когда всё сломается у пользователя. TypeScript — договор, подписанный заранее: «здесь всегда число». Редактор проверяет договор, пока ты пишешь код, и подчёркивает нарушение до запуска.

### Как это работает
>> `let n = 5` → TS сам выводит `number` → `n = 'a'` → ошибка ещё до запуска

- TypeScript — это JavaScript плюс типы. Файлы `.ts` и `.tsx` перед запуском превращаются в обычный JS, типы при этом стираются.
- Ошибки типов видны в редакторе и при сборке, в браузере их уже нет.
- Базовые типы: `string`, `number`, `boolean`, `null`, `undefined`, массивы `number[]`, `string[]`.
- Тип пишется после двоеточия: `let age: number = 27`.

Вывод типов: TypeScript сам догадывается о типе по значению. `let age = 27` — уже `number`. Явно типы указывают там, где догадаться нельзя: параметры функций, пустые массивы, данные с сервера.

`any` — «тип какой угодно», он отключает проверки. Его стараются не использовать.

?: Если типы стираются при сборке, как они помогают? || Вся польза — до запуска: редактор подсказывает поля, ловит опечатки и несовпадения типов, сборка не пропускает ошибки. Браузеру типы уже не нужны — к этому моменту код проверен.

### Пример
```ts

budget = "много";

const ids: number[] = [];
ids.push("7");
```

### Частые ошибки
- **Типы везде**, даже где TypeScript и так всё понял: `const name: string = "Анна"`.

- **Вера в проверку данных в работе.** TypeScript проверяет код до запуска; данные с сервера всё равно нужно проверять.

Описав форму объекта один раз, ты заставляешь TypeScript следить, чтобы все двадцать мест говорили на одном языке.

### На пальцах
`type` и `interface` — шаблон анкеты: какие поля в ней есть и что в каждое можно вписать. Описал один раз «Пользователь: имя — текст, возраст — число», и TypeScript проверит каждую анкету в программе: не забыли ли поле, не вписали ли в возраст слово.

### Как это работает
>> `type User = {…}` → `interface User {…}` → описать форму объекта → редактор подсказывает поля

```ts
type User = { name: string; age: number };
interface User2 { name: string; age: number }
```

Для описания объектов они почти одинаковы. Разница:

- `interface` можно расширять через `extends` и «дописывать» повторным объявлением.
- `type` умеет больше: объединения (`"new" | "paid"`), псевдонимы для любых типов, комбинации через `&`.

Практичное правило: для объектов и props — что принято в проекте (часто `type`), для объединений — только `type`.

```ts
interface Person { name: string }
interface Employee extends Person { position: string }
```

Поле только для чтения: `readonly id: number`. Необязательное поле: `assignee?: string`.

?: Почему тип статуса лучше описать как `"new" | "in_progress" | "done"`, а не просто `string`? || `string` пропустит любую опечатку: `"Done"`, `"finished"`, `"dnoe"`. Объединение литералов разрешает только три точных значения и ещё подсказывает их в редакторе при вводе.

### Пример
```ts

  title: string;
```

- **Все поля необязательные «на всякий случай»** — TypeScript перестаёт помогать.

Номер заказа приходит то числом `1042`, то строкой `"A-1042"`. Телефон у пользователя то есть, то нет. Запрос то успешен с данными, то с ошибкой и текстом. Код, который забывает про один из вариантов, падает в самый неподходящий момент. TypeScript умеет заставить тебя обработать все варианты — и при этом сам понимает, какой вариант перед ним.

### На пальцах
Объединение `string | number` — графа анкеты, куда можно вписать и текст, и число, например номер квартиры «12» или «12А». Необязательное поле — графа «Отчество (если есть)». TypeScript следит, чтобы ты учёл оба варианта, прежде чем работать со значением.

### Как это работает
>> `string | number` — одно из → `age?: number` — может не быть → сузить проверкой `typeof`

- Объединение (union): `let id: string | number`. Значение может быть одного из типов.
- Пока тип не уточнён, разрешены только операции, общие для всех вариантов.
- **Сужение типа**: после проверки TypeScript понимает, какой вариант перед ним. Проверки: `typeof x === "string"`, `x === null`, `"field" in obj`, `Array.isArray(x)`.
- Объединение строковых литералов — самый частый случай: `type Size = "s" | "m" | "l"`.
- Необязательное поле `phone?: string` имеет тип `string | undefined`. Перед использованием проверь или используй `?.` и `??`.

Размеченное объединение: у всех вариантов есть общее поле-«метка», по которому TypeScript точно определяет вариант.

?: Как TypeScript «узнаёт», что внутри `if (typeof id === "number")` переменная — число? || Он анализирует ход программы: в ветке, куда попадают только при истинной проверке, остаётся единственный подходящий вариант объединения. Это называется сужением типа, и работает оно с `typeof`, сравнениями, `in` и другими проверками.

### Пример
```ts
type Result =
  | { status: "ok"; data: string[] }
  | { status: "error"; message: string };

function show(r: Result) {
  console.log(r.data);
  if (r.status === "ok") console.log(r.data.length);
  else console.log(r.message);
}
```

?! Какая строка функции не скомпилируется и почему? || Первая — `console.log(r.data)`. До проверки `status` TypeScript не знает, какой вариант пришёл, а у варианта с ошибкой поля `data` нет. Внутри веток всё в порядке: тип уже сужен.

### Частые ошибки
- **Метод строки у `string | number` без проверки** — ошибка компиляции.
- **Необязательное поле как обязательное:** `u.phone.length`.
- **`!`, чтобы заглушить TypeScript:** `u.phone!.length`. Это обещание «значение точно есть», и если оно ложное — ошибка в работе.

### Проверь себя
?? Что можно делать со значением типа `string | number` без проверки? || Только то, что общее для обоих типов, например вызвать `toString()`.
?? Какой тип у необязательного поля `phone?: string`? || `string | undefined`.
?? Объясни своими словами, что такое размеченное объединение. || Несколько вариантов объекта с общим полем-меткой, например `status`. Проверив метку, TypeScript точно знает, какие ещё поля есть у объекта.

### На пальцах
Тип функции — инструкция на упаковке прибора: «на вход — 220 вольт, на выходе — горячая вода». Подключишь к 380 или будешь ждать лёд — TypeScript предупредит заранее. Тип массива — подпись на коробке: «здесь только яблоки».

### Как это работает
>> `(a: number, b: number): number` → `string[]` → ошибки в аргументах видны сразу

```ts
function sum(a: number, b: number): number { return a + b; }
const greet = (name: string, title = "гость"): string => `Привет, ${title} ${name}`;
```

- Параметрам типы указывают всегда — TypeScript не может их угадать.
- Тип результата после скобок можно не писать — его выведут. Явно пишут для публичных функций, чтобы случайно не вернуть не то.
- Необязательный параметр: `(name?: string)`. Значение по умолчанию тоже делает его необязательным.
- Функция, которая ничего не возвращает, — тип `void`.
- Тип самой функции (например, для колбэка): `(item: Task) => void`.

Массивы: `number[]` или `Array<number>`. Массив объектов: `Task[]`. Кортеж — массив фиксированной длины с разными типами: `[string, number]`.

Методы массивов наследуют типы: если `tasks: Task[]`, то `tasks.map(t => t.title)` — это `string[]` само собой.

?: Почему TypeScript выводит тип переменной из значения, но не может вывести тип параметра функции? || Значение переменной видно прямо в коде. А параметр получит значение позже, при вызове — и вызовов может быть много, с чем угодно. Поэтому договор о том, что принимает функция, ты пишешь сам.

### Пример
```ts
type Task = { id: number; title: string; done: boolean };

function toggle(tasks: Task[], id: number): Task[] {
  return tasks.map(t => (t.id === id ? { ...t, done: !t.done } : t));
}

const tasks: Task[] = [{ id: 1, title: "Макет", done: true }];
const titles = tasks.map(t => t.title);
toggle(tasks, "1");
```

?! Какой тип у `titles` и что скажет TypeScript о последней строке? || `titles` — `string[]`, выведено само из типа `Task`. Последняя строка — ошибка: передана строка `"1"`, а параметр `id` ожидает `number`.

### Частые ошибки
- **Параметры без типов** — молча становятся `any` (или ошибка при `strict`).
- **`Array` без указания, чего массив:** `const list: Array = []`.
- **`undefined` вместо `void`** в колбэках «ничего не возвращает».

?? Как описать тип колбэка, который принимает задачу и ничего не возвращает? || `(t: Task) => void`.
?? Что такое кортеж? || Массив фиксированной длины, где у каждой позиции свой тип, например `[number, number]` для координат.
?? Объясни своими словами, почему параметрам функции нужно явно писать типы. || TypeScript не знает, с чем функцию вызовут, поэтому договор о входных данных нужно задать вручную. Тогда неправильный вызов подсветится сразу.

### Ситуация
Ты пишешь функцию `first(arr)`, которая возвращает первый элемент массива. Для массива чисел она должна вернуть число, для пользователей — пользователя. Если написать `any`, TypeScript забудет, что именно ты достал, и подсказки пропадут. Писать отдельную функцию для каждого типа — абсурд. Generics решают это одной строкой.

### На пальцах
Generic — коробка с окошком для этикетки. Сама коробка одна, но на этикетке пишешь, что внутри: «коробка яблок», «коробка книг». И дальше TypeScript помнит: из коробки яблок достаются именно яблоки, а не «что-то».

### Как это работает
>> `function first<T>(arr: T[]): T` → тип подставляется сам → одна функция для любых данных

Иногда функция работает с любым типом, но важна связь между входом и выходом. С `any` эта связь теряется.

Generic — параметр-тип, обычно его называют `T`:

```ts
function first<T>(items: T[]): T | undefined {
  return items[0];
}
```

- `first([1, 2, 3])` — TypeScript сам понял, что `T = number`, результат — `number | undefined`.
- `first(["a"])` — `T = string`.

Ты уже пользуешься generics, даже не замечая: `Array<string>`, `Promise<User>`, `useState<string>()`, `Map<string, number>`.

Ограничение generic: `<T extends { id: number }>` — «любой тип, но у него должно быть поле id».

?: Чем `first<T>(items: T[]): T` лучше, чем `first(items: any[]): any`? || С `any` результат — «неизвестно что», и TypeScript не подскажет ни одного поля. С generic он помнит: передал массив пользователей — получил пользователя, со всеми подсказками и проверками.

### Пример
```ts
function byId<T extends { id: number }>(items: T[], id: number): T | undefined {
  return items.find(i => i.id === id);
}

type User = { id: number; name: string };
const users: User[] = [{ id: 1, name: "Анна" }];

const anna = byId(users, 1);
const word = byId(["a", "b"], 1);
```

?! Какой тип у `anna` и что не так со второй строкой вызова? || `anna` — `User | undefined`. Второй вызов не скомпилируется: у строк нет поля `id`, а ограничение `T extends { id: number }` этого требует.

### Частые ошибки
- **Generic там, где хватит обычного типа.** Он нужен, когда тип выхода зависит от типа входа.
- **`any` вместо generic** — подсказки потеряны.
- **Вера, что `getJson<User[]>` проверяет данные.** Это только обещание для компилятора, сервер может прислать что угодно.

### Проверь себя
?? Что такое `T` в записи `function first<T>(items: T[])`? || Параметр-тип: место для конкретного типа, который TypeScript подставит при вызове.
?? Что означает `<T extends { id: number }>`? || Подойдёт любой тип, но у него обязательно должно быть поле `id` типа `number`.
?? Объясни своими словами, где ты уже встречал generics. || В записях вроде `Array<string>`, `Promise<User>` и `useState<number>()` — в угловых скобках указывается, с каким типом работает конструкция.

### Ситуация
TypeScript ругается на десяток строк, и ты делаешь «как в интернете советуют»: ставишь `as any` или выключаешь `strict`. Ошибки пропали — и вместе с ними вся защита. Через месяц ловишь в продакшене «Cannot read properties of null», которую TypeScript честно пытался показать. Разберёмся, как работать с неизвестными данными, не отключая охрану.

### На пальцах
`any` — пропуск «всё можно» на любой этаж: удобно, но охрана больше ничего не проверяет. `unknown` — посылка без подписи: принять можно, но открывать и пользоваться — только после проверки, что внутри. `strict` в настройках — включить охрану на полную.

### Как это работает
>> `any` — проверки выключены → `unknown` — сначала проверь → `strict: true` — максимум защиты

- `any` отключает проверки для значения и всего, что из него получено.
- `unknown` — безопасная альтернатива для «неизвестно что». С ним ничего нельзя делать, пока не сузишь тип проверкой: `typeof`, `Array.isArray`, `instanceof`, проверка полей.
- Где встречается неизвестное: `JSON.parse`, ответ сервера, `catch (error)`, данные из `localStorage`.

`tsconfig.json` — настройки компилятора. Главная — `"strict": true`. Она включает набор проверок:

- `strictNullChecks` — `null` и `undefined` нельзя использовать там, где ждут значение.
- `noImplicitAny` — запрещает молчаливые `any`, например у параметров без типа.

В новых проектах (Vite, Next.js) `strict` включён по умолчанию — не выключай его.

?: Почему ошибка в `catch (error)` имеет тип `unknown`, а не `Error`? || В JavaScript бросить можно что угодно: строку, число, объект. TypeScript не может гарантировать, что пришёл именно `Error`, поэтому просит проверить: `error instanceof Error`.

### Пример
```ts
const data: unknown = JSON.parse('{"theme":"dark"}');
const a: any = JSON.parse('{"theme":"dark"}');

console.log(a.thme.toUpperCase());
console.log(data.theme);
```

?! Какая строка не скомпилируется, а какая скомпилируется, но упадёт при запуске? || `data.theme` не скомпилируется — у `unknown` нельзя брать поля без проверки. `a.thme.toUpperCase()` скомпилируется, потому что `any` разрешает всё, но в работе упадёт: опечатка `thme` даёт `undefined`. Вот почему `unknown` безопаснее.

### Частые ошибки
- **Выключать `strict`, потому что «слишком много ошибок».** Эти ошибки — настоящие баги.
- **`as any`, чтобы закрыть ошибку.**
- **Точный тип для ответа сервера без проверки.** Для внешних данных удобна валидация через zod — к ней вернёмся позже.

### Проверь себя
?? Чем `unknown` отличается от `any`? || С `any` можно делать что угодно без проверок. С `unknown` ничего нельзя делать, пока проверкой не уточнишь тип.
?? Какую настройку `tsconfig.json` нужно держать включённой? || `"strict": true`.
?? Объясни своими словами, что даёт `strictNullChecks`. || Не позволяет использовать значение, которое может быть `null` или `undefined`, без проверки. Это ловит одну из самых частых ошибок в JavaScript.
