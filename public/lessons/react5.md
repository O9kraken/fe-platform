### На пальцах
Бабушка хочет передать внучке пирожок, но между ними пять родственников, и каждый должен передать пирожок дальше, хотя самим им он не нужен. Prop drilling — когда данные протаскивают через много компонентов-«посредников» только ради того, чтобы они дошли до глубоко вложенного компонента.

### Как это работает
Пример: тема сайта нужна кнопке в самом низу дерева. `App → Layout → Header → Toolbar → ThemeButton`. Каждый промежуточный компонент принимает `theme` и передаёт дальше.

Когда это проблема:

- посредников больше двух-трёх;
- одни и те же данные нужны во многих местах (текущий пользователь, тема, язык, корзина);
- переименовать проп — значит править пять файлов.

Когда это нормально:

- передача на один-два уровня — это просто явный поток данных, его легко читать;
- данные нужны только одной ветке.

Что делать:

1. Композиция: передать готовый элемент через `children`, чтобы посредник не знал о данных.
2. Context — «радиовещание» для всего поддерева.
3. Менеджер состояния (Zustand) — для сложного общего состояния.

### На пальцах

### Как это работает
Context:

1. `const CartContext = createContext(...)` — создать «канал».
2. `<CartContext.Provider value={...}>` — вещать значение для всего, что внутри.
3. `useContext(CartContext)` — «настроиться на канал» в любом вложенном компоненте.

Когда значение провайдера меняется, перерисовываются все, кто его читает.

useReducer:

```tsx
const [state, dispatch] = useReducer(reducer, начальное);
dispatch({ type: "add", item });
```

- `reducer(state, action)` — чистая функция: по текущему состоянию и действию возвращает новое.
- Удобен, когда переходов много и они связаны: корзина, сложная форма, пошаговый мастер.

Вместе они дают простой «глобальный стор»: reducer хранит логику, Context раздаёт состояние и `dispatch`.

?: Почему reducer обязан быть чистой функцией? || React может вызвать его несколько раз, например в StrictMode, и ожидает одинаковый результат. Кроме того, чистый reducer легко тестировать: подал состояние и действие — сравнил результат, без браузера и сервера.

### Пример
```tsx
type Item = { id: number; title: string; qty: number };
type Action =
  | { type: "add"; item: Omit<Item, "qty"> }
  | { type: "remove"; id: number }
  | { type: "clear" };

function cartReducer(state: Item[], action: Action): Item[] {
  switch (action.type) {
    case "add": {
      const found = state.find(i => i.id === action.item.id);
      return found
        ? state.map(i => (i.id === action.item.id ? { ...i, qty: i.qty + 1 } : i))
        : [...state, { ...action.item, qty: 1 }];
    }
    case "remove":
      return state.filter(i => i.id !== action.id);
    case "clear":
      return [];
  }
}

let s: Item[] = [];
s = cartReducer(s, { type: "add", item: { id: 1, title: "Чай" } });
s = cartReducer(s, { type: "add", item: { id: 1, title: "Чай" } });
s = cartReducer(s, { type: "add", item: { id: 2, title: "Кофе" } });
```

?! Что будет в корзине `s` после трёх действий? || Два товара: чай с `qty: 2` (второй раз он уже был в корзине, поэтому выросло количество) и кофе с `qty: 1`.

### На пальцах
TanStack Query — личный курьер для серверных данных. Ты говоришь: «мне нужны товары». Курьер смотрит в кладовку (кеш): если там свежие — отдаёт сразу, если устарели — отдаёт что есть и тут же едет за новыми. Сам повторяет поездку, если не получилось, и следит, чтобы за одним и тем же не ездили два курьера сразу.

### Как это работает
1. `npm install @tanstack/react-query`
2. Создать `QueryClient` и обернуть приложение в `QueryClientProvider`.
3. В компоненте: `useQuery({ queryKey, queryFn })`.

- `queryKey` — уникальный ключ данных в кеше: `["products"]`, `["product", id]`. Изменился ключ — новый запрос.
- `queryFn` — функция, которая возвращает промис с данными.
- Результат: `data`, `isPending` (первая загрузка), `isError`, `error`, `isFetching` (обновление в фоне), `refetch`.
- `staleTime` — сколько данные считаются свежими. По умолчанию 0: при каждом возвращении на страницу данные обновятся в фоне.

Изменения на сервере — через `useMutation`, а после успеха кеш помечают устаревшим: `queryClient.invalidateQueries({ queryKey: ["todos"] })` — и списки обновятся сами.

?: Зачем в `queryKey` класть параметры запроса, например `["product", id]`? || Ключ — это адрес данных в кеше. Если для разных товаров ключ одинаковый `["product"]`, все они лягут в одну ячейку и будут перезаписывать друг друга. С `id` в ключе у каждого товара своя ячейка.

### Ситуация
Корзина в Context работает, но тормозит: при добавлении товара перерисовывается весь сайт, включая футер и меню, которым корзина вообще не нужна. Провайдеров стало пять, они вложены друг в друга, как матрёшки. Для клиентского состояния, нужного во многих местах, есть инструмент проще и быстрее.

### На пальцах
Zustand — общий блокнот на холодильнике для всей семьи. Любой может подойти, прочитать и дописать, не передавая записки через других. По сравнению с Context он проще и аккуратнее: тот, кого интересует только список покупок, не отвлекается, когда кто-то правит расписание.

### Как это работает
- `npm install zustand`
- `create(...)` создаёт хук-стор: внутри состояние и функции, которые его меняют.
- В компоненте вызываешь хук с функцией-селектором: `useCart(s => s.items)`. Компонент перерисуется, только когда изменится выбранная часть.
- Провайдер не нужен — стор можно использовать где угодно, даже вне React.
- Есть готовое сохранение в `localStorage` — middleware `persist`.

Когда Zustand оправдан:

- клиентское состояние нужно во многих несвязанных местах: корзина, избранное, настройки интерфейса;
- Context тормозит из-за лишних перерисовок;
- логика изменений разрослась.

Когда не нужен:

- серверные данные — для них TanStack Query;
- состояние одного компонента или ветки — `useState`;
- одна-две глобальные настройки — хватит Context.

?: Как селектор `useCart(s => s.items.length)` избавляет от лишних перерисовок? || Zustand сравнивает результат селектора до и после изменения стора. Если выбранная часть не изменилась, компонент не перерисовывается, даже когда в сторе поменялось что-то другое.

### Пример
```tsx
import { create } from "zustand";
import { persist } from "zustand/middleware";

type CartState = {
  items: { id: number; qty: number }[];
  add: (id: number) => void;
  clear: () => void;
};

export const useCart = create<CartState>()(
  persist(
    set => ({
      items: [],
      add: id => set(s => ({ items: [...s.items, { id, qty: 1 }] })),
      clear: () => set({ items: [] }),
    }),
    { name: "cart" }
  )
);

function CartBadge() {
  const count = useCart(s => s.items.length);
  return <span>{count}</span>;
}

function Footer() {
  const store = useCart();
  return <footer>© 2026</footer>;
}
```

?! Пользователь добавил товар. Какие из двух компонентов перерисуются и что будет после обновления страницы? || Перерисуются оба: `CartBadge` — потому что изменилась длина, а `Footer` — потому что подписан на весь стор без селектора, хотя корзина ему не нужна. После обновления страницы корзина останется: `persist` сохранил её в `localStorage` под ключом `cart`.

- **Ответы сервера в Zustand** с ручным обновлением — для этого есть TanStack Query.
- **Мутация состояния внутри `set`** вместо возврата новых объектов.
