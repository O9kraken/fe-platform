### На пальцах
Как узнать, что пришла посылка? **Polling** — каждые 5 минут ходить к почтовому ящику и проверять. **Server-Sent Events** — почтальон сам звонит в дверь, когда есть посылка, но ты ему ничего передать не можешь. **WebSocket** — открытая телефонная линия: говорить могут обе стороны в любой момент.

### Как это работает
| Способ | Как работает | Направление | Когда выбирать |
|---|---|---|---|
| Polling | клиент делает обычный запрос каждые N секунд | клиент спрашивает | редкие обновления, простота важнее всего |
| Long polling | запрос «висит», пока не появятся данные, потом новый | клиент спрашивает, сервер отвечает когда есть | устаревший компромисс |
| SSE (Server-Sent Events) | одно HTTP-соединение, сервер шлёт события текстом | только сервер → клиент | уведомления, лента, прогресс задачи, стриминг ответа нейросети |
| WebSocket | постоянное двустороннее соединение | обе стороны | чаты, совместное редактирование, игры, онлайн-статусы |

- Polling тратит запросы впустую, когда ничего не изменилось, и даёт задержку до N секунд.
- SSE работает поверх обычного HTTP, браузер сам переподключается при обрыве (`EventSource`), проходит через большинство прокси.
- WebSocket — отдельный протокол (`ws://`, `wss://`), нужен для обмена в обе стороны с минимальной задержкой.

Каждое открытое SSE- или WebSocket-соединение держит ресурсы сервера, а serverless-платформы (Vercel Functions) долгие соединения не любят — для них нужны отдельные сервисы (Pusher, Ably, Supabase Realtime).

### Пример
```js
// SSE на сервере (Express)
app.get("/api/events", (req, res) => {
  res.set({ "Content-Type": "text/event-stream", "Cache-Control": "no-cache", Connection: "keep-alive" });
  res.flushHeaders();
  const timer = setInterval(() => {
    res.write(`data: ${JSON.stringify({ time: new Date().toISOString() })}\n\n`);
  }, 2000);
  req.on("close", () => clearInterval(timer));
});
```

```js
// SSE в браузере
const es = new EventSource("/api/events");
es.onmessage = (e) => console.log("Событие:", JSON.parse(e.data));
```

```js
// polling — для сравнения
setInterval(async () => {
  const r = await fetch("/api/orders/42/status");
  console.log((await r.json()).status);
}, 5000);
```

### Частые ошибки
- WebSocket там, где хватило бы SSE или даже polling раз в минуту.
- Polling каждую секунду у тысяч пользователей — лишняя нагрузка на сервер.
- Не очищать таймеры и подписки при закрытии соединения.

### На пальцах
ws — простой телефонный аппарат: соединение есть, говорите что хотите. Socket.IO — офисная АТС: события с названиями («новое сообщение», «печатает…»), комнаты (переговорки, где слышат только участники), автоматическое переподключение при обрыве и подтверждение доставки.

### Как это работает
**ws** — минималистичная библиотека WebSocket для Node.js. Сообщения — строки или байты, всё остальное (события, комнаты) — своими руками.

**Socket.IO** — надстройка с удобствами:

- **события**: `socket.emit("message", data)` на одной стороне, `socket.on("message", handler)` на другой;
- **комнаты**: `socket.join("project:42")`, `io.to("project:42").emit(...)` — отправить всем в комнате;
- **broadcast**: `socket.broadcast.emit(...)` — всем, кроме отправителя;
- автоматическое переподключение и запасной транспорт, если WebSocket недоступен;
- подтверждения (acknowledgements) — колбэк, когда сервер получил сообщение.

Socket.IO требует клиентскую библиотеку `socket.io-client` — с обычным `new WebSocket()` он несовместим.

### Пример
```js
// server.js
import express from "express";
import { createServer } from "node:http";
import { Server } from "socket.io";

const app = express();
const httpServer = createServer(app);
const io = new Server(httpServer, { cors: { origin: "http://localhost:5173", credentials: true } });

io.on("connection", (socket) => {
  socket.on("join", (projectId) => socket.join(`project:${projectId}`));

  socket.on("message", ({ projectId, text }, ack) => {
    const msg = { text, at: Date.now(), from: socket.id };
    socket.to(`project:${projectId}`).emit("message", msg);   // всем в комнате, кроме автора
    ack?.({ ok: true });
  });

  socket.on("typing", (projectId) => socket.to(`project:${projectId}`).emit("typing", socket.id));
});

httpServer.listen(3000);
```

```js
// клиент
import { io } from "socket.io-client";
const socket = io("http://localhost:3000", { withCredentials: true });
socket.emit("join", 42);
socket.on("message", (m) => console.log("Новое сообщение:", m.text));
socket.emit("message", { projectId: 42, text: "Привет!" }, (res) => console.log("Доставлено", res));
```

### Частые ошибки
- Подключаться к серверу Socket.IO через обычный `WebSocket` — не заработает.
- Слать всем через `io.emit`, когда нужно в одну комнату.
- Доверять данным из события без проверки: это такой же ввод пользователя, как тело HTTP-запроса.

### На пальцах
Открыть телефонную линию может кто угодно. Значит, до того как соединить звонящего с переговоркой, нужно проверить, кто он: сотрудник или посторонний. И потом проверять, в какие переговорки ему можно. Аутентификация в WebSocket — та же проверка пропуска, только на входе в постоянное соединение.

### Как это работает
WebSocket-соединение начинается с обычного HTTP-запроса (handshake), поэтому:

- **cookie** отправляются автоматически, если фронтенд и сервер на одном домене или настроены `credentials`. Сервер читает cookie сессии при подключении;
- **токен** можно передать при подключении: в Socket.IO — `auth: { token }`;
- передавать токен в адресе (`?token=...`) нежелательно — он попадает в логи.

Где проверять:

1. **При подключении** — middleware Socket.IO `io.use(...)`: нет сессии — отказать в соединении.
2. **При входе в комнату** — имеет ли пользователь доступ к этому проекту или чату.
3. **При каждом действии** — может ли он писать, удалять и так далее.

Сессия может закончиться, пока соединение открыто (пользователь вышел, его заблокировали). Для важных систем соединения отключают при выходе или периодически перепроверяют.

### Пример
```js
import cookie from "cookie";
import jwt from "jsonwebtoken";

io.use(async (socket, next) => {
  try {
    const cookies = cookie.parse(socket.handshake.headers.cookie ?? "");
    const token = cookies.session ?? socket.handshake.auth?.token;
    const { uid } = jwt.verify(token, process.env.JWT_SECRET);
    socket.data.user = await usersRepo.findById(uid);
    if (!socket.data.user) throw new Error();
    next();
  } catch {
    next(new Error("unauthorized"));     // клиент получит connect_error
  }
});

io.on("connection", (socket) => {
  socket.on("join", async (projectId, ack) => {
    const allowed = await projectsRepo.isMember(projectId, socket.data.user.id);
    if (!allowed) return ack?.({ error: "Нет доступа к проекту" });
    socket.join(`project:${projectId}`);
    ack?.({ ok: true });
  });
});
```

```js
// клиент
socket.on("connect_error", (err) => {
  if (err.message === "unauthorized") location.href = "/login";
});
```

### Частые ошибки
- Открытый WebSocket без проверки — любой может подключиться и читать сообщения.
- Проверка только при подключении, а вход в любую комнату — без проверки прав.
- Токен в адресе подключения, который пишется в логи прокси.

### Мини-задание
Добавь в свой чат проверку сессии при подключении и проверку членства в проекте при входе в комнату. Попробуй подключиться без cookie и войти в чужую комнату — убедись, что оба раза отказ.

### На пальцах
Некоторые дела не связаны с конкретным запросом пользователя: каждую ночь сделать резервную копию, каждое утро разослать отчёт, каждый час удалить просроченные брони. Cron — будильник на сервере: «каждый день в 03:00 — делай это».

### Как это работает
Расписание cron — пять полей: минута, час, день месяца, месяц, день недели.

| Выражение | Когда |
|---|---|
| `0 3 * * *` | каждый день в 03:00 |
| `*/15 * * * *` | каждые 15 минут |
| `0 9 * * 1-5` | по будням в 09:00 |
| `0 0 1 * *` | первого числа каждого месяца в полночь |

Проверить выражение — crontab.guru.

Где запускать:

- **внутри приложения** — библиотека `node-cron`. Просто, но если экземпляров сервера несколько, задача выполнится в каждом. А если сервер «уснул» (бесплатный Render), задача не выполнится;
- **cron хостинга** — Render Cron Jobs, Vercel Cron, GitHub Actions по расписанию — надёжнее: запускают отдельную команду или дергают защищённый адрес;
- **очередь с повторяющимися задачами** (BullMQ repeatable jobs) — если очередь уже есть.

Правила для фоновых задач: идемпотентность (повторный запуск не навредит), логирование начала, конца и ошибок, ограничение времени выполнения, защита адреса, если задачу запускают по HTTP.

### Пример
```js
// внутри приложения — node-cron
import cron from "node-cron";

cron.schedule("0 * * * *", async () => {           // каждый час
  const { rowCount } = await q("DELETE FROM bookings WHERE status = 'pending' AND created_at < now() - interval '30 minutes'");
  logger.info({ removed: rowCount }, "Просроченные брони удалены");
}, { timezone: "Europe/Moscow" });
```

```js
// задачу запускает внешний планировщик по HTTP — адрес защищён секретом
app.post("/internal/cron/daily-report", async (req, res) => {
  if (req.get("Authorization") !== `Bearer ${process.env.CRON_SECRET}`) return res.status(401).end();
  await sendDailyReport();
  res.json({ ok: true });
});
```

```yaml
# GitHub Actions как планировщик
on:
  schedule:
    - cron: "0 6 * * *"     # 09:00 по Москве (время в UTC)
jobs:
  report:
    runs-on: ubuntu-latest
    steps:
      - run: curl -X POST -H "Authorization: Bearer ${{ secrets.CRON_SECRET }}" https://api.studio.ru/internal/cron/daily-report
```

### Частые ошибки
- `node-cron` при трёх экземплярах сервера — письмо уходит трижды.
- Забыть про часовой пояс: многие планировщики работают в UTC.
- Открытый адрес `/cron/...` без проверки — любой может запускать тяжёлую задачу.

### На пальцах
Курьер приехал, а клиента нет дома. Плохой курьер выбрасывает посылку. Хороший — заедет через час, потом вечером, потом завтра, а если так и не получится — вернёт на склад с пометкой «не доставлено», и менеджер разберётся. Очередь с повторными попытками — хороший курьер для фоновых задач.

### Как это работает
Почему задачи падают: внешний сервис временно недоступен, таймаут сети, лимит запросов у API, перезапуск сервера посреди задачи.

Стратегия повторов:

- **ограниченное число попыток** — например, 5;
- **растущая пауза (exponential backoff)** — 1 мин, 2, 4, 8… чтобы не добивать и без того перегруженный сервис;
- **случайный разброс (jitter)** — чтобы тысяча задач не повторилась в одну и ту же секунду;
- **очередь «мёртвых» задач** (dead letter) — исчерпавшие попытки откладываются для ручного разбора и алерта.

Не все ошибки стоит повторять: неверный email или удалённый пользователь — повтор не поможет. Такие задачи сразу помечают как неудачные.

Идемпотентность обязательна: задача может выполниться дважды (например, отработала, но не успела отметиться перед падением воркера). Приём — уникальный ключ операции и проверка «уже сделано?» перед выполнением.

### Пример
```js
await emailQueue.add("invoice", { invoiceId: 77 }, {
  attempts: 6,
  backoff: { type: "exponential", delay: 30_000 },    // 30 с, 1 мин, 2 мин, 4 мин...
  removeOnComplete: 1000,
  removeOnFail: false,                                 // неудачные храним для разбора
});

new Worker("emails", async (job) => {
  const invoice = await invoicesRepo.find(job.data.invoiceId);
  if (!invoice) throw new UnrecoverableError("Счёт удалён — повторять бессмысленно");
  if (invoice.emailSentAt) return;                     // уже отправлено — идемпотентность
  await mailer.send(invoice.clientEmail, "Счёт на оплату", renderInvoice(invoice));
  await invoicesRepo.markSent(invoice.id);
}, { connection });

worker.on("failed", (job, err) => {
  if (job.attemptsMade >= job.opts.attempts) logger.error({ jobId: job.id, err }, "Задача окончательно не выполнена");
});
```

### Частые ошибки
- Бесконечные повторы без паузы — «атака» на упавший сервис.
- Повтор задач, которые не могут выполниться в принципе.
- Нет алерта на окончательно упавшие задачи — о проблеме узнают от клиентов.

### На пальцах
Реальное время и фоновые задачи — специи, а не основное блюдо. В одних местах без них никак (чат без мгновенных сообщений — не чат), в других они только усложнят рецепт. Важно понимать, где именно пользователь ждёт мгновенной реакции, а где можно спокойно обработать в фоне.

### Как это работает
| Задача | Решение |
|---|---|
| Чат, комментарии в реальном времени | WebSocket (Socket.IO) |
| «Печатает…», «в сети» | WebSocket, данные в Redis |
| Уведомления в личном кабинете | SSE или WebSocket |
| Статус заказа «готовится → в пути → доставлен» | SSE или polling раз в 10–30 секунд |
| Прогресс долгой операции (импорт, генерация) | фоновая задача + SSE или polling статуса |
| Стриминг ответа нейросети | SSE (так работает наставник в этом курсе) |
| Совместное редактирование документа | WebSocket + специальные алгоритмы (CRDT) |
| Письма, отчёты, обработка картинок | очередь фоновых задач |
| Ежедневная рассылка, чистка старых данных | cron |
| Дашборд, который смотрят раз в день | обычный запрос при открытии |

Типичная связка: пользователь запустил импорт → API кладёт задачу в очередь и сразу отвечает `202 Accepted` с id задачи → воркер выполняет и пишет прогресс в Redis → фронтенд получает прогресс через SSE → по завершении приходит уведомление.

### Пример
```js
// 1. запуск долгой операции
app.post("/api/imports", requireUser, async (req, res) => {
  const job = await importQueue.add("csv", { fileId: req.body.fileId, userId: req.user.id });
  res.status(202).json({ jobId: job.id });
});

// 2. прогресс через SSE
app.get("/api/imports/:id/events", requireUser, async (req, res) => {
  res.set({ "Content-Type": "text/event-stream", "Cache-Control": "no-cache" });
  const timer = setInterval(async () => {
    const job = await importQueue.getJob(req.params.id);
    const state = await job.getState();
    res.write(`data: ${JSON.stringify({ state, progress: job.progress })}\n\n`);
    if (state === "completed" || state === "failed") { clearInterval(timer); res.end(); }
  }, 1000);
  req.on("close", () => clearInterval(timer));
});
```

### Частые ошибки
- WebSocket для данных, которые меняются раз в час.
- Долгая операция прямо в запросе, который обрывается по таймауту хостинга через 30 секунд.
- Нет обратной связи пользователю о фоновой операции — «нажал и ничего не происходит».
