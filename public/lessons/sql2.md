### Ситуация
У студии клиент «Кофейня Зерно» и шесть проектов. В каждом проекте написано имя клиента — и где-то «Кофейня Зерно», где-то «кофейня "Зерно"», где-то «Зерно кофе». Клиент сменил название — правишь шесть мест и всё равно что-то пропускаешь. Связи между таблицами придуманы ровно для этого: каждое значение хранится в одном месте.

### На пальцах
Первичный ключ — номер паспорта: у каждой строки свой, не повторяется и не меняется. Внешний ключ — ссылка на чужой паспорт: в карточке проекта написано не имя клиента целиком, а «клиент № 3». Так данные о клиенте хранятся в одном месте, а все проекты на него просто ссылаются.

### Как это работает
>> `clients.id` — первичный ключ → `projects.client_id` — внешний → связь таблиц

- **Первичный ключ** (`PRIMARY KEY`) — колонка (обычно `id`), уникально определяющая строку. Не может быть `NULL`. Часто генерируется автоматически: `id integer GENERATED ALWAYS AS IDENTITY` или `uuid`.
- **Внешний ключ** (`REFERENCES`) — колонка, которая хранит первичный ключ строки из другой таблицы: `projects.client_id → clients.id`.
- База следит за целостностью: нельзя создать проект с `client_id = 999`, если такого клиента нет. И нельзя удалить клиента, у которого есть проекты (если не настроено иначе).

Зачем так делать, а не писать имя клиента в каждом проекте:

- клиент переименовался — меняем в одном месте;
- нет опечаток «Кофейня Зерно» / «кофейня "Зерно"»;
- база не позволит сослаться на несуществующего клиента.

?: Почему email плохо подходит на роль первичного ключа пользователя? || Email может измениться — человек сменил почту. Тогда пришлось бы менять ключ во всех таблицах, которые на него ссылаются. Первичный ключ должен быть постоянным, поэтому берут технический `id`, а email делают просто уникальным.

### Пример
```sql
CREATE TABLE clients (
  id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL
);

CREATE TABLE projects (
  id        integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  client_id integer NOT NULL REFERENCES clients(id),
  title     text NOT NULL
);

INSERT INTO clients (name) VALUES ('Кофейня «Зерно»');
INSERT INTO projects (client_id, title) VALUES (1, 'Лендинг');
INSERT INTO projects (client_id, title) VALUES (999, 'Сайт');
DELETE FROM clients WHERE id = 1;
```

?! Какие из последних трёх команд выполнятся, а какие база отклонит? || Первая вставка проекта пройдёт — клиент 1 существует. Вторая упадёт с «violates foreign key constraint»: клиента 999 нет. Удаление клиента 1 тоже будет отклонено: на него ссылается проект «Лендинг».

### Частые ошибки
- **Имя клиента в каждом проекте** вместо `client_id`.
- **Таблица без первичного ключа** — строки невозможно надёжно обновить или удалить по одной.
- **Изменяемое значение как ключ** (email, телефон).

### Проверь себя
?? Чем первичный ключ отличается от внешнего? || Первичный ключ уникально определяет строку в своей таблице. Внешний хранит первичный ключ строки из другой таблицы и связывает их.
?? Что сделает база, если попытаться сослаться внешним ключом на несуществующую строку? || Отклонит операцию с ошибкой нарушения ограничения внешнего ключа.
?? Объясни своими словами, зачем хранить в проекте `client_id`, а не имя клиента. || Данные клиента лежат в одном месте: их легко изменить, нет разнобоя в написании, а база гарантирует, что ссылка ведёт на существующего клиента.

### Ситуация
Данные разложены по трём таблицам: в проектах — только `client_id`, в платежах — только `project_id`. А бухгалтер просит отчёт: «Клиент, проект, сумма, дата». Ни одна таблица не содержит всего сразу. JOIN склеивает таблицы обратно — и это, пожалуй, самая частая тема SQL на собеседованиях.

### На пальцах
JOIN — склеить две таблицы по общей графе. INNER JOIN — «покажи пары, у которых есть совпадение»: проекты вместе с их клиентами. LEFT JOIN — «покажи всех из левой таблицы, а совпадения — если есть»: всех клиентов, даже тех, у кого пока нет ни одного проекта (у них графы проекта будут пустыми).

### Как это работает
>> `FROM clients` → `JOIN projects ON …` → `INNER` — только с парой → `LEFT` — все клиенты

```sql
SELECT ... FROM a
JOIN b ON b.a_id = a.id;
```

| Вид | Что возвращает |
|---|---|
| `INNER JOIN` (или просто `JOIN`) | только строки, у которых нашлась пара |
| `LEFT JOIN` | все строки левой таблицы; если пары нет — колонки правой `NULL` |
| `RIGHT JOIN` | наоборот (используют редко — проще поменять таблицы местами) |
| `FULL JOIN` | все строки обеих таблиц |

- Условие соединения — в `ON`.
- Давай таблицам короткие псевдонимы и пиши колонки с префиксом: `c.name`, `p.title`.
- Можно соединять три и больше таблиц цепочкой.
- Найти «тех, у кого нет пары»: `LEFT JOIN ... WHERE b.id IS NULL`.

Если у одного клиента пять проектов, после JOIN клиент появится в пяти строках — это нормально.

?: Почему условие на правую таблицу в `WHERE` превращает `LEFT JOIN` в обычный? || У строк без пары все колонки правой таблицы — `NULL`. Условие вроде `p.status = 'active'` для `NULL` не истинно, и `WHERE` выкидывает именно те строки, ради которых брали `LEFT JOIN`. Такое условие нужно писать в `ON`.

### Пример
```sql
SELECT c.name, p.title
FROM clients c
LEFT JOIN projects p ON p.client_id = c.id
WHERE p.status = 'active';
```

?! Задумка: «все клиенты и их активные проекты, включая клиентов без активных проектов». Покажет ли запрос клиентов, у которых нет активных проектов? || Нет. `WHERE p.status = 'active'` выкинет строки, где `p.status` — `NULL`, то есть всех клиентов без подходящих проектов. Условие нужно перенести в `ON`: `ON p.client_id = c.id AND p.status = 'active'`.

### Частые ошибки
- **Нет `ON` или не те колонки** — декартово произведение: каждая строка с каждой.
- **`INNER JOIN`, когда нужны все из левой таблицы.**
- **Фильтр по правой таблице в `WHERE` после `LEFT JOIN`** — он становится обычным `INNER`.

### Проверь себя
?? Чем `INNER JOIN` отличается от `LEFT JOIN`? || `INNER JOIN` возвращает только пары с совпадением. `LEFT JOIN` возвращает все строки левой таблицы, а у тех, кому не нашлось пары, колонки правой будут `NULL`.
?? Как найти клиентов, у которых нет ни одного проекта? || `LEFT JOIN projects` и условие `WHERE p.id IS NULL`.
?? Объясни своими словами, почему после JOIN клиент может появиться в нескольких строках. || JOIN создаёт строку на каждую найденную пару. Если у клиента пять проектов, получится пять пар — и пять строк с этим клиентом.

### Ситуация
Директор спрашивает: «Сколько у нас проектов? На какую сумму? Какой средний чек?». Выгрузить таблицу в Excel и считать там — долго, и цифры устареют через час. Агрегатные функции считают прямо в базе, за миллисекунды, на миллионах строк. Только одна из них коварно отвечает «ничего» там, где ждёшь ноль.

### На пальцах
Агрегатные функции — калькулятор над целой колонкой: «сколько всего проектов» (`COUNT`), «какая общая сумма платежей» (`SUM`), «какой средний бюджет» (`AVG`), «самый дешёвый и самый дорогой» (`MIN`, `MAX`). Вместо множества строк получаешь одно число.

### Как это работает
>> Много строк → `COUNT`, `SUM`, `AVG`, `MIN`, `MAX` → одно число

| Функция | Что делает |
|---|---|
| `COUNT(*)` | число строк |
| `COUNT(колонка)` | число строк, где значение не `NULL` |
| `COUNT(DISTINCT колонка)` | число уникальных значений |
| `SUM(колонка)` | сумма |
| `AVG(колонка)` | среднее |
| `MIN`, `MAX` | минимум и максимум (работает и с датами, и со строками) |

- Агрегаты игнорируют `NULL` (кроме `COUNT(*)`).
- Можно комбинировать с `WHERE`: сначала отфильтровать, потом посчитать.
- `ROUND(AVG(budget))` — округлить.
- Если нет ни одной строки, `SUM` вернёт `NULL`, а не 0. Используй `COALESCE(SUM(...), 0)`.
- Без `GROUP BY` агрегат считается по всей выборке, и обычные колонки рядом с ним писать нельзя.

?: Почему `AVG(budget)` может отличаться от «суммы бюджетов, делённой на число проектов»? || `AVG` игнорирует `NULL`: проекты без бюджета не участвуют ни в сумме, ни в количестве. А «сумма делить на `COUNT(*)`» учитывает в знаменателе все проекты, включая неоценённые, — среднее получится меньше.

### Пример
```sql
SELECT
  COUNT(*)      AS projects,
  COUNT(budget) AS with_budget
FROM projects;

SELECT SUM(amount) AS paid
FROM payments
WHERE paid_at >= '2030-01-01';
```

?! В таблице 10 проектов, у трёх бюджет `NULL`. Что вернёт первый запрос? И что вернёт второй, если платежей в 2030 году ещё нет? || Первый — `10` и `7`: `COUNT(*)` считает все строки, `COUNT(budget)` — только с заполненным бюджетом. Второй вернёт `NULL`, а не 0: суммировать нечего. Чтобы получить ноль, нужно `COALESCE(SUM(amount), 0)`.

### Частые ошибки
- **`SELECT title, COUNT(*) FROM projects` без `GROUP BY`** — ошибка: непонятно, какое название показать рядом с общим числом.
- **Ожидание 0 от `SUM`** по пустой выборке.
- **`COUNT(budget)` вместо `COUNT(*)`**, когда нужно посчитать все строки.

### Проверь себя
?? Чем `COUNT(*)` отличается от `COUNT(колонка)`? || `COUNT(*)` считает все строки. `COUNT(колонка)` — только те, где в колонке не `NULL`.
?? Как посчитать количество уникальных городов клиентов? || `SELECT COUNT(DISTINCT city) FROM clients`.
?? Объясни своими словами, зачем `COALESCE(SUM(...), 0)`. || Если подходящих строк нет, `SUM` возвращает `NULL`. `COALESCE` заменяет его на 0, чтобы в отчёте и в коде было число, а не пустота.

### Ситуация
Общая выручка — это хорошо, но директору нужно больше: «Сколько клиентов в каждом городе? Сколько проектов в каждом статусе? Какие проекты оплачены больше чем на 50 тысяч?». Писать отдельный запрос на каждый город — абсурд. `GROUP BY` считает агрегаты для каждой группы разом, а `HAVING` отбирает нужные группы.

### На пальцах
`GROUP BY` — разложить карточки по стопкам: стопка «Москва», стопка «Казань» — и посчитать что-то в каждой стопке отдельно. `HAVING` — выкинуть стопки, которые не подходят: «оставить только города, где больше одного клиента». `WHERE` фильтрует карточки до раскладки, `HAVING` — стопки после.

### Как это работает
>> `WHERE` — фильтр строк → `GROUP BY client_id` → агрегат → `HAVING` — фильтр групп

```sql
SELECT колонка_группы, АГРЕГАТ(...)
FROM таблица
WHERE условие_на_строки
GROUP BY колонка_группы
HAVING условие_на_группы
ORDER BY ...;
```

- Каждая колонка в `SELECT` должна быть либо в `GROUP BY`, либо внутри агрегата.
- Группировать можно по нескольким колонкам: `GROUP BY city, status`.
- `WHERE` — до группировки, условие на отдельные строки.
- `HAVING` — после группировки, условие на результат агрегата.
- Группировка часто идёт вместе с `JOIN`: сколько проектов у каждого клиента, сколько оплачено по каждому проекту.

?: Почему каждая колонка в `SELECT` должна быть в `GROUP BY` или внутри агрегата? || После группировки от каждой стопки остаётся одна строка. Если в стопке «Москва» пять клиентов, база не знает, чьё имя показать рядом с количеством. Колонка из `GROUP BY` одинакова для всей стопки, агрегат сводит значения в одно — остальное неопределённо.

### Пример
```sql
SELECT c.name, COUNT(*) AS projects
FROM clients c
LEFT JOIN projects p ON p.client_id = c.id
GROUP BY c.id, c.name;
```

?! У клиента «Пекарня» нет ни одного проекта. Сколько проектов покажет запрос напротив неё? Как исправить? || 1, а не 0. `LEFT JOIN` дал для «Пекарни» одну строку с пустыми колонками проекта, и `COUNT(*)` посчитал эту строку. Нужно `COUNT(p.id)` — он не считает `NULL`.

### Частые ошибки
- **Колонка в `SELECT` не в `GROUP BY` и не в агрегате.**
- **Агрегат в `WHERE`** вместо `HAVING`.
- **Группировка по имени, а не по id:** у двух разных клиентов может быть одинаковое имя.

### Проверь себя
?? Чем `WHERE` отличается от `HAVING`? || `WHERE` фильтрует отдельные строки до группировки. `HAVING` фильтрует группы после неё, по результатам агрегатов.
?? Как найти города, где больше одного клиента? || `SELECT city FROM clients GROUP BY city HAVING COUNT(*) > 1`.
?? Объясни своими словами, почему группировать лучше по id, а не по имени. || Имена могут совпадать у разных записей, и тогда разные клиенты сольются в одну группу. Id уникален и гарантирует, что группа — один клиент.

### Ситуация
«Покажи проекты дороже среднего». Ты не знаешь средний бюджет заранее — его нужно сначала посчитать, а потом использовать как порог. Или: «Посчитай долг по каждому проекту — бюджет минус всё, что уже оплачено». Это задача в несколько шагов, и записывать её одним плоским запросом — мучение. Подзапросы и CTE позволяют рассуждать по шагам.

### На пальцах
Подзапрос — вопрос внутри вопроса: «Покажи проекты, у которых бюджет больше, чем средний бюджет по всем проектам». Сначала нужно узнать средний — это и есть внутренний вопрос. CTE (`WITH`) — та же идея, но вопросы выписаны отдельно по порядку и подписаны, как черновые расчёты на полях.

### Как это работает
>> `WITH big AS (…)` → именованный подзапрос → основной `SELECT` из него

Подзапрос пишется в скобках и может стоять:

- в `WHERE`: `WHERE budget > (SELECT AVG(budget) FROM projects)`;
- в `WHERE ... IN (...)`: `WHERE client_id IN (SELECT id FROM clients WHERE city = 'Москва')`;
- в `FROM` как временная таблица: `FROM (SELECT ...) AS t`;
- в `SELECT` как отдельное значение для каждой строки.

`EXISTS (подзапрос)` — истинно, если подзапрос вернул хоть одну строку.

CTE:

```sql
WITH имя AS (запрос),
     другое AS (запрос, может использовать «имя»)
SELECT ... FROM имя JOIN другое ...;
```

CTE делает сложные запросы читаемыми: каждый шаг называется по смыслу.

?: Почему `NOT IN` с подзапросом опасен, если там встречается `NULL`? || `x NOT IN (1, 2, NULL)` значит «x не равен 1, и не равен 2, и не равен NULL». Последнее сравнение даёт «неизвестно», и всё условие становится неизвестным — ни одна строка не проходит. `NOT EXISTS` такой ловушки не имеет.

### Пример
```sql
WITH paid AS (
  SELECT project_id, SUM(amount) AS total
  FROM payments
  GROUP BY project_id
)
SELECT p.title, p.budget - paid.total AS debt
FROM projects p
JOIN paid ON paid.project_id = p.id;
```

?! Покажет ли этот запрос проект, по которому ещё не было ни одного платежа? Какой у него должен быть долг? || Не покажет: обычный `JOIN` отбросит проекты без строки в `paid`. А это как раз самые большие должники — долг равен всему бюджету. Нужен `LEFT JOIN paid` и `COALESCE(paid.total, 0)`.

### Частые ошибки
- **Подзапрос в `=` возвращает несколько строк** — «more than one row returned». Используй `IN`.
- **`NOT IN` с `NULL`** — пустой результат. Безопаснее `NOT EXISTS`.
- **Пять уровней вложенных подзапросов** вместо понятных CTE.

### Проверь себя
?? Как найти проекты, бюджет которых выше среднего? || `SELECT title FROM projects WHERE budget > (SELECT AVG(budget) FROM projects)`.
?? Что проверяет `EXISTS (подзапрос)`? || Вернул ли подзапрос хотя бы одну строку.
?? Объясни своими словами, чем CTE удобнее вложенных подзапросов. || Каждый промежуточный шаг выписан отдельно и назван по смыслу, поэтому сложный запрос читается сверху вниз как последовательность понятных расчётов.

### Мини-задание

### Ситуация
Пока клиентов было сто, поиск по email работал мгновенно. Сейчас их миллион, и вход в личный кабинет занимает четыре секунды. Код не менялся. Гадать, что тормозит, бесполезно: база может сама рассказать, как она выполняет запрос и почему медленно. Это первое, что делает бэкендер при жалобе на скорость.

### На пальцах
`EXPLAIN` — попросить навигатор показать маршрут до того, как ехать. База отвечает: «Пойду пешком по всем улицам подряд» (полный перебор) или «Поеду по шоссе» (индекс) и примерно сколько это займёт. Если маршрут глупый — значит, не хватает дороги (индекса) или запрос написан неудачно.

### Как это работает
>> `EXPLAIN ANALYZE` → план → `Seq Scan` или `Index Scan` → время

- `EXPLAIN запрос` — показать план выполнения без запуска.
- `EXPLAIN ANALYZE запрос` — выполнить и показать реальное время каждого шага. Осторожно с `UPDATE` и `DELETE` — они действительно выполнятся.

| В плане | Что значит |
|---|---|
| `Seq Scan on projects` | полный перебор таблицы — нормально для маленьких таблиц, плохо для больших |
| `Index Scan using ...` | поиск по индексу — быстро |
| `Index Only Scan` | всё нужное есть в индексе — ещё быстрее |
| `Hash Join`, `Nested Loop`, `Merge Join` | способы соединения таблиц |
| `Sort` | сортировка; на больших данных может быть дорогой |
| `cost=0.00..35.50` | условная стоимость: старт..итог |
| `rows=1200` | сколько строк ожидается |
| `actual time=...` | реальное время (в `ANALYZE`) |

В SQLite (песочница курса) аналог — `EXPLAIN QUERY PLAN`.

?: Почему на маленькой таблице база выбирает полный перебор, даже когда индекс есть? || Обращение к индексу тоже стоит времени: нужно открыть его, найти позицию и потом сходить за строками. Перебрать 10 строк подряд быстрее. Планировщик сравнивает стоимость вариантов и выбирает дешёвый.

### Пример
```sql
EXPLAIN ANALYZE DELETE FROM payments WHERE paid_at < '2020-01-01';
```

?! Ты просто хотел посмотреть, насколько быстро выполнится удаление старых платежей. Что произошло на самом деле? || Платежи реально удалились: `EXPLAIN ANALYZE` выполняет запрос. Для безопасной проверки — обычный `EXPLAIN` без `ANALYZE` или запуск внутри транзакции с последующим `ROLLBACK`.

### Частые ошибки
- **Выводы по плану на пустой или крошечной таблице.**
- **`EXPLAIN ANALYZE DELETE ...` на боевой базе** — удаление реально выполнится.
- **Индексы на всё подряд**, не посмотрев план.

### Проверь себя
?? Чем `EXPLAIN` отличается от `EXPLAIN ANALYZE`? || `EXPLAIN` только показывает план, не выполняя запрос. `EXPLAIN ANALYZE` выполняет запрос и показывает реальное время каждого шага.
?? Что означает `Seq Scan` в плане запроса? || Полный последовательный перебор всех строк таблицы.
?? Объясни своими словами, как с помощью `EXPLAIN` понять, что не хватает индекса. || Если медленный запрос по большой таблице с фильтром показывает `Seq Scan`, база перебирает все строки. После создания индекса на колонку фильтра план должен смениться на `Index Scan`, а время — упасть.

### Мини-задание
В песочнице выполни `EXPLAIN QUERY PLAN` для поиска проектов по `client_id`, создай индекс и посмотри план снова. Изучи схему «Зачем индекс» в уроке и задачу «Индекс» в лаборатории.
