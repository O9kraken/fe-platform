### На пальцах
Первичный ключ — номер паспорта: у каждой строки свой, не повторяется и не меняется. Внешний ключ — ссылка на чужой паспорт: в карточке проекта написано не имя клиента целиком, а «клиент № 3». Так данные о клиенте хранятся в одном месте, а все проекты на него просто ссылаются.

### Как это работает
- **Первичный ключ** (`PRIMARY KEY`) — колонка (обычно `id`), уникально определяющая строку. Не может быть `NULL`. Часто генерируется автоматически: `id integer GENERATED ALWAYS AS IDENTITY` или `uuid`.
- **Внешний ключ** (`REFERENCES`) — колонка, которая хранит первичный ключ строки из другой таблицы: `projects.client_id → clients.id`.
- База следит за целостностью: нельзя создать проект с `client_id = 999`, если такого клиента нет. И нельзя удалить клиента, у которого есть проекты (если не настроено иначе).

Зачем так делать, а не писать имя клиента в каждом проекте:

- клиент переименовался — меняем в одном месте;
- нет опечаток «Кофейня Зерно» / «кофейня "Зерно"»;
- база не позволит сослаться на несуществующего клиента.

### Пример
```sql
CREATE TABLE clients (
  id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL
);

CREATE TABLE projects (
  id        integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  client_id integer NOT NULL REFERENCES clients(id),
  title     text NOT NULL
);

INSERT INTO clients (name) VALUES ('Кофейня «Зерно»');      -- получит id = 1
INSERT INTO projects (client_id, title) VALUES (1, 'Лендинг');  -- ок
INSERT INTO projects (client_id, title) VALUES (999, 'Сайт');   -- ❌ violates foreign key constraint
```

### Частые ошибки
- Хранить имя клиента в каждом проекте вместо `client_id`.
- Таблица без первичного ключа — строки невозможно надёжно обновить или удалить по одной.
- Использовать как ключ что-то изменяемое (email, телефон).

### На пальцах
JOIN — склеить две таблицы по общей графе. INNER JOIN — «покажи пары, у которых есть совпадение»: проекты вместе с их клиентами. LEFT JOIN — «покажи всех из левой таблицы, а совпадения — если есть»: всех клиентов, даже тех, у кого пока нет ни одного проекта (у них графы проекта будут пустыми).

### Как это работает
```sql
SELECT ... FROM a
JOIN b ON b.a_id = a.id;
```

| Вид | Что возвращает |
|---|---|
| `INNER JOIN` (или просто `JOIN`) | только строки, у которых нашлась пара |
| `LEFT JOIN` | все строки левой таблицы; если пары нет — колонки правой `NULL` |
| `RIGHT JOIN` | наоборот (используют редко — проще поменять таблицы местами) |
| `FULL JOIN` | все строки обеих таблиц |

- Условие соединения — в `ON`.
- Давай таблицам короткие псевдонимы и пиши колонки с префиксом: `c.name`, `p.title` — иначе база не поймёт, о какой колонке `id` речь.
- Можно соединять три и больше таблиц цепочкой.
- Найти «тех, у кого нет пары»: `LEFT JOIN ... WHERE b.id IS NULL`.

Если у одного клиента пять проектов, после JOIN клиент появится в пяти строках — это нормально.

### Пример
```sql
-- проекты с именами клиентов
SELECT p.title, c.name AS client
FROM projects p
JOIN clients c ON c.id = p.client_id;

-- все клиенты и их проекты, включая клиентов без проектов
SELECT c.name, p.title
FROM clients c
LEFT JOIN projects p ON p.client_id = c.id
ORDER BY c.name;

-- клиенты, у которых нет ни одного проекта
SELECT c.name
FROM clients c
LEFT JOIN projects p ON p.client_id = c.id
WHERE p.id IS NULL;

-- три таблицы: платежи → проект → клиент
SELECT c.name, p.title, pay.amount, pay.paid_at
FROM payments pay
JOIN projects p ON p.id = pay.project_id
JOIN clients c ON c.id = p.client_id;
```

### Частые ошибки
- Забыть `ON` или указать не те колонки — получится декартово произведение: каждая строка с каждой.
- Использовать `INNER JOIN`, когда нужны все из левой таблицы.
- Фильтр по правой таблице в `WHERE` после `LEFT JOIN` превращает его в обычный `INNER` — такие условия пиши в `ON`.

### На пальцах
Агрегатные функции — калькулятор над целой колонкой: «сколько всего проектов» (`COUNT`), «какая общая сумма платежей» (`SUM`), «какой средний бюджет» (`AVG`), «самый дешёвый и самый дорогой» (`MIN`, `MAX`). Вместо множества строк получаешь одно число.

### Как это работает
| Функция | Что делает |
|---|---|
| `COUNT(*)` | число строк |
| `COUNT(колонка)` | число строк, где значение не `NULL` |
| `COUNT(DISTINCT колонка)` | число уникальных значений |
| `SUM(колонка)` | сумма |
| `AVG(колонка)` | среднее |
| `MIN`, `MAX` | минимум и максимум (работает и с датами, и со строками) |

- Агрегаты игнорируют `NULL` (кроме `COUNT(*)`).
- Можно комбинировать с `WHERE`: сначала отфильтровать, потом посчитать.
- `ROUND(AVG(budget))` — округлить.
- Если нет ни одной строки, `SUM` вернёт `NULL`, а не 0. Используй `COALESCE(SUM(...), 0)`.
- Без `GROUP BY` агрегат считается по всей выборке, и обычные колонки рядом с ним писать нельзя.

### Пример
```sql
SELECT COUNT(*) AS total FROM projects;

SELECT
  COUNT(*)         AS projects,
  COUNT(budget)    AS with_budget,
  SUM(budget)      AS total_budget,
  ROUND(AVG(budget)) AS avg_budget,
  MIN(budget)      AS min_budget,
  MAX(budget)      AS max_budget
FROM projects;

SELECT COALESCE(SUM(amount), 0) AS paid_in_july
FROM payments
WHERE paid_at >= '2026-07-01' AND paid_at < '2026-08-01';

SELECT COUNT(DISTINCT city) AS cities FROM clients;
```

### Частые ошибки
- `SELECT title, COUNT(*) FROM projects` без `GROUP BY` — ошибка: непонятно, какое название показать рядом с общим числом.
- Ждать 0 от `SUM` по пустой выборке.
- `COUNT(budget)` вместо `COUNT(*)`, когда нужно посчитать все строки, включая проекты без бюджета.

### Мини-задание
Посчитай: сколько всего клиентов и в скольких городах они находятся; общую сумму всех платежей; средний бюджет активных проектов; дату первого и последнего платежа.

### На пальцах
`GROUP BY` — разложить карточки по стопкам: стопка «Москва», стопка «Казань» — и посчитать что-то в каждой стопке отдельно. `HAVING` — выкинуть стопки, которые не подходят: «оставить только города, где больше одного клиента». `WHERE` фильтрует карточки до раскладки, `HAVING` — стопки после.

### Как это работает
```sql
SELECT колонка_группы, АГРЕГАТ(...)
FROM таблица
WHERE условие_на_строки
GROUP BY колонка_группы
HAVING условие_на_группы
ORDER BY ...;
```

- Каждая колонка в `SELECT` должна быть либо в `GROUP BY`, либо внутри агрегата.
- Группировать можно по нескольким колонкам: `GROUP BY city, status`.
- `WHERE` — до группировки, условие на отдельные строки.
- `HAVING` — после группировки, условие на результат агрегата.
- Группировка часто идёт вместе с `JOIN`: сколько проектов у каждого клиента, сколько оплачено по каждому проекту.

### Пример
```sql
-- клиентов по городам
SELECT city, COUNT(*) AS clients
FROM clients
GROUP BY city
ORDER BY clients DESC;

-- проекты по статусам с суммой бюджетов
SELECT status, COUNT(*) AS cnt, COALESCE(SUM(budget), 0) AS total
FROM projects
GROUP BY status;

-- сколько оплачено по каждому проекту, только где больше 50 000
SELECT p.title, SUM(pay.amount) AS paid
FROM projects p
JOIN payments pay ON pay.project_id = p.id
GROUP BY p.id, p.title
HAVING SUM(pay.amount) > 50000
ORDER BY paid DESC;

-- города, где больше одного клиента
SELECT city FROM clients GROUP BY city HAVING COUNT(*) > 1;
```

### Частые ошибки
- Колонка в `SELECT` не в `GROUP BY` и не в агрегате.
- Агрегат в `WHERE` вместо `HAVING`.
- Группировать по имени, а не по id: у двух разных клиентов может быть одинаковое имя.

### Мини-задание

### На пальцах
Подзапрос — вопрос внутри вопроса: «Покажи проекты, у которых бюджет больше, чем средний бюджет по всем проектам». Сначала нужно узнать средний — это и есть внутренний вопрос. CTE (`WITH`) — та же идея, но вопросы выписаны отдельно по порядку и подписаны, как черновые расчёты на полях.

### Как это работает
Подзапрос пишется в скобках и может стоять:

- в `WHERE`: `WHERE budget > (SELECT AVG(budget) FROM projects)`;
- в `WHERE ... IN (...)`: `WHERE client_id IN (SELECT id FROM clients WHERE city = 'Москва')`;
- в `FROM` как временная таблица: `FROM (SELECT ...) AS t`;
- в `SELECT` как отдельное значение для каждой строки.

`EXISTS (подзапрос)` — истинно, если подзапрос вернул хоть одну строку. Удобно для «есть ли платежи у проекта».

CTE:

```sql
WITH имя AS (запрос),
     другое AS (запрос, может использовать «имя»)
SELECT ... FROM имя JOIN другое ...;
```

CTE делает сложные запросы читаемыми: каждый шаг называется по смыслу. В PostgreSQL CTE обычно не медленнее подзапроса.

### Пример
```sql
-- проекты дороже среднего
SELECT title, budget FROM projects
WHERE budget > (SELECT AVG(budget) FROM projects);

-- проекты московских клиентов
SELECT title FROM projects
WHERE client_id IN (SELECT id FROM clients WHERE city = 'Москва');

-- проекты, по которым ещё не было платежей
SELECT title FROM projects p
WHERE NOT EXISTS (SELECT 1 FROM payments pay WHERE pay.project_id = p.id);

-- долг по каждому проекту: бюджет минус оплачено
WITH paid AS (
  SELECT project_id, SUM(amount) AS total
  FROM payments
  GROUP BY project_id
)
SELECT p.title, p.budget, COALESCE(paid.total, 0) AS paid,
       p.budget - COALESCE(paid.total, 0) AS debt
FROM projects p
LEFT JOIN paid ON paid.project_id = p.id
WHERE p.budget IS NOT NULL
ORDER BY debt DESC;
```

### Частые ошибки
- Подзапрос в `=` возвращает несколько строк — ошибка «more than one row returned». Используй `IN`.
- `NOT IN` с подзапросом, где встречается `NULL`, возвращает пустой результат. Безопаснее `NOT EXISTS`.
- Огромный запрос из вложенных подзапросов в пять уровней вместо понятных CTE.

### Мини-задание

### На пальцах
`EXPLAIN` — попросить навигатор показать маршрут до того, как ехать. База отвечает: «Пойду пешком по всем улицам подряд» (полный перебор) или «Поеду по шоссе» (индекс) и примерно сколько это займёт. Если маршрут глупый — значит, не хватает дороги (индекса) или запрос написан неудачно.

### Как это работает
- `EXPLAIN запрос` — показать план выполнения без запуска.
- `EXPLAIN ANALYZE запрос` — выполнить и показать реальное время каждого шага. Осторожно с `UPDATE` и `DELETE` — они действительно выполнятся.

Что искать в плане:

| В плане | Что значит |
|---|---|
| `Seq Scan on projects` | полный перебор таблицы — нормально для маленьких таблиц, плохо для больших |
| `Index Scan using ...` | поиск по индексу — быстро |
| `Index Only Scan` | всё нужное есть в индексе — ещё быстрее |
| `Hash Join`, `Nested Loop`, `Merge Join` | способы соединения таблиц |
| `Sort` | сортировка; на больших данных может быть дорогой |
| `cost=0.00..35.50` | условная стоимость: старт..итог |
| `rows=1200` | сколько строк ожидается |
| `actual time=...` | реальное время (в `ANALYZE`) |

Типичный сценарий: запрос с `WHERE email = ...` по таблице в миллион строк медленный → `EXPLAIN` показывает `Seq Scan` → создаём индекс на `email` → `EXPLAIN` показывает `Index Scan`, время падает с секунд до миллисекунд.

На маленьких учебных таблицах база часто выбирает `Seq Scan` даже при наличии индекса — перебрать 10 строк быстрее, чем открывать индекс.

### Пример
```sql
EXPLAIN SELECT * FROM clients WHERE city = 'Москва';
-- Seq Scan on clients  (cost=0.00..1.07 rows=2 width=...)
--   Filter: (city = 'Москва')

CREATE INDEX clients_city_idx ON clients (city);

EXPLAIN ANALYZE SELECT * FROM clients WHERE city = 'Москва';
-- на большой таблице: Index Scan using clients_city_idx on clients ...
--   actual time=0.020..0.025 rows=2
```

В SQLite (песочница курса) аналог — `EXPLAIN QUERY PLAN`:

```sql
EXPLAIN QUERY PLAN SELECT * FROM projects WHERE client_id = 1;
```

### Частые ошибки
- Делать выводы по плану на пустой или крошечной таблице.
- `EXPLAIN ANALYZE DELETE ...` на боевой базе — удаление реально выполнится.
- Создавать индексы на всё подряд, не посмотрев план.
