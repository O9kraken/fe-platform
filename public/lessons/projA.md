### На пальцах
Сайт «работает» и сайт «готов» — как отремонтированная квартира с торчащими проводами и квартира, где всё доделано. Полировка — пройти по всем комнатам с фонариком: заглянуть в углы (узкие экраны), проверить выключатели (клавиатура) и подписи на дверях (доступность).

### Как это работает
Чек-лист адаптива:

- Ширины 320, 375, 768, 1024, 1440px — нет горизонтальной прокрутки, ничего не наезжает.
- Длинные слова и названия (`overflow-wrap: anywhere`), пустые и очень длинные списки.
- Кнопки и ссылки на телефоне не меньше 44×44px.
- Картинки не растягиваются и не весят мегабайты.
- Шрифт основного текста не меньше 16px.

Чек-лист доступности:

- Всё проходится клавиатурой, фокус виден.
- У картинок осмысленный `alt`, у полей — `label`.
- Контраст текста — не меньше 4.5:1 (проверка во вкладке DevTools при выборе цвета).
- Один `h1`, заголовки по порядку.
- Состояния загрузки и ошибки озвучиваются: `role="status"` или `aria-live="polite"` для сообщений.

Найти горизонтальный скролл быстро: в консоли выполни `[...document.querySelectorAll("*")].filter(e => e.scrollWidth > document.documentElement.clientWidth)`.

### Пример
```css
/* частые «заплатки» после проверки */
img, video { max-width: 100%; height: auto; }
.card__title { overflow-wrap: anywhere; }
.btn { min-height: 44px; padding-inline: 16px; }
:focus-visible { outline: 3px solid var(--accent); outline-offset: 2px; }
```

```tsx
<p role="status" aria-live="polite">{loading ? "Загружаю каталог…" : ""}</p>
```

### Частые ошибки
- Проверять только на своём ноутбуке и одном телефоне.
- Отключить зум на мобильных через `maximum-scale=1` — людям со слабым зрением нужен зум.
- Оставить «рыбу» и тестовые данные в продакшене.

### На пальцах
Lighthouse — техосмотр для сайта. Тебе выдают оценки по четырём пунктам — скорость, доступность, лучшие практики, SEO — и список, что именно подкрутить. Как талон техосмотра, только бесплатно и за минуту.

### Как это работает
1. Открой сайт в Chrome в режиме инкогнито (чтобы не мешали расширения).
2. DevTools → вкладка Lighthouse.
3. Выбери категории и устройство (Mobile строже), нажми «Analyze page load».
4. Через полминуты — оценки от 0 до 100 и список рекомендаций.

| Категория | Что проверяет |
|---|---|
| Performance | скорость загрузки и отклика: LCP, CLS, TBT |
| Accessibility | alt, контраст, label, порядок заголовков |
| Best Practices | HTTPS, ошибки в консоли, устаревшие API |
| SEO | title, description, viewport, индексация |

Как читать: каждая рекомендация раскрывается и показывает конкретные элементы — какая картинка тяжёлая, у какой кнопки нет имени. Начинай с пунктов, которые дают больше всего «Estimated savings».

Оценка производительности плавает от запуска к запуску на ±5 — запускай пару раз. Проверяй собранную версию (`npm run build` + `npm run preview`) или опубликованный сайт, а не dev-сервер.

### Пример
Типичные советы и их исправление:

```text
Serve images in next-gen formats    → конвертируй JPG/PNG в WebP или AVIF
Properly size images                → не отдавай картинку 2000px в блок 400px
Image elements do not have explicit width and height → добавь width и height
Buttons do not have an accessible name → добавь текст или aria-label иконке-кнопке
Background and foreground colors do not have sufficient contrast → темнее текст
```

```html
<button class="icon-btn" aria-label="Закрыть окно">✕</button>
<img src="hero.webp" width="1200" height="600" alt="..." fetchpriority="high">
```

### Частые ошибки
- Запускать Lighthouse на `npm run dev` — оценка будет занижена.
- Гнаться за 100 по производительности ценой удобства. 90+ — отличный результат.
- Исправлять только то, что даёт баллы, и не проверять реальный опыт с телефона.

### На пальцах
Переменные окружения — настройки, которые живут не в коде, а «в квартире», где код запущен. Дома (у тебя на компьютере) API по адресу localhost, на сервере — боевой адрес. Код один, а записка с адресом на холодильнике в каждой квартире своя.

### Как это работает
- В проекте Vite переменные хранят в файлах `.env`, `.env.local`, `.env.production`.
- В код попадают только переменные с префиксом `VITE_`: `VITE_API_URL=https://api.site.ru`.
- Читаются так: `import.meta.env.VITE_API_URL`.
- Значения подставляются в код на этапе сборки. Поменял переменную — пересобери проект.
- На хостинге (Vercel, Netlify) переменные задают в настройках проекта, файлы `.env` туда не загружают.

Самое важное: всё, что попало во фронтенд, видит любой посетитель — достаточно открыть DevTools. Поэтому во фронтенде нельзя хранить секреты: ключи платных API, пароли, токены доступа к базе. Префикс `VITE_` — это защита от случайной утечки остальных переменных, а не способ спрятать.

Если нужен секретный ключ — запрос идёт через свой сервер (бэкенд или serverless-функцию), где ключ хранится в серверных переменных.

### Пример
```bash
# .env.local — не коммитим
VITE_API_URL=http://localhost:3000
```

```bash
# .env.example — коммитим, как подсказку
VITE_API_URL=
```

```ts
// src/api/client.ts
const API = import.meta.env.VITE_API_URL ?? "";

export async function getProducts() {
  const r = await fetch(`${API}/api/products`);
  if (!r.ok) throw new Error(`Ошибка ${r.status}`);
  return r.json();
}
```

```ts
// src/vite-env.d.ts — чтобы TypeScript знал о переменной
interface ImportMetaEnv { readonly VITE_API_URL: string }
```

### Частые ошибки
- Переменная без префикса `VITE_` — в коде `undefined`.
- Секретный ключ API с префиксом `VITE_` — он открыт всем.
- Закоммитить `.env.local` и не добавить его в `.gitignore`.

### Мини-задание
Вынеси адрес API своего каталога в `VITE_API_URL`, создай `.env.example` и опиши переменную в README. Собери проект и найди адрес в собранном JS-файле в `dist/` — убедись, что он действительно виден.

### На пальцах
Vercel и Netlify — автоматические типографии. Ты отдаёшь им рукопись (репозиторий на GitHub), и каждый раз, когда ты вносишь правку, они сами печатают свежий тираж (собирают и публикуют сайт). Плюс бесплатный адрес, HTTPS и превью для каждой правки.

### Как это работает
1. Код на GitHub.
2. Зарегистрируйся на vercel.com или netlify.com через GitHub.
3. «Add New Project» → выбери репозиторий.
4. Платформа сама определит Vite и подставит команду сборки `npm run build` и папку `dist`.
5. Добавь переменные окружения (например, `VITE_API_URL`) в настройках проекта.
6. Deploy — через минуту сайт доступен по адресу вида `my-shop.vercel.app`.

Дальше каждый `git push` в `main` публикует новую версию, а каждый pull request получает свою превью-ссылку — удобно показать изменения до слияния.

Одностраничное приложение с роутером: прямой заход на `/catalog` должен отдавать `index.html`. Vercel для Vite делает это сам, на Netlify нужен файл `public/_redirects` со строкой `/* /index.html 200`.

### Пример
```text
# public/_redirects (только для Netlify)
/*  /index.html  200
```

```json
// vercel.json — если нужно явно
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
```

```bash
git add .
git commit -m "feat: фильтр по цене"
git push            # через минуту изменения уже на сайте
```

### Частые ошибки
- Забыть переменные окружения на хостинге — локально работает, на сайте данные не грузятся.
- Указать не ту папку результата (`build` вместо `dist`).
- 404 при обновлении страницы на вложенном адресе — не настроено перенаправление на `index.html`.

### Мини-задание
Опубликуй свой каталог на Vercel или Netlify. Сделай ветку, внеси изменение, открой pull request и найди превью-ссылку. Добавь адрес сайта в описание репозитория.

### На пальцах
README — витрина и инструкция проекта одновременно. Работодатель открывает репозиторий и за 30 секунд решает, смотреть ли дальше. Если там пусто — он уходит. Если видно скриншот, ссылку на живой сайт и понятный список технологий — он кликает дальше.

### Как это работает
README.md лежит в корне репозитория, GitHub показывает его на главной странице проекта. Пишется в Markdown.

Обязательные разделы:

1. **Название и одна фраза**, что это и для кого.
2. **Ссылка на живой сайт** и скриншот или GIF.
3. **Возможности** — 3–6 пунктов.
4. **Стек** — технологии.
5. **Как запустить** — команды по шагам.
6. **Переменные окружения** — какие нужны.

По желанию: что было сложным и как решил, что бы улучшил, структура папок, результаты Lighthouse.

Скриншот кладут в папку `docs/` или `.github/` и вставляют `![Описание](docs/screenshot.png)`.

### Пример
```markdown
# Каталог кроссовок

Каталог с поиском, фильтрами и корзиной. Учебный проект на React + TypeScript.

**Демо:** https://sneakers-catalog.vercel.app

![Главная страница каталога](docs/screenshot.png)

## Возможности
- Поиск и фильтр по бренду, размеру и цене
- Корзина с сохранением в localStorage
- Адаптив от 320px, доступно с клавиатуры
- Lighthouse: 96 / 100 / 100 / 100

## Стек
React 18, TypeScript, Vite, React Router, TanStack Query, CSS Modules

## Запуск
    git clone https://github.com/anna/sneakers-catalog.git
    cd sneakers-catalog
    npm install
    cp .env.example .env.local
    npm run dev

## Переменные окружения
| Переменная | Описание |
|---|---|
| VITE_API_URL | адрес API каталога |
```

- Нет ссылки на живой сайт.
- Инструкция запуска, которая не работает на чистом компьютере.
