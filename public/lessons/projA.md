Ты показываешь каталог работодателю, он открывает его на своём iPhone SE — и видит горизонтальную прокрутку, кнопку «В корзину» размером с горошину и название товара, вылезающее за карточку. Сайт «работает», но выглядит недоделанным. Последние 10% полировки решают, как воспримут все предыдущие 90%.

### На пальцах
Сайт «работает» и сайт «готов» — как отремонтированная квартира с торчащими проводами и квартира, где всё доделано. Полировка — пройти по всем комнатам с фонариком: заглянуть в углы (узкие экраны), проверить выключатели (клавиатура) и подписи на дверях (доступность).

### Как это работает
>> Телефон 320px → клавиатура и фокус → контраст → `alt` и подписи

Чек-лист адаптива:

- Ширины 320, 375, 768, 1024, 1440px — нет горизонтальной прокрутки, ничего не наезжает.
- Длинные слова и названия (`overflow-wrap: anywhere`), пустые и очень длинные списки.
- Кнопки и ссылки на телефоне не меньше 44×44px.
- Картинки не растягиваются и не весят мегабайты.
- Шрифт основного текста не меньше 16px.

Чек-лист доступности:

- Всё проходится клавиатурой, фокус виден.
- У картинок осмысленный `alt`, у полей — `label`.
- Контраст текста — не меньше 4.5:1.
- Один `h1`, заголовки по порядку.
- Состояния загрузки и ошибки озвучиваются: `role="status"` или `aria-live="polite"`.

Найти виновника горизонтального скролла: в консоли выполни `[...document.querySelectorAll("*")].filter(e => e.scrollWidth > document.documentElement.clientWidth)`.

?: Почему кнопки на телефоне должны быть не меньше 44×44 пикселей? || Подушечка пальца гораздо крупнее курсора мыши. В маленькую кнопку легко промахнуться и нажать соседнюю — особенно на ходу или одной рукой. 44 пикселя — проверенный минимум из рекомендаций Apple и WCAG.

### Пример
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1">
```

```css
.card__title { white-space: nowrap; }
.btn-icon { width: 28px; height: 28px; }
```

?! Найди в этом коде три проблемы, которые всплывут при проверке на телефоне. || `maximum-scale=1` запрещает увеличивать страницу пальцами — людям со слабым зрением это мешает. `nowrap` у названий вытолкнет длинные заголовки за край карточки. Кнопка-иконка 28×28 слишком мала для пальца — нужно хотя бы 44×44.

### Частые ошибки
- **Проверка только на своём ноутбуке и одном телефоне.**
- **Отключённый зум** через `maximum-scale=1`.
- **«Рыба» и тестовые данные в продакшене.**

### Проверь себя
?? На каких ширинах стоит проверить адаптивную вёрстку? || Как минимум 320, 375, 768, 1024 и 1440 пикселей.
?? Как в CSS не дать длинному слову вылезти за карточку? || `overflow-wrap: anywhere` (или `break-word`) у текстового элемента.
?? Объясни своими словами, зачем сообщения о загрузке помечают `role="status"`. || Чтобы скринридер сам зачитал их пользователю: иначе незрячий человек не узнает, что данные загружаются или произошла ошибка.

### На пальцах
Lighthouse — техосмотр для сайта. Тебе выдают оценки по четырём пунктам — скорость, доступность, лучшие практики, SEO — и список, что именно подкрутить. Как талон техосмотра, только бесплатно и за минуту.

### Как это работает
>> DevTools → Lighthouse → отчёт по 4 разделам → исправить красное

1. Открой сайт в Chrome в режиме инкогнито (чтобы не мешали расширения).
2. DevTools → вкладка Lighthouse.
3. Выбери категории и устройство (Mobile строже), нажми «Analyze page load».
4. Через полминуты — оценки от 0 до 100 и список рекомендаций.

| Категория | Что проверяет |
|---|---|
| Performance | скорость загрузки и отклика: LCP, CLS, TBT |
| Accessibility | alt, контраст, label, порядок заголовков |
| Best Practices | HTTPS, ошибки в консоли, устаревшие API |
| SEO | title, description, viewport, индексация |

Каждая рекомендация раскрывается и показывает конкретные элементы. Начинай с пунктов, которые дают больше всего «Estimated savings».

Оценка производительности плавает на ±5 — запускай пару раз. Проверяй собранную версию или опубликованный сайт, а не dev-сервер.

?: Почему Lighthouse лучше запускать в режиме инкогнито? || Расширения браузера — блокировщики рекламы, переводчики, менеджеры паролей — добавляют свои скрипты на страницу и замедляют её. В инкогнито они обычно выключены, и оценка отражает сам сайт.

### Пример
```text
Performance: 52
- Serve images in next-gen formats
- Image elements do not have explicit width and height
Accessibility: 78
- Buttons do not have an accessible name
- Background and foreground colors do not have sufficient contrast
```

?! Что конкретно исправить по каждой из четырёх рекомендаций? || Перевести картинки в WebP или AVIF. Добавить `width` и `height` к `img`. Дать кнопкам-иконкам текст или `aria-label`. Сделать текст темнее или фон светлее, пока контраст не станет 4.5:1.

### Частые ошибки
- **Lighthouse на `npm run dev`** — оценка занижена.
- **Погоня за 100** ценой удобства. 90+ — отличный результат.
- **Исправления ради баллов** без проверки реального опыта с телефона.

### Проверь себя
?? Какие четыре категории оценивает Lighthouse? || Performance, Accessibility, Best Practices и SEO.
?? Почему нельзя оценивать производительность на dev-сервере? || Режим разработки не оптимизирован: код не сжат и содержит отладочные инструменты, поэтому оценка будет хуже, чем у собранного сайта.
?? Объясни своими словами, с чего начинать работу над рекомендациями Lighthouse. || С пунктов, которые дают наибольшую экономию времени загрузки, и с ошибок доступности, которые мешают людям пользоваться сайтом.

### Ситуация
Локально каталог ходит в API по адресу `localhost:3000`, на сервере — в `api.shop.ru`. Ты меняешь адрес в коде руками перед каждой публикацией и однажды забываешь — сайт на проде пытается достучаться до твоего ноутбука. А ещё кто-то на форуме советует положить ключ платного API в `.env` фронтенда «для безопасности». Это опасный совет, и сейчас станет понятно почему.

### На пальцах
Переменные окружения — настройки, которые живут не в коде, а «в квартире», где код запущен. Дома (у тебя на компьютере) API по адресу localhost, на сервере — боевой адрес. Код один, а записка с адресом на холодильнике в каждой квартире своя.

### Как это работает
>> `.env` → `VITE_API_URL=…` → `import.meta.env.VITE_API_URL` → в коде

- В проекте Vite переменные хранят в файлах `.env`, `.env.local`, `.env.production`.
- В код попадают только переменные с префиксом `VITE_`: `VITE_API_URL=https://api.site.ru`.
- Читаются так: `import.meta.env.VITE_API_URL`.
- Значения подставляются в код на этапе сборки. Поменял переменную — пересобери проект.
- На хостинге (Vercel, Netlify) переменные задают в настройках проекта, файлы `.env` туда не загружают.

Если нужен секретный ключ — запрос идёт через свой сервер (бэкенд или serverless-функцию), где ключ хранится в серверных переменных.

?: Почему файл `.env` во фронтенде не прячет секретный ключ? || Значения переменных с `VITE_` встраиваются прямо в собранный JavaScript, который скачивает каждый посетитель. Открыв DevTools, любой найдёт ключ. Префикс защищает только от случайной утечки остальных переменных, а не прячет помеченные.

### Пример
```bash
# .env.local — не коммитим
VITE_API_URL=http://localhost:3000
API_SECRET=sk_live_123
```

```ts
const API = import.meta.env.VITE_API_URL;
const secret = import.meta.env.API_SECRET;
console.log(API, secret);
```

?! Что выведет `console.log` и почему? || `http://localhost:3000 undefined`. Переменная без префикса `VITE_` в браузерный код не попадает — и это правильно: секрет не должен оказаться во фронтенде вообще.

### Частые ошибки
- **Переменная без префикса `VITE_`** — в коде `undefined`.
- **Секретный ключ с префиксом `VITE_`** — он открыт всем.
- **Закоммиченный `.env.local`** без записи в `.gitignore`.

### Проверь себя
?? Как прочитать переменную окружения в коде проекта на Vite? || `import.meta.env.VITE_ИМЯ`.
?? Зачем нужен файл `.env.example`? || Он показывает, какие переменные нужны проекту, без реальных значений. Его коммитят как подсказку для других разработчиков.
?? Объясни своими словами, как использовать секретный ключ API во фронтенд-проекте. || Никак напрямую: запрос с ключом делает свой сервер или serverless-функция, где ключ хранится в серверных переменных, а фронтенд обращается к этому серверу.

### Мини-задание
Вынеси адрес API своего каталога в `VITE_API_URL`, создай `.env.example` и опиши переменную в README. Собери проект и найди адрес в собранном JS-файле в `dist/` — убедись, что он действительно виден.

### Ситуация
Раньше выложить сайт значило: арендовать сервер, настроить nginx, получить сертификат, копировать файлы по FTP после каждой правки. Сегодня ты делаешь `git push` — и через минуту изменения уже на живом сайте с HTTPS, а для каждого pull request появляется своя ссылка, чтобы показать заказчику. Бесплатно.

### На пальцах
Vercel и Netlify — автоматические типографии. Ты отдаёшь им рукопись (репозиторий на GitHub), и каждый раз, когда вносишь правку, они сами печатают свежий тираж (собирают и публикуют сайт). Плюс бесплатный адрес, HTTPS и превью для каждой правки.

### Как это работает
>> Push в GitHub → Vercel импортирует репозиторий → сборка → ссылка на сайт

1. Код на GitHub.
2. Зарегистрируйся на vercel.com или netlify.com через GitHub.
3. «Add New Project» → выбери репозиторий.
4. Платформа сама определит Vite и подставит команду сборки `npm run build` и папку `dist`.
5. Добавь переменные окружения (например, `VITE_API_URL`) в настройках проекта.
6. Deploy — через минуту сайт доступен по адресу вида `my-shop.vercel.app`.

Дальше каждый `git push` в `main` публикует новую версию, а каждый pull request получает свою превью-ссылку.

?: Почему одностраничному приложению нужно перенаправлять все адреса на `index.html`? || Страница `/catalog` существует только в JavaScript-роутере, а не как файл на сервере. При прямом заходе сервер ищет файл `catalog` и отвечает 404. Перенаправление отдаёт `index.html`, а роутер уже сам показывает каталог.

### Пример
```text
# public/_redirects (только для Netlify)
/*  /index.html  200
```

```json
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
```

?! На Netlify без файла `_redirects` пользователь открывает главную, кликает «Каталог» — всё работает. Потом жмёт F5. Что он увидит? || Страницу 404 от Netlify. Переход по клику обрабатывал роутер в браузере, а F5 отправил запрос `/catalog` на сервер, где такого файла нет.

### Частые ошибки
- **Нет переменных окружения на хостинге** — локально работает, на сайте данные не грузятся.
- **Не та папка результата** (`build` вместо `dist`).
- **404 при обновлении страницы** на вложенном адресе — не настроено перенаправление на `index.html`.

?? Что происходит на Vercel после `git push` в `main`? || Проект автоматически собирается и публикуется новая версия сайта.
?? Что такое превью-деплой? || Отдельная версия сайта со своим адресом, которую платформа собирает для каждой ветки или pull request.
?? Объясни своими словами, зачем на Netlify файл `_redirects` для одностраничного приложения. || Чтобы при прямом заходе на любой адрес сервер отдавал `index.html`, а нужную страницу уже показывал роутер в браузере.
