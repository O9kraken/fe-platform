### На пальцах
На входе в офисный центр охранник смотрит паспорт: «Ты действительно Анна?» — это аутентификация. Потом турникет решает, на какие этажи тебя пускать: «Анне можно на 3-й и в переговорку, но не в серверную» — это авторизация. Сначала узнаём, кто ты, потом решаем, что тебе можно.

### Как это работает
| | Аутентификация | Авторизация |
|---|---|---|
| Вопрос | кто ты? | что тебе можно? |
| Как | пароль, код из СМС, вход через Google, ключ | роли, владение записью, права |
| Ошибка | 401 Unauthorized — «войдите» | 403 Forbidden — «нельзя» |
| Когда | при входе, и потом сессия подтверждает личность в каждом запросе | в каждом запросе к защищённым данным |

Типичная схема:

1. Пользователь отправляет логин и пароль.
2. Сервер сверяет пароль с хешем в базе.
3. Создаёт сессию: cookie с идентификатором сессии или JWT-токен.
4. При следующих запросах клиент присылает cookie или токен — сервер понимает, кто это.
5. В каждом маршруте сервер проверяет права: этот пользователь — владелец проекта? у него роль admin?

Самая частая уязвимость — не в аутентификации, а в авторизации: пользователь вошёл и подставил чужой id в запрос, а сервер не проверил, чей это объект.

### Пример
```js
// аутентификация: кто это?
function requireUser(req, res, next) {
  const user = getUserFromSession(req);       // по cookie или токену
  if (!user) return res.status(401).json({ error: "Войдите в аккаунт" });
  req.user = user;
  next();
}

// авторизация: можно ли ему это?
app.delete("/api/projects/:id", requireUser, async (req, res) => {
  const project = await db.getProject(req.params.id);
  if (!project) return res.status(404).json({ error: "Не найдено" });
  if (project.ownerId !== req.user.id && req.user.role !== "admin") {
    return res.status(403).json({ error: "Нет прав" });
  }
  await db.deleteProject(project.id);
  res.status(204).end();
});
```

### Частые ошибки
- Путать 401 и 403.
- Проверять, что пользователь вошёл, но не проверять, что объект принадлежит ему.
- Считать скрытую кнопку во фронтенде защитой.

### На пальцах
Хранить пароли открыто — держать ключи от всех квартир на гвоздике у входа. Хеширование — мясорубка: из пароля легко сделать фарш (хеш), но из фарша невозможно собрать обратно пароль. При входе мы снова пропускаем введённый пароль через ту же мясорубку и сравниваем фарш. Соль — уникальная специя для каждого пользователя, чтобы одинаковые пароли давали разный фарш.

### Как это работает
- В базе хранится не пароль, а хеш: строка вида `$2b$11$Kq8...`.
- Обычные хеш-функции (MD5, SHA-256) для паролей не подходят: они очень быстрые, и миллиарды вариантов перебираются за минуты.
- Специальные функции **bcrypt** и **argon2** — нарочно медленные и настраиваемые (параметр «стоимости»). Один хеш — десятки миллисекунд: пользователю незаметно, а перебор становится непрактичным.
- **Соль** — случайная добавка, уникальная для каждого пароля. bcrypt и argon2 генерируют её сами и хранят внутри хеша. Благодаря соли у двух пользователей с паролем «123456» разные хеши, и заранее посчитанные таблицы не работают.

Правила:

- `bcrypt.hash(password, 11)` — стоимость 10–12 — разумно.
- Сравнение — только функцией `bcrypt.compare`.
- Минимальная длина пароля — от 8 символов; лучше проверять по списку утёкших паролей.
- При неудачном входе — одно сообщение «Неверный логин или пароль», не уточняя, что именно неверно.

### Пример
```js
import bcrypt from "bcryptjs";

app.post("/api/auth/register", async (req, res) => {
  const { email, password } = req.body ?? {};
  if (typeof password !== "string" || password.length < 8) {
    return res.status(400).json({ error: "Пароль от 8 символов" });
  }
  const hash = await bcrypt.hash(password, 11);
  const { rows } = await q(
    "INSERT INTO users (email, password_hash) VALUES (lower($1), $2) RETURNING id, email",
    [email, hash]
  );
  res.status(201).json(rows[0]);
});

app.post("/api/auth/login", async (req, res) => {
  const { email, password } = req.body ?? {};
  const { rows } = await q("SELECT * FROM users WHERE email = lower($1)", [email]);
  const user = rows[0];
  const ok = user && (await bcrypt.compare(password ?? "", user.password_hash));
  if (!ok) return res.status(401).json({ error: "Неверный email или пароль" });
  // ...создать сессию
  res.json({ id: user.id, email: user.email });
});
```

### Частые ошибки
- Хранить пароль открытым текстом или в обратимом шифровании.
- MD5 или SHA-256 без соли для паролей.
- Сообщение «Пользователь не найден» — злоумышленник узнаёт, какие email зарегистрированы.

### На пальцах
Сессия в cookie — гардероб: при входе тебе дают номерок, а пальто (данные о тебе) хранится у гардеробщика. Номерок можно аннулировать в любой момент. JWT — именной пропуск с голограммой: все данные написаны на самом пропуске, и охранник проверяет подлинность по голограмме, не звоня в отдел кадров. Быстро, но отозвать уже выданный пропуск трудно — он действует до конца срока.

### Как это работает
**Серверная сессия**:

1. После входа сервер создаёт запись сессии (в базе или Redis) со случайным id.
2. id отправляется в cookie.
3. На каждый запрос сервер ищет сессию по id.

Плюсы: легко отозвать (удалить запись), в cookie нет данных. Минусы: запрос к хранилищу сессий на каждый запрос.

**JWT (JSON Web Token)** — строка из трёх частей через точку: заголовок, данные (payload), подпись. Данные закодированы, но **не зашифрованы** — их может прочитать кто угодно. Подпись гарантирует, что данные не подделаны: изменить роль на admin без секретного ключа нельзя.

Плюсы: не нужно хранилище, удобно для нескольких сервисов. Минусы: нельзя мгновенно отозвать (до истечения срока), payload виден.

Практичные варианты:

- для обычного сайта с одним бэкендом — сессия или JWT, но **в httpOnly-cookie**;
- для JWT — короткий срок жизни плюс номер версии в базе (`token_version`), увеличение которого «отзывает» все старые токены;
- не хранить токены в `localStorage` — их украдёт любой XSS.

### Пример
```js
import jwt from "jsonwebtoken";

const SECRET = process.env.JWT_SECRET;   // длинная случайная строка

function issueToken(res, user) {
  const token = jwt.sign({ uid: user.id, tv: user.token_version }, SECRET, { expiresIn: "30d" });
  res.cookie("session", token, {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    maxAge: 30 * 24 * 3600 * 1000,
  });
}

async function requireUser(req, res, next) {
  try {
    const { uid, tv } = jwt.verify(req.cookies.session, SECRET);
    const { rows: [user] } = await q("SELECT id, email, role, token_version FROM users WHERE id = $1", [uid]);
    if (!user || user.token_version !== tv) throw new Error("revoked");
    req.user = user;
    next();
  } catch {
    res.status(401).json({ error: "Войдите в аккаунт" });
  }
}

// «выйти со всех устройств» — все старые токены перестают работать
await q("UPDATE users SET token_version = token_version + 1 WHERE id = $1", [userId]);
```

### Частые ошибки
- Класть в JWT секретные данные — они видны всем (проверь на jwt.io).
- Короткий или угадываемый `JWT_SECRET`.
- Хранить токен в `localStorage`.

### Мини-задание
Сделай вход с JWT в httpOnly-cookie и маршрут `/api/me`. Скопируй токен из DevTools → Application → Cookies и вставь на jwt.io — посмотри, что видно в payload. Добавь «выход со всех устройств» через `token_version`. Посмотри схему «JWT изнутри» в уроке.

### На пальцах
Cookie — записка, которую браузер сам прикладывает к каждому письму на сайт. Флаги — правила обращения с запиской: `httpOnly` — «не показывать скриптам на странице», `Secure` — «передавать только по защищённому каналу», `SameSite` — «не прикладывать, если письмо отправляет чужой сайт».

### Как это работает
| Флаг | Что делает | Защищает от |
|---|---|---|
| `HttpOnly` | JavaScript не может прочитать cookie через `document.cookie` | кражи сессии через XSS |
| `Secure` | cookie отправляется только по HTTPS | перехвата в открытой сети |
| `SameSite=Lax` | cookie не отправляется при запросах с других сайтов, кроме обычного перехода по ссылке | CSRF |
| `SameSite=Strict` | никогда с других сайтов, даже по ссылке | CSRF, но неудобно: пришёл по ссылке из письма — не залогинен |
| `SameSite=None` | отправляется везде, требует `Secure` | — (нужно для фронта и API на разных доменах) |
| `Max-Age` / `Expires` | срок жизни | — |
| `Path`, `Domain` | для каких адресов отправлять | — |

Для cookie сессии разумный набор по умолчанию: `HttpOnly; Secure; SameSite=Lax; Path=/`.

На локальной разработке по `http://localhost` флаг `Secure` мешает — его включают только в продакшене.

Выход из аккаунта — сервер удаляет cookie (`res.clearCookie`) и, если сессии серверные, удаляет запись сессии.

### Пример
```js
const isProd = process.env.NODE_ENV === "production";

res.cookie("session", token, {
  httpOnly: true,       // скрипты на странице не прочитают
  secure: isProd,       // только HTTPS в продакшене
  sameSite: "lax",      // чужие сайты не смогут отправить запрос с этой cookie
  path: "/",
  maxAge: 30 * 24 * 60 * 60 * 1000,
});

app.post("/api/auth/logout", (req, res) => {
  res.clearCookie("session", { path: "/" });
  res.json({ ok: true });
});
```

```http
Set-Cookie: session=eyJhbGci...; Path=/; Max-Age=2592000; HttpOnly; Secure; SameSite=Lax
```

### Частые ошибки
- Cookie сессии без `HttpOnly`.
- `SameSite=None` без необходимости.
- При выходе удалять cookie с другим `path`, чем при установке, — cookie остаётся.

### Мини-задание
Установи cookie сессии с правильными флагами и проверь их в DevTools → Application → Cookies. Выполни в консоли `document.cookie` и убедись, что httpOnly-cookie там не видно.

### На пальцах
Роль — должность в компании: «бухгалтер», «менеджер», «директор». От должности зависят двери, которые открываются. Но кроме должности есть и личные вещи: менеджер Анна может редактировать только своих клиентов, а не клиентов коллеги. Проверять нужно и то и другое — и обязательно на сервере, потому что фронтенд — это лишь табличка на двери, а не замок.

### Как это работает
Два уровня проверок:

1. **По роли**: `admin` может всё, `manager` — управлять клиентами, `student` — только своё. Удобно оформить как middleware `requireRole("admin")`.
2. **По владению**: запись принадлежит пользователю? `project.owner_id === req.user.id`.

Где проверять владение:

- прямо в SQL: `UPDATE projects SET ... WHERE id = $1 AND owner_id = $2` — если 0 строк, значит, не нашли или чужое;
- или загрузить запись и сравнить в коде.

Чужую запись лучше отвечать 404, а не 403 — так не раскрывается сам факт существования записи.

Списки всегда фильтруются по пользователю: `WHERE owner_id = $1`.

Фронтенд прячет кнопки по ролям только для удобства. Любой может отправить запрос напрямую.

### Пример
```js
const requireRole = (...roles) => (req, res, next) => {
  if (!roles.includes(req.user.role)) return res.status(403).json({ error: "Нет прав" });
  next();
};

// только админ видит всех пользователей
app.get("/api/admin/users", requireUser, requireRole("admin"), async (req, res) => {
  const { rows } = await q("SELECT id, email, role, created_at FROM users ORDER BY id");
  res.json(rows);
});

// пользователь видит только свои проекты
app.get("/api/projects", requireUser, async (req, res) => {
  const { rows } = await q("SELECT * FROM projects WHERE owner_id = $1 ORDER BY id", [req.user.id]);
  res.json(rows);
});

// изменить можно только своё — проверка прямо в запросе
app.patch("/api/projects/:id", requireUser, async (req, res) => {
  const { rows } = await q(
    "UPDATE projects SET title = $1 WHERE id = $2 AND owner_id = $3 RETURNING *",
    [req.body.title, Number(req.params.id), req.user.id]
  );
  if (!rows[0]) return res.status(404).json({ error: "Проект не найден" });
  res.json(rows[0]);
});
```

### Частые ошибки
- `UPDATE ... WHERE id = $1` без условия владельца — любой может поменять чужой проект, подставив id.
- Роль берётся из тела запроса или из payload токена без сверки с базой.
- Админка защищена только тем, что ссылка на неё спрятана.

### На пальцах
Вход через Google — когда охранник офиса не проверяет паспорт сам, а звонит в паспортный стол: «Это действительно Анна?» Паспортный стол (Google) подтверждает и сообщает имя и почту. Твой сайт не узнаёт пароль от Google — он получает только подтверждение и данные, на которые пользователь согласился.

### Как это работает
OAuth 2.0 — протокол «разрешить одному сервису доступ к данным в другом». OpenID Connect поверх него — для входа: «подтверди, кто это».

Упрощённо, вход через Google:

1. Пользователь нажимает «Войти через Google» — сайт перенаправляет его на страницу Google со своим `client_id` и адресом возврата.
2. Пользователь входит в Google (если ещё не вошёл) и соглашается поделиться email и именем.
3. Google перенаправляет обратно на сайт с одноразовым `code`.
4. Сервер сайта (не браузер!) обменивает `code` на токены, используя секретный `client_secret`.
5. Из ID-токена сервер узнаёт email и id пользователя в Google, находит или создаёт пользователя у себя и создаёт обычную сессию.

Что понадобится: зарегистрировать приложение в Google Cloud Console, получить `client_id` и `client_secret`, указать разрешённые адреса возврата.

Писать протокол руками не нужно — есть готовые решения: Auth.js (для Next.js), Passport.js, Lucia, сервисы Supabase Auth, Clerk.

### Пример
```text
Браузер → GET https://accounts.google.com/o/oauth2/v2/auth
          ?client_id=123.apps.googleusercontent.com
          &redirect_uri=https://studio.ru/auth/google/callback
          &response_type=code
          &scope=openid email profile
          &state=случайная_строка_против_подделки

Google  → 302 https://studio.ru/auth/google/callback?code=4/0Ab...&state=...

Сервер  → POST https://oauth2.googleapis.com/token
          (code + client_id + client_secret) → { id_token, access_token }

Сервер  → проверяет id_token, берёт email → находит или создаёт пользователя → ставит cookie сессии
```

### Частые ошибки
- Обменивать `code` на токен во фронтенде с `client_secret` — секрет утекает.
- Не проверять параметр `state` — возможна подмена входа.
- Связывать аккаунты только по имени, а не по подтверждённому email или id провайдера.
