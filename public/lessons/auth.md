### Ситуация
В интернет-магазине всё защищено: без входа в кабинет не попасть. Пользователь вошёл и открыл свой заказ по адресу `/api/orders/1042`. Из любопытства поменял на `1041` — и увидел чужой заказ: адрес, телефон, состав. Вход работал идеально, а защиты не было. Две похожие на слух вещи — «аутентификация» и «авторизация» — на деле разные, и путать их опасно.

### На пальцах
На входе в офисный центр охранник смотрит паспорт: «Ты действительно Анна?» — это аутентификация. Потом турникет решает, на какие этажи тебя пускать: «Анне можно на 3-й и в переговорку, но не в серверную» — это авторизация. Сначала узнаём, кто ты, потом решаем, что тебе можно.

### Как это работает
>> Аутентификация — кто ты (пароль) → авторизация — что тебе можно (права)

| | Аутентификация | Авторизация |
|---|---|---|
| Вопрос | кто ты? | что тебе можно? |
| Как | пароль, код из СМС, вход через Google, ключ | роли, владение записью, права |
| Ошибка | 401 Unauthorized — «войдите» | 403 Forbidden — «нельзя» |
| Когда | при входе, и потом сессия подтверждает личность в каждом запросе | в каждом запросе к защищённым данным |

Типичная схема:

1. Пользователь отправляет логин и пароль.
2. Сервер сверяет пароль с хешем в базе.
3. Создаёт сессию: cookie с идентификатором сессии или JWT-токен.
4. При следующих запросах клиент присылает cookie или токен — сервер понимает, кто это.
5. В каждом маршруте сервер проверяет права: этот пользователь — владелец проекта? у него роль admin?

?: Почему уязвимость «подставил чужой id» так распространена? || Проверку «вошёл ли пользователь» обычно ставят один раз middleware на все маршруты. А проверку «чей это объект» нужно писать в каждом маршруте отдельно — и её легко забыть. В рейтинге OWASP эта ошибка (Broken Access Control) на первом месте.

### Пример
```js
app.get("/api/orders/:id", requireUser, async (req, res) => {
  const order = await db.getOrder(req.params.id);
  if (!order) return res.status(404).json({ error: "Не найдено" });
  res.json(order);
});
```

?! Пользователь Анна вошла в аккаунт и запрашивает `/api/orders/1041`, который принадлежит Борису. Что она получит и чего не хватает в коде? || Заказ Бориса целиком. `requireUser` проверил только, что Анна вошла (аутентификация), но никто не проверил, что заказ её (авторизация). Нужно сравнить `order.userId` с `req.user.id` и иначе вернуть 404.

### Частые ошибки
- **Путаница 401 и 403.**
- **Проверка «вошёл», но не «объект принадлежит ему».**
- **Скрытая кнопка во фронтенде вместо защиты на сервере.**

### Проверь себя
?? Чем аутентификация отличается от авторизации? || Аутентификация отвечает на вопрос «кто ты?», авторизация — «что тебе можно?».
?? Какой код ответа при отсутствии входа, а какой — при отсутствии прав? || 401 — не вошёл, 403 — вошёл, но нет прав.
?? Объясни своими словами, почему недостаточно проверить, что пользователь вошёл. || Вошедший пользователь может подставить в запрос id чужой записи. Сервер должен в каждом маршруте проверять, что запрошенный объект принадлежит этому пользователю или что у него есть нужная роль.

### Ситуация
Новость: «Утекла база сервиса — 10 миллионов пользователей». Если пароли там лежали открытым текстом, злоумышленники сразу попробуют их на почте, в банках и соцсетях — люди повторяют пароли. Если лежали правильные хеши, утечка почти безвредна для паролей. Разница — в одной функции, которую ты выбираешь при регистрации.

### На пальцах
Хранить пароли открыто — держать ключи от всех квартир на гвоздике у входа. Хеширование — мясорубка: из пароля легко сделать фарш (хеш), но из фарша невозможно собрать обратно пароль. При входе мы снова пропускаем введённый пароль через ту же мясорубку и сравниваем фарш. Соль — уникальная специя для каждого пользователя, чтобы одинаковые пароли давали разный фарш.

### Как это работает
>> Пароль → соль → `bcrypt.hash` → в базе только хеш → при входе `bcrypt.compare`

- В базе хранится не пароль, а хеш: строка вида `$2b$11$Kq8...`.
- Обычные хеш-функции (MD5, SHA-256) для паролей не подходят: они очень быстрые, и миллиарды вариантов перебираются за минуты.
- Специальные функции **bcrypt** и **argon2** — нарочно медленные и настраиваемые (параметр «стоимости»). Один хеш — десятки миллисекунд: пользователю незаметно, а перебор становится непрактичным.
- **Соль** — случайная добавка, уникальная для каждого пароля. bcrypt и argon2 генерируют её сами и хранят внутри хеша.

Правила:

- `bcrypt.hash(password, 11)` — стоимость 10–12 — разумно.
- Сравнение — только функцией `bcrypt.compare`.
- Минимальная длина пароля — от 8 символов; лучше проверять по списку утёкших паролей.
- При неудачном входе — одно сообщение «Неверный логин или пароль».

?: Почему для паролей нужна нарочно медленная функция? || Злоумышленник с украденной базой перебирает варианты пароля на своих видеокартах. Быстрый SHA-256 позволяет проверять миллиарды вариантов в секунду. Если каждый хеш стоит десятки миллисекунд, перебор растягивается на годы, а пользователь при входе ждёт незаметные доли секунды.

### Пример
```js
app.post("/api/auth/login", async (req, res) => {
  const { email, password } = req.body ?? {};
  const { rows } = await q("SELECT * FROM users WHERE email = lower($1)", [email]);
  const user = rows[0];
  if (!user) return res.status(401).json({ error: "Пользователь не найден" });
  if (!(await bcrypt.compare(password, user.password_hash))) {
    return res.status(401).json({ error: "Неверный пароль" });
  }
  res.json({ id: user.id });
});
```

?! Какую информацию этот код невольно сообщает злоумышленнику? || По разным сообщениям видно, зарегистрирован ли email. Можно проверить список адресов и узнать, кто пользуется сервисом, — а потом подбирать пароли только к ним. Сообщение должно быть одинаковым: «Неверный email или пароль».

### Частые ошибки
- **Пароль открытым текстом** или в обратимом шифровании.
- **MD5 или SHA-256 без соли** для паролей.
- **«Пользователь не найден»** — злоумышленник узнаёт, какие email зарегистрированы.

### Проверь себя
?? Почему MD5 и SHA-256 не подходят для хранения паролей? || Они слишком быстрые: украденные хеши можно перебирать миллиардами вариантов в секунду.
?? Что такое соль и зачем она? || Случайная добавка к паролю, уникальная для каждого пользователя. Из-за неё одинаковые пароли дают разные хеши, и заранее посчитанные таблицы не работают.
?? Объясни своими словами, как сервер проверяет пароль, если хранит только хеш. || Он хеширует введённый пароль тем же способом и с той же солью и сравнивает результат с сохранённым хешем. Если совпало — пароль верный.

### Ситуация
Пользователь вошёл. Как сервер узнает его в следующем запросе через минуту? HTTP ничего не помнит: каждый запрос — как от незнакомца. Нужна «память»: либо номерок, по которому сервер находит запись о тебе, либо подписанный пропуск, который ты носишь с собой. На собеседовании про сессии и JWT спрашивают почти всегда. Кстати, вход на этой платформе устроен именно так, как в примере ниже.

### На пальцах
Сессия в cookie — гардероб: при входе тебе дают номерок, а пальто (данные о тебе) хранится у гардеробщика. Номерок можно аннулировать в любой момент. JWT — именной пропуск с голограммой: все данные написаны на самом пропуске, и охранник проверяет подлинность по голограмме, не звоня в отдел кадров. Быстро, но отозвать уже выданный пропуск трудно — он действует до конца срока.

### Как это работает
>> Сессия: запись на сервере + id в cookie → JWT: подписанные данные у клиента

**Серверная сессия**:

1. После входа сервер создаёт запись сессии (в базе или Redis) со случайным id.
2. id отправляется в cookie.
3. На каждый запрос сервер ищет сессию по id.

Плюсы: легко отозвать (удалить запись), в cookie нет данных. Минусы: запрос к хранилищу на каждый запрос.

**JWT (JSON Web Token)** — строка из трёх частей через точку: заголовок, данные (payload), подпись. Данные закодированы, но **не зашифрованы** — их может прочитать кто угодно. Подпись гарантирует, что данные не подделаны.

Плюсы: не нужно хранилище, удобно для нескольких сервисов. Минусы: нельзя мгновенно отозвать, payload виден.

Практичные варианты:

- для обычного сайта с одним бэкендом — сессия или JWT, но **в httpOnly-cookie**;
- для JWT — короткий срок жизни плюс номер версии в базе (`token_version`), увеличение которого «отзывает» все старые токены;
- не хранить токены в `localStorage` — их украдёт любой XSS.

?: Если payload JWT может прочитать кто угодно, почему его нельзя подделать? || Подпись вычисляется из заголовка, данных и секретного ключа, который есть только у сервера. Поменяешь в payload роль на admin — подпись перестанет сходиться, и сервер отклонит токен. Читать можно, менять — нет.

### Пример
```js
function issueToken(res, user) {
  const token = jwt.sign({ uid: user.id, tv: user.token_version }, SECRET, { expiresIn: "30d" });
  res.cookie("session", token, { httpOnly: true, sameSite: "lax", secure: true });
}

async function requireUser(req, res, next) {
  try {
    const { uid, tv } = jwt.verify(req.cookies.session, SECRET);
    const { rows: [user] } = await q("SELECT * FROM users WHERE id = $1", [uid]);
    if (!user || user.token_version !== tv) throw new Error("revoked");
    req.user = user;
    next();
  } catch {
    res.status(401).json({ error: "Войдите в аккаунт" });
  }
}

await q("UPDATE users SET token_version = token_version + 1 WHERE id = $1", [userId]);
```

Что произойдёт с запросом с телефона, хотя его токен ещё не истёк? || Подпись токена по-прежнему верна, но `tv` в нём — старая версия, а в базе версия выросла на единицу. `requireUser` увидит несовпадение и ответит 401 — телефон «разлогинится».

### Частые ошибки
- **Секретные данные в JWT** — они видны всем (проверь на jwt.io).
- **Короткий или угадываемый `JWT_SECRET`.**
- **Токен в `localStorage`.**

### Проверь себя
?? Из каких трёх частей состоит JWT? || Заголовок, данные (payload) и подпись, разделённые точками.
?? Чем серверная сессия удобнее JWT? || Её можно мгновенно отозвать, удалив запись на сервере, и в cookie не хранится никаких данных пользователя.
?? Объясни своими словами, как `token_version` позволяет отзывать JWT. || Номер версии записан и в токене, и в базе. Увеличив его в базе, ты делаешь все ранее выданные токены недействительными — сервер видит, что версия в токене устарела.

### Ситуация
На сайте нашли XSS: в комментарии кто-то вставил скрипт, который отправляет `document.cookie` на чужой сервер. Если cookie сессии без флага `HttpOnly`, злоумышленник получил аккаунты всех, кто открыл страницу. С флагом — скрипт видит пустоту. Безопасность сессии во многом определяют несколько слов в заголовке `Set-Cookie`.

### На пальцах
Cookie — записка, которую браузер сам прикладывает к каждому письму на сайт. Флаги — правила обращения с запиской: `httpOnly` — «не показывать скриптам на странице», `Secure` — «передавать только по защищённому каналу», `SameSite` — «не прикладывать, если письмо отправляет чужой сайт».

### Как это работает
>> `httpOnly` — не видно скриптам → `Secure` — только HTTPS → `SameSite` — не уходит с чужих сайтов

| Флаг | Что делает | Защищает от |
|---|---|---|
| `HttpOnly` | JavaScript не может прочитать cookie через `document.cookie` | кражи сессии через XSS |
| `Secure` | cookie отправляется только по HTTPS | перехвата в открытой сети |
| `SameSite=Lax` | не отправляется при запросах с других сайтов, кроме обычного перехода по ссылке | CSRF |
| `SameSite=Strict` | никогда с других сайтов, даже по ссылке | CSRF, но неудобно |
| `SameSite=None` | отправляется везде, требует `Secure` | — (для фронта и API на разных доменах) |
| `Max-Age` / `Expires` | срок жизни | — |
| `Path`, `Domain` | для каких адресов отправлять | — |

Для cookie сессии разумный набор по умолчанию: `HttpOnly; Secure; SameSite=Lax; Path=/`.

На локальной разработке по `http://localhost` флаг `Secure` мешает — его включают только в продакшене.

?: Как `SameSite=Lax` защищает от CSRF-атаки? || При CSRF чужой сайт тайно отправляет запрос на твой, например форму «перевести деньги», надеясь, что браузер приложит твою cookie. С `Lax` браузер не прикладывает cookie к таким запросам с других сайтов, и сервер видит неавторизованный запрос.

### Пример
```js
res.cookie("session", token, { path: "/api", httpOnly: true, sameSite: "lax" });

app.post("/api/auth/logout", (req, res) => {
  res.clearCookie("session");
  res.json({ ok: true });
});
```

?! Пользователь нажал «Выйти». Удалится ли cookie сессии? || Нет. Cookie была установлена с `path: "/api"`, а `clearCookie` без параметров удаляет cookie с `path: "/"`. Это разные cookie для браузера, и сессия останется. Нужно указать тот же `path`, что при установке.

### Частые ошибки
- **Cookie сессии без `HttpOnly`.**
- **`SameSite=None` без необходимости.**
- **Удаление cookie с другим `path`**, чем при установке.

### Проверь себя
?? От чего защищает флаг `HttpOnly`? || От чтения cookie скриптами на странице и, значит, от кражи сессии через XSS.
?? Какой набор флагов разумен для cookie сессии по умолчанию? || `HttpOnly; Secure; SameSite=Lax; Path=/`.
?? Объясни своими словами, зачем флаг `Secure`. || Чтобы браузер отправлял cookie только по HTTPS. Тогда её нельзя перехватить в открытой Wi-Fi-сети при случайном запросе по HTTP.

### Мини-задание
Установи cookie сессии с правильными флагами и проверь их в DevTools → Application → Cookies. Выполни в консоли `document.cookie` и убедись, что httpOnly-cookie там не видно.

### Ситуация
Фронтенд показывает кнопку «Удалить пользователя» только админам. Всё выглядит безопасно. Но обычный пользователь открывает DevTools, копирует запрос из Network, меняет id — и удаляет кого угодно, потому что сервер проверил только, что запрос от вошедшего человека. Роли и права — работа сервера, а не интерфейса.

### На пальцах
Роль — должность в компании: «бухгалтер», «менеджер», «директор». От должности зависят двери, которые открываются. Но кроме должности есть и личные вещи: менеджер Анна может редактировать только своих клиентов, а не клиентов коллеги. Проверять нужно и то и другое — и обязательно на сервере, потому что фронтенд — это лишь табличка на двери, а не замок.

### Как это работает
>> Запрос → кто это (сессия) → какая роль → его ли запись → разрешить или 403/404

Два уровня проверок:

1. **По роли**: `admin` может всё, `manager` — управлять клиентами, `student` — только своё. Удобно оформить как middleware `requireRole("admin")`.
2. **По владению**: запись принадлежит пользователю? `project.owner_id === req.user.id`.

Где проверять владение:

- прямо в SQL: `UPDATE projects SET ... WHERE id = $1 AND owner_id = $2` — если 0 строк, значит, не нашли или чужое;
- или загрузить запись и сравнить в коде.

Чужую запись лучше отвечать 404, а не 403 — так не раскрывается сам факт существования записи.

Списки всегда фильтруются по пользователю: `WHERE owner_id = $1`.

?: Почему роль нужно брать из базы, а не из тела запроса или только из токена? || Тело запроса пишет клиент — он впишет `role: "admin"`. Токен подделать нельзя, но роль в нём может устареть: админа разжаловали, а токен действует ещё месяц. Свежая роль из базы — единственный надёжный источник.

### Пример
```js
app.patch("/api/projects/:id", requireUser, async (req, res) => {
  const { rows } = await q(
    "UPDATE projects SET title = $1 WHERE id = $2 RETURNING *",
    [req.body.title, Number(req.params.id)]
  );
  if (!rows[0]) return res.status(404).json({ error: "Проект не найден" });
  res.json(rows[0]);
});
```

?! Чем опасен этот маршрут и как исправить его одной правкой в SQL? || Любой вошедший пользователь может переименовать чужой проект, подставив его id. Нужно добавить условие владельца: `WHERE id = $2 AND owner_id = $3` с `req.user.id` — для чужого проекта обновится 0 строк, и вернётся 404.

### Частые ошибки
- **`UPDATE ... WHERE id = $1` без условия владельца.**
- **Роль из тела запроса** или из токена без сверки с базой.
- **Админка защищена только тем, что ссылка на неё спрятана.**

### Ситуация
Пользователи не любят придумывать ещё один пароль: на форме регистрации половина уходит. Кнопка «Войти через Google» поднимает конверсию, а тебе не нужно хранить пароли вообще. Но если реализовать её небрежно, можно выдать секретный ключ приложения или позволить войти в чужой аккаунт. Разберёмся, что на самом деле происходит за одной кнопкой.

### На пальцах
Вход через Google — когда охранник офиса не проверяет паспорт сам, а звонит в паспортный стол: «Это действительно Анна?» Паспортный стол (Google) подтверждает и сообщает имя и почту. Твой сайт не узнаёт пароль от Google — он получает только подтверждение и данные, на которые пользователь согласился.

### Как это работает
>> «Войти через Google» → Google спрашивает согласие → код → сервер получает профиль

OAuth 2.0 — протокол «разрешить одному сервису доступ к данным в другом». OpenID Connect поверх него — для входа: «подтверди, кто это».

Упрощённо, вход через Google:

1. Пользователь нажимает «Войти через Google» — сайт перенаправляет его на страницу Google со своим `client_id` и адресом возврата.
2. Пользователь входит в Google и соглашается поделиться email и именем.
3. Google перенаправляет обратно на сайт с одноразовым `code`.
4. Сервер сайта (не браузер!) обменивает `code` на токены, используя секретный `client_secret`.
5. Из ID-токена сервер узнаёт email и id пользователя в Google, находит или создаёт пользователя у себя и создаёт обычную сессию.

Что понадобится: зарегистрировать приложение в Google Cloud Console, получить `client_id` и `client_secret`, указать разрешённые адреса возврата.

Писать протокол руками не нужно — есть готовые решения: Auth.js (для Next.js), Passport.js, Lucia, сервисы Supabase Auth, Clerk.

?: Зачем нужен промежуточный одноразовый `code`, почему Google сразу не присылает токены в браузер? || Адрес с параметрами виден в истории браузера и может утечь. Одноразовый `code` бесполезен без `client_secret`, который есть только у сервера. Токены получает сервер напрямую от Google, и они не проходят через браузер.

### Пример
```text
Браузер → GET https://accounts.google.com/o/oauth2/v2/auth
          ?client_id=123.apps.googleusercontent.com
          &redirect_uri=https://studio.ru/auth/google/callback
          &response_type=code
          &scope=openid email profile
          &state=случайная_строка

Google  → 302 https://studio.ru/auth/google/callback?code=4/0Ab...&state=...
```

?! Что должен проверить сервер, получив запрос на `/auth/google/callback`, до обмена `code` на токены? || Что `state` совпадает с тем, который сервер сгенерировал и сохранил перед перенаправлением (например, в cookie). Иначе злоумышленник может подсунуть свой `code` и залогинить жертву в чужой аккаунт.

### Частые ошибки
- **Обмен `code` на токен во фронтенде с `client_secret`** — секрет утекает.
- **Нет проверки `state`** — возможна подмена входа.
- **Связывание аккаунтов по имени**, а не по подтверждённому email или id провайдера.

?? Чем OAuth 2.0 отличается от OpenID Connect? || OAuth 2.0 — протокол выдачи доступа к данным в другом сервисе. OpenID Connect построен поверх него и предназначен для входа: подтвердить, кто пользователь.
?? Где должен храниться `client_secret`? || Только на сервере, в переменных окружения; во фронтенд он попадать не должен.
?? Объясни своими словами, что получает сайт при входе через Google. || Подтверждение от Google, что это конкретный пользователь, и данные, на которые он согласился: обычно email, имя и id в Google. Пароль от Google сайт не узнаёт.
