### Ситуация
Вчера всё работало. Сегодня ты «чуть-чуть улучшил» стили, и вёрстка развалилась. Что именно ты менял — уже не помнишь. Без Git остаётся гадать и переписывать. С Git — одна команда, и ты видишь каждую изменённую строчку или откатываешься к вчерашнему рабочему состоянию.

### На пальцах
Git — машина времени для проекта. Каждый коммит — фотография всех файлов в момент, когда ты сказал «сохрани это состояние». `git add` — положить вещи в коробку, `git commit` — заклеить коробку и подписать.

### Как это работает
1. `git init` — один раз в папке проекта. Появится скрытая папка `.git` — там вся история.
2. Работаешь как обычно: меняешь файлы.
3. `git status` — что изменилось с последнего коммита. Красное — ещё не в коробке, зелёное — уже в коробке.
4. `git add файл` или `git add .` (все изменения) — положить в коробку. Это называется индекс или staging.
5. `git commit -m "Что сделал"` — запечатать снимок с подписью.
6. `git log --oneline` — список снимков, от новых к старым.

?: Зачем два шага, add и commit, если можно было бы сразу сохранять? || Чтобы собирать в один коммит только связанные изменения. Поменял шапку и подвал — делаешь два понятных коммита вместо одного «всё подряд», и потом любой из них можно отменить отдельно.

Перед первым коммитом Git попросит представиться — один раз на компьютер:

```bash
git config --global user.name "Анна Смирнова"
git config --global user.email "anna@example.com"
```

### Пример
```bash
cd web-learning
git init
git add index.html
git commit -m "Добавил страницу о себе"
# правим index.html...
git status
git add .
git commit -m "Добавил список навыков"
git log --oneline
```

?! Что покажет `git status` после правки файла и сколько строк выведет `git log --oneline` в конце? || `git status` покажет `modified: index.html` красным — изменение ещё не в коробке. `git log --oneline` выведет две строки: «Добавил список навыков» сверху и «Добавил страницу о себе» под ней.

### Частые ошибки
- **`git init` в домашней папке или на Рабочем столе** — Git начинает следить за всем компьютером. Только в папке проекта.
- **Один коммит раз в неделю «на всё».** Откатить что-то одно уже невозможно. Коммить каждый законченный маленький шаг.
- **Забыл `git add`** — коммит пустой или в нём не всё. Перед коммитом смотри `git status`.

### Проверь себя
?? Чем отличаются `git add` и `git commit`? || `add` кладёт изменения в индекс (готовит к снимку), `commit` сохраняет снимок с сообщением в историю.
?? Какая команда покажет, какие файлы изменены и ещё не закоммичены? || `git status`
?? Объясни своими словами, что такое коммит. || Сохранённый снимок всех файлов проекта с подписью. К любому снимку можно вернуться или посмотреть, что в нём изменилось.

### Ситуация
Рекрутер пишет: «Пришлите ссылку на GitHub». Если там пусто, разговор заканчивается, не начавшись. А ещё ноутбук однажды может не включиться — и весь учебный год уйдёт вместе с ним. Обе проблемы решает одна команда, которую ты будешь набирать каждый день: `git push`.

### На пальцах
Git на компьютере — личный фотоальбом. GitHub — облачный архив, куда альбом копируется: не потеряешь, если сломается ноутбук, можно показать работодателю и работать вместе. `git push` — отнести свежие фото в архив.

### Как это работает
1. Зарегистрируйся на github.com.
2. Нажми «New repository», придумай имя (например, `web-learning`). Не ставь галочку «Add README», если проект уже есть на компьютере.
3. GitHub покажет адрес вида `https://github.com/твой-логин/web-learning.git`.
4. Свяжи свою папку с этим адресом — один раз:

```bash
git remote add origin https://github.com/твой-логин/web-learning.git
git branch -M main
git push -u origin main
```

`origin` — короткое имя удалённого репозитория, `main` — основная ветка. Флаг `-u` запоминает связь, дальше хватает простого `git push`.

Рабочий цикл: изменил → `git add .` → `git commit -m "..."` → `git push`.

При первом push Git попросит войти. Проще всего — через браузер, который предложит Git Credential Manager, или через GitHub Desktop. Обычный пароль от аккаунта в терминале не подойдёт.

?: Почему для существующего проекта нужно создавать на GitHub пустой репозиторий, без README? || Если GitHub создаст README, у репозитория появится свой первый коммит, которого нет у тебя. Две истории начинаются по-разному, и Git откажется их просто склеить при push.

### Пример
```bash
git remote -v
git add .
git commit -m "Добавил контакты"
git push
```

?! Что выведет `git remote -v`, если связь настроена правильно, и где увидишь результат `git push`? || Две строки с адресом `origin` — для fetch и для push. Результат push виден на странице репозитория на GitHub: там появится коммит «Добавил контакты».

### Частые ошибки
- **Отправил на GitHub пароли или ключи.** Боты сканируют GitHub круглосуточно и находят ключи за минуты. Файл `.env` добавляй в `.gitignore` до первого коммита.
- **«Updates were rejected»** после создания репозитория с README. Для существующего проекта создавай пустой репозиторий.
- **Скопировал чужую скрытую папку `.git`** в новый проект — истории перепутались. Каждому проекту — свой `git init`.

### Проверь себя
?? Чем Git отличается от GitHub? || Git — программа, которая ведёт историю на твоём компьютере. GitHub — сайт, где хранятся копии репозиториев и где можно работать вместе.
?? Что делает флаг `-u` в `git push -u origin main`? || Запоминает связь локальной ветки с удалённой, чтобы дальше писать просто `git push`.
?? Объясни своими словами, зачем делать push каждый день. || Чтобы работа была в безопасности вне ноутбука, а работодатель видел живую историю твоего прогресса.

### Ситуация
Через полгода ты ищешь, когда сломалась форма заявки. Открываешь историю, а там: «fix», «asdf», «правки», «ещё правки», «финал», «финал2». Ты сам себе не помощник. Работодатель, который открыл твой GitHub, видит то же самое — и делает выводы о том, как ты работаешь в команде.

### На пальцах
Сообщение коммита — подпись на коробке при переезде. «Разное» не поможет найти чайник через месяц, «Кухня: посуда и чайник» — поможет. История коммитов — оглавление проекта: её читают коллеги, работодатель и ты сам через полгода.

### Как это работает
Хорошее сообщение отвечает на вопрос: «Что изменится, если применить этот коммит?»

Правила:

- Один стиль на весь проект: «Добавил форму» или «Добавить форму» — выбери и держись.
- Конкретно: что и где. «Исправил отступы в шапке на мобильных» вместо «fix».
- Первая строка до 50–70 символов. Подробности — после пустой строки.
- Один коммит — одно логическое изменение. Хочется написать «и ещё…» — это два коммита.

Многие команды используют Conventional Commits: в начале тип изменения.

| Тип | Значение |
|---|---|
| `feat:` | новая возможность |
| `fix:` | исправление ошибки |
| `style:` | оформление кода без изменения логики |
| `docs:` | документация |
| `refactor:` | переделка кода без новых функций |

?: Почему важно, чтобы один коммит содержал одно изменение? || Тогда его можно отменить, не задев остальное, а при поиске ошибки сразу видно, какое именно изменение её внесло.

### Пример
Плохая история:

```text
asdf
fix
изменения
ещё правки
```

Хорошая история:

```text
feat: добавить форму обратной связи
fix: исправить переполнение меню на iPhone SE
style: выровнять отступы карточек
docs: описать запуск проекта в README
```

?! Ты поправил опечатку в README и заодно починил кнопку, которая не отправляла форму. Сколько коммитов и с какими типами сделать? || Два: `docs: исправить опечатку в README` и `fix: починить отправку формы`. Разные по смыслу изменения — разные коммиты.

### Частые ошибки
- **Сообщения-пустышки:** «update», «fix», «123». Через неделю они ничего не значат.
- **Процесс вместо результата:** «пытался починить, вроде работает». Пиши, что изменилось.
- **Всё в одном коммите:** исправление ошибки, новый раздел и переименование файлов. Отменить что-то одно уже нельзя.

### Проверь себя
?? На какой вопрос должно отвечать сообщение коммита? || «Что изменится, если применить этот коммит?»
?? Что означают префиксы `feat:` и `fix:`? || `feat:` — новая возможность, `fix:` — исправление ошибки.
?? Объясни своими словами, кому нужна аккуратная история коммитов. || Коллегам, чтобы понимать изменения; работодателю, чтобы оценить, как ты работаешь; и тебе самому, чтобы быстро найти, где и когда что-то сломалось.
